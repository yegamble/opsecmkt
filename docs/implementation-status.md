# Implementation status

The Figma reference is adapted to Go-rendered HTML and CSS. The browser loads no JavaScript or third-party resources. A listing without photos shows a decorative CSS illustration labelled "ILLUSTRATION"; a listing with photos its vendor uploaded shows those instead (A-189): the first as a decorative thumbnail on its catalog and vendor-page card and at full size on its product page, which then says "Photos are supplied by the vendor; the market does not verify them." ## Fresh-install payment boundary

The development build removes pooled address creation, deposit polling and payout
sending. New purchases use per-order escrow, on supported test networks only,
with both adapters off by default. Migration 107 refuses any legacy drain blocker,
including mainnet pooled history, before startup, and migration 108 (A-492)
refuses any database holding pooled payment history (a `payouts` or
`payment_addresses` row); both tables then refuse new rows. The old enabled
intake setting becomes escrow only and existing pauses remain paused. Nonblank
legacy RPC settings are refused before the database opens. Read
[UPGRADING section 58](../UPGRADING.md#58-pooled-wallet-removal-for-fresh-installs-a-448)
and [section 59](../UPGRADING.md#59-pooled-history-refused-migration-108-a-492).

Current boundary (2026-10-11): escrow only, off by default, test networks only.
Bitcoin escrow runs on regtest, signet and testnet4 and Monero escrow on a local
fakechain or stagenet. Bitcoin mainnet and testnet3 are refused at startup, and
so are Monero mainnet and testnet, until a mainnet release is built (A-460); there
is no mainnet opt-in. Owner directive: pooled mode is not tested and not drained.

Nothing below describes a working pooled wallet. What the pooled build did is
summarised once, under [Prior build (pooled wallet, removed)](#prior-build-pooled-wallet-removed-2026-10-11);
its views (the order payment record, the administrator payout table, unsent
payouts and the payout count) are removed with its mutation forms and routes.
There is no existing deployed market in the owner setup, so no real-market drain
is claimed. A-458 now has Sparrow 2.5.5
GUI per-order practice, release and sibling-refund evidence on isolated regtest
at frozen app revision `f229a1a65172986065bbab4f3aa24a09725695ad`
([record](evidence/sparrow/2026-10-11-f229a1a65172/README.md)). A separate Sparrow GUI import
of the supplied descriptor produced the expected escrow receive address; that watch-only import
does not prove key attachment or signing from the imported wallet. Ledger Flex via Sparrow 2.5.5:
attempted, failed before signing, unresolved ([diagnostic](evidence/sparrow/ledger-flex-2026-10-11.md));
only software signing is verified, and public Sparrow signing remains unverified. Frozen public proof revisions remain unchanged by this removal.

## Working application behavior

- Token-protected, transactional first-run administrator setup; repeated setup is rejected. The operator can instead create the first administrator on the host with `-bootstrap-admin HANDLE` (password on stdin, no setup token, same transaction and lock; no web path).
- Buyer registration, bcrypt password hashing, rotating hashed sessions, session revocation, CSRF validation, bounded forms and authentication concurrency.
- Two HttpOnly, SameSite=Strict cookies: `session` is set only at sign-in (with a fresh token) and cleared at sign-out or revocation; `anon` holds the pre-login token that CSRF forms and the CAPTCHA are bound to while no session is present. A request without cookies (for example, a link followed from another site, which Strict withholds) gets only a new `anon` cookie and never overwrites `session`, so the user stays signed in on their next direct visit. A form rendered on such a landing page carries an `anon`-derived CSRF token; its same-site POST, which then sends both cookies, is served as the anonymous request it was rendered for (it cannot act as the signed-in user, but its sign-in form and CAPTCHA work). Origin and `Sec-Fetch-Site` checks apply to every POST. Session cookies from before this change keep working.
- **Return to the page after sign-in** (A-126): an anonymous request for a signed-in page (for example "Review order draft" or "Contact vendor") is redirected to `/login?next=<page>`, and `/login` says "Sign in to see <page title>." Signing in, registering (`/register` keeps the target, and the links between the two pages carry it) and finishing `/challenge` (TOTP or PGP code; the pending sign-in stores the target, so the PGP code request and a failed attempt keep it) land on that page; a wrong CAPTCHA answer re-renders the form with the target kept (A-269). A recovery-code sign-in still lands on `/totp`, which shows the remaining codes and a "Continue to <page>" link, both with its one-shot notice only (a reload or a crafted `/totp?next=` shows neither, A-287). The target is accepted only as a registered page named exactly (`/checkout`, never `//host`, a scheme, a backslash, an encoded character or an action path) other than the sign-in pages, with at most its `id` query and the `/messages` recipient `to` (other query parameters are dropped; a malformed one refuses the target); it is rebuilt by the server, so it can never lead off the market, and anything refused signs in to `/` as before. The header's "Sign in" link carries no target.
- **Refusal pages** (A-514, A-59 widened): a refused form post (any 4xx from the request checks, the action's checks or a pre-check, and the busy hardware-PSBT upload refusal), an unknown or switched-off page, a page whose object does not exist, a page the account may not see, and an invalid query string answer with one server-rendered HTML page (`web/templates/partials/refusal.html`, `refusal.go`) in the usual layout and with the usual headers (`Cache-Control: no-store`, the CSP), keeping the status code: the title "Error: …", one heading, the reason in the error alert, and a link back to the page the form belongs to (the registered page the action path names, else a same-origin `Referer` that is a registered page, rebuilt with at most its `id` or `to`, never copied; else `/`). A 401 to a browser that is not signed in adds a Sign in link that returns there. A refused post that passed the Origin checks shows its long text fields (title, description, delivery content, message or review body, dispute reason, reply and decision, notes, a pasted PSBT, a PGP key, the operator key and canary statement, a claim or refund address) in read-only, unnamed textareas under "Your text, to copy", each cut to its form's limit and escaped; passwords, authenticator, recovery, PGP sign-in and CAPTCHA codes, the setup token, CSRF tokens and form nonces are never shown, and nothing shown is stored or logged. A refused `/login` or `/register` post gets its form again with the typed handle (never the password) and a fresh CAPTCHA. A listing refusal names each field in error ("Bitcoin price: use a positive amount with at most 8 decimal places.", "Stock: …", "Category: …"). 5xx faults (with a reference), the admission-control busy answer, raw downloads (PSBTs, the audit export, CAPTCHA images) and image routes still answer as before (`TestRefusalPageForRefusedPostEchoesText`, `TestRefusalPageBackLinkIsLocal`, `TestRefusalPageExpiredSessionOffersSignIn`, `TestRefusedSignInKeepsHandle`, `TestRefusedListingNamesFieldAndKeepsText`, `TestEscrowRefusedPSBTIsEchoed`, `TestRefusalPageInPreview`).
- Server-enforced buyer, vendor, moderator, and administrator roles.
- **Staff attention counts** (A-35): moderators and administrators see separate, uncapped counts for disputes, payment reviews and escrow alerts (the pooled payout count was removed with pooled payments, A-492). The counts represent actionable categories and may overlap; role, suspension and non-party visibility are rechecked when loaded.
- PostgreSQL-backed listing creation, catalog search/category/region filters, product and vendor pages.
- **Catalog search and paging** (A-181, with A-16 for the catalog and A-60 PA-8): the search term is cut to 64 characters (so at most 256 bytes; the search boxes carry `maxlength="64"`, which never admits more, so a typed term is searched in full) and matched literally as a substring of title or description, case-insensitively, so `%`, `_` and `\` are ordinary characters. The category and region filters are capped at 80 bytes each. A query string holding a NUL byte or invalid UTF-8, here as on every page, is refused with 400 "Invalid address: a query parameter is not valid UTF-8 or contains a NUL character." before the page is loaded (QA5W4B-5; the bytes used to be dropped from the term and filters here, and made other pages answer 500). The catalog shows 25 listings a page, newest first, with the total count, "showing X–Y" and plain *Previous*/*Next* links ("Page X of Y", marked `aria-current`) that keep the search, filters and display currency; a page number past the end shows the last page and anything else that is not a positive number shows the first. Listing cards on the catalog, vendor page and vendor desk show at most 300 characters of the description (cut on a character boundary, ending "…"); the product and checkout pages show all of it. A catalog page of maximum-size listings (140-character titles, 10 000-character descriptions) is about 44 KB. Search still scans titles and descriptions (`ILIKE`, no trigram index: `pg_trgm` is deferred because creating the extension fails on locked-down external databases); migration 062 indexes `products(archived, created)` for the unfiltered listing order. The vendor page is paged the same way, 25 listings a page with links that keep the display currency (A-189); the orders page, messages and notifications keep their row caps (A-16).
- Atomic-unit BTC/XMR price storage; idempotent **unfunded draft** creation and owner-only order access. Draft creation does not reserve stock or collect payment; requesting payment from the order page does (see P3, P5).
- A-58: migration 105 leaves historical order listing snapshots NULL; the central Draft → Awaiting payment stock reservation copies the listing’s title, full description and fulfillment kind under the listing row lock in the same transaction. The buyer/vendor order and dispute views use the saved terms, with an explicit unavailable label for orders without a copy; the current listing remains a separate live link. The full saved description is shown only on an authorized order page and retained with the order and backups after later listing edits or archiving. Automatic delivery content is not part of the copy.
- Orders carry a canonical state (`draft`, `awaiting_payment`, `paid`, `shipped`, `delivered`, `completed`, `disputed`, `resolved`, `cancelled`). A server-side transition table, row locks and compare-and-set updates guard every change and log it in `order_events`. Buyers, vendors, moderators and the payment watcher move orders only through it (see P3 Orders and P5 Payments).
- Versioned, idempotent schema migrations applied at startup under an advisory lock (see [migrations](operator-guide.md#migrations)). Startup refuses, changing nothing, a database that records a migration the server does not include (one migrated by a newer release). Connecting, waiting for the migration lock, migrating and payment provider startup have separate bounds (`DATABASE_CONNECT_TIMEOUT` 15s, `MIGRATION_LOCK_TIMEOUT` 10m, `MIGRATION_TIMEOUT` 10m, payments a fixed 15s); a timeout exits with an error naming the phase, and a timed-out migration is rolled back. A failed connection names its class (authentication failed, database missing, host not found, connection refused, timed out or TLS required) without printing `DATABASE_URL`.
- **Database session timeouts** (A-177): every connection of the application's pool (and the one `/healthz` connection) starts with `statement_timeout` 8 s, `lock_timeout` 3 s and `idle_in_transaction_session_timeout` 15 s; startup checks that the database accepts them before migrating, so a pooler that refuses these startup parameters stops startup with nothing changed ([Connection poolers](operator-guide.md#connection-poolers)). A payment request, and whatever may queue behind one (a checkout, listing edit, archive or takedown, a cancellation returning stock, a payment-intake change, and an administrator's suspension, second-factor reset or role change), waits up to 11 s for a row lock (its statement limit is raised to 11 s with it), because the request holds its rows while the escrow node is asked about the escrow address; one account has at most one payment request in progress at a time (another is refused at once with 429 and `Retry-After: 5`), so a burst from one account cannot hold the pool's connections queued on its own row. A page or form whose statement hits one is answered 503 with `Retry-After`, not 500, and logged with cause `57014` or `55P03`. So is one whose database connection is lost or refused mid-request (a restart or failover: SQLSTATE `57P01`–`57P03`, `53300`, `08000`, `08001`, `08003`, `08004`, `08006`, or cause `db-connection`; QA-178-2), when the failed statement ran before the change was committed. A lost `COMMIT` acknowledgement for password-confirmed actions and TOTP changes answers 500 with an outcome-unknown message and no `Retry-After`; the change may have committed, so staff should reload and check its state before acting again. Ordinary pre-commit database failures remain retryable busy 503 responses. An upload's lost `COMMIT` answers 500 with an outcome-unknown page and no `Retry-After`: the photo or avatar may have been saved, so reload the listing or account to check before uploading again. The shared form path's own commit, and an audit row that fails after its change was already committed, also answer 500. Migrations run on a separate connection without them (bounded by `MIGRATION_TIMEOUT` instead), as do `-status`, `-bootstrap-admin`, `-reset-admin-password` and the backup and restore scripts, which open their own sessions. The signed audit export's single streamed query lifts the statement limit (it runs under the export's own one-minute bound instead of the 12 s request bound, keeping the lock and idle-transaction limits; one million audit rows took about 6 s), and each payment watcher pass is bounded to 5 minutes, so a pass that cannot get a database connection ends, logs and leaves its work to the next pass.
- **Overload admission** (A-178): the server accepts at most 2048 connections at once (later clients wait in the kernel's backlog; while all 2048 are taken, HTTP keep-alive is off, so idle keep-alive connections are closed and cannot hold the slots), serves at most 64 page requests (GET/HEAD), 16 form posts charged to a signed-in account's write budget and 16 public ones (sign-in, registration, the sign-in challenge, whoever sends them) at once, 16 requests to the public image route (A-187; they take no page slot), and at most 8 CAPTCHA image renders and 4 password checks within those; a request that finds its class full is refused at once with 503, `Retry-After: 5` and `Connection: close`, and is not logged: a page before any database work, a form post after its session lookup (the only database read before its slot). A form post takes its slot only after its body is read (64 KiB cap, 15 s read timeout; a body with more than 64 fields is refused with 400 before it is parsed, so a flood of junk bodies costs about 150 KB of allocation each instead of 3.7 MB) and its Origin, `Sec-Fetch-Site` and CSRF checks pass, so slow-body posts hold only a connection; sign-in, registration and setup posts with a malformed handle or password, or a CAPTCHA id that is not a live one issued to that browser session, are refused (400) before taking a slot, as are sign-in challenges without a pending sign-in cookie (401). A post's session lookup, one indexed read, takes a slot of its own class of 16 for that query only, waiting its turn for up to 2 s before a 503; pages never take it, so a flood of pages cannot refuse a signed-in or staff post. A flood of well-formed public posts, anonymous or from a signed-in account, can still refuse real sign-ins as busy; signed-in and staff changes are unaffected by it. `/healthz` and `/static/` take no slot, and `/healthz` pings the database on its own connection, so a flood of pages or an exhausted pool does not starve the health probe. Every 503 carries `Retry-After: 5` and every 429 `Retry-After: 600` (the ten-minute limiter window), except the 429 refusing a second concurrent payment request from one account (one at a time per app process), which carries `Retry-After: 5`. A slot is released as soon as the response starts, so a slow reader holds only its connection. Server-error log lines are limited to 10 a second; the rest are counted in one `http 5xx suppressed=N` line. Measured with `TestLoadSearchFloodKeepsHealthz` (500 concurrent catalog searches from one keep-alive client, a fresh-connection `/healthz` probe every 20 ms; opt-in with `LOAD_TEST=1`, manual only and never run in CI, [command](ci-cd.md)): on Linux (a Docker container with 8 CPUs, backlog 4096) probe p99 103–145 ms and maximum 172 ms over three 10 s runs, with about 16 000–18 000 requests a second answered, 3–4 % of them search results and the rest refusals, with the connection cap then at 256; with the check on the server's own cap of 2048 (`market.MaxConns`), one 10 s run on a shared 4-CPU Linux host gave probe p99 162 ms and maximum 170 ms, with about 9 700 requests a second answered, 10 % of them search results; on macOS (backlog 128) the flood overflows the accept backlog and dropped connection attempts retried after 1–4 s, so the check is meaningful only on Linux. Load was generated on the same host, not over Tor.
- **Image scanner client** (A-185; the upload pipeline it serves is A-186, below): with `CLAMD_ADDRESS` set, the app polls clamd every 30 s (PING and VERSION) and caches its state: *Ready*, *Unavailable* or *Signatures stale* (the daily signature database is older than `SCANNER_MAX_SIGNATURE_AGE_DAYS`, default 30, 7–90, or its date is unreadable); without it, *Disabled*. `/admin#image-scanner` shows the state, engine, daily version, build date and age, the last successful scan and about 24 hours of in-memory counts (stored, refused as infected by signature, refused because the scanner failed), never linked to accounts; pages read only the cache, and `/healthz` never contacts clamd. The client sends upload bytes once, unmodified, with zINSTREAM (64 KiB chunks, 3 s to connect, 10 s per exchange) and accepts them only on the exact reply `stream: OK`; any other reply, a timeout or a closed connection refuses the upload, and so does an OK the client can see was sent with part of the stream unread (a write that fails, or a reset instead of an orderly close); the client cannot detect a server that reads everything and answers OK without scanning, so clamd itself is trusted. ClamAV checks uploads for known malware; it does not review picture content. A matched signature name appears only in one log line beside a reference the uploader is shown, and in the admin counts; the uploader's audit row is fixed copy. Tested against a fake clamd (`clamd_test.go`, `db-admin.spec.ts`); the opt-in `TestRealClamd` (`CLAMD_TEST_ADDRESS`) passed locally against ClamAV 1.5.4 (`clamav/clamav-debian:stable`, macOS and a Linux container: VERSION parsed, a stream with no match accepted, EICAR found, a stream over `StreamMaxLength` refused without pausing the scanner). `TestRealClamd` does not run in CI; CI's container job runs the production image against the pinned clamd in both database modes instead (A-192, `scripts/ci-smoke.sh <mode> scanner`), with one test signature as its only database, packed at job time into an unsigned `daily.cud` whose build date clamd reports in `VERSION`, so the 30-day gate passes on any day. That proves the app's use of a real clamd (a marker PNG refused and nothing stored, one without the marker stored and served re-encoded, uploads refused while clamd is stopped and resumed after it starts, `SHUTDOWN` refused, clamd unable to reach the database or outside), not detection quality: it is not a production signature feed. [Operations tests](operations-tests.md#malware-scanner-leg-in-ci) list what it checks.
- **Photo and avatar upload pipeline** (A-186; the forms that post to it are A-188, below; stored images are served by the image routes (A-187, below) and shown on pages (A-189, below)): `POST /listings/photo` (vendors and administrators, on a listing they may manage that is neither archived nor taken down) and `POST /account/avatar` (vendors, administrators and moderators; always the poster's own avatar, replacing any earlier one) are the only routes that take a file; a multipart post to any other route is refused with a 415 page before its body is read. The order of work: Origin checks, a `Content-Length` of at most 8 MB (else 411 or 413, unread), the session, the role, the account's change budget and an upload budget of 20 per 10 minutes, a post slot, one of 2 upload slots and one upload at a time per account; only then may the body take 90 s and the answer 150 s (the server's own limits are 15 s and 20 s). Every refusal reads the rest of the body into nothing (never into memory) before answering with an HTML page, so a browser sees the page rather than a reset. The form is `csrf` first, then an optional listing `id` and `description` (250 characters), then `photo` (4 MB); the file name and the part's type are never read. Before the scan: JPEG or PNG by magic bytes only, at most 4096 px a side and 4096×3072 pixels in all (about 12.6 megapixels, so a 4032×3024 phone photo fits), no CMYK JPEG, no JPEG with more than 100 progressive scans, and an estimated decode memory of at most 64 MiB, an upper bound on what Go's decoders allocate (a JPEG counts its planes, 4 more bytes a pixel for an RGB one, and when progressive 256 bytes for every 8×8 coefficient block of each component at its own sampling, so a progressive 4:4:4 JPEG counts 15 bytes a pixel, a 4:2:0 one 9, a baseline RGB one 7 and a progressive 4:4:4 RGB one 19, on its size rounded up to whole MCUs; checked against real decodes by `TestDecodeAllocationWithinEstimate` and `FuzzDecodeReencode`), and a JPEG that `image/jpeg` would read differently from the header check (stray `FF 00`, or a marker it does not parse as a segment) is refused. The bytes received are then scanned (above) and, only when clamd found nothing, decoded one at a time, turned upright by their EXIF orientation, flattened on white, resized (never enlarged) and re-encoded by Go's JPEG encoder: a photo fitting 1200×1200 (quality 82) with a 320×240 letterboxed thumbnail (quality 70), an avatar a 256×256 centre square with a 64×64 thumbnail. Nothing but the pixels survives: no EXIF, XMP, IPTC, ICC profile, comment, embedded thumbnail, PNG text chunk or data after the image (`images_test.go`). One transaction then re-checks the session and role (waiting for, and seeing, an administrator's change to the account or the listing's vendor in progress: it takes their users rows before the listing, in the same order as that change, so the two cannot deadlock), locks the listing, enforces 4 photos a listing, 50 MB an account and `IMAGE_STORAGE_LIMIT_MB` (default 2048) for the market (409 pages), stores the two JPEGs, their size, the description, owner, listing and time in the `images` table (migration 063; no column for a file name, type, original size, hash or scan result), writes a fixed-copy audit row and, when an administrator added the photo to another vendor's listing, records "Photo added to listing <8-char id> by an administrator" in that vendor's audit trail and notifies them (A-190). Tested with generated fixtures and a fake clamd, over `httptest` and loopback connections (`uploads_test.go`, `uploads_integration_test.go`, `uploads_quota_test.go`); in Chromium and Firefox with JavaScript off against the fake clamd (`db-listing-photos.spec.ts`, below); and in CI with curl against the production image and a real clamd holding only a test signature (A-192, above); not over Tor or with production signatures. What the server keeps (below and `/canary#records`) lists what an image row holds and who can see it (A-191). Migration 063 also stores the owner's staff-visibility choices (a per-account "hide me" flag, hidden by default, and a "public staff list" setting, off by default) for A-187 and A-189; the image routes and pages read them (below). An administrator sets the public staff list on `/admin` (A-189); staff set their own flag on `/account` (A-188, below).
- **Image routes** (A-187; the pages that link them are A-189, below): stored images are served only by two routes, as the re-encoded JPEG (`-f`, at most 1200 px) or its thumbnail (`-t`), addressed by the row's 128-bit random id (32 lowercase hex). `GET`/`HEAD /img/<id>-t|-f` is public: it runs before any cookie or session code (it reads no session and sets no cookie), takes one of 16 image slots of its own (`imageWork`) instead of a page slot, so a page of thumbnails or a flood of image requests cannot refuse pages (and a full image class answers 503 with `Retry-After: 5`), and serves a photo only while its listing is published (not archived, not taken down) and its vendor (or the administrator whose listing it is) is not suspended and still has that role, a vendor's avatar while the vendor is not suspended, and a moderator's or administrator's avatar only while the "public staff list" setting is on and that account has not hidden itself (both off/hidden by default; owner decision). `GET`/`HEAD /desk/img/<id>-t|-f` reads only the session cookie (under a page slot, like a page) and serves an image to its owner whatever its state (an archived or taken-down listing's photo), any image to an administrator, a staff member's avatar to the buyer, vendor and moderators of an order on which that member recorded the dispute decision, and an archived (or taken-down) listing's photos to whoever may read an order placed on that listing by the order page's rule (A-264: its buyer and vendor, and moderators and administrators while that order is disputed or resolved or has a dispute record from a party concession or has a flagged payment); moderators get nothing else there (they see vendors' images on the public route), and the public route still refuses an archived listing's photos (`TestArchivedListingPhotosThroughOrder`). Every other GET or HEAD (a malformed path, a hidden image, no session) gets the same 404 as an unknown image id (status, headers and body; neither route sets a cookie), so an id cannot be probed; a POST gets 405. The image bytes held by responses still being written are capped at 64 MiB on `/img` and, separately, 32 MiB on `/desk/img`, so a signed-in flood of the desk route cannot refuse public images (`TestDeskImageFloodLeavesPublicImages`) (a GET reserves the largest size of what it asked for before its query, never waiting, and keeps what the image needs until it has been written): a client that never reads cannot pin memory beyond that, and a GET whose largest size no longer fits gets the busy 503 with `Retry-After: 5` while pages are unaffected and a HEAD, which reads only the length, still answers (`TestImageSlowReadersBoundedByByteBudget`: 33 clients that never read fill it, the heap grew 61 MiB with 49 of them connected). A served image carries exactly `Content-Type: image/jpeg`, `Content-Length`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: private, max-age=86400, immutable` (a browser may reuse a viewed image for a day without asking again, and keep it on disk until its cache is cleared: `max-age` sets freshness, not retention), `Cross-Origin-Resource-Policy: same-origin` and `Content-Disposition: inline; filename="image.jpg"`: no `ETag`, `Last-Modified` or `Set-Cookie`. No other query reads image bytes: outside `image_routes.go`, no SQL string or concatenation of strings and constants names the `full` or `thumb` column (in any case) except inside `octet_length(...)` or an `INSERT INTO images(...)` column list, none reads whole `images` rows (`*`, `alias.*`, the row itself, `row_to_json` and the like), and no other file uses the helper that builds the byte-reading query (`TestOnlyImageRoutesSelectImageBytes`; the checker's own evasion cases are `TestImageBytesCheckerCatchesEvasions`). It reads Go source text, so SQL assembled at run time from non-constant parts is outside what it can see. Tested over `httptest` and a loopback server against PostgreSQL (`image_routes_test.go`), not in a real browser or over Tor; `/canary#records` says what a browser keeps (A-191).
- **Upload forms, own removal and the staff "hide me" choice** (A-188; the pages that show them are A-189, below): each listing's edit page has a **Photos** panel (`#photos`) listing the listing's stored photos from the database, oldest first, each with its thumbnail through `/desk/img`, a link to the full image, "Photo N: JPEG, W×H, N KB" (sizes from `octet_length`, never the bytes), its description or "No description", and its own urlencoded remove form; above them "N of 4 photos · X MB of 50 MB" (X is the listing's vendor's photos and avatar, rounded up to a tenth). Below is the listing's only multipart form (`POST /listings/photo`: hidden `csrf` first, then `id`, an optional description of up to 250 characters, then the file input, `accept="image/jpeg,image/png"`, never `capture`); the limits (4 MB, 4096 pixels a side and 4096×3072 in all), the re-encoding, the 90-second Tor timing, the ClamAV line and a privacy notice (what is removed; what is not, including anything visible and sensor noise; screenshots; public to anyone; never reuse a photo) precede the input and describe it (`aria-describedby`). An archived, taken-down or full (4 photos) listing shows why instead of the form. `/account#avatar` does the same for the account's avatar (vendors, administrators and moderators; staff also read that a staff photo links their identity across every dispute decision), showing the current one through `/desk/img` with a remove form; an account demoted since still sees and can remove one it has. ## What the server keeps

`/canary#records` tells users the same thing, and `/register`, `/account` and the `/messages` notice link to it. Most records below are kept in PostgreSQL and in backups until removed, except photos and avatars (below); form submission receipts expire and are swept as described below; there is no account, message or order deletion. Migration 098 clears the deprecated XMPP profile values from the live database while retaining the column for compatibility. Backups made before that migration can still contain the old values until restored and upgraded or the backup is removed. The operator, anyone else who controls the server or database, and anyone holding a decrypted backup can read retained data; the list says who else can read it through the application. Checked against `internal/market/schema.sql` and `internal/market/migrations/` (001–108).

- **Form submission receipts** (`form_submissions`, migration 100; A-130, partial): receipt-backed replay returns the committed result for the same account, session, action and exact request on listing create/update/archive/restore, media removal, PGP ownership challenge/verification, TOTP enrollment, notification read/mark-all forms, settlement/hardware signature uploads and `/escrow/bump-sign`, `/messages`, `/orders`, `/disputes`, `/disputes/reply`, `/reviews`, and ordinary order transitions. `/orders/pay` also returns the recorded result after a completed payment request; while one request is in flight, a repeat is bounded and refused before another wallet RPC. A receipt guarantees one committed market action; it does not guarantee that an external wallet skipped address generation before a rolled-back transaction. The receipt holds a random form id, a session-token hash, a keyed request hash, route, redirect and notice; it does not store submitted text, IP address or browser details. Receipts expire after 24 hours and are swept at startup and every minute in bounded batches. Upload idempotency remains separate (A-193). Tests include `TestFormNonceDraftDisputeReplyAndReviewFormsReplay`, `TestFormNonceOtherOrderTransitionsReplayOnce`, `TestFormNonceLostCommitAcknowledgementCanReplayRecordedSuccess`, `TestFormNonceListingManagementFormsAndReplay`, and `TestMediaRemovalReceiptsReplayAndBindActorSessionAndBody`. Confirmed `/resolve`, `/admin/suspend` and `/admin/reset-factors` receipts additionally recheck the current password hash, live session, role and route eligibility; exact replay spends no second authenticator code and builds no second settlement. Their real-PostgreSQL race tests include actual committed transactions with a lost acknowledgment. The same confirmed receipt guard now covers BTC/XMR claim, Bitcoin ship/recover/bump request, Monero ship/receipt confirmation, PGP sign-in setting changes, archived delivery cleanup, admin review/listing changes, the captcha/staff-contact/staff-list/operator-key/canary/deadline/intake/fee settings, and moderator payment/XMR-collision dispositions. BTC/XMR escrow checkout and admin payment-address-collision dismissal also have ordinary receipt coverage. Bitcoin dispute decisions and Monero settlement re-request/retry-build use confirmed receipts with current nonparty eligibility; old saved success does not overwrite later decisions or clear a newer build failure. Party concessions have the same amount-bound confirmation and receipt guard. BTC/XMR restore rebroadcast and Monero wallet-destruction confirmation also return saved responses without repeating a send request or wipe; destruction replay rechecks current nonparty eligibility. Old saved responses do not restore older settings, repeat cleanup, reopen a watcher request or change a later disposition; current actor/session/password/role and route eligibility still apply. Migration 106 adds a boolean recording whether a dynamic account, admin or escrow-key form originally required password confirmation; it stores no password, authenticator code, recovery code, PGP key or practice PSBT. Completed identical requests still recheck the current account, role and live session, and password-confirmed ones verify the current password before returning the saved response. TOTP activation, recovery-code replacement and TOTP disable now record their result in the same transaction as the factor change, so repeating the identical form does not spend another one-time code or undo newer factor state. The broad A-130 aggregate remains partial. Session-rotating password, logout and revoke actions preserve the live-session boundary and need separate treatment. Image-upload idempotency remains conditional under A-193.
- **Handle and role** (`users.handle`, `role`, `created`; `suspended_at`, migration 011). The handle cannot be changed (`/register` and `/setup` say so). Shown to trading and messaging partners, moderators and administrators, and publicly with a vendor's listings and vendor page. Moderators' and administrators' handles and roles are public on `/canary#staff` only while an administrator has turned the public staff list on and that account has chosen to be listed (A-189). Administrators see every handle and role and the suspended accounts with their time.
- **Password** (`users.password_hash`, bcrypt).
- **Second factors** (migrations 010, 012, 013, 020): TOTP secret and pending secret sealed with AES-256-GCM under a key derived from `APP_SECRET_KEY` (or `SETUP_TOKEN` on a legacy installation, so the database plus that secret opens them); recovery codes as SHA-256 hashes, with newly issued codes sealed in `users.recovery_reveal` for at most about 11 minutes; `pgp_2fa`; `pending_logins.factor_failed` marks a pending sign-in whose second factor already failed once (migration 012); `pending_logins.password_digest` is the SHA-256 of the password hash the sign-in's password was checked against (migration 013, A-157), so a password change also ends a sign-in whose password was checked just before it. The account and administrators (second-factor reset list) see which factors are on.
- **PGP public key** (`users.pgp`, stored canonically; `pgp_fingerprint`, `pgp_verified_at`, migration 020; `pgp_changed_at`, when the key was last added, replaced, removed or updated without keeping its proof, and `pgp_expiry_notice`, the last expiry notice sent, migration 067). Shown to any signed-in account that looks up the handle, to trading partners, and publicly on a vendor page (see P2).
- **Messages** (`messages`: sender, recipient, canonical ciphertext, `created`, `encrypted`, `recipient_match`, nullable `recipient_extra_keys`). The last field is the send-time count of distinct visible additional recipient key IDs; legacy rows and unknown recipient keys remain unmeasured. No separate recipient IDs are stored outside the ciphertext. The server cannot decrypt them. Sender and recipient see them; moderators and administrators have no message view. While a dispute is open, staff who are not party to it see, on the moderation desk and `/disputes`, how many messages each party sent to each current moderator or administrator since it opened and the time of the latest, from `sender_id`, `recipient_id` and `created` only (A-162).
- **Payment-provider outage episodes** (`provider_episodes`, `provider_episode_deliveries`, migration 101): fixed Bitcoin and Monero escrow keys (rows written by the prior pooled build may remain), an episode counter, first failed/skipped time, alert state and per-administrator outage/recovery delivery receipts. Neither table holds RPC errors, wallet replies, addresses, credentials or notification text. Receipts for the prior episode are deleted when a new one begins; the current episode's rows remain in PostgreSQL and backups. Current unsuspended administrators alone see the plain-text notices; paused new-payment intake is not an outage.
- **Notifications** (`notifications`): plain text such as "New message from <handle>", short order IDs with the new state (for a move neither party made, the payment watcher's or a moderator's, followed by its reason, e.g. "Cancelled — payment window expired", "Resolved — refund to buyer"; never an absolute time; A-123), payment notes and settlement transaction IDs; read state. Migration 104 adds a nullable full order ID for explicitly associated new order-specific notices, used for an order link without widening order-read authorization. Legacy and account-only notices remain unlinked; notification text is never parsed to invent an association. Only the account sees its notifications.
- **Orders and drafts**, including unpaid drafts and cancelled orders (`orders`; `order_events` with actor, time and notes such as the vendor's note to the buyer and the cancellation reason). The buyer and vendor, and moderators and administrators while the order is disputed or resolved or has a dispute record from a party concession, a payment on it is flagged, or its escrow has an open staff alert (see P3).
- **Disputes** (`disputes`: reason, resolution, outcome, plain text; the other party's one reply is an `order_events` row whose note starts "Dispute reply: ", plain text, A-124). The parties, moderators and administrators.
- **Reviews** (`reviews`, migration 030): rating and text; public on product and vendor pages by month without the reviewer's handle; the vendor sees the review with the buyer's handle on the order page. Administrators can hide a review from the public pages (`reviews.hidden_at`, migration 031); a hidden review is kept, not deleted, and administrators still see it.
- **Digital deliveries and listings** (`deliveries`, migration 030; `products` including `delivery_content`): delivered content is unencrypted and shown to the buyer and vendor, and to moderators and administrators once disputed; listings are public; automatic delivery content is shown only to the vendor.
- **Listing photos and avatars** (`images`, migration 063; A-186 to A-191): for a listing photo, a vendor's avatar or a staff member's (moderator's or administrator's) avatar, only the re-encoded JPEG, its thumbnail, its dimensions, an optional description (listing photos only; the avatar form has none), the owner, the listing for a photo and the time added. The uploaded file, its name and its metadata are never kept: no column holds them, and the re-encoding keeps only the pixels (see the upload pipeline above). Listing photos and their descriptions are public to anyone, signed in or not, while the listing is published and its vendor (or the administrator whose listing it is) keeps that role and is not suspended; a vendor's avatar is public while the account is a vendor and not suspended. A staff avatar is public on `/canary#staff` (and on an administrator's vendor page) only while an administrator has turned the public staff list on and that staff member has chosen to be listed (`users.staff_hidden`, hidden by default); otherwise it is shown only beside that staff member's dispute decisions, to the buyer and vendor of those orders and to moderators, and to administrators (the parties' and moderators' access needs that member to have decided a dispute and to be still staff and not suspended; administrators can open any image on `/desk/img`). Demoting a staff member removes their staff avatar: an administrator changing a moderator's role deletes it in that transaction, notifies them and records "Staff avatar removed when the role changed" in their activity log, and resets their public staff list choice to hidden, so a later promotion starts hidden again (PR #28 review). Demoting a vendor to buyer, archiving a listing, an administrator's listing takedown and suspending the account hide its images from the public without deleting them; administrators, and the owner while signed in, still see them on `/desk/img`. The image routes send `Cache-Control: private, max-age=86400, immutable`. A normal browser may keep viewed images in its disk cache: it reuses them for a day without asking the server, and the files can stay until its cache is cleared. Tor Browser keeps them in memory only, until it closes (not yet tried in Tor Browser, A-199). Removing or replacing an image, or a staff takedown, deletes it from the database at once; copies remain in backups made before that and, until PostgreSQL reuses the space, in its data files and write-ahead log. If the operator restores a backup made before a removal, the image returns until it is removed again (`scripts/restore.sh` says how many images it restored). The activity log keeps that an image was added, replaced, removed or taken down (with the listing's short id and a takedown's reason, never the image), and a takedown's reason also reaches the owner as a notification. ClamAV checks uploads for known malware; it does not review picture content. An upload it flags stores no image: the uploader's activity log records "Upload refused by the malware scanner", and the server log keeps the signature name and the reference shown to the uploader, for as long as Docker's logs are kept (3 × 10 MB rotation), and its time can be matched to the uploader's activity-log row; the log line itself names no account (see the [operator guide](operator-guide.md#troubleshooting)).
- **Payments** (`payment_addresses`, `payments`: addresses, amounts, transaction IDs, confirmations; for a flagged deposit, the staff review with its reason or note, migration 066; older rows may hold a hand refund's transaction ID and amount). Amounts, confirmations and payment status are shown to both parties. `payment_addresses` holds no rows (migration 108, A-492). Escrow deposit identifiers remain visible to both parties for verification. Deposits are recorded for escrows on a supported test network.
- **Historical payout addresses** (`users.payout_btc`/`payout_xmr`, migration 050; the time each was last saved or removed, `users.payout_btc_changed`/`payout_xmr_changed`, migration 057, NULL before it), saved before escrow and kept in the database; no page shows or edits them and no code reads them for an escrow (A-508). The pooled `payouts` and `payment_addresses` tables hold no rows: migration 108 refuses a database with any and both refuse new rows (A-492).
- **Bitcoin escrow keys** (`user_escrow_keys`, migration 074), only on a market running Bitcoin escrow (`ESCROW_BTC=on`, off by default and test networks only: regtest, signet or testnet4; [per-order escrow](escrow.md)): the account's extended public key, sealed with AES-256-GCM like the TOTP secrets; an HMAC of it that stops two accounts registering the same key; its origin fingerprint and path; its layout, Bitcoin Core or a per-order wallet (migration 088, development branch; a vendor's active key type is shown to anyone on their listings and profile while escrow is on); and when its practice transaction was signed. The pasted practice PSBT is not kept. The owner sees the origin and state on `/escrow-key`; the audit line and notification name no key, fingerprint or path. The escrow's arbiter wallet fingerprint and an HMAC of its complete account key are kept in `settings`. The latest Bitcoin escrow node-health snapshot (`bitcoin_escrow_health`, migration 093) stores whether escrow is enabled, a fixed status class, last successful check, chain and height, pin match, keypool and highest allocated child index, with timestamps; administrators see it. Each check replaces the snapshot, and it stores no RPC URL, credentials or wallet name. With an escrow signer configured (A-454, development branch; since A-456b it co-signs per-order escrows), the signer's account fingerprint and an HMAC of its account key are kept in `settings` (`escrow_signer_fingerprint`, `escrow_signer_xpub_hmac`); the signer's seed is kept only in the signer's own volume, never in the database, `.env` or `scripts/backup.sh`'s output ([operator guide](operator-guide.md#escrow-signer)). On the development branch (not released), escrow checkout also writes `escrows` (the escrow address, the market's child index, the buyer's refund address, pinned for the order, and the market fee in basis points with its destination, fixed at checkout) and `escrow_pubkeys` (the three child public keys, each with its party, and for the buyer and vendor their own key origin and child path; never an extended key), and the escrow's deposits in `payments`. The order page shows each party its own origin only; the refund address only to the buyer, until a settlement that pays it lists its outputs to both parties. Audit and order-history text name no key, fingerprint, address or refund address. A settlement (the vendor's claim or a refund) writes `settlements` (its destination: the vendor's claim address, given when the claim is requested, or the buyer's refund address; the unsigned PSBT and its transaction ID; the fee rate and network fee; which party signed and when), `settlement_outputs` (each output's address, amount and whom it pays) and `settlement_signatures` (the signing party's public key and signature on each input); the pasted PSBT is not kept. Each party sees the outputs, including the other party's destination, since either may sign; order-history and audit text name no address, key or PSBT. `payments.settlement_id` names the settlement that spends each escrow output. Since migration 076 a settlement also keeps the final signed transaction the market stored before broadcasting it (`raw_tx`, which carries both signatures and is public once broadcast; shown to the parties, and to staff reading the order, only after the broadcast), who completed it (the market or both parties), when it was stored, broadcast and confirmed, why it was not sent yet (a fixed class), and the transaction ID that spent its coins when another transaction did; a superseded settlement of a changed dispute decision stays with its state. `payments.escrow_left_out` marks a deposit a bounded build left for a stray refund (`payments.escrow_too_few_by`, migration 087, names the refund whose too-small failure left it out, so a changed decision counts it again), and `escrows.recover_requested` when the buyer asked to recover coins at the escrow. The market fee an administrator saves is kept in `settings` (`escrow_btc_fee_bps`, `escrow_btc_fee_address`), as is the time of the last daily stray-refund check (`escrow_btc_stray_check`). The market-signed PSBT is never kept. Since migration 077 a confirmed settlement also records when its transaction had 100 confirmations (`settlements.reorg_safe_at`; it is followed until then, A-246 P1-d1), a settlement whose transaction the market found already on the network is recorded as completed by `network` when the stored signatures do not show who signed it, an escrow deposit spent by a transaction the market did not make, with no settlement covering it, is marked (`payments.spent_outside`, with that transaction's ID in `payments.spent_by` when the watch-only wallet names it) and flagged for staff, and `escrow_orphans` lists for administrators each address the escrow watch-only wallet holds with no `escrows` row (the address, the order ID from the wallet label, what the wallet says it received, when first and last seen). Outside the database, the escrow node's watch-only wallet keeps every escrow's bare-key descriptor and address, labelled `escrow:<order ID>`, with no age limit (ES-8). Since migration 089 (A-456a, development branch; open to users since A-456b) a per-order escrow also keeps its order wallet's 29 sibling addresses (`escrow_siblings`; its `escrow_pubkeys` rows hold the per-order child keys, never an extended key), and the watch-only wallet also holds that order wallet's two ranged descriptors, which name only the rooted per-order keys, and each sibling address labelled `escrow:<order ID>`. Since migration 080 (WR-escrow P2-d, development branch) a fee bump of a broadcast settlement writes `settlement_bumps` (who asked for it, its number, fee rate and network fee, the unsigned PSBT and its transaction ID, which party signed first and when, the final signed transaction once stored, who completed it (since migration 082 also `network` for one the parties broadcast themselves, or one a restore lost, whose stored signatures do not show who signed it, A-382), when it was stored, broadcast and confirmed, and why it was not built or sent, a fixed class) and `settlement_bump_signatures` (each signing party's public key and signature on each input); the pasted PSBT is not kept and the settlement's own row does not change. A restore holds a restored fee bump with a stored transaction (`settlement_bumps.send_error`) as it holds a settlement. Since migration 083 (WR-escrow P2-e, development branch) the escrow watcher's orphan sweep keeps `escrow_reserved_keys` (each of the three public keys of an address the watch-only wallet holds with no `escrows` row, with that address and when it was reserved), so that no new escrow uses them again, and a restore by `scripts/restore.sh` writes `escrow_index_floors` (for each account with an escrow key, the lowest child index its next escrow may use) and the setting `escrow_sweep_required` (escrow checkout waits until the sweep has run). The owner sees their next child index on `/escrow-key` once it passes 900, with the advice to refill their wallet's keys, and the order page gives the same advice for their child key in that escrow (A-397). Since migration 079 (WR-escrow Phase 2, development branch) a physical listing keeps its dispatch window (`products.dispatch_days`, 1 to 30 days; empty for a listing from before the migration), and an escrow keeps the release deadline length and dispatch window it was created with (`escrows.release_days`, `dispatch_days`), the time a buyer may cancel an unshipped paid order (`ship_by`), the release deadline (`release_at`), when the buyer was reminded (`reminded_at`) and whether a restore moved the deadline (`release_recheck`); the administrator's release deadline length is kept in `settings` (`escrow_release_days`). `/canary#records` lists these escrow records (A-333).
- **Monero escrow** (migrations 084 to 086 and 090; WR-escrow Phase 3, development branch): `escrows.coin` records each escrow's coin (`BTC` for every Bitcoin escrow) and `escrows.xmr_slot_id` a Monero escrow's account. The Monero tables: `xmr_escrow_wallets` (each monthly escrow wallet's name, primary address, restore height, seed sealed to the operator's OpenPGP key with that key's fingerprint, state and retention dates), `xmr_escrow_slots` (each wallet account's index and address, and the order that claimed it), `xmr_settlements` and `xmr_settlement_outputs` (each settlement's destinations and amounts, and its stored transaction) and `payments.xmr_settlement_id`. With `ESCROW_XMR=on` (off by default, a local fakechain or, since A-449, stagenet) the Monero escrow watcher writes the wallets and slots, Monero escrow checkout writes `escrows` (the slot's address, the buyer's refund address, the market fee) and claims a slot, the escrow's deposits go to `payments` like the others, a cancellation holding coins (an underpaid order at the end of its payment window included) or a dispute decided for the buyer writes a requested refund to `xmr_settlements`, and the watcher requests a stray refund for deposits after close or left out of a settlement; the watcher alone builds each settlement and stores it (its outputs in `xmr_settlement_outputs`, its transaction hash, metadata, blob, fee, input total and key images, and the claim of each deposit it spends in `payments.xmr_settlement_id`) before it relays it, then records it relayed, confirmed and 100 confirmations deep, or external or failed; `xmr_settlements.send_error` (migration 085) records why a settlement waits, failed or is held, or that it is set aside because building it twice made the escrow wallet-rpc stop responding; an administrator's request to build a set-aside settlement again clears it and is an order-history note and an audit event. An administrator's re-request of a failed settlement is a `xmr_settlement_rerequests` row (migration 085: the settlement, the administrator, when it was asked and decided, refused with a fixed reason or done with the new settlement) and an audit event; carried out, it supersedes the failed settlement with a new row. The watcher keeps each wallet's `last_closed_at` and `destroy_after` (90 days after its last order closed), retains a closing wallet with no open order, and destroys a retained wallet once nothing is left in it (its password replaced by one never kept, `seed_sealed` wiped, `destroyed_at` recorded); the start of each destruction is recorded first (`destroy_started_at`, migration 086); a wallet that no longer opens is `missing` with its seal kept (destroyed again automatically only when its destruction was recorded as started, it then refuses its own password, staff were never told it holds something, and no restore is being reconciled), and an administrator's confirmation of a missing wallet's destruction past `destroy_after` wipes its seal and is an audit event; `escrow_xmr_destroy_held_<wallet id>` records that administrators were told a wallet past its destruction date still holds something. After a restore (`scripts/restore.sh`), Monero settlements with a stored transaction are held in `send_error`, free slots are retired, active and sealed wallets are closing, and `xmr_escrow_sweep_required` stays set until the watcher's sweep has recorded the wallets created after the backup (`orphan`, then sealed and `retained`) and checked every wallet; an administrator's confirmation of a held settlement's relay is its `send_error` and an audit event. `settings` keeps the secret verifier and seed key fingerprint pins, the sweep marker and, while coins sit at a wallet's account 0, a marker so administrators are told once (`escrow_xmr_account0_<wallet id>`). A deposit the database refused as another order's escrow account is one row of `xmr_escrow_collisions` (migration 090, A-480): the order, the wallet name and account, the transaction ID (its first 20 characters only for a row backfilled from an earlier order note), when it was noted and, once recorded, the staff member, the time and their plain-text note of what was done. Moderators and administrators who are not parties read it on the order page; the parties do not.
- **Activity log** (`audit_events`: action text naming handles, key fingerprints, short order IDs and transaction IDs, with time), including every sign-in and sign-out. The account sees its latest 15 on `/account`; administrators see every account's on `/admin` and in the signed audit export (see P6).
- **Temporary sign-in records**: hashed session tokens (`sessions`, 12 hours: the token's SHA-256, the account, and when the session started and ends; no IP address, user agent or other client data; the owner sees the start times on `/account`, A-157), pending sign-ins (10 minutes; with the page the sign-in returns to, A-126), the ids of CAPTCHA challenges that were answered (`captcha_spent`: the id and its expiry, at most 10 minutes after the challenge was shown, deleted by a sweep every minute; a challenge that is only shown stores nothing) and PGP ownership challenges (30 minutes). Expired sessions and pending sign-ins are deleted opportunistically, not by a timed sweep; an expired PGP challenge stays until the account starts another, proves ownership or changes its key.
- **Not recorded**: no IP address, user agent or other browser details and no access log (no table has such a column and no handler reads them), and no email address. A reverse proxy, the Tor service or the hosting provider in front of the application may log connections. The only application log line that can carry a network address is Go's `http: panic serving <address>` if a handler panics; behind the bundled deployments that address is the proxy's or Tor's, not the visitor's. Server errors (5xx) are logged as one line with the route, status, a reference shown to the user and a cause class, never the request, its sender or the error text, at most 10 lines a second with the rest counted in one summary line; overload refusals are not logged ([operator guide](operator-guide.md#troubleshooting)).
- **Signed audit export**: it names every account's activity, so it is private operator evidence, never to be published; `/canary` publishes only its public key so the operator can prove an export they hold came from this server.

## Feature packages

Each package updates only its own subsection when it lands.

### P1 Authentication

- **TOTP second factor** (`/totp`): RFC 6238 (HMAC-SHA-1, 30-second steps, 6 digits, one step of clock skew either way) implemented with the Go standard library. Enrollment generates a random 160-bit secret, stored encrypted (AES-256-GCM, key derived from `SETUP_TOKEN`) and inactive until the user confirms a correct code. Activating TOTP needs the current password on every account, including one with no factor yet (starting enrollment does not), so a session alone cannot add a factor that locks the owner out after "Sign out everywhere" (A-152); the audit row notes the confirmation. Every accepted code advances a per-account step counter, so a code cannot be used twice, including by concurrent requests. Turning TOTP off requires the password and a current code or recovery code. Someone who lost the authenticator can also turn it off while signing in (A-154), so one recovery code is enough to recover without staff: the recovery-code form on `/challenge` has an unchecked "I lost my authenticator — turn two-step sign-in off" checkbox, honoured only with a recovery code (ignored with an authenticator code). In the sign-in's transaction it turns TOTP off (secret, pending secret, step counter, every recovery code and any unrevealed codes), writes one audit row "TOTP turned off at sign-in with a recovery code (N remaining)" in place of the usual recovery-code row and notifies the owner once. Other sessions and pending sign-ins are left as `/totp/disable` leaves them; PGP sign-in, when also on, stays on and is asked for at the next sign-in; a suspended account's sign-in is refused and nothing changes. Every recovery-code sign-in lands on `/totp`, which says once (a one-shot notice set with the new session, A-287) how many recovery codes remain (or that TOTP is now off). Every path that changes an account's pending sign-ins, recovery codes or account row takes the row locks in the order `/challenge` does (pending sign-in, then recovery codes, then the account row): the sign-in, password change, TOTP activation, recovery-code replacement, turning TOTP off, the administrator's factor reset and suspension, and the `-reset-admin-password` tool, so none of them deadlocks with a concurrent sign-in.
- **Sign-in challenge**: after a correct password, an account with TOTP enabled normally receives a 10-minute pending login and must complete `/challenge`; no session is issued before its factor succeeds. A-159(a) adds a narrow exception for a paused sole administrator: the optional current authenticator code on `/login` completes password and TOTP together, with current account checks and one atomic replay-guard/session transaction. All administrator rows count toward the sole-admin rule, including suspended ones; recovery codes are not accepted by this path. Code guesses are limited to 10 per pending login and 10 per account per ten minutes (in-memory limits, per application instance). Limiter entries are created only for pending logins that exist and, for sign-in, registration and setup (each 10 per handle per ten minutes, case-insensitive, with separate budgets), only for a well-formed handle whose request passed the CAPTCHA (when it is on; setup has none), so a wrong or absent CAPTCHA never spends a handle's budget. Only failed passwords spend a handle's sign-in budget: a correct sign-in spends nothing, and registration and setup attempts never touch it. After 10 failed passwords the handle's sign-in is refused (429, even with the right password) for the rest of that ten-minute window, with a message that sign-in for this handle is paused for up to 10 minutes, that someone else may have caused it and that the password may be fine. Because the budget is per handle (there is no per-client signal over Tor), anyone who knows a handle, including the administrator's, can keep it paused with 10 wrong guesses per ten minutes, each needing a solved CAPTCHA when it is on and nothing when it is off. While any handle is paused, sign-in failures and refusals log `sign-in limiter refusing handles=N` at most once a minute (a count, never a handle); restarting the application clears the in-memory limits ([operator guide](operator-guide.md#authentication)). Registering a taken handle is answered "Handle unavailable" before any password hashing and spends no budget. Password checks and hashing run at most four at a time. A sign-in or registration takes one of these slots only after its input, CAPTCHA, free-handle and limit checks pass, so requests refused by those checks never keep real sign-ins or confirmations waiting; a password confirmation is refused before taking a slot once its account's budget is spent, and otherwise takes its slot before its attempt is counted. Every password-confirmed change (the administrator and moderator actions, resolving a dispute, payment reviews, settings, key, TOTP and password changes) shares one per-account budget of 10 **failed** confirmations per ten minutes (A-274, as A-153 for sign-in): a wrong password, or, when TOTP is enrolled, a wrong authenticator or recovery code after the right password. Each password reserves one attempt before bcrypt runs and each code another under the account row lock, and a right one gives it back, so a correct confirmation spends nothing (a moderator can resolve any number of disputes) and concurrent guesses still cannot exceed it. After 10 failures the account's confirmations are refused (429 "Too many failed password confirmations. Try again in ten minutes.") for the rest of that window, even with the right password; only someone signed in to the account can spend it, and restarting the application clears it. A sign-in, registration or password confirmation refused because every slot is busy (503) spends none of its budget. When the in-memory table (4096 entries) is full, the non-blocking entry with the lowest count is evicted; an entry that is currently refusing requests is never evicted, so junk keys cannot reset a blocked counter. If every entry is blocking, new keys are refused with 429 until entries expire (at most ten minutes); filling the table that way takes a limit's worth of requests per key, each passing the CAPTCHA for sign-in keys when it is on.
- **Recovery codes**: 10 codes of 80 random bits each, issued on activation and on replacement (which requires the current password and a current authenticator code and invalidates all earlier codes). Codes are checked against stored SHA-256 hashes; each code is marked used in the same transaction that signs in. The plaintext codes are displayed once, on the first `/totp` view within 10 minutes of issue; until then they are kept encrypted in `users.recovery_reveal` (AES-256-GCM, key derived from `SETUP_TOKEN`, so a copy of the database plus `SETUP_TOKEN` reveals them). That view deletes them. If it never happens, they are deleted by a background sweep that every running app process runs at startup and then once a minute, or earlier when the account opens `/account`, `/pgp`, `/admin` or `/totp` after the window. So the encrypted codes exist for at most about 11 minutes after issue while the app runs; if it is stopped they remain until it next starts, and a backup taken within that time contains them.
- **Image CAPTCHA** on `/login` and `/register` (not on first-run setup): six characters from a 30-character alphabet, drawn server-side as a same-origin PNG from a built-in 5×7 bitmap font with jitter, shear, wave and noise. Each challenge is bound to the browser's session or pre-login (`anon`) token, single-use (a wrong answer consumes it; the 400 answer to one is the same form again with the error and a fresh challenge, so no reload is needed without JavaScript) and expires after 10 minutes. Challenges are stateless (A-176): the id carries its expiry and a MAC over it and the session, and the answer derives from the id under the server key, so showing `/login`, `/register` or the image writes nothing to the database; posting an answer records the id in `captcha_spent`, and a second use of it is refused. There is no per-session issuance cap: a page view costs no database write, and at most 8 images render at once (more are refused with 503 and `Retry-After`). The image of a used, unexpired id can still be fetched (it is the same image); only its answer is refused. A challenge shown before the upgrade that introduced this is refused after it: reload for a new one. It is on for new and upgraded installations; administrators can turn it off or on from `/admin`, and each change is audited. The image has no audio or text alternative (it fails WCAG 2.2 criterion 3.3.8 for a person who cannot read it), and there is no second way in (A-517): while it is required and the staff contact is unset or a bare handle (which only an account can message), `/admin` shows a warning, and `/login` and `/register` say there is no way in without the image; with a contact that is not a bare handle they say to write to it and ask for the CAPTCHA to be turned off. `install.sh check` cannot warn, because both settings are only in the database. Tests: `captcha_contact_test.go`.
- **Sessions on `/account`** (A-157): the Sessions panel lists the account's live sessions (count, each one's start time to the minute in UTC; this browser's first, marked "This session", then the newest others, at most 20 listed and all counted, since a correct password spends no sign-in budget). A session row holds nothing about the client, so no IP address, device or browser is shown or kept. "Sign out everywhere" (POST `/revoke-sessions`) ends every session of the account, this one included, and every pending sign-in (so someone parked at `/challenge` after the password step cannot finish), deleting the pending sign-ins first (the `/challenge` lock order), and is audited ("Revoked all sessions: ended N session(s) and M pending sign-in(s)"). The panel says that this does not stop someone who knows the password, who can sign in again (with the second factor too, if one is on); only a password change stops them. There is no per-session sign-out: "Sign out" ends this browser's session only; its POST form is the first control in the /account content and keeps its CSRF token (A-129, `TestAccountSignOutIsNearTopAndKeepsItsCSRF`). A password-checked sign-in racing an administrator's suspension cannot leave a usable session (`TestSuspendDuringSignInLeavesNoSession`, A-108).
- **Password change** (`/account`, POST `/account/password`): needs the current password and, when TOTP is enrolled, a current authenticator code or an unused recovery code (spent). The new password follows the registration rule (12–72 bytes) and must be typed twice and differ from the current one; it is hashed with bcrypt at the application's cost before the transaction. The same transaction ends every other session and pending sign-in of the account and rotates the current session token, and is audited ("Changed password; ended N other session(s) …", with how it was confirmed). A sign-in whose password was checked before the change committed but that starts its session or reaches `/challenge` only afterwards is refused too ("Sign-in verification expired. Sign in again."): its pending sign-in, or the password-only sign-in itself, carries the password hash it was checked against, and the session starts only while the account still has that hash (A-157; the operator's `-reset-admin-password` gets the same effect). Wrong passwords and codes spend the per-account budget of 10 failed confirmations per ten minutes; a correct confirmation spends nothing (A-274).
- **Security notifications and sign-in records** (A-152): in the same transaction as the change, the owner gets one plain-text notification and one audit row for TOTP turned on or off, recovery codes replaced, a sign-in with a recovery code ("N remaining"; "TOTP turned off at sign-in with a recovery code (N remaining)" when it also turned TOTP off, A-154), the PGP key added, changed, renewed (A-155) or removed, key ownership proved and PGP sign-in turned on or off. After a correct password, the first failed second-factor check of a pending sign-in (a wrong, used or missing code, or a PGP code not yet requested) writes "Correct password but failed second sign-in step (TOTP | recovery code | PGP code)" and notifies the owner; later failures of the same pending sign-in add nothing, and the pending sign-in stays usable. The texts carry no code, secret, fingerprint, address or link and end "If this was not you, someone else may know your password: change it and contact the market staff." New "Signed in" rows name the method ("Signed in with password", "Signed in with password and TOTP", "… and recovery code", "… and PGP code"); rows written before this keep the plain "Signed in" and are not rewritten, so earlier signed exports stay byte-identical. The owner reading a notification does not stop someone who has the password: only changing it does.
- **Administrator second-factor reset** (`/admin`, POST `/admin/reset-factors`): for a user who lost their authenticator and recovery codes or their PGP private key. The administrator confirms with their own password (and authenticator code when enrolled; recovery codes are not accepted here). It turns TOTP off (clearing the secret, pending secret, step counter, recovery codes and any undisplayed codes) and PGP sign-in off, keeping the saved PGP key and its verification; ends the user's sessions and pending sign-ins; writes an audit row on both accounts naming the other side and what was turned off; and notifies the user, who then signs in with the password only. The form takes the account's handle (exact, case-sensitive), looked up on the server, so any account can be reset however many accounts exist; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle kept, before the password is checked. It is refused for the administrator's own account, for other administrators (403) and for accounts with no second factor (409). Beside the form, a collapsed list shows up to 100 non-administrator accounts that have a factor, by handle, and says it is capped.
- **Administrator second factors are reset only from the host** (A-137): `docker compose run --rm app -reset-admin-factors HANDLE` (`market.ResetAdminFactors`; no stdin, no web server), for an administrator with no recovery code left or whose TOTP secret became unreadable after a key rotation. Under advisory lock 782493, in one transaction taking the sign-in's lock order (pending sign-ins, recovery codes, account row), it does to the administrator what the web reset does to other accounts: TOTP off (secret, pending secret, step counter, recovery codes and any undisplayed codes) and PGP sign-in off, keeping the PGP key and its verification; sessions and pending sign-ins ended; the audit row "Second factors reset by host command: … turned off; ended N session(s) and any pending sign-ins"; and a notification. It refuses a non-administrator (pointing to the web reset), an unknown handle, an administrator with no second factor and a database recording migrations the binary does not include.
- **Account suspension** (`/admin`, POST `/admin/suspend`, *Suspend or restore an account*): contains a compromised or abusive non-administrator account. The administrator enters the handle (exact, case-sensitive, looked up on the server; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle and choice kept, before the password is checked), chooses suspend or restore and confirms with their own password (and authenticator code when enrolled). Suspending sets `users.suspended_at` (migration 011) and, in the same transaction, ends every session and pending sign-in of the account, writes an audit row on both accounts naming the other side ("Suspended account H; ended N session(s) and any pending sign-ins", "Account suspended by administrator A; …") and notifies the account. A suspended account cannot sign in: the password step answers "This account is suspended. Contact the market staff: <staff contact>." ("This account is suspended. Ask the operator of this market." while no staff contact is set, A-119) (403) only after the correct password, so a wrong password gets the usual "Invalid handle or password"; a sign-in challenge (TOTP or PGP) that was already pending is refused the same way when it would create the session; and a session row that still exists never authenticates. The prior pooled build also held the account's unsent payouts; no payout rows exist now (migration 108), so suspension and restore touch only the account, its sessions and its notices. Restoring audits both accounts and notifies the account, which can sign in again. Role, listings and existing orders are not touched: a suspended vendor's listings show “Unavailable” and refuse new drafts and payment requests, including Bitcoin and Monero escrow checkout, until restored; a buyer can cancel an unfunded draft, and existing awaiting-payment or paid orders continue through their normal actions. New intake uses non-waiting buyer and vendor account locks so a concurrent suspension, role change or confirmed administrator action returns the retryable “The market is busy” (503) response before any wallet request, stock hold or escrow slot claim; retry after the action finishes. A vendor cannot act while suspended, but the other party can still complete, cancel where allowed, or open a dispute. To take away a vendor's listings, change the role instead. Suspended moderators and administrators are not resolvers or contacts: they are left out of the dispute and payment-review notifications, of the independent-resolver check (see *Disputes*) and of the order page's "Contact dispute staff" list, and count again once restored. Refused for the administrator's own account and for other administrators (403); suspending a suspended account or restoring one that is not suspended is answered 409 without change. A list under the form shows up to 100 suspended accounts, most recently suspended first, with the time.
- **Staff contact** (A-119; `/admin` *Staff contact*, POST `/admin/staff-contact`, settings key `staff_contact`, no migration): one administrator setting, free text (a handle, onion address or XMPP address) of at most 200 characters on one line (surrounding space trimmed; a line break, control or text-direction character, invalid UTF-8 or 201 characters → 400; saving the value in force → 409; empty clears it). It needs the administrator's own password (and authenticator code when enrolled; missing password → 400, wrong → 401) and is audited old→new ("Staff contact changed from (not set) to “…” (confirmed with password)"). It is shown as escaped text, never as a link, on `/canary` (*Staff contact*), in the suspended-account sign-in refusal, as the lost-factors line on `/challenge` ("Lost your authenticator and recovery codes? Only a market administrator can turn your second factors off, or, for an administrator account, the operator on the server."; "Lost your PGP key?" for a PGP-only account; `/challenge` does not know the role before sign-in, so it names both the web reset and the operator's `-reset-admin-factors`, A-289), as "Can’t read the image?" help beside the CAPTCHA on `/login` and `/register`, in the "Selling needs an administrator to give your account the vendor role." line on `/register` (and `/account` for a buyer), in the expired-key refusal on `/challenge/pgp` (A-155) and the unreadable-key refusal on `/login` (A-272), and under every notification that tells its reader to contact the market staff (the sign-in and security notices among them): "Contact the market staff: <contact>." Unset, each says "Ask the operator of this market." When the contact is exactly the handle of a moderator or administrator who is not suspended and whose key can receive encrypted messages (the A-83 check), a signed-in reader other than that person also gets a *Send <handle> an encrypted message* link to `/messages?to=<handle>`; signed-out readers (and the refusal pages) get the text only, since they could not use it. Tests: `staff_contact_test.go`, `tests/e2e/db-staff-contact.spec.ts`, `preview-auth.spec.ts`, `preview-transparency.spec.ts`.
- **Role changes** (`/admin`, *Assign an account role*) take the account's handle (exact, case-sensitive), looked up on the server, so any buyer, vendor or moderator can be changed however many accounts were created after it; an unknown handle, or an administrator's, is answered 404 with the admin page again, the reason in an alert and the handle and role kept. Role changes are recorded on both accounts: the administrator's row names the account and old and new role, and the target account's row identifies the acting administrator by handle. The account gets the audit row "Role changed from OLD to NEW by host command"; leaving vendor archives the listings and leaving staff removes the staff avatar, as on the web form; removing an administrator ends its pending sign-ins and sessions (taken in the suspension's lock order). A compromised administrator is contained by demoting it this way and then suspending it on the web ([operator guide](operator-guide.md#administrators)). Changes that run through `confirmedTx` (every password-confirmed administrator action, PGP, TOTP enrollment, recovery-code and password changes, and the profile save) re-read the signed-in account's role and suspension from the account row they lock, so one authenticated just before a demotion or suspension is refused with 403 and changes nothing (`TestConfirmedActionRefusedAfterCallerDemotedOrSuspended`). The current site-name save also uses the locked actor recheck without a password confirmation. Turning TOTP off still uses its separate transaction; receipt work for recovery-factor flows remains outstanding.
- Not provided: QR codes for enrollment (the secret and `otpauth://` URI are shown as text), an audio or other non-visual CAPTCHA alternative, WebAuthn/security keys, administrator-forced TOTP, and any password reset for a forgotten password (no email; administrators cannot reset passwords). Administrator lockout is recovered only by the operator on the host: a lost administrator password with `docker compose run --rm app -reset-admin-password <handle>`, lost administrator second factors with `docker compose run --rm app -reset-admin-factors <handle>` ([operator guide](operator-guide.md#authentication)). A CAPTCHA only slows automated sign-ups; it does not stop a determined attacker or a solving service.

### P2 PGP identity

- Profile keys are parsed with OpenPGP (`internal/market/pgp.go`); garbage, private keys, revoked keys and multi-key blocks are rejected, and so is a key in which a revoked user ID carrying only its revocation sits next to a revoked user ID that keeps its self-signature, a structure on which the OpenPGP library (go-crypto v1.4.1) dereferences nil (A-266; a minimal export with revoked user IDs, which carry only their revocations, is accepted). Such a key already stored is treated as unreadable everywhere ("No usable key" to others); the expiry sweep skips an unreadable key, or one on which the library panics, with the fixed log line "pgp expiry sweep: skipped one key that could not be read" and carries on, and a proof signature that makes the library panic is answered as not verifying (`TestKeyWithUnreadableUserIDsRefused`, `TestKeyExpirySweepSkipsUnreadableStoredKey`, `TestUnreadableStoredKeyPagesRender`, `TestProofSignedBySubkeyOfKeyWithoutUserIDSelfSignatureRefused`). A saved key that cannot be read never lets PGP sign-in fall back to the password alone (A-272): while PGP sign-in is on and the key cannot be read (or no longer matches its ownership proof), a correct password on `/login` either leads to `/challenge` asking for the authenticator code or a recovery code (TOTP enrolled; the PGP method is not offered) or is refused with 409 and no session or pending sign-in: "PGP sign-in is on for this account, but your saved PGP key can no longer be read …", that PGP sign-in is the account's only method, that an administrator can turn it off with *Reset a user's second factors* (for an administrator, whom that web reset refuses, only the operator's `-reset-admin-factors` is named), what to do after that, and the staff contact (A-119). A wrong password still gets "Invalid handle or password". After a correct password the owner is notified once per saved key (plain text: no key, fingerprint or code; not again until the key is changed; concurrent sign-ins send one, as the account row is locked first) that PGP sign-in could not be used (`TestUnreadableKeyRefusesPasswordOnlySignIn`, `TestUnreadableKeyWithTOTPSignsInWithAuthenticator`, `TestUnreadableKeyNoticeOncePerSavedKey`, `TestUnreadableKeyNoticeConcurrentCallsSendOne`). The key is stored as a canonical re-armor of its decoded packets: the packets (user IDs, signatures, subkeys) are unchanged, but text before or after the block, armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped. Keys saved before this are shown in the same canonical form wherever they are displayed (no rewrite migration; a stored key that no longer parses is handled as before), and saving the profile again stores the canonical form. Re-saving the same key, as pasted or as the canonical text the form shows, is not a key change: ownership proof and PGP sign-in stay and no confirmation is asked. The account page shows the fingerprint and the key's user IDs and, above the key field, who can see the key. Re-armoring does not remove user IDs, the creation time or third-party signatures from the key; the note tells users to use a key made only for this market. Only public key, public subkey, user ID and signature packets are accepted and published (A-110). A key carrying a photo ID (an OpenPGP user attribute packet, usually an image of the owner's face) is refused on `/account` before any password check, with the `gpg --edit-key <fingerprint>`, `uid <n>`, `deluid`, `save` steps to remove it; a key with any other packet type (a compressed packet or a private/experimental one can carry a photo ID that GnuPG still imports; keyring trust packets) is refused with a `gpg --armor --export <fingerprint>` hint. Nothing is saved. A key stored with such packets before this refusal is never shown with them: its canonical form keeps only the allowed packets, dropping the signatures that follow a removed packet except direct-key signatures and key revocations (every other packet unchanged, same fingerprint), and the owner saving the account form stores that form. If that form is not exactly one key with the same fingerprint (a skipped packet sat between a user ID or subkey and its signature), the stored key is treated as unreadable: others see "No usable key", never the broken key or its ownership proof. There is no rewrite migration.
- Ownership is marked **Verified** (with UTC date) only after the user signs a server nonce (clearsigned or armored detached signature) or decrypts a nonce the server encrypted to the key, on `/pgp`. Decrypt challenges store only the nonce's SHA-256. Changing or removing the key clears verification, PGP sign-in and any open challenge (renewing the same key may keep them, see *Renewing the same key*); every change is audited with the fingerprint. Adding, changing or removing the key and turning PGP sign-in on or off need the current password on every account (A-152), plus a current authenticator code when TOTP is enrolled (recovery codes are not accepted here), as turning TOTP off does: a stolen session can neither add a factor that outlives "Sign out everywhere" nor swap in the key buyers encrypt shipping addresses to. The audit row notes how the change was confirmed. Saving the profile with the stored key unchanged does not re-parse it, so an older key the parser now rejects does not block the form, unless it holds a photo ID or a packet outside the A-110 allowlist: that key is refused until the owner pastes an export without them or removes it with their password.
- Optional PGP sign-in verification (second factor), available only for a verified key that can receive encrypted messages. After the password, the user requests a one-time code (POST `/challenge/pgp`), decrypts it locally and submits it on `/challenge`; only its SHA-256 is stored and it is deleted with the pending sign-in.
- PGP sign-in code hashes are bound to the current key fingerprint and exact ownership proof. Replacing/re-verifying a key invalidates older codes, even if the original key is later restored. Sensitive password-confirmed changes serialize with TOTP enrollment.
- `/messages` rejects anything that is not an OpenPGP-encrypted message (plaintext, signed-only, malformed or fake armor). The pasted text must be exactly one armored PGP MESSAGE block with only whitespace around it; the whole base64 body is decoded and must be session key packets followed by exactly one integrity-protected encrypted-data packet that runs to the end, so text before, inside or after the block is refused. The server stores a canonical re-armor of those packets: armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped, never stored or shown. Each message shows "Encrypted (to recipient’s key)", "Encrypted (NOT to recipient’s key)" or "Encrypted (recipient unknown)", derived from the recipient key IDs in its packets compared with the recipient's saved key at send time. Migration 103 preserves a nullable send-time count of distinct visible additional key IDs; a badge warns about other visible keys even alongside hidden-recipient packets. Hidden recipients may also exist, and packet IDs do not prove decryptability. Labeled readonly textareas support keyboard copying of messages, deliveries and PGP challenges while preserving leading newlines and escaping markup. Messages stored before this check are inspected when displayed; their recipient match is reported as unknown. Messages stored as encrypted before the strict armor check are re-inspected when displayed and shown as not encrypted if they fail it; those that pass, and older messages found encrypted, are displayed as the canonical re-armor, so a stored armor header is never shown.
- **Message and recipient-lookup budgets** (A-516, in memory per app process, cleared by a restart): an account sends at most 20 messages in 10 minutes, apart from its budget of 100 changes; an attempt counts once its armor passes the format check, before the recipient lookup and packet inspection, so an unknown recipient or a refused packet counts too, and the 21st is refused with 429 "Message not sent: an account can send at most 20 messages in 10 minutes" and writes nothing (no message, notification or audit row; `TestMessageBudgetSeparateFromWrites`). `/messages?to=<handle>` looks up at most 60 different handles per account in 10 minutes (A-92); looking up a handle again in that window costs nothing. Past it the page shows neither the key nor "No other account found", only that lookups are paused, so it no longer tells whether a handle exists (`TestMessageRecipientLookupBudget`).
- Limits: the server cannot decrypt messages, so a key-ID match does not prove the contents (the bytes inside a well-formed encrypted-data packet are opaque to it); hidden-recipient and passphrase-only messages are "recipient unknown". Losing or letting the key expire locks PGP sign-in unless another factor is enrolled; an administrator can then turn PGP sign-in off for a non-administrator account (see P1 second-factor reset). When no code can be encrypted to the key, `/challenge/pgp` answers 409 saying so and naming what is left: the authenticator or a recovery code when TOTP is on, otherwise that PGP sign-in is the account's only method and an administrator can turn it off with *Reset a user's second factors* (for an administrator, only the operator's `-reset-admin-factors`), after which the owner renews the key (A-155).
- **Key expiry** (A-155): `/account` and `/pgp` show when the primary key and the encryption subkey expire (UTC date, "Never", or "Expired …"; for a key nothing can be encrypted to any more, the subkey that expired last). When encryption to the key stops within 30 days they say so with the renewal commands (`gpg --quick-set-expire <fingerprint> 2y`, and `… 2y '*'` for the subkeys); when nothing can be encrypted to the key now (`canReceiveEncrypted`) they say "Buyers cannot encrypt to this key" (A-225). Every running process checks all saved keys at startup and then once a day and notifies the owner once when encryption to the key stops within 30 days and once when it has stopped (the key or its encryption subkey expired), with the renewal commands and no fingerprint; `users.pgp_expiry_notice` records the notice per key and expiry, so each is sent once, also when sweeps overlap (a compare-and-set on that column), and a renewed or replaced key is warned about again (`TestKeyExpiryNotifiedOnce`, `TestConcurrentKeyExpirySweepsNotifyOnce`). A key that is signing only, revoked or unreadable gets no expiry notice. PGP sign-in can still be turned on for a key close to expiry; the dates and the notices are the warning.
- **Renewing the same key** (A-155): a pasted key with the saved key's fingerprint but different packets (a new expiry from `gpg --quick-set-expire`, a new user ID or subkey, a third-party certification) needs the password like any key change. It keeps the ownership proof and PGP sign-in, with the notice "Key updated: the same key (same fingerprint) with new signatures…", one owner notification and an audit row "Updated PGP key (same fingerprint …; ownership proof and PGP sign-in kept)", when every revocation signature (key, subkey or user ID) in the saved key is still in it and still revokes the same key, subkey or user ID as OpenPGP software reads the pasted key (A-261: a subkey or user ID revocation moved before the first user ID, where readers ignore it, or a revoked subkey or user ID left out, or an unrevoked copy of a revoked subkey added beside it, counts as a dropped revocation) and the encryption subkey it selects is the saved key's or one created no earlier (not a rollback to an older subkey). Otherwise it is saved as a changed key: proof, PGP sign-in and any open challenge are cleared, the change time is recorded, the owner is notified and `/account` shows an alert naming the missing revocation or the older subkey, never the plain "Profile saved." notice (`TestKeyExpiryShownAndRenewalKeepsSignIn`, `TestKeyUpdateThatDropsRevocationOrRollsBackSubkeyClearsProof`).
- Vendor pages and order pages show the other party's armored public key, grouped fingerprint and "Ownership verified YYYY-MM-DD" (UTC date only; the owner's `/account` and `/pgp` show the minute) only when a proof matches the saved key (otherwise "Ownership not verified"); a user without a usable key is named with a note that messages cannot be sent until they add one. A key is usable only if something can be encrypted to it now (A-68, one check, `canReceiveEncrypted` in `pgp.go`): not expired or revoked, with an encryption-capable subkey (or primary key) that is neither expired nor revoked. A saved key that has expired, is signing-only, or whose encryption subkey expired or was revoked is shown wherever a contact key is offered (vendor page, `/messages?to=`, order page, dispute staff contacts) as "No usable key", without its fingerprint or armored text; this is checked each time the page is shown, so a key that expires later stops being offered (`TestHuntUnusableEncryptionKeyShownAsUsableContact`). The owner's `/account` and `/pgp` pages say "Buyers cannot encrypt to this key"; on a paid physical order the vendor also sees a warning to update the key on `/account` (A-225, `TestPaidOrderVendorKeyStopsBeingUsable`). On a paid physical order, the buyer's view of the vendor's key says "This key was changed or re-verified on YYYY-MM-DD UTC, after this order was placed — confirm with the vendor before sending your address" when the key was added, replaced or updated without keeping its proof (`users.pgp_changed_at`, migration 067) or its ownership was proved again (`pgp_verified_at`) after the order was created; a key last changed and proved before the order shows nothing, nor does the vendor's view (A-158, `TestVendorKeyChangedAfterOrderWarnsBuyer`). Keys changed before migration 067 have no recorded change time, so only a later proof or change is warned about; a renewal that keeps the proof (A-155) is not a change. Vendor pages are public, so a vendor's key is shown to anonymous visitors. Contact and message links open `/messages?to=<handle>` with the recipient filled in (values not matching the handle pattern are ignored); that page shows the key, fingerprint and verification of any existing handle to any signed-in account, whether or not they trade.

### P3 Orders

Implemented on the Foundation state machine; every action goes through the server-side transition table, row lock and compare-and-set, so a forbidden move returns 403, a stale or repeated one 409, and nothing reports success without a recorded state change.

- **A-15 confirmation wait:** an awaiting-payment order with a deposit below its required threshold has a fixed cancellation cutoff: the later of the original issue time plus `PAYMENT_EXPIRY` and the first eligible deposit recorded by the wallet plus the longer of 14 days and `PAYMENT_EXPIRY`. Historical first-seen rows, including dropped/conflicted rows, anchor the wait so small top-ups cannot extend it indefinitely. Bitcoin and Monero escrow use the rule, applied only after a successful synced node or wallet read. Cancellation returns stock and never credits or sends an unconfirmed deposit; a later confirmation follows the escrow refund or stray-refund path. The order page shows this wait separately from the ordinary unpaid/confirmed-underpaid payment window.
- **Payment request** (buyer, draft → awaiting payment, by escrow checkout: `/orders/escrow` for Bitcoin and `/orders/escrow-xmr` for Monero; `/orders/pay` answers 404 since the pooled removal): refused with 409 unless that coin's escrow is on and its intake is not paused (`TestEscrowIntakeOnlyAllowsEscrowOrPaused`); the order page shows the step as unavailable instead of a button. For a physical order it is also refused (409, before any stock is reserved or the wallet is asked for an address) while the vendor has no key that can receive encrypted messages (none saved, unreadable, expired or signing-only; the A-68 check), since the buyer could not send a shipping address (A-83). The order page then shows "Unavailable. This vendor has no usable encryption key, so you could not send your shipping address. Ask them to add one." instead of the button, and the listing's product and checkout pages say so; a draft can still be saved and paid once the vendor adds a usable key. Digital orders are unaffected. Vendors are not yet stopped from publishing a physical listing without a usable key (A-91) (`TestPhysicalEscrowRefusedWithoutUsableVendorKey`). On success the draft is repriced from the listing's current price, one unit of stock is reserved and the escrow is created with its address (no address is ever invented by the application; the escrow rules and refusals are under P5 and in [per-order escrow](escrow.md)). A buyer may hold at most 3 orders awaiting payment (409 beyond that); the escrow watcher cancels unpaid orders after `PAYMENT_EXPIRY` (see P5).
- **Cancellation** (`/orders/cancel`): buyer cancels a draft; buyer or vendor cancels an order awaiting payment (the system does when the payment window expires); vendor cancels a paid order. Reserved stock is returned. When confirmed deposits exist, the escrow refund is requested for the buyer (see P5). A vendor's cancel of a paid order needs the settlement confirmation below.
- **Shipping** (vendor, physical, paid → shipped) with an optional note; **digital delivery** (vendor, digital, paid → delivered) with 1–32000 characters of content; **completion** (buyer, shipped/delivered → completed; an escrow order's buyer completes it by signing the release or, for Monero, with Confirm receipt, below). The transition table also lists system completions (shipped/delivered → completed) marked escrow-only (`escrowOnly`, A-244): the system completes only an escrow order (403 otherwise, `TestEscrowOnlySystemEdgesRefusedForPooledOrders`). On the development branch with `ESCROW_BTC=on` a physical escrow order is marked shipped with a claim address and the vendor's password (`/escrow/ship`), the buyer's plain Complete is refused on it (`buyerCompleteRefused`, A-373), and the buyer may cancel a paid one the vendor has not shipped within its dispatch window plus 48 hours (paid → cancelled, escrow only; `TestEscrowShipNeedsClaimAddress`, `TestEscrowPooledCompleteRefusedOnEscrow`, `TestEscrowNoShipCancel`). On the development branch with `ESCROW_BTC=on` (test networks only, not released), an escrow order (`Order.Escrow`: it has an `escrows` row) completes on funding: the escrow watcher moves it to paid, automatic delivery to delivered and the system to completed, each through the transition table (`TestEscrowFundingCompletesOrder`; real Core regtest: `TestEscrowRegtestFunding`). On the development branch with `ESCROW_XMR=on` (a local Monero fakechain or stagenet, not released) the same holds for a Monero escrow order: the Monero escrow watcher completes a digital one on funding (`TestXMREscrowFundingThreshold`; real fakechain: `TestXMREscrowRegtestFunding`); the vendor marks a paid physical one shipped with a claim address and their password (`/escrow-xmr/ship`), the buyer's Confirm receipt (`/escrow-xmr/confirm`, password step-up, shipped → completed by the buyer, the one exception to the refusal of the buyer's plain Complete on an escrow order) or the release deadline completes it, and the buyer's no-ship cancel is shared with Bitcoin escrow (`TestXMREscrowShipStepUp`, `TestXMREscrowConfirmReceiptStepUp`, `TestXMREscrowDeadlineWithBTCOff`, `TestXMREscrowNoShipCancel`; real fakechain: `TestXMREscrowRegtestPhysical`).
- **Settlement confirmation** (A-161, A-122, A-508): a vendor's cancel of a paid order, a staff resolution and a party's concession each decide where the escrowed coins go, so their forms state it: the amount counted now (every deposit that counts for the order, confirmed or still confirming; not a locked transfer, a deposit after the order closed or one left out of a settlement), the recipients' handles and the settlement each outcome builds from the escrow. A refund returns everything counted, less the network fee, to the buyer's refund address given at checkout. A release pays the vendor the escrow less the market fee and the network fee; an amount paid above the price goes back in full to the buyer's refund address as its own output of the release, except that one below the minimum output (0.0001 BTC; 0.001 XMR) is added to the vendor's output, and the form says which applies (`planSettlement`, `planXMRSettlement`). A release already built or requested at shipment is named, and a final one is stated as the outcome with the refund refused. No form mentions a saved payout address: none is used. Each form has a required confirmation checkbox (missing: 400, nothing changes) and a hidden `amount_seen`, compared with the amount counted under the order's row locks: a different amount refuses the whole action with 409 "The amount changed to X — review again", so the order does not move and a dispute stays Open. Repeated or concurrent submissions still decide once. Tests: `TestEscrowResolveNeedsConfirmationAndUnchangedAmount`, `TestEscrowCancelNeedsConfirmationAndUnchangedAmount`, `TestEscrowOrderActionMatrix`.
- **Overpayments:** an escrow settles exactly what it was built to pay; coins that no settlement covers (a deposit above the price, one after the order closed, one that did not count) are returned to the buyer's pinned refund address by a stray refund, or stay in the escrow when too small to spend (see P5 and [per-order escrow](escrow.md)). While an escrow order is paid, shipped, delivered or disputed and holds more than the price, its order page states what each outcome does with the excess: a release returns it in full to the buyer's refund address as its own output, or adds it to the vendor's output when it is below the minimum output (0.0001 BTC; 0.001 XMR), and a refund returns everything, less the network fee. Once a dispute's release is final the notice says a refund is no longer possible (A-509; `TestEscrowOrderPageStatesTheBitcoinSettlement`, `TestEscrowOrderPageStatesTheMoneroSettlement`, `TestEscrowOverpaidNoticeWithAFinalReleaseOffersNoRefund`).
- **Automatic delivery**: when the escrow watcher marks a digital order paid and the listing has delivery content, the content is recorded and the order moves to delivered as the system actor in the same transaction.
- Delivery content is stored **unencrypted** in PostgreSQL, is written only in the same transaction as the delivered transition, and is shown only to the order's buyer and vendor, and read-only to moderators and administrators once the order is disputed.
- **Party concessions** (A-166): the buyer may release a disputed order to the vendor; the vendor may refund it to the buyer. The amount statement, required acknowledgment and current password/authenticator confirmation apply. The dispute closes atomically before the order transition; a simultaneous staff resolution has one winner and one conflict. Concession does not return stock. Parties see withdrawn concessions in the closed list and counts, and independent staff retain order access through the dispute record. Closure notices go to currently eligible unsuspended independent staff, with administrator fallback; no durable opening-recipient list exists.

- **Disputes** move a paid, shipped or delivered order to disputed. Opening one notifies every moderator and administrator who is not a party to the order and not suspended (the parties get the usual state-change notice). If every moderator and administrator who is not suspended is a party, the dispute is still accepted: a system note in the order history records that no independent resolver was available, every administrator is notified that it needs a moderator who is not a party, and the moderation desk shows administrators a "No eligible resolver" note on it while that remains true. **Resolution** requires an outcome (release to vendor or refund to buyer) and a written decision, and is refused to a moderator or administrator who is party to the order. It also needs the resolver's current password, and an authenticator code when TOTP is enrolled (A-32; the same `confirmedTx` step-up as the other staff actions, which also re-reads the resolver's role and suspension): resolving decides where the escrowed coins go, so a hijacked session or a mis-click is not enough. Without the password it is refused (400 "Enter your current password to confirm this change."), with a wrong password or code 401, and nothing changes (the order, the dispute, the settlement, order history, audit and notifications); the audit row says how it was confirmed ("Resolved dispute on order … (outcome: refund) (confirmed with password)"). Moderators and administrators who are not parties still resolve disputes (`TestEscrowResolveNeedsConfirmationAndUnchangedAmount`, `TestEscrowOrderActionMatrix`). The outcome is recorded before the resolved transition so the escrow watcher can act on it: a refund outcome has it build the refund of the whole counted amount to the buyer, a release outcome the release to the vendor (see *Overpayments*). The decision is stored unencrypted and read by both parties; its field says so and never to quote an address, real name or tracking number.
- **Dispute reply** (A-124; POST `/disputes/reply`): while a dispute is open, the party who did not open it (the actor of the move to disputed) may put one reply of 20–5000 characters on record from the order page. It is stored once as a disputed → disputed `order_events` row (note "Dispute reply: …"; no state change, the transition table is not involved) and shown under Dispute on the order page to both parties and staff reviewers, and on `/disputes` and the moderation desk, labelled with its author's role; the history entry says only that a reply was made. The reason, reply and decision keep their line breaks (`white-space: pre-wrap`). The opener is refused (403), a second reply, a reply after resolution, on an order with no dispute or on a dispute with no recorded opener are refused (409), and nothing is written; the dispute row is locked first, so concurrent replies store one. The dispute-opened notice to the other party says it may reply. The form carries the same stored-unencrypted warning as the other plaintext fields, and first points to encrypted messages to dispute staff when one of them has a usable key (or says none has). The resolve form says whether the other party replied, and carries what it showed (`reply_seen`): once a reply is on record, `/resolve` refuses a form that did not show it (or does not say) with 409 and the moderation desk again, showing the reply, the reason in its alert ("The vendor replied to this dispute after the form was loaded. …") and the typed decision kept, and nothing changes; the check runs under the dispute row lock the reply takes, so a reply racing the decision is either seen or refused (A-280; `TestDisputeCounterpartyResponse`, `TestResolveRefusesFormLoadedBeforeReply`; browser: `db-disputes.spec.ts`).
- **Evidence holders** (A-162): the resolve form and desk entry of each open dispute list, for staff who are not party to it, the moderators and administrators each party messaged since the dispute opened, with the count and the latest time ("Buyer → mod_a (2, latest …)", "Vendor → none"; a holder suspended since is labelled "mod_a (suspended) (2, latest …)", A-280; one removed from staff after the message, as its role-change audit row records, stays listed as "mod_a (no longer staff) (2, latest …)" counting only the messages sent before the latest such change, A-294, A-304), read from message metadata only; a party's own staff account is never listed as a holder (A-285) (never a body or ciphertext); the resolve help says to ask those holders before deciding, or that neither party messaged a current moderator or administrator, nor one recorded as removed from staff after being messaged. The parties' "Contact dispute staff" panel says other staff can see which staff member they messaged and when, never what (`TestDeskShowsWhoHoldsDisputeEvidence`). The role-change rows are read through the partial index `audit_events_role_change` (migration 072, A-301), not by scanning the audit log (`TestDisputeEvidenceReadsRoleChangesByIndex`).
- **Verified reviews**: one per completed order, by its buyer, rating 1–5 and up to 2000 characters. Product, vendor and order pages label them "Completed order (test network)" on a test market because each is keyed to a completed order; reviewer handles and order ids are not shown publicly and dates are shown by month.
- **Hiding reviews** (A-125; POST `/admin/review`): administrators can hide a review, for example one that exposes a vendor's identity, and restore it. An administrator viewing a product or vendor page gets *Hide this review* under each review (a `<details>` form; no ID is typed), confirmed with their own password (and authenticator code when enrolled). A hidden review is kept (`reviews.hidden_at`, migration 031): it is left out of the public list and of the rating average and count on both pages; the buyer and vendor still see it on the order, labelled "Hidden from the listing and vendor pages by an administrator". Administrators see hidden reviews on the product and vendor pages labelled "Hidden by an administrator", with a count of hidden reviews and a *Restore this review* form, which works the same way. Both actions are audited on the administrator ("Hid review of order <8-character order ID> (confirmed with password)", "Restored review of order …") and on the reviewer ("Review of order … hidden by administrator <handle>"), and the reviewer gets a link-free notification; none of them copies the review text. Hiding a hidden review or restoring a public one is answered 409 without change; an unknown review 404; moderators, vendors and buyers 403 (reviews are content moderation, an administrator power like suspension and listing edits; moderators handle disputes and payment reviews). There is no report-a-review button: someone who wants a review hidden contacts the market staff. Tests: `review_hide_test.go`, `tests/e2e/db-review-hide.spec.ts`.
- Order pages show the full transition history (actor and time), the moves available to the viewer, the dispute reason, the other party's reply and the decision, the other party's PGP key, and the delivery and review panels. Orders, vendor desk and moderator desk list the relevant orders with their state; the moderator desk links each dispute to its order page. Open work is never hidden by a row cap: the moderation desk and the disputes page list every open dispute (oldest first) before the 100 most recent resolved ones, the vendor desk lists every paid order on the vendor's listings (oldest first, counted in "To fulfil") before the 100 most recent other orders, and each page says when older history is not shown. The disputes page offers every paid, shipped or delivered order for a new dispute. The orders page, messages and notifications still show only the 100 most recent rows. There is no admin order list (A-127): staff see an order only while it is disputed or resolved or a payment on it is flagged for review ([What the server keeps](#what-the-server-keeps)).
- Moderators and administrators not party to an order can open its page read-only once its dispute record exists, including after a party concession (summary, history, dispute, delivery record, payment ledger), and while any of its deposits is flagged for payment review (summary, history with the flag notes, payment ledger; digital delivery content stays hidden unless the order is disputed). An escrow order is also readable to them, the same way, while it has an open staff alert (A-470, `escrowStaffAlert`, derived from existing rows): a Bitcoin settlement queued or stuck (A-441) until the watch-only wallet sees it, a Bitcoin release failed too-small (A-461) until it is superseded, or a Monero escrow deposit refused as another order's escrow account (A-480, an open `xmr_escrow_collisions` record, migration 090) until a non-party moderator or administrator records what was done about it in the order page's staff-only *Refused Monero deposits* form (POST `/moderator/xmr-collision`: 10–500 characters, password and TOTP confirmation, audit row, 409 on a repeat; `TestXMREscrowCollisionStaffAlert`, `TestXMREscrowCollisionConcurrentDisposition`, `TestXMREscrowCollisionRecordedOnce`, DB integration with the fake wallet-rpc; `db-xmr-collision.spec.ts`, browser DB with the record seeded in SQL); when the alert clears the page is 404 to them again unless another rule admits them. The moderation desk lists these orders under *Escrow alerts* (same rule, linked, no action on the desk; the 100 newest by when each order's open alert opened, QA5W2-3, with a count of how many more orders it leaves out, QA5W1-2) and, when only the alert admits staff, the order page names the open alert and links that list instead of Payment review (QA5W1-1) and `/admin`'s queued-or-stuck line links the order (`TestEscrowStallAlertStaffRead`, `TestEscrowReleaseTooFewStaffAlertRead`, DB integration). No buyer or vendor action renders for them and the order actions return 404. Any other order stays 404.
- **No shipping address field.** For a paid physical order the buyer is prompted to send the address as a message encrypted to the vendor's key; the vendor is told to check Messages. If the vendor's key stopped being usable after payment (expired or removed), the buyer sees "No usable key" in place of that prompt, with a warning never to send the address unencrypted: message the vendor or open a dispute (`TestPaidOrderVendorKeyStopsBeingUsable`). The market keeps that encrypted message (and who sent it to whom and when) but cannot read it. It cannot stop an address being typed into a plaintext field: the vendor's note to the buyer, the cancellation reason, the dispute reason, the dispute reply and the review text are stored unencrypted. Each of those fields says so, who can read it (the other party; moderators and administrators when the order is disputed or a payment on it is flagged, or every moderator and administrator for a dispute reason or reply; the public, and the vendor with the buyer's handle, for a review; the operator and backups), and never to include an address, real name or tracking number but to send them encrypted from the order page. The help is tied to its field with `aria-describedby`.

Limits: service listings have no ship/deliver step, so a paid service order can only be cancelled by the vendor or disputed. There are no auto-completion timers. Moderators cannot see the parties' messages, which are encrypted to the recipient's key (a resolver sees only whom each party messaged since the dispute opened, and when); parties must describe evidence in the dispute reason or the other party's one reply, which are stored unencrypted and read by the other party, or send it (and anything identifying, such as an address) as an encrypted message to an independent moderator or administrator from the order page's "Contact dispute staff" keys, which both dispute forms point to (suspended staff are not listed).

### P4 Inventory

- Vendors edit their own listings at `/listing-edit?id=` (title, description, category, region, fulfillment type, stock, BTC/XMR reference prices, optional automatic delivery content). Administrators may edit any listing except its automatic delivery content: an administrator editing another vendor's listing sees only whether content is set ("only the vendor can view or change it"), their saves keep the stored content whatever the form sends, and changing such a listing to physical is refused (400) while content is stored. The audit log records "as administrator". When an administrator's save changes another vendor's listing, the same transaction notifies the vendor (link-free, naming the listing and the changed fields: title, description, category, region, fulfillment type, Bitcoin price, Monero price, stock, dispatch window) and records "Listing <8-char id> edited by administrator <handle>: changed …" in the vendor's audit trail; a save that changes nothing, and a vendor's edit of their own listing, write neither (A-516, `TestAdminListingEditNotifiesVendor`). Other vendors get 404.
- Create and edit share one validator. Only `physical` and `digital` fulfillment are accepted: the order state machine has no fulfillment step for a `service` kind, so the form no longer offers it. The Bitcoin price must be at least 0.0001 BTC (10,000 satoshi) and the Monero price at least 0.001 XMR (since A-232), the floors below which a settlement could not be sent (see *Listing price floors* under P5), otherwise 400 with the reason; the forms say so. Listings priced lower before this rule keep their price until edited; an edit must raise it. Until then they take no new orders in that currency (A-216, A-232): a draft, or a payment request on a draft saved earlier, is refused with 400 naming the minimum before any stock is reserved or the escrow node is asked for an address (after the paused-intake and escrow-off reasons); orders in the other currency on the same listing are unaffected (`TestLegacySubFloorListingRefusesBTCOrder`).
- **Legacy service listings (A-20):** product, checkout and listing-edit pages identify the actual product kind; a legacy `service` listing cannot be ordered or funded, and editing requires an explicit supported fulfillment kind instead of silently converting it. Backend refusals remain in force (`TestLegacyServiceListingRequiresExplicitSupportedKind`, `TestLegacyServiceCannotBeOrdered`).
- Archive/restore (`/listings/archive`, `/listings/restore`): archived listings disappear from the catalog, search, checkout and vendor pages, and new order drafts are refused (400). The owner still sees them on the vendor desk with an "Archived" badge. Existing orders are not changed. The product page of an archived (or taken-down) listing answers 404 except to whoever may read an order placed on it, by the order page's rule: its buyer and vendor, and moderators and administrators while that order is disputed or resolved or has a dispute record from a party concession or has a flagged payment (A-164). They see the listing as it is now with an "Archived" badge, no order-draft link and no delivery content (never the takedown reason); its photos are shown there on the signed-in `/desk/img` route under the same rule, while the public image route still refuses them (A-264). The order page links to the listing ("Listing as it is now; it may have changed since purchase"), as do the moderation desk's dispute entries and payment-review rows, the `/disputes` entries and the vendor desk's incoming-order rows, for whoever may open the order (A-265, `TestDeskOrderRowsLinkTheirListing`); no snapshot of the listing at payment is kept yet (A-58).
- **Listing takedown** (A-163; POST `/admin/listing`): an administrator archives another vendor's listing only by taking it down from its edit page (*Take down listing*, a `<details>` form), with a reason of 10–500 characters (after trimming, with no NUL byte; otherwise 400) and their own password (and authenticator code when enrolled). The plain archive answers an administrator 400 on another vendor's listing; an administrator's own listing is archived from the vendor desk as usual. The reason is stored unencrypted in `products.admin_archive_reason` (migration 041; non-NULL only while archived) and shown to the vendor on `/listing-edit` and on the vendor desk card ("Taken down"), never on public pages. Both accounts are audited with the reason ("Took down listing <8-character ID> of <vendor>: …", "Listing … taken down by administrator <handle>: …") and the vendor gets one link-free notification with the listing's title, the reason and what it means. The vendor can still edit the listing, but their restore is answered 409 quoting the reason and telling them to ask an administrator to review it, with the staff contact (A-119, A-279), as the vendor desk card and the edit page do; the takedown notification shows it under it on `/notifications`; an administrator's plain restore is 409 as well. Only the administrator's *Restore listing* form, confirmed the same way, clears the reason; like every restore it is refused (409) when the owner is no longer a vendor, and it share-locks the owner's account row so a concurrent role change is not missed (A-70). Archiving by a role change never sets a reason. While a listing is taken down, a payment confirmed on one of its digital orders leaves the order paid instead of releasing the automatic delivery content, with the history note "Not delivered automatically: an administrator took this listing down…"; the vendor delivers by hand or cancels and refunds. Other roles get 403. Tests: `listing_takedown_test.go`, `tests/e2e/db-listing-takedown.spec.ts`.
- Changing a vendor's role to buyer or moderator archives their active listings in the same transaction (audited for the administrator and the account). Listings whose owner is not a vendor or administrator refuse new drafts (400), payment requests (409) and restores (409); existing orders continue and the former vendor can still fulfil them.
- The fulfillment type cannot change while the listing has open orders (409), because orders read it from the listing. A draft takes the current price when it is resubmitted and again when payment is requested; from then on the order keeps that price.
- Stock edits are refused (409) when stock changed after the form was opened (payment requests reserve stock); saving other fields keeps the current stock.
- Automatic delivery content is digital-only, at most 32000 characters, **stored unencrypted in PostgreSQL**, and never loaded on public pages. It is released only by the order package's confirmed-payment step, so the editor says "Automatic delivery requires a payment provider" whenever no provider is configured.
- Migration `040_inventory.sql` adds `products.updated` and `products.archived_at`; `041_listing_takedown.sql` adds `products.admin_archive_reason`.
- **Interrupted listing uploads (A-207):** after a valid listing ID is parsed, an upload refusal while the multipart body is still being read links back to that listing; invalid IDs and photo-first forms retain the vendor-desk fallback. The no-JavaScript oversized-photo regression covers the listing backlink.

### P5 Payments

Implemented: **per-order escrow only, off by default, test networks only.** Bitcoin escrow (`ESCROW_BTC=on`) runs on regtest, signet or testnet4 and Monero escrow (`ESCROW_XMR=on`) on a local fakechain or stagenet. Bitcoin mainnet and testnet3 are refused at startup, and so are Monero mainnet and testnet daemons, until a mainnet release is built (A-460); there is no mainnet opt-in. The pooled custodial wallet is removed (A-448, A-492): no deposit address is issued from a market wallet, no pooled deposit is polled and no payout is sent. Owner directive (2026-10-11): pooled mode is neither tested nor drained. See [feature configuration](operator-guide.md#feature-configuration), [per-order escrow](escrow.md) and, for what existed before, [Prior build (pooled wallet, removed)](#prior-build-pooled-wallet-removed-2026-10-11).

- **Configuration and refusals.** The escrow adapters read only the `ESCROW_*` settings: a Bitcoin Core node holding the arbiter and watch-only wallets, and a `monero-wallet-rpc` holding only escrow wallets beside a fakechain or stagenet daemon. A non-blank `BITCOIN_RPC_URL`, `BITCOIN_WALLET`, `MONERO_WALLET_RPC_URL` or `MONERO_RPC_URL` stops startup before the database opens, with an error naming the variables and never their values, because they configured the removed pooled providers (`refuseObsoletePooledEnv`; `TestObsoletePooledEnvironmentIsRefusedWithoutEchoingValues`, `TestNewRefusesObsoletePooledEnvironmentBeforeDatabaseAndRPC`, `TestSharedEscrowEnvironmentIsAccepted`). `BITCOIN_CHAIN=main` or `MONERO_NETWORK=mainnet` with escrow on stops startup as well, as does an escrow node that reports mainnet or testnet3. The shared `PAYMENT_CONFIRMATIONS_*`, `PAYMENT_EXPIRY`, `PAYMENT_POLL_INTERVAL`, `BITCOIN_MAX_TIP_AGE` and `MONERO_MAX_TIP_AGE` settings still apply to escrow.
- **Payment intake.** Administrators set new BTC and XMR payments independently to *escrow only* (labelled *Escrow* on `/admin`; the stored value is `escrow`) or *paused* (`/admin/payment-intake`, password and TOTP confirmation when enrolled, audited; `TestEscrowIntakeOnlyAllowsEscrowOrPaused`, `TestPaymentIntakeConfirmedReceiptAndLostAcknowledgement`). Migration 107 turned a legacy enabled setting into escrow only and left pauses paused. Paused refuses new escrow checkouts with 409 and does not stop monitoring, refunds or settlements already under way. A readiness panel on `/admin` counts and lists the active listings that cannot use escrow and the vendors with no active Bitcoin escrow key, and a listing in that state shows "not available for purchase" with the reason and no buy form in that coin (`escrow_readiness.go`). An older build reads `escrow` as paused (UPGRADING.md section 37).
- **Node and daemon sync guard** (A-439, A-449; details in the paragraphs below): the Bitcoin escrow watcher skips its pass while its node is syncing or not synced (headers ahead of blocks, or on a public chain no peers or a tip older than `BITCOIN_MAX_TIP_AGE`, default 2h, regtest exempt from the last two) and the Monero escrow watcher while its daemon is not synchronized or, on stagenet, has no peers or a top block older than `MONERO_MAX_TIP_AGE` (default 1h, fakechain exempt). Nothing is read, recorded, expired or announced until it catches up and `/admin` names the reason (`TestEscrowWatcherSkipsWhileNotSynced`, `TestXMREscrowSkipsWhileNotSynced`, `TestXMREscrowFakechainExemptFromPeerAndTipChecks`; fake node and daemon).
- **Listing price floors.** The Bitcoin price must be at least 0.0001 BTC (10,000 satoshi) and the Monero price at least 0.001 XMR (since A-232), below which a settlement could not pay its network fee and a minimum output (the escrow settlement minimum); a listing priced lower earlier keeps its price until edited and takes no new drafts or escrow checkouts in that currency (400 naming the minimum) (`TestListingRefusesBTCPriceBelowPayoutFloor`, `TestEscrowCheckoutPriceFloor`, `TestLegacySubFloorListingRefusesBTCOrder`).

- **Locked Monero transfers** (non-zero `unlock_time`) are recorded and shown as "Locked transfer — not counted", never counted toward payment and never paid out; the order history and moderators get one "locked transfer ignored" note and the buyer one notification (migration 051 adds `payments.locked`; the Monero escrow watcher records them).
- **Payment-review flags**: a deposit flagged to moderators is marked `payments.flagged`, a system note ending "Moderator review required." is added to the order history, and every moderator and administrator who is not suspended is notified ("Payment review needed for order" plus the first 8 characters of the order ID; for a credited deposit regression, staff who are party to the order get the buyer/vendor notification instead). The moderation desk lists flagged deposits under *Payment review*: every open flag first, oldest first and never cut, then the 100 most recently flagged others, with the count of others and a notice when older ones are cut. A flag is open while it has nothing that settles it and no recorded review: a locked transfer, a deposit received after settlement or after the order closed, or a credited deposit in an announced regression that has not confirmed again, or an escrow deposit spent outside the market or left out of its settlement, credited or not (an escrow deposit that counts for the order, credited or not, is never open); the desk and the review handler read this one rule, and the late-deposit notice episode is held only by a flag it opens (`paymentFlagOpenRule`, QA462C; `TestPaymentReviewEscrowMatrix`); one escalated to an administrator stays open, a reviewed one (no action or refunded by hand) is not listed. Each row shows the full order ID linking to the order, amount and currency, full transaction ID and output, flag time (the latest flag note for the deposit; "Not recorded" if none matches) and a reason from the deposit's current confirmations: "Credited deposit conflicted or missing", "Credited deposit below threshold (N of T confirmations)", "Credited deposit confirmed again (N confirmations)", "Locked transfer (unlock time), not counted or paid out", "Below the escrow minimum output, not paid as its own output" or "Deposit after settlement or after the order closed, not paid out" (the last two with "; now conflicted or missing" once it is); on an escrow order also "Escrow deposit spent by a transaction this market did not make, …", "Escrow deposit left out of its settlement, not counted; a stray refund from the escrow returns it to the buyer" (credited or not, open: QA462D-2), "Deposit to an escrow after the order closed, not counted; …", "Escrow deposit counted for the order, though not credited toward its funding …" and "Escrow deposit counted for the order (credited toward its funding); the order's release or refund settles it" (neither open; never "confirmed again": QA462D-3), against the escrow's own confirmation threshold. Staff not party to the order can open it read-only (see P3).
- **Payment-review dispositions** (A-31; POST `/moderator/payment-review`, `payments.disposition`, `disposition_note`, `disposition_txid`, `disposition_amount`, `disposed_at`, migration 066): each open flag on the desk has *Record the review* for a moderator or administrator who is not party to the order, confirmed with their password (and authenticator code when enrolled; the role and suspension are read again, A-156): *no action* (a 10–1000 character reason) or *escalate to an administrator* (moderators only; every administrator not party to the order is notified and only an administrator then records one of the other two). Nothing is sent and no settlement changes. *Refunded by hand* is refused with 409 (A-330): every reviewed deposit is in an escrow, not in a market wallet, so a stray refund from the escrow returns it to the buyer's refund address instead. Each review writes one order event (read by both parties), one audit row and a buyer notification. A reviewed flag leaves the desk; the deposit label reads "…; reviewed by market staff on DATE: no action" / "…; escalated to an administrator on DATE"; a late-deposit notice episode ends once every open late flag of the order is reviewed (escalated ones keep it open). A second review of the same flag is refused (409), including one submitted at the same moment (the order and payment rows are locked and the disposition is written by compare-and-set, A-252), as is one by staff party to the order (403); buyers and vendors get 403. A credited deposit that regresses again after confirming is a new, unreviewed flag, and so is every flag a check sets anew on a deposit (left out again after a changed decision counted it again, spent outside the market, of a settlement spent outside or failed, below the minimum): it starts with no recorded review, the history keeping the earlier one (QA462E-1). Every note that flags escrow deposits names each ("deposit <txid prefix> (<amount>)"), so the desk dates the flag by the latest such note, a reopened flag by the note of its new event (QA462D-4, QA462E-2, QA462E-3; spent outside the market and Bitcoin or Monero settlements spent outside or failed since QA462F-1). There is no action that pays out a flagged deposit ([runbook](testnet-runbook.md#handle-a-payment-review-flag)). Evidence: `TestPaymentReviewEscrowMatrix` (PostgreSQL) and `db-payment-review.spec.ts` (Chromium with JavaScript off, flags seeded in SQL; no wallet, so the order page lists no deposits and the browser test reads the outcome in the order history).
- Order and checkout pages for an escrow name the chain with a badge (`REGTEST`, `SIGNET` or `TESTNET4` for Bitcoin; fakechain or stagenet for Monero) and say "no real funds" for a test network; the Monero escrow pages say the market can move the coins (custody sentence). With escrow off, the checkout offer says payment is unavailable. `/canary#records` lists what each escrow keeps. The administrator's payments panel shows each escrow's node status, chain pin, sync state, recovery gate and queued or stuck settlements (A-441, A-439, P1-d1), not a pooled provider.
- **Settlements.** An escrow order's coins leave only by a settlement (no payout row exists). A cancellation holding coins requests the refund there, which the escrow watcher builds, a party signs, and the market then co-signs and broadcasts (when both parties sign it, the market broadcasts it without signing); a Monero settlement is built, stored, relayed and followed by the Monero escrow watcher alone. Coins no settlement covers are returned by a stray refund.
- The payment step and the other order actions (ship, complete, cancel, dispute outcomes) are provided by the Orders package; `TestEscrowOrderActionMatrix` drives them against escrow fixtures, and the escrow browser journeys cover the forms.

Not implemented: marketplace commission accounting beyond the escrow market fee (`ESCROW_BTC_FEE_BPS`, `ESCROW_XMR_FEE_BPS`; fee destinations are administrator-set and, for Bitcoin, test-network addresses only), automatic retries of a failed Monero settlement build (an administrator re-requests it under guards) and any mainnet path. Multisig escrow is in no release: Bitcoin escrow's first two phases are built and tested on regtest and a private signet, and since A-443 accept signet and testnet4 (public signet practice/claim/refund recorded; public testnet4 unrun), off by default (below), and Monero escrow (Phase 3, custodial, not multisig) on a local fakechain, and since A-449 stagenet (one public digital claim recorded; other public journeys unrun), off by default (below). See [per-order escrow](escrow.md) for the design and its status.

Recovery and reconciliation (P1-d1): while the restore gate is set the escrow watcher builds, co-signs and broadcasts nothing, and each restored settlement with a stored transaction is broadcast again exactly once after an administrator confirms it on `/admin` with password step-up (`TestEscrowRestoreGatePausesAndAdminRebroadcasts`, `TestEscrowHeldSettlementSeenOnTheNetwork`; real Core regtest: `TestEscrowRegtestGate`; checked once by hand on the real binary); while the gate is set a second confirmation after that send is refused and nothing is sent again (A-363: `TestEscrowRebroadcastNotRepeatedUnderGate`), and with `ESCROW_BTC` off `/admin` lists held settlements without the confirmation form, whose route is off (A-360: `TestEscrowRebroadcastFormOnlyWithEscrowOn`); while the gate is set escrow checkout is refused with 503 "Bitcoin escrow is paused while this market restores its records from a backup. ### P6 Transparency

- **Operator key.** An administrator saves the operator's armored OpenPGP public key (`/admin/operator-key`); it is parsed (single, unrevoked public key; private keys, photo IDs and other non-public-key packets rejected), stored without armor metadata, and its fingerprint recorded in the audit log. Previously stored operator keys are shown with only public keys, subkeys, user IDs and signatures; an unusable stripped key is not shown.
- **Warrant canary.** The administrator pastes a statement the operator clearsigned offline (`/admin/canary`). It is rejected with the reason unless it is exactly one clearsigned message, with nothing before or after it, that verifies against the operator key. Accepted text is stored as pasted in a single-row `canary` table (migration 060). `/canary` re-verifies it on every view and shows exactly one of: "No signed canary published", "Signature verified" (statement, grouped fingerprint, signature date, posted date, the signed message and public key for independent `gpg --verify`), or "INVALID" with the reason (for example after a key change or database tampering). The application never writes, edits or signs canary text.
- **Signed audit export.** Administrators download `/admin/audit-export?upto=N` as NDJSON (`id`, `user_id`, `handle`, `action`, `created` in RFC 3339 UTC, ordered by id) and `&sig=1` as a text file with the Ed25519 public key, SHA-256 and signature over the exact export bytes. The key is read only from `AUDIT_SIGNING_KEY`; when it is unset or malformed the export returns 409 and the admin and `/canary` pages say it is unavailable. `upto` must not exceed the latest settled event (a brief `SHARE` lock waits for in-flight audit writers), so the same `upto` always yields byte-identical files. Rate limit: 10 downloads per 10 minutes per administrator. One export per server process is admitted through its final response write, bounding concurrent export buffers; another receives 503 with `Retry-After: 5` (`TestAuditExportOneBufferThroughFailedDownload`). The public key is published on `/canary`. The export sets its own time limits (A-139): one minute to read the events instead of the 12 s request bound (it also moves the server's 15 s read deadline, defensively only: net/http already clears the read deadline once a body-less GET has been read, so that timeout never cancels the export), then 20 s plus one second per 32 KiB to send the file instead of the server's 20 s write timeout, so a large export survives onion throughput (0.19–0.45 MB/s measured); every other route keeps the server's timeouts (`TestAuditExportOutlivesServerTimeouts`, `TestAuditExportBuildOutlivesRequestBound`, `TestAuditExportWriteWindowScalesWithSize`). A download cut short fails `verify-audit` with "export sha256 does not match the signature file", and the admin page says so.
- **Verifier.** `go run ./cmd/verify-audit -pub <hex> export.jsonl export.sig` (standard library only) checks the signature with the pinned key, not the key named in the `.sig` file, and that events are well formed with ascending ids; exit status 0 or 1.
- **Limits.** The signature proves origin from the server-held key only. Anyone controlling the server (or `AUDIT_SIGNING_KEY`) can sign an altered history; exports are not a tamper-proof log. Canary verification proves which key signed the text, not that its author acts freely or that the statement is true.

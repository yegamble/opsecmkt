# Implementation status

The Figma reference is adapted to Go-rendered HTML and CSS. The browser loads no JavaScript or third-party resources. A listing without photos shows a decorative CSS illustration labelled "ILLUSTRATION"; a listing with photos its vendor uploaded shows those instead (A-189): the first as a decorative thumbnail on its catalog and vendor-page card and at full size on its product page, which then says "Photos are supplied by the vendor; the market does not verify them." The original `[OPSECMKT]` wordmark is retained.

## Working application behavior

- Token-protected, transactional first-run administrator setup; repeated setup is rejected. The operator can instead create the first administrator on the host with `-bootstrap-admin HANDLE` (password on stdin, no setup token, same transaction and lock; no web path).
- Buyer registration, bcrypt password hashing, rotating hashed sessions, session revocation, CSRF validation, bounded forms and authentication concurrency.
- Two HttpOnly, SameSite=Strict cookies: `session` is set only at sign-in (with a fresh token) and cleared at sign-out or revocation; `anon` holds the pre-login token that CSRF forms and the CAPTCHA are bound to while no session is present. A request without cookies (for example, a link followed from another site, which Strict withholds) gets only a new `anon` cookie and never overwrites `session`, so the user stays signed in on their next direct visit. A form rendered on such a landing page carries an `anon`-derived CSRF token; its same-site POST, which then sends both cookies, is served as the anonymous request it was rendered for (it cannot act as the signed-in user, but its sign-in form and CAPTCHA work). Origin and `Sec-Fetch-Site` checks apply to every POST. Session cookies from before this change keep working.
- **Return to the page after sign-in** (A-126): an anonymous request for a signed-in page (for example "Review order draft" or "Contact vendor") is redirected to `/login?next=<page>`, and `/login` says "Sign in to see <page title>." Signing in, registering (`/register` keeps the target, and the links between the two pages carry it) and finishing `/challenge` (TOTP or PGP code; the pending sign-in stores the target, so the PGP code request and a failed attempt keep it) land on that page; a wrong CAPTCHA answer re-renders the form with the target kept (A-269). A recovery-code sign-in still lands on `/totp`, which shows the remaining codes and a "Continue to <page>" link, both with its one-shot notice only (a reload or a crafted `/totp?next=` shows neither, A-287). The target is accepted only as a registered page named exactly (`/checkout`, never `//host`, a scheme, a backslash, an encoded character or an action path) other than the sign-in pages, with at most its `id` query and the `/messages` recipient `to` (other query parameters are dropped; a malformed one refuses the target); it is rebuilt by the server, so it can never lead off the market, and anything refused signs in to `/` as before. The header's "Sign in" link carries no target.
- Server-enforced buyer, vendor, moderator, and administrator roles.
- PostgreSQL-backed listing creation, catalog search/category/region filters, product and vendor pages.
- **Catalog search and paging** (A-181, with A-16 for the catalog and A-60 PA-8): the search term is cut to 64 characters (so at most 256 bytes; the search boxes carry `maxlength="64"`, which never admits more, so a typed term is searched in full) and matched literally as a substring of title or description, case-insensitively, so `%`, `_` and `\` are ordinary characters. NUL bytes and invalid UTF-8 are dropped from the term and from the category (80 bytes) and region (80 bytes) filters instead of failing the page. The catalog shows 25 listings a page, newest first, with the total count, "showing X–Y" and plain *Previous*/*Next* links ("Page X of Y", marked `aria-current`) that keep the search, filters and display currency; a page number past the end shows the last page and anything else that is not a positive number shows the first. Listing cards on the catalog, vendor page and vendor desk show at most 300 characters of the description (cut on a character boundary, ending "…"); the product and checkout pages show all of it. A catalog page of maximum-size listings (140-character titles, 10 000-character descriptions) is about 44 KB. Search still scans titles and descriptions (`ILIKE`, no trigram index: `pg_trgm` is deferred because creating the extension fails on locked-down external databases); migration 062 indexes `products(archived, created)` for the unfiltered listing order. The vendor page is paged the same way, 25 listings a page with links that keep the display currency (A-189); the orders page, messages and notifications keep their row caps (A-16).
- Atomic-unit BTC/XMR price storage; idempotent **unfunded draft** creation and owner-only order access. Draft creation does not reserve stock or collect payment; requesting payment from the order page does (see P3, P5).
- Orders carry a canonical state (`draft`, `awaiting_payment`, `paid`, `shipped`, `delivered`, `completed`, `disputed`, `resolved`, `cancelled`). A server-side transition table, row locks and compare-and-set updates guard every change and log it in `order_events`. Buyers, vendors, moderators and the payment watcher move orders only through it (see P3 Orders and P5 Payments).
- Versioned, idempotent schema migrations applied at startup under an advisory lock (see [migrations](operator-guide.md#migrations)). Startup refuses, changing nothing, a database that records a migration the server does not include (one migrated by a newer release). Connecting, waiting for the migration lock, migrating and payment provider startup have separate bounds (`DATABASE_CONNECT_TIMEOUT` 15s, `MIGRATION_LOCK_TIMEOUT` 10m, `MIGRATION_TIMEOUT` 10m, payments a fixed 15s); a timeout exits with an error naming the phase, and a timed-out migration is rolled back. A failed connection names its class (authentication failed, database missing, host not found, connection refused, timed out or TLS required) without printing `DATABASE_URL`.
- **Database session timeouts** (A-177): every connection of the application's pool (and the one `/healthz` connection) starts with `statement_timeout` 8 s, `lock_timeout` 3 s and `idle_in_transaction_session_timeout` 15 s; startup checks that the database accepts them before migrating, so a pooler that refuses these startup parameters stops startup with nothing changed ([Connection poolers](operator-guide.md#connection-poolers)). A payment request, and whatever may queue behind one (a checkout, listing edit, archive or takedown, a cancellation returning stock, a payment-intake change, a payout to the buyer, and an administrator's suspension, second-factor reset or role change), waits up to 11 s for a row lock (its statement limit is raised to 11 s with it), because the request holds its rows while the wallet is asked for an address; one account has at most one payment request in progress at a time (another is refused at once with 429 and `Retry-After: 5`), so a burst from one account cannot hold the pool's connections queued on its own row. A page or form whose statement hits one is answered 503 with `Retry-After`, not 500, and logged with cause `57014` or `55P03`. So is one whose database connection is lost or refused mid-request (a restart or failover: SQLSTATE `57P01`–`57P03`, `53300`, `08000`, `08001`, `08003`, `08004`, `08006`, or cause `db-connection`; QA-178-2), when the failed statement ran before the change was committed. The same busy 503 also answers a lost `COMMIT` of the forms confirmed with a password (and of TOTP changes and uploads), although that commit may have landed: a retry then fails its checks or changes nothing, except an upload, which stores the photo again within the account's limits, and nothing pays twice (payouts are compare-and-set and sent only by the watcher). Only the shared form path's own commit, and an audit row that fails after its change was already committed, answer 500. Migrations run on a separate connection without them (bounded by `MIGRATION_TIMEOUT` instead), as do `-status`, `-bootstrap-admin`, `-reset-admin-password` and the backup and restore scripts, which open their own sessions. Recording a payout's outcome lifts the lock and statement limits inside its own transaction (it keeps its 10 s bound), the signed audit export's single streamed query lifts the statement limit (it runs under the export's own one-minute bound instead of the 12 s request bound, keeping the lock and idle-transaction limits; one million audit rows took about 6 s), and each payment watcher pass is bounded to 5 minutes, so a pass that cannot get a database connection ends, logs and leaves its work to the next pass; a wallet send already under way keeps its own 30 s bound.
- **Overload admission** (A-178): the server accepts at most 2048 connections at once (later clients wait in the kernel's backlog; while all 2048 are taken, HTTP keep-alive is off, so idle keep-alive connections are closed and cannot hold the slots), serves at most 64 page requests (GET/HEAD), 16 form posts charged to a signed-in account's write budget and 16 public ones (sign-in, registration, the sign-in challenge, whoever sends them) at once, 16 requests to the public image route (A-187; they take no page slot), and at most 8 CAPTCHA image renders and 4 password checks within those; a request that finds its class full is refused at once with 503, `Retry-After: 5` and `Connection: close`, and is not logged: a page before any database work, a form post after its session lookup (the only database read before its slot). A form post takes its slot only after its body is read (64 KiB cap, 15 s read timeout; a body with more than 64 fields is refused with 400 before it is parsed, so a flood of junk bodies costs about 150 KB of allocation each instead of 3.7 MB) and its Origin, `Sec-Fetch-Site` and CSRF checks pass, so slow-body posts hold only a connection; sign-in, registration and setup posts with a malformed handle or password, or a CAPTCHA id that is not a live one issued to that browser session, are refused (400) before taking a slot, as are sign-in challenges without a pending sign-in cookie (401). A post's session lookup, one indexed read, takes a slot of its own class of 16 for that query only, waiting its turn for up to 2 s before a 503; pages never take it, so a flood of pages cannot refuse a signed-in or staff post. A flood of well-formed public posts, anonymous or from a signed-in account, can still refuse real sign-ins as busy; signed-in and staff changes are unaffected by it. `/healthz` and `/static/` take no slot, and `/healthz` pings the database on its own connection, so a flood of pages or an exhausted pool does not starve the health probe. Every 503 carries `Retry-After: 5` and every 429 `Retry-After: 600` (the ten-minute limiter window), except the 429 refusing a second concurrent payment request from one account (one at a time per app process), which carries `Retry-After: 5`. A slot is released as soon as the response starts, so a slow reader holds only its connection. Server-error log lines are limited to 10 a second; the rest are counted in one `http 5xx suppressed=N` line. Measured with `TestLoadSearchFloodKeepsHealthz` (500 concurrent catalog searches from one keep-alive client, a fresh-connection `/healthz` probe every 20 ms; opt-in with `LOAD_TEST=1`, manual only and never run in CI, [command](ci-cd.md)): on Linux (a Docker container with 8 CPUs, backlog 4096) probe p99 103–145 ms and maximum 172 ms over three 10 s runs, with about 16 000–18 000 requests a second answered, 3–4 % of them search results and the rest refusals, with the connection cap then at 256; with the check on the server's own cap of 2048 (`market.MaxConns`), one 10 s run on a shared 4-CPU Linux host gave probe p99 162 ms and maximum 170 ms, with about 9 700 requests a second answered, 10 % of them search results; on macOS (backlog 128) the flood overflows the accept backlog and dropped connection attempts retried after 1–4 s, so the check is meaningful only on Linux. Load was generated on the same host, not over Tor.
- **Image scanner client** (A-185; the upload pipeline it serves is A-186, below): with `CLAMD_ADDRESS` set, the app polls clamd every 30 s (PING and VERSION) and caches its state: *Ready*, *Unavailable* or *Signatures stale* (the daily signature database is older than `SCANNER_MAX_SIGNATURE_AGE_DAYS`, default 30, 7–90, or its date is unreadable); without it, *Disabled*. `/admin#image-scanner` shows the state, engine, daily version, build date and age, the last successful scan and about 24 hours of in-memory counts (stored, refused as infected by signature, refused because the scanner failed), never linked to accounts; pages read only the cache, and `/healthz` never contacts clamd. The client sends upload bytes once, unmodified, with zINSTREAM (64 KiB chunks, 3 s to connect, 10 s per exchange) and accepts them only on the exact reply `stream: OK`; any other reply, a timeout or a closed connection refuses the upload, and so does an OK the client can see was sent with part of the stream unread (a write that fails, or a reset instead of an orderly close); the client cannot detect a server that reads everything and answers OK without scanning, so clamd itself is trusted. ClamAV checks uploads for known malware; it does not review picture content. A matched signature name appears only in one log line beside a reference the uploader is shown, and in the admin counts; the uploader's audit row is fixed copy. Tested against a fake clamd (`clamd_test.go`, `db-admin.spec.ts`); the opt-in `TestRealClamd` (`CLAMD_TEST_ADDRESS`) passed locally against ClamAV 1.5.4 (`clamav/clamav-debian:stable`, macOS and a Linux container: VERSION parsed, a stream with no match accepted, EICAR found, a stream over `StreamMaxLength` refused without pausing the scanner). `TestRealClamd` does not run in CI; CI's container job runs the production image against the pinned clamd in both database modes instead (A-192, `scripts/ci-smoke.sh <mode> scanner`), with one test signature as its only database, packed at job time into an unsigned `daily.cud` whose build date clamd reports in `VERSION`, so the 30-day gate passes on any day. That proves the app's use of a real clamd (a marker PNG refused and nothing stored, one without the marker stored and served re-encoded, uploads refused while clamd is stopped and resumed after it starts, `SHUTDOWN` refused, clamd unable to reach the database or outside), not detection quality: it is not a production signature feed. [Operations tests](operations-tests.md#malware-scanner-leg-in-ci) list what it checks.
- **Photo and avatar upload pipeline** (A-186; the forms that post to it are A-188, below; stored images are served by the image routes (A-187, below) and shown on pages (A-189, below)): `POST /listings/photo` (vendors and administrators, on a listing they may manage that is neither archived nor taken down) and `POST /account/avatar` (vendors, administrators and moderators; always the poster's own avatar, replacing any earlier one) are the only routes that take a file; a multipart post to any other route is refused with a 415 page before its body is read. The order of work: Origin checks, a `Content-Length` of at most 8 MB (else 411 or 413, unread), the session, the role, the account's change budget and an upload budget of 20 per 10 minutes, a post slot, one of 2 upload slots and one upload at a time per account; only then may the body take 90 s and the answer 150 s (the server's own limits are 15 s and 20 s). Every refusal reads the rest of the body into nothing (never into memory) before answering with an HTML page, so a browser sees the page rather than a reset. The form is `csrf` first, then an optional listing `id` and `description` (250 characters), then `photo` (4 MB); the file name and the part's type are never read. Before the scan: JPEG or PNG by magic bytes only, at most 4096 px a side and 4096×3072 pixels in all (about 12.6 megapixels, so a 4032×3024 phone photo fits), no CMYK JPEG, no JPEG with more than 100 progressive scans, and an estimated decode memory of at most 64 MiB, an upper bound on what Go's decoders allocate (a JPEG counts its planes, 4 more bytes a pixel for an RGB one, and when progressive 256 bytes for every 8×8 coefficient block of each component at its own sampling, so a progressive 4:4:4 JPEG counts 15 bytes a pixel, a 4:2:0 one 9, a baseline RGB one 7 and a progressive 4:4:4 RGB one 19, on its size rounded up to whole MCUs; checked against real decodes by `TestDecodeAllocationWithinEstimate` and `FuzzDecodeReencode`), and a JPEG that `image/jpeg` would read differently from the header check (stray `FF 00`, or a marker it does not parse as a segment) is refused. The bytes received are then scanned (above) and, only when clamd found nothing, decoded one at a time, turned upright by their EXIF orientation, flattened on white, resized (never enlarged) and re-encoded by Go's JPEG encoder: a photo fitting 1200×1200 (quality 82) with a 320×240 letterboxed thumbnail (quality 70), an avatar a 256×256 centre square with a 64×64 thumbnail. Nothing but the pixels survives: no EXIF, XMP, IPTC, ICC profile, comment, embedded thumbnail, PNG text chunk or data after the image (`images_test.go`). One transaction then re-checks the session and role (waiting for, and seeing, an administrator's change to the account or the listing's vendor in progress: it takes their users rows before the listing, in the same order as that change, so the two cannot deadlock), locks the listing, enforces 4 photos a listing, 50 MB an account and `IMAGE_STORAGE_LIMIT_MB` (default 2048) for the market (409 pages), stores the two JPEGs, their size, the description, owner, listing and time in the `images` table (migration 063; no column for a file name, type, original size, hash or scan result), writes a fixed-copy audit row and, when an administrator added the photo to another vendor's listing, records "Photo added to listing <8-char id> by an administrator" in that vendor's audit trail and notifies them (A-190). Tested with generated fixtures and a fake clamd, over `httptest` and loopback connections (`uploads_test.go`, `uploads_integration_test.go`, `uploads_quota_test.go`); in Chromium and Firefox with JavaScript off against the fake clamd (`db-listing-photos.spec.ts`, below); and in CI with curl against the production image and a real clamd holding only a test signature (A-192, above); not over Tor or with production signatures. What the server keeps (below and `/canary#records`) lists what an image row holds and who can see it (A-191). Migration 063 also stores the owner's staff-visibility choices (a per-account "hide me" flag, hidden by default, and a "public staff list" setting, off by default) for A-187 and A-189; the image routes and pages read them (below). An administrator sets the public staff list on `/admin` (A-189); staff set their own flag on `/account` (A-188, below).
- **Image routes** (A-187; the pages that link them are A-189, below): stored images are served only by two routes, as the re-encoded JPEG (`-f`, at most 1200 px) or its thumbnail (`-t`), addressed by the row's 128-bit random id (32 lowercase hex). `GET`/`HEAD /img/<id>-t|-f` is public: it runs before any cookie or session code (it reads no session and sets no cookie), takes one of 16 image slots of its own (`imageWork`) instead of a page slot, so a page of thumbnails or a flood of image requests cannot refuse pages (and a full image class answers 503 with `Retry-After: 5`), and serves a photo only while its listing is published (not archived, not taken down) and its vendor (or the administrator whose listing it is) is not suspended and still has that role, a vendor's avatar while the vendor is not suspended, and a moderator's or administrator's avatar only while the "public staff list" setting is on and that account has not hidden itself (both off/hidden by default; owner decision). `GET`/`HEAD /desk/img/<id>-t|-f` reads only the session cookie (under a page slot, like a page) and serves an image to its owner whatever its state (an archived or taken-down listing's photo), any image to an administrator, a staff member's avatar to the buyer, vendor and moderators of an order on which that member recorded the dispute decision, and an archived (or taken-down) listing's photos to whoever may read an order placed on that listing by the order page's rule (A-264: its buyer and vendor, and moderators and administrators while that order is disputed or resolved or has a flagged payment); moderators get nothing else there (they see vendors' images on the public route), and the public route still refuses an archived listing's photos (`TestArchivedListingPhotosThroughOrder`). Every other GET or HEAD (a malformed path, a hidden image, no session) gets the same 404 as an unknown image id (status, headers and body; neither route sets a cookie), so an id cannot be probed; a POST gets 405. The image bytes held by responses still being written are capped at 64 MiB on `/img` and, separately, 32 MiB on `/desk/img`, so a signed-in flood of the desk route cannot refuse public images (`TestDeskImageFloodLeavesPublicImages`) (a GET reserves the largest size of what it asked for before its query, never waiting, and keeps what the image needs until it has been written): a client that never reads cannot pin memory beyond that, and a GET whose largest size no longer fits gets the busy 503 with `Retry-After: 5` while pages are unaffected and a HEAD, which reads only the length, still answers (`TestImageSlowReadersBoundedByByteBudget`: 33 clients that never read fill it, the heap grew 61 MiB with 49 of them connected). A served image carries exactly `Content-Type: image/jpeg`, `Content-Length`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: private, max-age=86400, immutable` (a browser may reuse a viewed image for a day without asking again, and keep it on disk until its cache is cleared: `max-age` sets freshness, not retention), `Cross-Origin-Resource-Policy: same-origin` and `Content-Disposition: inline; filename="image.jpg"`: no `ETag`, `Last-Modified` or `Set-Cookie`. No other query reads image bytes: outside `image_routes.go`, no SQL string or concatenation of strings and constants names the `full` or `thumb` column (in any case) except inside `octet_length(...)` or an `INSERT INTO images(...)` column list, none reads whole `images` rows (`*`, `alias.*`, the row itself, `row_to_json` and the like), and no other file uses the helper that builds the byte-reading query (`TestOnlyImageRoutesSelectImageBytes`; the checker's own evasion cases are `TestImageBytesCheckerCatchesEvasions`). It reads Go source text, so SQL assembled at run time from non-constant parts is outside what it can see. Tested over `httptest` and a loopback server against PostgreSQL (`image_routes_test.go`), not in a real browser or over Tor; `/canary#records` says what a browser keeps (A-191).
- **Upload forms, own removal and the staff "hide me" choice** (A-188; the pages that show them are A-189, below): each listing's edit page has a **Photos** panel (`#photos`) listing the listing's stored photos from the database, oldest first, each with its thumbnail through `/desk/img`, a link to the full image, "Photo N: JPEG, W×H, N KB" (sizes from `octet_length`, never the bytes), its description or "No description", and its own urlencoded remove form; above them "N of 4 photos · X MB of 50 MB" (X is the listing's vendor's photos and avatar, rounded up to a tenth). Below is the listing's only multipart form (`POST /listings/photo`: hidden `csrf` first, then `id`, an optional description of up to 250 characters, then the file input, `accept="image/jpeg,image/png"`, never `capture`); the limits (4 MB, 4096 pixels a side and 4096×3072 in all), the re-encoding, the 90-second Tor timing, the ClamAV line and a privacy notice (what is removed; what is not, including anything visible and sensor noise; screenshots; public to anyone; never reuse a photo) precede the input and describe it (`aria-describedby`). An archived, taken-down or full (4 photos) listing shows why instead of the form. `/account#avatar` does the same for the account's avatar (vendors, administrators and moderators; staff also read that a staff photo links their identity across every dispute decision), showing the current one through `/desk/img` with a remove form; an account demoted since still sees and can remove one it has. The forms follow the cached scanner state: *Ready* shows them; *Unavailable* or *Signatures stale* puts them in a `<fieldset disabled>` with the paused copy; *Disabled* shows no file input, only "Photo uploads are off on this market: …" (the refused posts themselves are A-186's 503 pages). Listing text forms stay urlencoded, and publishing a listing now lands on `/listing-edit?id=<new>#photos` with a one-shot "Listing created. Add photos here." notice inside the panel (A-117: success notices are a cookie holding a code from a fixed server table, set on the 303 of a successful signed-in post and cleared by the next page, never a URL flag); after an upload the page says, in the Photos panel and once (A-287), that the photo was saved as a re-encoded JPEG with metadata removed and to check the picture itself. `POST /listings/photo/remove` (vendors and administrators; the listing's vendor or any administrator, as `lockListing` decides, whatever the listing's state) hard-deletes the photo, audits "Removed a photo from listing <8-char id>" (with "as administrator" for another vendor's) and, when an administrator removed it, records "Photo removed from listing <8-char id> by an administrator" in the vendor's audit trail and notifies the vendor (A-190; like every listing action, it locks the actor's and the vendor's users rows before the listing, so it waits for an administrator's role change for that vendor instead of deadlocking with it; PR #24 review); another vendor's photo, an avatar and an unknown id get the same 404. `POST /account/avatar/remove` deletes the poster's own avatar (no id is read) and audits "Removed avatar". Moderators and administrators have a "Hide me from the public staff list" checkbox (`/account#staff-list`, urlencoded, `POST /account/staff-list`), ticked by default (`users.staff_hidden`), whose changes are audited "Public staff list choice changed: hidden → shown" (or the reverse); saving the same choice records nothing, and vendors and buyers get 403. Tested against PostgreSQL with a fake clamd (`upload_forms_test.go`), in the read-only preview (`preview-inventory.spec.ts`, `preview.spec.ts`: the preview has no scanner and shows a Ready sample, `?scanner=off` and `?scanner=paused` the other states) and in Chromium with JavaScript off against a real database and the loopback fake clamd (`db-listing-photos.spec.ts`); its upload, scanner-refusal and over-4-MB cases also run in Firefox with JavaScript off (the `database-firefox` project, A-192), where the over-4-MB upload shows the 413 page naming the limit, not a connection reset. Not over Tor or with a real ClamAV in a browser (CI's scanner leg drives the real clamd with curl).
- **Images on pages** (A-189; the upload forms are A-188): pages link stored images by id and never read their bytes, and each page chooses its images with the visibility rule of the route it links, so a hidden image is never linked. Catalog and vendor-page cards show the first public photo's thumbnail as `<img src="/img/<id>-t" alt="" width="320" height="240">` (decorative: the card link is named "View <title>"), letterboxed over the card's background with no illustration label or scanline and the kind badge on a solid chip (a thumbnail that fails to load, such as a 404 after a takedown race or a busy 503 when the image slots or byte budget are full, leaves the card's layout intact: Firefox and Tor Browser show the card's art background, Chromium and WebKit show their broken-image icon; no fix without JavaScript is known under the image CSP); cards without a public photo keep the CSS illustration and its label. The vendor desk's cards stay illustrations. The product page shows photo 1 at full size (`object-fit: contain`), its text alternative its description or "Photo 1 of N: <title>", and the other photos as thumbnails linking to their full size, named "Photo 2 of 4, full size (JPEG, 180 KB)" (KB of 1024 bytes) with their description beneath; its notice then reads "Photos are supplied by the vendor; the market does not verify them." An archived listing's product page (shown only to those who may read an order on it, A-164) shows its photos the same way on `/desk/img`, with no staff remove form (A-264). The vendor page shows the vendor's avatar thumbnail at 58×58 (`alt=""`) when the public route serves it, else the text glyph, and pages its listings at 25, so a view loads at most 25 thumbnails and the avatar (the browser suite measured 25 thumbnails, about 98 KB, and no image request on a second view). No other page shows an avatar (cards, messages, orders), except the staff avatar beside a dispute decision. **Public staff list** (owner decision 1): an administrator turns "Show a public staff list" on or off on `/admin#staff-list` (POST `/admin/staff-list`, confirmed with their password and authenticator code when enrolled, audited as "Public staff list changed from off to on"; off by default; a form for the state already in force changes nothing, 409). While it is off, `/canary` shows no staff list. While it is on, `/canary#staff` lists each moderator and administrator who is not suspended and has not hidden themselves (every account is hidden by default), administrators first, by handle and role with their avatar on the public route; hidden staff are not listed at all. **Decision avatar** (owner decision 1(c)): on the order page, the history entry that moves a dispute to Resolved shows the deciding staff member's 64 px avatar (`alt=""`) on `/desk/img`, chosen with that route's own rule for the viewer, so the buyer, the vendor and staff see it even while that member is hidden from the public list, and once the member is suspended, or demoted other than by the admin role form (which deletes a demoted moderator's avatar, PR #28 review), only administrators see it (the desk route serves administrators any image). **Preview**: the read-only preview (no database) serves three generated sample pictures, re-encoded by the pipeline's own resize and JPEG steps, through the public route's response writer and header set: two on the encrypted drive sample and one, with a description, on the security research sample. Tested with PostgreSQL over `httptest` (`image_pages_test.go`), in the preview browser projects (`preview-accessibility.spec.ts`, `preview-transparency.spec.ts`) and in the database browser project with one photo uploaded through the real route against the suite's fake clamd (`db-image-rendering.spec.ts`); not over Tor.
- **Staff image takedown** (A-190, ruling D4; owner decision 1): moderators take down a vendor's listing photo or avatar, and administrators any listing photo or avatar, a staff avatar included, with `POST /images/remove` (urlencoded: `id` and a reason of 10–500 characters after trimming, without a NUL byte; buyers and vendors get 403, and owners keep A-188's own remove forms). The reason is checked first (400); then an image the actor may not take down (a moderator only a vendor's image that the public route serves, never a staff avatar or a photo on an administrator's own listing; an administrator any image), the actor's own image and an unknown or malformed id all get the same 404 ("Image not found. Nothing was removed."). The takedown deletes the row, both sizes, in the action's transaction: no stub row, hidden flag or purge log, so the image routes then answer exactly as for an unknown id. It takes the actor's and the owner's users rows (`FOR KEY SHARE`) before deleting, in `lockListing`'s order, and re-reads the actor's role under that lock, so a takedown racing an administrator's demotion of the actor waits for the demotion and is then refused (403). It writes one audit row for the actor ("Took down a photo on listing <8-char id>: <reason>", or "Took down the avatar of <handle>: <reason>") and one for the owner ("Photo on listing <8-char id> removed by staff: <reason>", or "Avatar removed by staff: <reason>"), never the image id, and a link-free notification with the reason (not `notifyOwner`, whose copy is for sign-in events). Moderators gain no other listing capability (`/listings/update`, `/listings/archive`, `/listings/restore`, `/admin/listing`, `/listing-edit` and photo upload and removal stay 403). The owner's listing edit page shows "Photo removed by staff: <reason>" with the time for the five latest takedowns of that listing's photos, read from the owner's own audit row (the takedown's only permanent record; notifications carry the same reason in prose), so it survives reloads and is seen only by the vendor and administrators; it is never shown publicly. **Forms**: `/moderator#recent-photos` ("Recent photos") lists the 50 newest images the public route serves (for a moderator only vendors' images, the ones they may take down), newest first, each with its thumbnail on `/img`, its listing and owner links (a moderator's avatar links the public staff list), when it was added and a `<details>` remove form; moderators cannot see hidden images (A-187), so hidden ones are not listed. Staff also get a `<details>` remove form per photo on the product page and for the avatar on the vendor page, only for images they may take down, and return there with "Image removed. Its owner was notified with your reason." **After a restore**: a restored database has every image the backup had, including those removed since; `scripts/restore.sh` says so with the image count and the dump's creation time, and Recent photos is where staff re-check. An administrator adding or removing a photo on another vendor's listing is recorded in that vendor's audit trail and notifies them (A-186, A-188, above). Tested against PostgreSQL (`image_takedown_test.go`), in the database browser project with JavaScript off, the photo uploaded through the real route against the fake clamd (`db-image-takedown.spec.ts`), and in both restore rehearsals (`scripts/test-backup-restore.sh`, `scripts/test-internal-db-restore.sh`); not over Tor.
- Storage of messages the sender encrypted with OpenPGP beforehand (packets are inspected and plaintext is rejected; see P2), in-app recipient notifications (linked from the main navigation at every width, with the unread count as text), and account audit history. The server cannot decrypt messages.
- Moderators resolve disputes on paid, shipped or delivered orders with a release or refund outcome, confirmed with their password (and authenticator code when enrolled); the payment system then queues the matching test-network payout from the operator's wallet (see P3, P5).
- Docker internal/external database selection, separate clearnet/Tor exposure (a pinned tor from the Tor Project's repository with proof-of-work, introduction-point and per-circuit stream limits, checked offline in CI but not measured under a real attack; see [Denial-of-service defences](operator-guide.md#denial-of-service-defences)), memory, CPU and process limits and log rotation on every container, optional operator-supplied node containers (pruned by default, full node on request), encrypted database backup and transactional restore scripts, and documented commands (run verbatim, offline, by `scripts/test-tor-identity-restore.sh`) to back up and restore `.env` and the onion identities with age.

## What the server keeps

`/canary#records` tells users the same thing, and `/register`, `/account` and the `/messages` notice link to it. Everything below is kept in PostgreSQL (and in every backup) until the operator removes it: there is no account, message or order deletion, except photos and avatars (below). The operator, anyone else who controls the server or database, and anyone holding a decrypted backup can read all of it; the list says who else can read it through the application. Checked against `internal/market/schema.sql` and `internal/market/migrations/` (001–074).

- **Handle and role** (`users.handle`, `role`, `created`; `suspended_at`, migration 011). The handle cannot be changed (`/register` and `/setup` say so). Shown to trading and messaging partners, moderators and administrators, and publicly with a vendor's listings and vendor page. Moderators' and administrators' handles and roles are public on `/canary#staff` only while an administrator has turned the public staff list on and that account has chosen to be listed (A-189). Administrators see every handle and role and the suspended accounts with their time.
- **Password** (`users.password_hash`, bcrypt).
- **Second factors** (migrations 010, 012, 013, 020): TOTP secret and pending secret sealed with AES-256-GCM under a key derived from `SETUP_TOKEN` (so the database plus `SETUP_TOKEN` opens them); recovery codes as SHA-256 hashes, with newly issued codes sealed in `users.recovery_reveal` for at most about 11 minutes; `pgp_2fa`; `pending_logins.factor_failed` marks a pending sign-in whose second factor already failed once (migration 012); `pending_logins.password_digest` is the SHA-256 of the password hash the sign-in's password was checked against (migration 013, A-157), so a password change also ends a sign-in whose password was checked just before it. The account and administrators (second-factor reset list) see which factors are on.
- **PGP public key** (`users.pgp`, stored canonically; `pgp_fingerprint`, `pgp_verified_at`, migration 020; `pgp_changed_at`, when the key was last added, replaced, removed or updated without keeping its proof, and `pgp_expiry_notice`, the last expiry notice sent, migration 067). Shown to any signed-in account that looks up the handle, to trading partners, and publicly on a vendor page (see P2).
- **XMPP address** (`users.xmpp`). Rendered only on the owner's `/account`.
- **Messages** (`messages`: sender, recipient, canonical ciphertext, `created`, `encrypted`, `recipient_match`). The server cannot decrypt them. Sender and recipient see them; moderators and administrators have no message view. While a dispute is open, staff who are not party to it see, on the moderation desk and `/disputes`, how many messages each party sent to each current moderator or administrator since it opened and the time of the latest, from `sender_id`, `recipient_id` and `created` only (A-162).
- **Notifications** (`notifications`): plain text such as "New message from <handle>", short order IDs with the new state (for a move neither party made, the payment watcher's or a moderator's, followed by its reason, e.g. "Cancelled — payment window expired", "Resolved — refund to buyer"; never an absolute time; A-123), payment notes and payout transaction IDs; read state. Only the account sees them.
- **Orders and drafts**, including unpaid drafts and cancelled orders (`orders`; `order_events` with actor, time and notes such as the vendor's note to the buyer and the cancellation reason). The buyer and vendor, and moderators and administrators while the order is disputed or resolved or a payment on it is flagged (see P3).
- **Disputes** (`disputes`: reason, resolution, outcome, plain text; the other party's one reply is an `order_events` row whose note starts "Dispute reply: ", plain text, A-124). The parties, moderators and administrators.
- **Reviews** (`reviews`, migration 030): rating and text; public on product and vendor pages by month without the reviewer's handle; the vendor sees the review with the buyer's handle on the order page. Administrators can hide a review from the public pages (`reviews.hidden_at`, migration 031); a hidden review is kept, not deleted, and administrators still see it.
- **Digital deliveries and listings** (`deliveries`, migration 030; `products` including `delivery_content`): delivered content is unencrypted and shown to the buyer and vendor, and to moderators and administrators once disputed; listings are public; automatic delivery content is shown only to the vendor.
- **Listing photos and avatars** (`images`, migration 063; A-186 to A-191): for a listing photo, a vendor's avatar or a staff member's (moderator's or administrator's) avatar, only the re-encoded JPEG, its thumbnail, its dimensions, an optional description (listing photos only; the avatar form has none), the owner, the listing for a photo and the time added. The uploaded file, its name and its metadata are never kept: no column holds them, and the re-encoding keeps only the pixels (see the upload pipeline above). Listing photos and their descriptions are public to anyone, signed in or not, while the listing is published and its vendor (or the administrator whose listing it is) keeps that role and is not suspended; a vendor's avatar is public while the account is a vendor and not suspended. A staff avatar is public on `/canary#staff` (and on an administrator's vendor page) only while an administrator has turned the public staff list on and that staff member has chosen to be listed (`users.staff_hidden`, hidden by default); otherwise it is shown only beside that staff member's dispute decisions, to the buyer and vendor of those orders and to moderators, and to administrators (the parties' and moderators' access needs that member to have decided a dispute and to be still staff and not suspended; administrators can open any image on `/desk/img`). Demoting a staff member removes their staff avatar: an administrator changing a moderator's role deletes it in that transaction, notifies them and records "Staff avatar removed when the role changed" in their activity log, and resets their public staff list choice to hidden, so a later promotion starts hidden again (PR #28 review). Demoting a vendor to buyer, archiving a listing, an administrator's listing takedown and suspending the account hide its images from the public without deleting them; administrators, and the owner while signed in, still see them on `/desk/img`. The image routes send `Cache-Control: private, max-age=86400, immutable`. A normal browser may keep viewed images in its disk cache: it reuses them for a day without asking the server, and the files can stay until its cache is cleared. Tor Browser keeps them in memory only, until it closes (not yet tried in Tor Browser, A-199). Removing or replacing an image, or a staff takedown, deletes it from the database at once; copies remain in backups made before that and, until PostgreSQL reuses the space, in its data files and write-ahead log. If the operator restores a backup made before a removal, the image returns until it is removed again (`scripts/restore.sh` says how many images it restored). The activity log keeps that an image was added, replaced, removed or taken down (with the listing's short id and a takedown's reason, never the image), and a takedown's reason also reaches the owner as a notification. ClamAV checks uploads for known malware; it does not review picture content. An upload it flags stores no image: the uploader's activity log records "Upload refused by the malware scanner", and the server log keeps the signature name and the reference shown to the uploader, for as long as Docker's logs are kept (3 × 10 MB rotation), and its time can be matched to the uploader's activity-log row; the log line itself names no account (see the [operator guide](operator-guide.md#troubleshooting)).
- **Payments** (`payment_addresses`, `payments`: addresses, amounts, transaction IDs, confirmations; for a flagged deposit, the staff review with its reason or note and a hand refund's transaction ID and amount, migration 066). The parties, moderators and administrators on disputed, resolved or flagged orders, administrators on payouts, except that a hand refund's transaction ID is never shown to the vendor (A-31, A-214); transactions are also recorded on the test network (or on mainnet, on a mainnet market).
- **Payout addresses** (`users.payout_btc`/`payout_xmr`, copied onto `payouts.address` with the payout `txid`, migration 050; the time each was last saved or removed, `users.payout_btc_changed`/`payout_xmr_changed`, migration 057, NULL before it). The account; administrators on payouts that need attention; a payout's destination only its recipient (on /account#payout and on the order page, A-120); its transaction ID only its recipient (on the order page and in their notification) and staff reading the order, never the other party (A-214).
- **Bitcoin escrow keys** (`user_escrow_keys`, migration 074), only on a market running Bitcoin escrow (`ESCROW_BTC=on`, off by default and regtest only; [per-order escrow](escrow.md)): the account's extended public key, sealed with AES-256-GCM like the TOTP secrets; an HMAC of it that stops two accounts registering the same key; its origin fingerprint and path; and when its practice transaction was signed. The pasted practice PSBT is not kept. The owner sees the origin and state on `/escrow-key`; the audit line and notification name no key, fingerprint or path. The escrow's arbiter wallet fingerprint is kept in `settings`. Migration 074's `escrows`, `escrow_pubkeys` and `settlements` tables and `payments.settlement_id` stay empty in this release. Not yet listed on `/canary#records`, which gains the escrow records when escrow creation ships.
- **Activity log** (`audit_events`: action text naming handles, key fingerprints, short order IDs and transaction IDs, with time), including every sign-in and sign-out. The account sees its latest 15 on `/account`; administrators see every account's on `/admin` and in the signed audit export (see P6).
- **Temporary sign-in records**: hashed session tokens (`sessions`, 12 hours: the token's SHA-256, the account, and when the session started and ends; no IP address, user agent or other client data; the owner sees the start times on `/account`, A-157), pending sign-ins (10 minutes; with the page the sign-in returns to, A-126), the ids of CAPTCHA challenges that were answered (`captcha_spent`: the id and its expiry, at most 10 minutes after the challenge was shown, deleted by a sweep every minute; a challenge that is only shown stores nothing) and PGP ownership challenges (30 minutes). Expired sessions and pending sign-ins are deleted opportunistically, not by a timed sweep; an expired PGP challenge stays until the account starts another, proves ownership or changes its key.
- **Not recorded**: no IP address, user agent or other browser details and no access log (no table has such a column and no handler reads them), and no email address. A reverse proxy, the Tor service or the hosting provider in front of the application may log connections. The only application log line that can carry a network address is Go's `http: panic serving <address>` if a handler panics; behind the bundled deployments that address is the proxy's or Tor's, not the visitor's. Server errors (5xx) are logged as one line with the route, status, a reference shown to the user and a cause class, never the request, its sender or the error text, at most 10 lines a second with the rest counted in one summary line; overload refusals are not logged ([operator guide](operator-guide.md#troubleshooting)).
- **Signed audit export**: it names every account's activity, so it is private operator evidence, never to be published; `/canary` publishes only its public key so the operator can prove an export they hold came from this server.

## Feature packages

Each package updates only its own subsection when it lands.

### P1 Authentication

- **TOTP second factor** (`/totp`): RFC 6238 (HMAC-SHA-1, 30-second steps, 6 digits, one step of clock skew either way) implemented with the Go standard library. Enrollment generates a random 160-bit secret, stored encrypted (AES-256-GCM, key derived from `SETUP_TOKEN`) and inactive until the user confirms a correct code. Activating TOTP needs the current password on every account, including one with no factor yet (starting enrollment does not), so a session alone cannot add a factor that locks the owner out after "Sign out everywhere" (A-152); the audit row notes the confirmation. Every accepted code advances a per-account step counter, so a code cannot be used twice, including by concurrent requests. Turning TOTP off requires the password and a current code or recovery code. Someone who lost the authenticator can also turn it off while signing in (A-154), so one recovery code is enough to recover without staff: the recovery-code form on `/challenge` has an unchecked "I lost my authenticator — turn two-step sign-in off" checkbox, honoured only with a recovery code (ignored with an authenticator code). In the sign-in's transaction it turns TOTP off (secret, pending secret, step counter, every recovery code and any unrevealed codes), writes one audit row "TOTP turned off at sign-in with a recovery code (N remaining)" in place of the usual recovery-code row and notifies the owner once. Other sessions and pending sign-ins are left as `/totp/disable` leaves them; PGP sign-in, when also on, stays on and is asked for at the next sign-in; a suspended account's sign-in is refused and nothing changes. Every recovery-code sign-in lands on `/totp`, which says once (a one-shot notice set with the new session, A-287) how many recovery codes remain (or that TOTP is now off). Every path that changes an account's pending sign-ins, recovery codes or account row takes the row locks in the order `/challenge` does (pending sign-in, then recovery codes, then the account row): the sign-in, password change, TOTP activation, recovery-code replacement, turning TOTP off, the administrator's factor reset and suspension, and the `-reset-admin-password` tool, so none of them deadlocks with a concurrent sign-in.
- **Sign-in challenge**: after a correct password, an account with TOTP enabled always receives a 10-minute pending login and must complete `/challenge`; no session is issued before that. Code guesses are limited to 10 per pending login and 10 per account per ten minutes (in-memory limits, per application instance). Limiter entries are created only for pending logins that exist and, for sign-in, registration and setup (each 10 per handle per ten minutes, case-insensitive, with separate budgets), only for a well-formed handle whose request passed the CAPTCHA (when it is on; setup has none), so a wrong or absent CAPTCHA never spends a handle's budget. Only failed passwords spend a handle's sign-in budget: a correct sign-in spends nothing, and registration and setup attempts never touch it. After 10 failed passwords the handle's sign-in is refused (429, even with the right password) for the rest of that ten-minute window, with a message that sign-in for this handle is paused for up to 10 minutes, that someone else may have caused it and that the password may be fine. Because the budget is per handle (there is no per-client signal over Tor), anyone who knows a handle, including the administrator's, can keep it paused with 10 wrong guesses per ten minutes, each needing a solved CAPTCHA when it is on and nothing when it is off. While any handle is paused, sign-in failures and refusals log `sign-in limiter refusing handles=N` at most once a minute (a count, never a handle); restarting the application clears the in-memory limits ([operator guide](operator-guide.md#authentication)). Registering a taken handle is answered "Handle unavailable" before any password hashing and spends no budget. Password checks and hashing run at most four at a time. A sign-in or registration takes one of these slots only after its input, CAPTCHA, free-handle and limit checks pass, so requests refused by those checks never keep real sign-ins or confirmations waiting; a password confirmation is refused before taking a slot once its account's budget is spent, and otherwise takes its slot before its attempt is counted. Every password-confirmed change (the administrator, moderator and payout actions, resolving a dispute, payment reviews, settings, key, TOTP and password changes) shares one per-account budget of 10 **failed** confirmations per ten minutes (A-274, as A-153 for sign-in): a wrong password, or, when TOTP is enrolled, a wrong authenticator or recovery code after the right password. Each password reserves one attempt before bcrypt runs and each code another under the account row lock, and a right one gives it back, so a correct confirmation spends nothing (a moderator can resolve any number of disputes) and concurrent guesses still cannot exceed it. After 10 failures the account's confirmations are refused (429 "Too many failed password confirmations. Try again in ten minutes.") for the rest of that window, even with the right password; only someone signed in to the account can spend it, and restarting the application clears it. A sign-in, registration or password confirmation refused because every slot is busy (503) spends none of its budget. When the in-memory table (4096 entries) is full, the non-blocking entry with the lowest count is evicted; an entry that is currently refusing requests is never evicted, so junk keys cannot reset a blocked counter. If every entry is blocking, new keys are refused with 429 until entries expire (at most ten minutes); filling the table that way takes a limit's worth of requests per key, each passing the CAPTCHA for sign-in keys when it is on.
- **Recovery codes**: 10 codes of 80 random bits each, issued on activation and on replacement (which requires the current password and a current authenticator code and invalidates all earlier codes). Codes are checked against stored SHA-256 hashes; each code is marked used in the same transaction that signs in. The plaintext codes are displayed once, on the first `/totp` view within 10 minutes of issue; until then they are kept encrypted in `users.recovery_reveal` (AES-256-GCM, key derived from `SETUP_TOKEN`, so a copy of the database plus `SETUP_TOKEN` reveals them). That view deletes them. If it never happens, they are deleted by a background sweep that every running app process runs at startup and then once a minute, or earlier when the account opens `/account`, `/pgp`, `/admin` or `/totp` after the window. So the encrypted codes exist for at most about 11 minutes after issue while the app runs; if it is stopped they remain until it next starts, and a backup taken within that time contains them.
- **Image CAPTCHA** on `/login` and `/register` (not on first-run setup): six characters from a 30-character alphabet, drawn server-side as a same-origin PNG from a built-in 5×7 bitmap font with jitter, shear, wave and noise. Each challenge is bound to the browser's session or pre-login (`anon`) token, single-use (a wrong answer consumes it; the 400 answer to one is the same form again with the error and a fresh challenge, so no reload is needed without JavaScript) and expires after 10 minutes. Challenges are stateless (A-176): the id carries its expiry and a MAC over it and the session, and the answer derives from the id under the server key, so showing `/login`, `/register` or the image writes nothing to the database; posting an answer records the id in `captcha_spent`, and a second use of it is refused. There is no per-session issuance cap: a page view costs no database write, and at most 8 images render at once (more are refused with 503 and `Retry-After`). The image of a used, unexpired id can still be fetched (it is the same image); only its answer is refused. A challenge shown before the upgrade that introduced this is refused after it: reload for a new one. It is on for new and upgraded installations; administrators can turn it off or on from `/admin`, and each change is audited.
- **Sessions on `/account`** (A-157): the Sessions panel lists the account's live sessions (count, each one's start time to the minute in UTC; this browser's first, marked "This session", then the newest others, at most 20 listed and all counted, since a correct password spends no sign-in budget). A session row holds nothing about the client, so no IP address, device or browser is shown or kept. "Sign out everywhere" (POST `/revoke-sessions`) ends every session of the account, this one included, and every pending sign-in (so someone parked at `/challenge` after the password step cannot finish), deleting the pending sign-ins first (the `/challenge` lock order), and is audited ("Revoked all sessions: ended N session(s) and M pending sign-in(s)"). The panel says that this does not stop someone who knows the password, who can sign in again (with the second factor too, if one is on); only a password change stops them. There is no per-session sign-out: "Sign out" ends this browser's session only.
- **Password change** (`/account`, POST `/account/password`): needs the current password and, when TOTP is enrolled, a current authenticator code or an unused recovery code (spent). The new password follows the registration rule (12–72 bytes) and must be typed twice and differ from the current one; it is hashed with bcrypt at the application's cost before the transaction. The same transaction ends every other session and pending sign-in of the account and rotates the current session token, and is audited ("Changed password; ended N other session(s) …", with how it was confirmed). A sign-in whose password was checked before the change committed but that starts its session or reaches `/challenge` only afterwards is refused too ("Sign-in verification expired. Sign in again."): its pending sign-in, or the password-only sign-in itself, carries the password hash it was checked against, and the session starts only while the account still has that hash (A-157; the operator's `-reset-admin-password` gets the same effect). Wrong passwords and codes spend the per-account budget of 10 failed confirmations per ten minutes; a correct confirmation spends nothing (A-274).
- **Security notifications and sign-in records** (A-152): in the same transaction as the change, the owner gets one plain-text notification and one audit row for TOTP turned on or off, recovery codes replaced, a sign-in with a recovery code ("N remaining"; "TOTP turned off at sign-in with a recovery code (N remaining)" when it also turned TOTP off, A-154), the PGP key added, changed, renewed (A-155) or removed, key ownership proved and PGP sign-in turned on or off. After a correct password, the first failed second-factor check of a pending sign-in (a wrong, used or missing code, or a PGP code not yet requested) writes "Correct password but failed second sign-in step (TOTP | recovery code | PGP code)" and notifies the owner; later failures of the same pending sign-in add nothing, and the pending sign-in stays usable. The texts carry no code, secret, fingerprint, address or link and end "If this was not you, someone else may know your password: change it and contact the market staff." New "Signed in" rows name the method ("Signed in with password", "Signed in with password and TOTP", "… and recovery code", "… and PGP code"); rows written before this keep the plain "Signed in" and are not rewritten, so earlier signed exports stay byte-identical. The owner reading a notification does not stop someone who has the password: only changing it does.
- **Administrator second-factor reset** (`/admin`, POST `/admin/reset-factors`): for a user who lost their authenticator and recovery codes or their PGP private key. The administrator confirms with their own password (and authenticator code when enrolled; recovery codes are not accepted here). It turns TOTP off (clearing the secret, pending secret, step counter, recovery codes and any undisplayed codes) and PGP sign-in off, keeping the saved PGP key and its verification; ends the user's sessions and pending sign-ins; writes an audit row on both accounts naming the other side and what was turned off; and notifies the user, who then signs in with the password only. The form takes the account's handle (exact, case-sensitive), looked up on the server, so any account can be reset however many accounts exist; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle kept, before the password is checked. It is refused for the administrator's own account, for other administrators (403) and for accounts with no second factor (409). Beside the form, a collapsed list shows up to 100 non-administrator accounts that have a factor, by handle, and says it is capped.
- **Administrator second factors are reset only from the host** (A-137): `docker compose run --rm app -reset-admin-factors HANDLE` (`market.ResetAdminFactors`; no stdin, no web server), for an administrator with no recovery code left or whose TOTP secret became unreadable after a key rotation. Under advisory lock 782493, in one transaction taking the sign-in's lock order (pending sign-ins, recovery codes, account row), it does to the administrator what the web reset does to other accounts: TOTP off (secret, pending secret, step counter, recovery codes and any undisplayed codes) and PGP sign-in off, keeping the PGP key and its verification; sessions and pending sign-ins ended; the audit row "Second factors reset by host command: … turned off; ended N session(s) and any pending sign-ins"; and a notification. It refuses a non-administrator (pointing to the web reset), an unknown handle, an administrator with no second factor and a database recording migrations the binary does not include.
- **Account suspension** (`/admin`, POST `/admin/suspend`, *Suspend or restore an account*): contains a compromised or abusive non-administrator account. The administrator enters the handle (exact, case-sensitive, looked up on the server; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle and choice kept, before the password is checked), chooses suspend or restore and confirms with their own password (and authenticator code when enrolled). Suspending sets `users.suspended_at` (migration 011) and, in the same transaction, ends every session and pending sign-in of the account, writes an audit row on both accounts naming the other side ("Suspended account H; ended N session(s) and any pending sign-ins", "Account suspended by administrator A; …") and notifies the account. A suspended account cannot sign in: the password step answers "This account is suspended. Contact the market staff: <staff contact>." ("This account is suspended. Ask the operator of this market." while no staff contact is set, A-119) (403) only after the correct password, so a wrong password gets the usual "Invalid handle or password"; a sign-in challenge (TOTP or PGP) that was already pending is refused the same way when it would create the session; and a session row that still exists never authenticates. Suspending also holds the account's unsent payouts in the same transaction: `pending` and `blocked` payouts to it, and payouts the watcher holds for a re-confirming deposit, become `held` with an error starting "Suspended account:" (the audit rows add "held N unsent payout(s)"), and a payout queued for a suspended recipient (an order completed, cancelled or resolved in its favour, or a late refund queued by the watcher) is created held the same way; queueing takes a share lock on the recipient's account row, so a payout queued while a suspension is in progress is held too. /admin labels them "Held: account suspended — check the payout address before releasing". Neither restoring the account nor the watcher releases them (the watcher lifts only its own hold). An administrator releases one only with their password and an explicit "Payout address checked" confirmation (the release form shows the address); without it, or while the payout has no address (it gains one when the recipient saves it after being restored), the release is refused with 409 and nothing changes; the release is audited with the address and noted in the order history, and a deposit still below the threshold keeps it held as before. The suspension notice says how many unsent payouts it held. Restoring clears the flag, audits both accounts and notifies the account, which can sign in again; the notice says how many payouts to it stay held for the address check (A-120). Role, listings and orders are not touched: orders waiting on this account stop until it is restored; the other party can still complete, cancel where allowed, or open a dispute. To take away a vendor's listings, change the role instead. Suspended moderators and administrators are not resolvers or contacts: they are left out of the dispute and payment-review notifications, of the independent-resolver check (see *Disputes*) and of the order page's "Contact dispute staff" list, and count again once restored. Refused for the administrator's own account and for other administrators (403); suspending a suspended account or restoring one that is not suspended is answered 409 without change. A list under the form shows up to 100 suspended accounts, most recently suspended first, with the time.
- **Staff contact** (A-119; `/admin` *Staff contact*, POST `/admin/staff-contact`, settings key `staff_contact`, no migration): one administrator setting, free text (a handle, onion address or XMPP address) of at most 200 characters on one line (surrounding space trimmed; a line break, control or text-direction character, invalid UTF-8 or 201 characters → 400; saving the value in force → 409; empty clears it). It needs the administrator's own password (and authenticator code when enrolled; missing password → 400, wrong → 401) and is audited old→new ("Staff contact changed from (not set) to “…” (confirmed with password)"). It is shown as escaped text, never as a link, on `/canary` (*Staff contact*), in the suspended-account sign-in refusal, as the lost-factors line on `/challenge` ("Lost your authenticator and recovery codes? Only a market administrator can turn your second factors off, or, for an administrator account, the operator on the server."; "Lost your PGP key?" for a PGP-only account; `/challenge` does not know the role before sign-in, so it names both the web reset and the operator's `-reset-admin-factors`, A-289), as "Can’t read the image?" help beside the CAPTCHA on `/login` and `/register`, in the expired-key refusal on `/challenge/pgp` (A-155) and the unreadable-key refusal on `/login` (A-272), and under every notification that tells its reader to contact the market staff (the payout-address change notice, A-102, among them): "Contact the market staff: <contact>." Unset, each says "Ask the operator of this market." When the contact is exactly the handle of a moderator or administrator who is not suspended and whose key can receive encrypted messages (the A-83 check), a signed-in reader other than that person also gets a *Send <handle> an encrypted message* link to `/messages?to=<handle>`; signed-out readers (and the plain-text refusals) get the text only, since they could not use it. Since A-279 it is also named with a taken-down listing (the vendor desk card and `/listing-edit`, with the link under the same rule, and the plain-text restore 409: "… If you think this is wrong, ask an administrator to review it. Contact the market staff: <contact>."), in the malware-scanner refusal of a flagged photo ("… send the market staff this reference. Contact the market staff: <contact>. Reference: <ref>") and in the `/totp` notice after a sign-in with the last recovery code; these plain-text lines carry no link. Tests: `staff_contact_test.go`, `tests/e2e/db-staff-contact.spec.ts`, `preview-auth.spec.ts`, `preview-transparency.spec.ts`.
- **Role changes** (`/admin`, *Assign an account role*) take the account's handle (exact, case-sensitive), looked up on the server, so any buyer, vendor or moderator can be changed however many accounts were created after it; an unknown handle, or an administrator's, is answered 404 with the admin page again, the reason in an alert and the handle and role kept. A collapsed list beside the form shows the 100 newest accounts and their roles. Role changes are recorded on both accounts: the administrator's row names the account and the old and new role ("Changed role of H from buyer to vendor"), and the account gets "Role changed from buyer to vendor by an administrator" in the same transaction. The admin audit trail shows the account each row is recorded on. Rows written before this change keep their original text ("Changed user role").
- **Administrators are added and removed only from the host** (A-156): `docker compose run --rm app -set-role HANDLE ROLE` (`market.SetRole`; no stdin, no web server) sets any role, including `admin`, under advisory lock 782493, so concurrent runs are serialized. It refuses an unknown handle, an invalid role, the role the account already has, removing the last administrator that is not suspended, making a suspended account an administrator and a database recording migrations the binary does not include. The account gets the audit row "Role changed from OLD to NEW by host command"; leaving vendor archives the listings and leaving staff removes the staff avatar, as on the web form; removing an administrator ends its pending sign-ins and sessions (taken in the suspension's lock order). A compromised administrator is contained by demoting it this way and then suspending it on the web ([operator guide](operator-guide.md#administrators)). Changes that run through `confirmedTx` (every password-confirmed administrator action, the payout address, PGP, TOTP enrollment, recovery-code and password changes, and the profile save) re-read the signed-in account's role and suspension from the account row they lock, so one authenticated just before a demotion or suspension is refused with 403 and changes nothing (`TestConfirmedActionRefusedAfterCallerDemotedOrSuspended`). Forms outside it do not re-check: admin forms that take no password (site name and role form, sign-in protection, operator key, canary) and turning TOTP off.
- Not provided: QR codes for enrollment (the secret and `otpauth://` URI are shown as text), an audio or other non-visual CAPTCHA alternative, WebAuthn/security keys, administrator-forced TOTP, and any password reset for a forgotten password (no email; administrators cannot reset passwords). Administrator lockout is recovered only by the operator on the host: a lost administrator password with `docker compose run --rm app -reset-admin-password <handle>`, lost administrator second factors with `docker compose run --rm app -reset-admin-factors <handle>` ([operator guide](operator-guide.md#authentication)). A CAPTCHA only slows automated sign-ups; it does not stop a determined attacker or a solving service.

### P2 PGP identity

- Profile keys are parsed with OpenPGP (`internal/market/pgp.go`); garbage, private keys, revoked keys and multi-key blocks are rejected, and so is a key in which a revoked user ID carrying only its revocation sits next to a revoked user ID that keeps its self-signature, a structure on which the OpenPGP library (go-crypto v1.4.1) dereferences nil (A-266; a minimal export with revoked user IDs, which carry only their revocations, is accepted). Such a key already stored is treated as unreadable everywhere ("No usable key" to others); the expiry sweep skips an unreadable key, or one on which the library panics, with the fixed log line "pgp expiry sweep: skipped one key that could not be read" and carries on, and a proof signature that makes the library panic is answered as not verifying (`TestKeyWithUnreadableUserIDsRefused`, `TestKeyExpirySweepSkipsUnreadableStoredKey`, `TestUnreadableStoredKeyPagesRender`, `TestProofSignedBySubkeyOfKeyWithoutUserIDSelfSignatureRefused`). A saved key that cannot be read never lets PGP sign-in fall back to the password alone (A-272): while PGP sign-in is on and the key cannot be read (or no longer matches its ownership proof), a correct password on `/login` either leads to `/challenge` asking for the authenticator code or a recovery code (TOTP enrolled; the PGP method is not offered) or is refused with 409 and no session or pending sign-in: "PGP sign-in is on for this account, but your saved PGP key can no longer be read …", that PGP sign-in is the account's only method, that an administrator can turn it off with *Reset a user's second factors* (for an administrator, whom that web reset refuses, only the operator's `-reset-admin-factors` is named), what to do after that, and the staff contact (A-119). A wrong password still gets "Invalid handle or password". After a correct password the owner is notified once per saved key (plain text: no key, fingerprint or code; not again until the key is changed; concurrent sign-ins send one, as the account row is locked first) that PGP sign-in could not be used (`TestUnreadableKeyRefusesPasswordOnlySignIn`, `TestUnreadableKeyWithTOTPSignsInWithAuthenticator`, `TestUnreadableKeyNoticeOncePerSavedKey`, `TestUnreadableKeyNoticeConcurrentCallsSendOne`). The key is stored as a canonical re-armor of its decoded packets: the packets (user IDs, signatures, subkeys) are unchanged, but text before or after the block, armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped. Keys saved before this are shown in the same canonical form wherever they are displayed (no rewrite migration; a stored key that no longer parses is handled as before), and saving the profile again stores the canonical form. Re-saving the same key, as pasted or as the canonical text the form shows, is not a key change: ownership proof and PGP sign-in stay and no confirmation is asked. The account page shows the fingerprint and the key's user IDs and, above the key field, who can see the key. Re-armoring does not remove user IDs, the creation time or third-party signatures from the key; the note tells users to use a key made only for this market. Only public key, public subkey, user ID and signature packets are accepted and published (A-110). A key carrying a photo ID (an OpenPGP user attribute packet, usually an image of the owner's face) is refused on `/account` before any password check, with the `gpg --edit-key <fingerprint>`, `uid <n>`, `deluid`, `save` steps to remove it; a key with any other packet type (a compressed packet or a private/experimental one can carry a photo ID that GnuPG still imports; keyring trust packets) is refused with a `gpg --armor --export <fingerprint>` hint. Nothing is saved. A key stored with such packets before this refusal is never shown with them: its canonical form keeps only the allowed packets, dropping the signatures that follow a removed packet except direct-key signatures and key revocations (every other packet unchanged, same fingerprint), and the owner saving the account form stores that form. If that form is not exactly one key with the same fingerprint (a skipped packet sat between a user ID or subkey and its signature), the stored key is treated as unreadable: others see "No usable key", never the broken key or its ownership proof. There is no rewrite migration.
- Ownership is marked **Verified** (with UTC date) only after the user signs a server nonce (clearsigned or armored detached signature) or decrypts a nonce the server encrypted to the key, on `/pgp`. Decrypt challenges store only the nonce's SHA-256. Changing or removing the key clears verification, PGP sign-in and any open challenge (renewing the same key may keep them, see *Renewing the same key*); every change is audited with the fingerprint. Adding, changing or removing the key and turning PGP sign-in on or off need the current password on every account (A-152), plus a current authenticator code when TOTP is enrolled (recovery codes are not accepted here), as turning TOTP off does: a stolen session can neither add a factor that outlives "Sign out everywhere" nor swap in the key buyers encrypt shipping addresses to. The audit row notes how the change was confirmed. Saving the profile with the stored key unchanged does not re-parse it, so an older key the parser now rejects does not block the form, unless it holds a photo ID or a packet outside the A-110 allowlist: that key is refused until the owner pastes an export without them or removes it with their password.
- Optional PGP sign-in verification (second factor), available only for a verified key that can receive encrypted messages. After the password, the user requests a one-time code (POST `/challenge/pgp`), decrypts it locally and submits it on `/challenge`; only its SHA-256 is stored and it is deleted with the pending sign-in.
- PGP sign-in code hashes are bound to the current key fingerprint and exact ownership proof. Replacing/re-verifying a key invalidates older codes, even if the original key is later restored. Sensitive password-confirmed changes serialize with TOTP enrollment.
- `/messages` rejects anything that is not an OpenPGP-encrypted message (plaintext, signed-only, malformed or fake armor). The pasted text must be exactly one armored PGP MESSAGE block with only whitespace around it; the whole base64 body is decoded and must be session key packets followed by exactly one integrity-protected encrypted-data packet that runs to the end, so text before, inside or after the block is refused. The server stores a canonical re-armor of those packets: armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped, never stored or shown. Each message shows "Encrypted (to recipient’s key)", "Encrypted (NOT to recipient’s key)" or "Encrypted (recipient unknown)", derived from the recipient key IDs in its packets compared with the recipient's saved key at send time. Messages stored before this check are inspected when displayed; their recipient match is reported as unknown. Messages stored as encrypted before the strict armor check are re-inspected when displayed and shown as not encrypted if they fail it; those that pass, and older messages found encrypted, are displayed as the canonical re-armor, so a stored armor header is never shown.
- Limits: the server cannot decrypt messages, so a key-ID match does not prove the contents (the bytes inside a well-formed encrypted-data packet are opaque to it); hidden-recipient and passphrase-only messages are "recipient unknown". Losing or letting the key expire locks PGP sign-in unless another factor is enrolled; an administrator can then turn PGP sign-in off for a non-administrator account (see P1 second-factor reset). When no code can be encrypted to the key, `/challenge/pgp` answers 409 saying so and naming what is left: the authenticator or a recovery code when TOTP is on, otherwise that PGP sign-in is the account's only method and an administrator can turn it off with *Reset a user's second factors* (for an administrator, only the operator's `-reset-admin-factors`), after which the owner renews the key (A-155).
- **Key expiry** (A-155): `/account` and `/pgp` show when the primary key and the encryption subkey expire (UTC date, "Never", or "Expired …"; for a key nothing can be encrypted to any more, the subkey that expired last). When encryption to the key stops within 30 days they say so with the renewal commands (`gpg --quick-set-expire <fingerprint> 2y`, and `… 2y '*'` for the subkeys); when nothing can be encrypted to the key now (`canReceiveEncrypted`) they say "Buyers cannot encrypt to this key" (A-225). Every running process checks all saved keys at startup and then once a day and notifies the owner once when encryption to the key stops within 30 days and once when it has stopped (the key or its encryption subkey expired), with the renewal commands and no fingerprint; `users.pgp_expiry_notice` records the notice per key and expiry, so each is sent once, also when sweeps overlap (a compare-and-set on that column), and a renewed or replaced key is warned about again (`TestKeyExpiryNotifiedOnce`, `TestConcurrentKeyExpirySweepsNotifyOnce`). A key that is signing only, revoked or unreadable gets no expiry notice. PGP sign-in can still be turned on for a key close to expiry; the dates and the notices are the warning.
- **Renewing the same key** (A-155): a pasted key with the saved key's fingerprint but different packets (a new expiry from `gpg --quick-set-expire`, a new user ID or subkey, a third-party certification) needs the password like any key change. It keeps the ownership proof and PGP sign-in, with the notice "Key updated: the same key (same fingerprint) with new signatures…", one owner notification and an audit row "Updated PGP key (same fingerprint …; ownership proof and PGP sign-in kept)", when every revocation signature (key, subkey or user ID) in the saved key is still in it and still revokes the same key, subkey or user ID as OpenPGP software reads the pasted key (A-261: a subkey or user ID revocation moved before the first user ID, where readers ignore it, or a revoked subkey or user ID left out, or an unrevoked copy of a revoked subkey added beside it, counts as a dropped revocation) and the encryption subkey it selects is the saved key's or one created no earlier (not a rollback to an older subkey). Otherwise it is saved as a changed key: proof, PGP sign-in and any open challenge are cleared, the change time is recorded, the owner is notified and `/account` shows an alert naming the missing revocation or the older subkey, never the plain "Profile saved." notice (`TestKeyExpiryShownAndRenewalKeepsSignIn`, `TestKeyUpdateThatDropsRevocationOrRollsBackSubkeyClearsProof`).
- Vendor pages and order pages show the other party's armored public key, grouped fingerprint and "Ownership verified YYYY-MM-DD" (UTC date only; the owner's `/account` and `/pgp` show the minute) only when a proof matches the saved key (otherwise "Ownership not verified"); a user without a usable key is named with a note that messages cannot be sent until they add one. A key is usable only if something can be encrypted to it now (A-68, one check, `canReceiveEncrypted` in `pgp.go`): not expired or revoked, with an encryption-capable subkey (or primary key) that is neither expired nor revoked. A saved key that has expired, is signing-only, or whose encryption subkey expired or was revoked is shown wherever a contact key is offered (vendor page, `/messages?to=`, order page, dispute staff contacts) as "No usable key", without its fingerprint or armored text; this is checked each time the page is shown, so a key that expires later stops being offered (`TestHuntUnusableEncryptionKeyShownAsUsableContact`). The owner's `/account` and `/pgp` pages say "Buyers cannot encrypt to this key" (A-225); the vendor's own order pages do not yet. On a paid physical order, the buyer's view of the vendor's key says "This key was changed or re-verified on YYYY-MM-DD UTC, after this order was placed — confirm with the vendor before sending your address" when the key was added, replaced or updated without keeping its proof (`users.pgp_changed_at`, migration 067) or its ownership was proved again (`pgp_verified_at`) after the order was created; a key last changed and proved before the order shows nothing, nor does the vendor's view (A-158, `TestVendorKeyChangedAfterOrderWarnsBuyer`). Keys changed before migration 067 have no recorded change time, so only a later proof or change is warned about; a renewal that keeps the proof (A-155) is not a change. Vendor pages are public, so a vendor's key is shown to anonymous visitors. Contact and message links open `/messages?to=<handle>` with the recipient filled in (values not matching the handle pattern are ignored); that page shows the key, fingerprint and verification of any existing handle to any signed-in account, whether or not they trade.

### P3 Orders

Implemented on the Foundation state machine; every action goes through the server-side transition table, row lock and compare-and-set, so a forbidden move returns 403, a stale or repeated one 409, and nothing reports success without a recorded state change.

- **Payment request** (`/orders/pay`, buyer, draft → awaiting payment): refused with 409 "Payment unavailable for BTC/XMR" unless a test-network wallet provider is configured for that currency; the order page shows the step as unavailable instead of a button. For a physical order it is also refused (409, before any stock is reserved or the wallet is asked for an address) while the vendor has no key that can receive encrypted messages (none saved, unreadable, expired or signing-only; the A-68 check), since the buyer could not send a shipping address (A-83). The order page then shows "Unavailable. This vendor has no usable encryption key, so you could not send your shipping address. Ask them to add one." instead of the button, and the listing's product and checkout pages say so; a draft can still be saved and paid once the vendor adds a usable key. Digital orders are unaffected. Vendors are not yet stopped from publishing a physical listing without a usable key (A-91) (`TestPhysicalPayRefusedWithoutUsableVendorKey`). On success the draft is repriced from the listing's current price, one unit of stock is reserved and the live provider's address is stored. No address is ever invented by the application. When the wallet returns an address the database already issued to another order (a wallet restored from an older backup or seed, A-288), the request is refused with 503 "BTC payment addresses are being restored on this market. Nothing was charged and your order is still a draft; try again later." (or XMR) and `Retry-After: 5`, without retrying: the draft keeps no address, reservation or event, one `payments:` log line names only the currency and the running count, and the *Payment providers* panel of `/admin` shows the count, the time of the last refusal and the runbook section "Restore the wallets" until an administrator dismisses it (audited; a dismissal made on a stale count is refused). Any other failure saving the address stays a 500 (`TestPaymentAddressCollisionRefusedAndReported`; fake wallet). A buyer may hold at most 3 orders awaiting payment (409 beyond that); the payment watcher cancels unpaid orders after `PAYMENT_EXPIRY` (see P5).
- **Cancellation** (`/orders/cancel`): buyer cancels a draft; buyer or vendor cancels an order awaiting payment (the system does when the payment window expires); vendor cancels a paid order. Reserved stock is returned. When confirmed deposits exist, the payment package queues a refund to the buyer (see P5). A vendor's cancel of a paid order needs the payout confirmation below.
- **Shipping** (vendor, physical, paid → shipped) with an optional note; **digital delivery** (vendor, digital, paid → delivered) with 1–32000 characters of content; **completion** (buyer, shipped/delivered → completed), which needs the payout confirmation below. The transition table also lists system completions (shipped/delivered → completed) marked escrow-only (`escrowOnly`, A-244): they are for per-order escrow, which is not built, so every order is pooled (`Order.Escrow` is always false) and the system cannot complete an order (403, `TestEscrowOnlySystemEdgesRefusedForPooledOrders`).
- **Payout confirmation** (A-161, A-122): completing, a vendor's cancel of a paid order and resolving a dispute each queue one payout, so their forms state it: the amount the payout would pay now (every deposit that is not a locked transfer and is credited or at the provider's confirmation threshold; credited only without a provider — the same rule the payout uses), the recipient's handle, the difference from the price and "(test network)"; the resolve form states both outcomes and each recipient's payout state ("no payout address: the payout waits for one", "account suspended: an administrator must check the address"), or "nothing counted yet; deposits confirming later go to the chosen party". Each form has a required confirmation checkbox (missing: 400, nothing changes) and a hidden `amount_seen`, compared with the amount counted under the payout's row locks: a different amount refuses the whole action with 409 "The amount changed to X — review again", so the order does not move and a dispute stays Open. Repeated or concurrent submissions still queue one payout.
- **Overpayments** (migration 064): a release pays the vendor exactly the price and returns the excess to the buyer as a second payout (`payouts.kind` `return`; at most one payout of each kind per order). Migration 069 (A-218) restores the database's one-settlement rule that 064 loosened: a release and a refund for the same order are refused (`payouts_one_settlement`, a unique index on `payouts(order_id)` for those two kinds), and migration 070 (A-276) refuses a refund beside a return (`payouts_refund_or_return`, for those two kinds), which would pay the excess twice, so an order has a release with at most one return, or one refund (`TestPayoutKindsPerOrder`; on a database that already holds either pair, the migration stops with an error naming the orders and changes nothing, `TestOneSettlementMigrationRefusesExistingClash`, `TestSettlementClashGuide`). UPGRADING.md section 14 settles such an order by hand: list its payouts with any return, check each in the wallet, delete the settlement that does not stand (a release always together with its return; a cancelled order whose return alone was sent keeps that sent row as its refund, with an order-history note of the price sent by hand) and check that no order keeps a release and a refund, a refund and a return, or a return without a release (`TestSettlementClashGuide` runs that SQL). Migration 073 (A-268) refuses a return without a release: the constraint trigger `payouts_return_needs_release`, deferred to commit (so one transaction may insert a release and its return in either order), refuses any transaction that leaves an order with a return and no release, whether it inserted, deleted or changed the kind or order of a row, naming the order and changing nothing; it checks only the orders a row entered or left, through 064's unique index, under one transaction advisory lock so that two transactions changing either side of one order check one after the other (`TestReturnNeedsRelease`, `TestReturnGuardSerializesConcurrentCommits`). The application queues a return only together with its release, and its other payout writes (holds, releases, requeues, moves, *Mark sent*, sends, the restore script) change only a payout's state, address, error or transaction ID, so the trigger never refuses them. On a database that already holds a return without a release the migration stops naming the orders and changes nothing; UPGRADING.md section 18 settles each (restore the release held for an administrator, or record it as paid, for a completed order; record a sent return of a cancelled order as its refund, or delete an unsent one) and `TestReturnWithoutReleaseGuide` runs that SQL. Both relabels of a sent return as the refund add, in the same transaction, an order-history note both parties read (A-312): "Refund recorded by hand (UPGRADING.md section 14/18): the overpayment returned to the buyer earlier is this order's refund, and the remaining AMOUNT was sent to the buyer by hand from the market wallet in transaction TXID."; the operator supplies the amount and transaction ID as psql variables, and a missing, empty or malformed one stops the block with nothing changed (both tests run those blocks through `psql` as written; without `psql` they skip locally and fail on CI). An excess below the minimum automatic payout (0.0001 BTC, 0.001 XMR) is not returned and goes to the vendor with the release, and both parties are told. A refund or return larger than the order price is held (`Larger than the order price:`) as a likely mistake and administrators are notified; a refund is held when it exceeds the price, a return only when the excess itself exceeds the price. Refunds and returns up to the price are sent automatically (pay and cancel, underpaid expiry, cancel then send), so the pooled wallet can be used to swap coins up to a listing's price without review (`TestRefundUpToPriceIsNotHeld`). Releasing a held one on `/admin` needs the password and an explicit "reviewed" confirmation (409 without), and a suspension of the recipient keeps the hold after its own text, so both checks are needed. Every payout, releases included, is sent with the network fee taken from the amount (Bitcoin `subtractfeefromamount`; Monero `transfer` `subtract_fee_from_outputs`, for releases since A-232), so no payout on either coin spends the market's funds on its fee: paying and being paid back, or a vendor buying its own listing, costs the market nothing in fees (the request is tested: `TestMoneroReleaseSentWithFeeFromAmount`, `TestMoneroReleaseTransferSubtractsFee`; on the real local chains at `1c62647` every Monero payout, releases included, arrived as its amount less the fee, [evidence table](verification.md#evidence-table)). The order page's payout panel, the complete, paid-cancel and resolve statements ("network fee deducted"), the Overpaid alert and `/admin` *Payouts* say so, as do the order-history notes and notifications that state a payout's amount when it is queued, held, blocked or sent, an administrator's release, requeue or move of a payout and the move notification (A-270), the kept or held excess notices and the underpaid-expiry refund notice ("the network fee is taken from …", A-250; `TestMoneroReleaseSentWithFeeFromAmount`, `TestSubFloorXMRPriceOverpaymentIsHeld`, `TestSmallExcessStaysWithVendor`, `TestAdminPayoutNotesStateTheFee`; notes and notifications stored earlier are unchanged). An administrator's *Mark sent* note makes no fee claim (a payout paid by hand may have had the wallet pay its fee). A cancel of a paid order refunds every deposit (held when above the price); a dispute resolved as a refund returns everything to the buyer, one resolved as a release splits as above. When the counted deposits of a paid, shipped or delivered order exceed the price, both parties' order pages say what completing does with the excess, and the complete, paid-cancel and resolve forms state each payout (`TestSplitPayoutRules`, `TestOverpaymentReturnedToBuyer`, `TestSmallExcessStaysWithVendor`, `TestLargeReturnHeldUntilAdminReview`, `TestSuspensionKeepsLargeHold`, `TestRestoreKeepsLargeHold`, `TestRefundIsSentWithFeeFromAmount`, `TestRefundUpToPriceIsNotHeld`, `TestPayoutKindsPerOrder`, `TestMoneroRefundSubtractsFee`, `TestOverpaidOrderPagesWarnBothParties`; the browser journey in `wallet-journey.spec.ts` pays one BTC order one and a half times its price through the production adapter and the simulated wallet RPC and checks that exactly one release of the price and one return of the excess are sent, and nothing more after further watcher passes (A-313); fake wallet and simulated wallet RPC only).
- **Payment QR code**: while an order awaits payment and something is still due, the buyer's order page shows an inline SVG QR code (server-rendered with `rsc.io/qr`, error correction M; no JavaScript, allowed by the page's CSP) for the wallet payment request of exactly the remaining amount: `bitcoin:<address>?amount=<BTC>` (BIP21) or `monero:<address>?tx_amount=<XMR>`, with the request also shown as text. Deposits seen, confirmed or not, are subtracted, so the code never asks for more than is due; once the full amount is seen it is not shown. Nothing else (no label or message) is encoded (`TestPaymentURI`, `TestQRSVGMatchesEncoding`, `TestOrderPageQRForAmountDue`). The rendered codes for a testnet and a mainnet Bitcoin request and a Monero subaddress request were decoded back to the exact request by an independent decoder (jsQR) from a Chromium screenshot during development; that check is not in CI and no log of it is kept. The caption tells a buyer whose browser shows no code to copy the address and amount above it.
- **Automatic delivery**: when the payment watcher marks a digital order paid and the listing has delivery content, the content is recorded and the order moves to delivered as the system actor in the same transaction.
- Delivery content is stored **unencrypted** in PostgreSQL, is written only in the same transaction as the delivered transition, and is shown only to the order's buyer and vendor, and read-only to moderators and administrators once the order is disputed.
- **Disputes** move a paid, shipped or delivered order to disputed. Opening one notifies every moderator and administrator who is not a party to the order and not suspended (the parties get the usual state-change notice). If every moderator and administrator who is not suspended is a party, the dispute is still accepted: a system note in the order history records that no independent resolver was available, every administrator is notified that it needs a moderator who is not a party, and the moderation desk shows administrators a "No eligible resolver" note on it while that remains true. **Resolution** requires an outcome (release to vendor or refund to buyer) and a written decision, and is refused to a moderator or administrator who is party to the order. It also needs the resolver's current password, and an authenticator code when TOTP is enrolled (A-32; the same `confirmedTx` step-up as the other staff actions, which also re-reads the resolver's role and suspension): resolving queues a payout that the payment watcher sends by itself, so a hijacked session or a mis-click is not enough. Without the password it is refused (400 "Enter your current password to confirm this change."), with a wrong password or code 401, and nothing changes (the order, the dispute, payouts, order history, audit and notifications); the audit row says how it was confirmed ("Resolved dispute on order … (outcome: refund) (confirmed with password)"). Moderators and administrators who are not parties still resolve disputes (`TestResolveNeedsPasswordStepUp`; browser: `wallet-journey.spec.ts`). The outcome is recorded before the resolved transition so payment hooks can act on it. Resolving as a refund queues one refund of the whole counted amount to the buyer; resolving as a release pays the vendor the price and returns an excess worth sending to the buyer, as completing does (see *Overpayments*). A refund or return larger than the price waits for an administrator's review; the payment watcher sends the rest automatically. The decision is stored unencrypted and read by both parties; its field says so and never to quote an address, real name or tracking number.
- **Dispute reply** (A-124; POST `/disputes/reply`): while a dispute is open, the party who did not open it (the actor of the move to disputed) may put one reply of 20–5000 characters on record from the order page. It is stored once as a disputed → disputed `order_events` row (note "Dispute reply: …"; no state change, the transition table is not involved) and shown under Dispute on the order page to both parties and staff reviewers, and on `/disputes` and the moderation desk, labelled with its author's role; the history entry says only that a reply was made. The reason, reply and decision keep their line breaks (`white-space: pre-wrap`). The opener is refused (403), a second reply, a reply after resolution, on an order with no dispute or on a dispute with no recorded opener are refused (409), and nothing is written; the dispute row is locked first, so concurrent replies store one. The dispute-opened notice to the other party says it may reply. The form carries the same stored-unencrypted warning as the other plaintext fields, and first points to encrypted messages to dispute staff when one of them has a usable key (or says none has). The resolve form says whether the other party replied, and carries what it showed (`reply_seen`): once a reply is on record, `/resolve` refuses a form that did not show it (or does not say) with 409 and the moderation desk again, showing the reply, the reason in its alert ("The vendor replied to this dispute after the form was loaded. …") and the typed decision kept, and nothing changes; the check runs under the dispute row lock the reply takes, so a reply racing the decision is either seen or refused (A-280; `TestDisputeCounterpartyResponse`, `TestResolveRefusesFormLoadedBeforeReply`; browser: `db-disputes.spec.ts`).
- **Evidence holders** (A-162): the resolve form and desk entry of each open dispute list, for staff who are not party to it, the moderators and administrators each party messaged since the dispute opened, with the count and the latest time ("Buyer → mod_a (2, latest …)", "Vendor → none"; a holder suspended since is labelled "mod_a (suspended) (2, latest …)", A-280; one removed from staff after the message, as its role-change audit row records, stays listed as "mod_a (no longer staff) (2, latest …)" counting only the messages sent before the latest such change, A-294, A-304), read from message metadata only; a party's own staff account is never listed as a holder (A-285) (never a body or ciphertext); the resolve help says to ask those holders before deciding, or that neither party messaged a current moderator or administrator, nor one recorded as removed from staff after being messaged. The parties' "Contact dispute staff" panel says other staff can see which staff member they messaged and when, never what (`TestDeskShowsWhoHoldsDisputeEvidence`). The role-change rows are read through the partial index `audit_events_role_change` (migration 072, A-301), not by scanning the audit log (`TestDisputeEvidenceReadsRoleChangesByIndex`).
- **Verified reviews**: one per completed order, by its buyer, rating 1–5 and up to 2000 characters. Product and vendor pages label them "Verified purchase" because each is keyed to a completed order; reviewer handles and order ids are not shown publicly and dates are shown by month.
- **Hiding reviews** (A-125; POST `/admin/review`): administrators can hide a review, for example one that exposes a vendor's identity, and restore it. An administrator viewing a product or vendor page gets *Hide this review* under each review (a `<details>` form; no ID is typed), confirmed with their own password (and authenticator code when enrolled). A hidden review is kept (`reviews.hidden_at`, migration 031): it is left out of the public list and of the rating average and count on both pages; the buyer and vendor still see it on the order, labelled "Hidden from the listing and vendor pages by an administrator". Administrators see hidden reviews on the product and vendor pages labelled "Hidden by an administrator", with a count of hidden reviews and a *Restore this review* form, which works the same way. Both actions are audited on the administrator ("Hid review of order <8-character order ID> (confirmed with password)", "Restored review of order …") and on the reviewer ("Review of order … hidden by administrator <handle>"), and the reviewer gets a link-free notification; none of them copies the review text. Hiding a hidden review or restoring a public one is answered 409 without change; an unknown review 404; moderators, vendors and buyers 403 (reviews are content moderation, an administrator power like suspension and listing edits; moderators handle disputes and payment reviews). There is no report-a-review button: someone who wants a review hidden contacts the market staff. Tests: `review_hide_test.go`, `tests/e2e/db-review-hide.spec.ts`.
- Order pages show the full transition history (actor and time), the moves available to the viewer, the dispute reason, the other party's reply and the decision, the other party's PGP key, and the delivery and review panels. Orders, vendor desk and moderator desk list the relevant orders with their state; the moderator desk links each dispute to its order page. Open work is never hidden by a row cap: the moderation desk and the disputes page list every open dispute (oldest first) before the 100 most recent resolved ones, the vendor desk lists every paid order on the vendor's listings (oldest first, counted in "To fulfil") before the 100 most recent other orders, and each page says when older history is not shown. The disputes page offers every paid, shipped or delivered order for a new dispute. The orders page, messages and notifications still show only the 100 most recent rows. There is no admin order list (A-127): staff see an order only while it is disputed or resolved or a payment on it is flagged for review ([What the server keeps](#what-the-server-keeps)).
- Moderators and administrators not party to an order can open its page read-only while it is disputed or resolved (summary, history, dispute, delivery record, payment ledger), and while any of its deposits is flagged for payment review (summary, history with the flag notes, payment ledger; digital delivery content stays hidden unless the order is disputed). No buyer or vendor action renders for them and the order actions return 404. Any other order stays 404.
- **No shipping address field.** For a paid physical order the buyer is prompted to send the address as a message encrypted to the vendor's key; the vendor is told to check Messages. If the vendor's key stopped being usable after payment (expired or removed), the buyer sees "No usable key" in place of that prompt, with a warning never to send the address unencrypted: message the vendor or open a dispute (`TestPaidOrderVendorKeyStopsBeingUsable`). The market keeps that encrypted message (and who sent it to whom and when) but cannot read it. It cannot stop an address being typed into a plaintext field: the vendor's note to the buyer, the cancellation reason, the dispute reason, the dispute reply and the review text are stored unencrypted. Each of those fields says so, who can read it (the other party; moderators and administrators when the order is disputed or a payment on it is flagged, or every moderator and administrator for a dispute reason or reply; the public, and the vendor with the buyer's handle, for a review; the operator and backups), and never to include an address, real name or tracking number but to send them encrypted from the order page. The help is tied to its field with `aria-describedby`.

Limits: service listings have no ship/deliver step, so a paid service order can only be cancelled by the vendor or disputed. There are no auto-completion timers. Moderators cannot see the parties' messages, which are encrypted to the recipient's key (a resolver sees only whom each party messaged since the dispute opened, and when); parties must describe evidence in the dispute reason or the other party's one reply, which are stored unencrypted and read by the other party, or send it (and anything identifying, such as an address) as an encrypted message to an independent moderator or administrator from the order page's "Contact dispute staff" keys, which both dispute forms point to (suspended staff are not listed).

### P4 Inventory

- Vendors edit their own listings at `/listing-edit?id=` (title, description, category, region, fulfillment type, stock, BTC/XMR reference prices, optional automatic delivery content). Administrators may edit any listing except its automatic delivery content: an administrator editing another vendor's listing sees only whether content is set ("only the vendor can view or change it"), their saves keep the stored content whatever the form sends, and changing such a listing to physical is refused (400) while content is stored. The audit log records "as administrator". Other vendors get 404.
- Create and edit share one validator. Only `physical` and `digital` fulfillment are accepted: the order state machine has no fulfillment step for a `service` kind, so the form no longer offers it. The Bitcoin price must be at least 0.0001 BTC (10,000 satoshi) and the Monero price at least 0.001 XMR (since A-232), the minimum automatic payouts (see *Minimum payouts* under P5), otherwise 400 with the reason; the forms say so. Listings priced lower before this rule keep their price until edited; an edit must raise it. Until then they take no new orders in that currency (A-216, A-232): a draft, or a payment request on a draft saved earlier, is refused with 400 naming the minimum before any stock is reserved or the wallet is asked for an address (after the paused-intake and no-wallet reasons); orders in the other currency on the same listing are unaffected (`TestLegacySubFloorListingRefusesBTCOrder`, `TestLegacySubFloorXMRListingRefusesXMROrder`). An order already placed at such a price is paid out as described under *Minimum payouts*.
- Archive/restore (`/listings/archive`, `/listings/restore`): archived listings disappear from the catalog, search, checkout and vendor pages, and new order drafts are refused (400). The owner still sees them on the vendor desk with an "Archived" badge. Existing orders are not changed. The product page of an archived (or taken-down) listing answers 404 except to whoever may read an order placed on it, by the order page's rule: its buyer and vendor, and moderators and administrators while that order is disputed or resolved or has a flagged payment (A-164). They see the listing as it is now with an "Archived" badge, no order-draft link and no delivery content (never the takedown reason); its photos are shown there on the signed-in `/desk/img` route under the same rule, while the public image route still refuses them (A-264). The order page links to the listing ("Listing as it is now; it may have changed since purchase"), as do the moderation desk's dispute entries and payment-review rows, the `/disputes` entries and the vendor desk's incoming-order rows, for whoever may open the order (A-265, `TestDeskOrderRowsLinkTheirListing`); no snapshot of the listing at payment is kept yet (A-58).
- **Listing takedown** (A-163; POST `/admin/listing`): an administrator archives another vendor's listing only by taking it down from its edit page (*Take down listing*, a `<details>` form), with a reason of 10–500 characters (after trimming, with no NUL byte; otherwise 400) and their own password (and authenticator code when enrolled). The plain archive answers an administrator 400 on another vendor's listing; an administrator's own listing is archived from the vendor desk as usual. The reason is stored unencrypted in `products.admin_archive_reason` (migration 041; non-NULL only while archived) and shown to the vendor on `/listing-edit` and on the vendor desk card ("Taken down"), never on public pages. Both accounts are audited with the reason ("Took down listing <8-character ID> of <vendor>: …", "Listing … taken down by administrator <handle>: …") and the vendor gets one link-free notification with the listing's title, the reason and what it means. The vendor can still edit the listing, but their restore is answered 409 quoting the reason and telling them to ask an administrator to review it, with the staff contact (A-119, A-279), as the vendor desk card and the edit page do; the takedown notification shows it under it on `/notifications`; an administrator's plain restore is 409 as well. Only the administrator's *Restore listing* form, confirmed the same way, clears the reason; like every restore it is refused (409) when the owner is no longer a vendor, and it share-locks the owner's account row so a concurrent role change is not missed (A-70). Archiving by a role change never sets a reason. While a listing is taken down, a payment confirmed on one of its digital orders leaves the order paid instead of releasing the automatic delivery content, with the history note "Not delivered automatically: an administrator took this listing down…"; the vendor delivers by hand or cancels and refunds. Other roles get 403. Tests: `listing_takedown_test.go`, `tests/e2e/db-listing-takedown.spec.ts`.
- Changing a vendor's role to buyer or moderator archives their active listings in the same transaction (audited for the administrator and the account). Listings whose owner is not a vendor or administrator refuse new drafts (400), payment requests (409) and restores (409); existing orders continue and the former vendor can still fulfil them.
- The fulfillment type cannot change while the listing has open orders (409), because orders read it from the listing. A draft takes the current price when it is resubmitted and again when payment is requested; from then on the order keeps that price.
- Stock edits are refused (409) when stock changed after the form was opened (payment requests reserve stock); saving other fields keeps the current stock.
- Automatic delivery content is digital-only, at most 32000 characters, **stored unencrypted in PostgreSQL**, and never loaded on public pages. It is released only by the order package's confirmed-payment step, so the editor says "Automatic delivery requires a payment provider" whenever no provider is configured.
- Migration `040_inventory.sql` adds `products.updated` and `products.archived_at`; `041_listing_takedown.sql` adds `products.admin_archive_reason`.

### P5 Payments

Implemented, **test networks by default, mainnet as an operator opt-in** (disabled unless configured; see [feature configuration](operator-guide.md#feature-configuration) and [Mainnet](operator-guide.md#mainnet)):

- Bitcoin Core adapter (testnet3, testnet4, signet, regtest, and mainnet with `BITCOIN_CHAIN=main`) over wallet JSON-RPC with Basic auth, and a monero-wallet-rpc adapter (stagenet, testnet, and mainnet with `MONERO_NETWORK=mainnet`) with HTTP Digest auth. Startup exits with an error when a node or wallet reports mainnet without that setting or `BITCOIN_CHAIN`/`MONERO_NETWORK` (blank = any test network) disagree with the node. A market is all mainnet or all test networks (a mix stops startup), and startup refuses a database whose deposit addresses were issued on the other class of network (`checkNetworkHistory`, from `payment_addresses.provider`). On a mainnet market every page, badge, order note and notification says `MAINNET` and "real funds" (`TestLiveMarketLabelsAndHistory`, `TestInitPaymentsLiveMarket`, `TestBitcoinMainnetOptIn`, `TestMoneroMainnetOptIn`; fake and simulated wallet RPC only — no mainnet run is recorded). An unreachable node or a wallet that is not loaded/open leaves that currency unavailable (payment requests refused, error on the admin page) and is checked again at the start of every watcher pass, which also reloads/reopens wallets after a node restart; a node that reports another network after startup disables its currency. Passes skip a currency while its node is syncing, or while its tip is below the highest tip the watcher has recorded for that currency (`payment_status.tip_height`, migration 056; Bitcoin `getblockchaininfo` `blocks`, monero-wallet-rpc `get_height`), as after a node restarted or restored from an older state or a wallet rescanning: nothing is read, recorded or announced until it catches up, and the admin page shows the reason. An order never expires unless its address was read from the wallet in the same pass. Wallet-returned addresses with another network's prefix are refused.
- Administrators independently pause/resume new BTC and XMR payment addresses with password/TOTP confirmation and audit. Existing monitoring, top-ups and payouts continue. Migration 052 persists this intake policy. The order panel shows the remaining amount after valid confirmed and unconfirmed receipts; enough unconfirmed funds prompts waiting instead of another payment.
- One background watcher per deployment (PostgreSQL advisory lock) polls every `PAYMENT_POLL_INTERVAL`. Deposits are recorded in an idempotent ledger keyed by `(currency, txid, output)`. An order moves from `awaiting_payment` to `paid` only through the state machine, once confirmed deposits reach the order amount at the configured confirmation threshold. Each pass reads the deposit address of every order awaiting payment and of every funded order that is not yet settled (`paid`, `shipped`, `delivered`, `disputed`), however long ago it last changed, plus terminal orders changed in the last 24 hours, every order with a payout waiting to be sent or held (by the watcher, or by a suspension or a restore from backup, so the ledger an administrator's release is checked against stays current) whatever its age, and the late-deposit window below. A payout is sent only in a pass that read its order's deposit address from the wallet and applied it to the ledger without error, and the send claim re-checks that ledger; a payout released while a pass runs (payout address saved, administrator release or requeue) for an order that pass did not read waits for the next pass.
- **Deposits after funding**: a deposit first recorded while its order is paid, shipped, delivered or disputed (not a locked transfer) is announced once: an order-history note (state unchanged, system actor) and a notification to the buyer and the vendor give its amount, labelled `TESTNET` (`MAINNET` on a mainnet market), and say that, if it has the confirmation threshold, as last recorded by the market, when the order is completed, cancelled or resolved, it is included in the order's settlement (a release with any excess returned, or a refund), and otherwise is not paid out automatically (a confirmation seen later is flagged to moderators, see Late deposits). Repeated passes add nothing (migration 054 adds `payments.late_notice`). The payout amount rule is unchanged: one payout per order, paying every credited or threshold-confirmed deposit. The payout is exactly the deposits it marks credited: they are row-locked while it is queued, so a deposit that confirms or conflicts at that moment is either paid and credited (and holds the payout if it conflicts) or left out and flagged if it confirms. When the currency's provider is configured but unavailable in that process (for example after a restart while its node is down), the payout still applies the configured threshold to the confirmations last recorded by the watcher, and a credited deposit recorded below it holds the payout. Nothing is sent until the provider is working again, and, as with a working provider, a credited deposit later found conflicted or below the threshold holds the unsent payout. With a disabled or unconfigured provider only deposits already credited count.
- **Credited deposit regressions**: a credited deposit that the watcher reads back below the confirmation threshold (conflicted or missing from the wallet, or at a lower depth after a reorg, including 0 confirmations) while its order is not closed or any of its payouts is not yet sent (a release sent while its overpayment return is still unsent counts as unsent, A-213) is announced once per episode: one order-history note (system actor, state unchanged, ending "Moderator review required."), a notification to the buyer and the vendor, and a "Payment review needed" notification to every moderator and administrator not party to the order and not suspended; the deposit is flagged, so staff can read the order and it is listed for payment review. The order is never reverted automatically, and unsent payouts are held (a payout queued later starts held). When the deposit reaches the threshold again the episode ends, the watcher lifts its own hold, whatever the age of the order and its address, and a later regression is announced again (migration 056 adds `payments.regress_notice`). A regression on a closed order whose payouts were all sent is not announced (if the deposit was flagged in an earlier episode, the desk shows its current reason among the other flags). While a credited deposit of the order is conflicted or missing (not merely re-confirming), the recipient of a payout the watcher holds reads "Held for review … market staff review it" and the other party "market staff review it", not that it is released by itself: a double-spent deposit never confirms again (`TestRegressionAfterReleaseSentFlagsUnsentReturn`, `TestRegressionAfterEveryPayoutSentIsNotAnnounced`). An order is read for this only while it is in the watch set above: a regression on a closed order whose address is more than 30 days old, last changed more than 24 hours ago and whose payout is blocked (no payout address) is found (and announced) in the first pass after the recipient saves an address, before anything is sent. The vendor is not prevented from shipping; the notification tells both parties the payment is not final until the deposit confirms again, and the order page shows the regression.
- **Payment window**: an order awaiting payment whose address is older than `PAYMENT_EXPIRY` (default 24h) with no deposit seen (conflicted or locked ones do not count) is cancelled by the watcher as the system actor ("payment window expired") and its stock is returned. An order with a deposit still confirming stays open. An underpaid order (every deposit confirmed, together short of the price) whose address is older than the window and whose last deposit arrived more than the window ago is cancelled the same way ("payment window expired underpaid: X of Y received"); the payout hook refunds its confirmed deposits to the buyer and the buyer is notified. The notification says which case applies (a refund of the amount queued, a refund waiting until the buyer saves a payout address, or below the minimum automatic payout: not refunded, staff notified) and that anything sent to the address after the cancellation is not refunded automatically; below the minimum, the order page's payment status reads "<amount> received, below the minimum automatic payout of <minimum>; not refunded; market staff were notified". While the order awaits payment, its page (buyer and vendor) states "If the order is still unpaid or short at <YYYY-MM-DD HH:MM UTC>, it can be cancelled; a new deposit moves this time; anything sent after cancellation is not refunded automatically.", computed at render from the watcher's inputs: the later of the address's issue time and the latest deposit that counts (not conflicted, not locked), plus `PAYMENT_EXPIRY`, truncated to the minute. A deposit still confirming postpones the cancellation, and the watcher acts only on a pass that read the wallet, so it can come later. The page's help says confirmed deposits are refunded to the buyer's saved payout address unless together they are below the minimum automatic payout (named), which is not refunded automatically and is flagged to staff (A-123, A-233(c); `TestAwaitingPageStatesCancellationTime`, `TestSystemAndModeratorTransitionsNotifyReason`). The parties' cancellation notification carries the reason ("Order x is now Cancelled — payment window expired" or "… expired underpaid: X of Y received"). Cancelling an order awaiting payment that has a deposit states the refund on the form and needs its confirmation and `amount_seen`, like a paid cancel (409 when a deposit arrived after the page was shown or the counted amount changed) (`TestUnderpaidOrderExpiresAndIsRefunded`, `TestUnderpaidOrderWithDepositConfirmingStaysOpen`, `TestUnderpaidExpiryWithoutPayoutAddressBlocksRefund`, `TestUnderpaidExpiryBelowRefundFloorIsFlagged`, `TestCancelUnderpaidOrderStatesRefund`, `TestCancelOrderWithConfirmingDepositStatesLaterRefund`, `TestCancelOrderWithoutDepositNeedsNoConfirmation`; fake wallet only).
- **Late deposits** (A-211, A-106): every cancelled, completed and resolved order's address is read for 30 days after it was issued, whatever the order's deposits. A deposit first recorded after the order closed (`payments.after_close`, migration 065) is never counted toward the order's settlement or refunded automatically, even when nothing was refunded at the cancellation (an unpaid order cancelled at the end of the payment window, or an underpaid order below the minimum automatic payout). A deposit recorded before a cancellation that confirms after it is refunded when the cancellation refunded nothing (blocked without an address) and the buyer is notified. Confirmed deposits that are not paid out (first recorded after the order closed, or confirmed after the settlement was queued on a completed, resolved or cancelled order) are flagged to moderators, never paid automatically. On the buyer's and vendor's order page such a deposit reads "Arrived after the order closed — not paid out; market staff notified" and is left out of the Confirmed figure (extra deposits on paid, shipped or delivered orders are still counted). One order note per watcher pass names the deposits it flagged; the buyer gets one notification naming the amount (no transaction ID; the vendor is not notified) and the staff one "Payment review needed" each, once per episode: an episode starts when the order has no such flag open and lasts while one is, so many small transactions give one notice each; once staff reviewed every such flag of the order (A-31, below), a later one is announced again. Cost: the watch set holds about 30 days of orders; each pass reads them in chunks of 200 (Bitcoin: one `listreceivedbyaddress` per chunk plus one `gettransaction` per transaction to those addresses; Monero: one `get_transfers` per chunk) and settles each in its own transaction; not measured at volume. Addresses older than 30 days are not polled for late deposits; they are read only while the order has a payout waiting to be sent or held, or changed in the last 24 hours (`TestLateTopUpAfterUnderpaidRefundIsDisclosed`, `TestLateDepositOnSettledOrderIsDisclosed`, `TestExtraDepositOnPaidOrderIsStillCounted`, `TestTopUpAfterUnderpaidExpiryOutsideDayIsRecorded`, `TestLateDepositFloodIsAnnouncedOnce`, `TestLateDepositAfterCloseIsHandled`; fake wallet only).
- **Locked Monero transfers** (non-zero `unlock_time`) are recorded and shown as "Locked transfer — not counted", never counted toward payment or payouts; the order history and moderators get one "locked transfer ignored" note and the buyer one notification (migration 051 adds `payments.locked`).
- **Payment-review flags**: "flagged to moderators" above means the deposit is marked `payments.flagged`, a system note ending "Moderator review required." is added to the order history, and every moderator and administrator who is not suspended is notified ("Payment review needed for order" plus the first 8 characters of the order ID; for a credited deposit regression or a payout below the minimum, staff who are party to the order get the buyer/vendor notification instead). The moderation desk lists flagged deposits under *Payment review*: every open flag first, oldest first and never cut, then the 100 most recently flagged others, with the count of others and a notice when older ones are cut. A flag is open while it has nothing that settles it and no recorded review: a locked transfer, a deposit received after settlement or after the order closed, or a deposit of a payout below the minimum until a payout includes it, or a credited deposit in an announced regression that has not confirmed again; one escalated to an administrator stays open, a reviewed one (no action or refunded by hand) is not listed. Each row shows the full order ID linking to the order, amount and currency, full transaction ID and output, flag time (the latest flag note for the deposit; "Not recorded" if none matches) and a reason from the deposit's current confirmations: "Credited deposit conflicted or missing", "Credited deposit below threshold (N of T confirmations)", "Credited deposit confirmed again (N confirmations)", "Locked transfer (unlock time), not counted or paid out", "Below the minimum automatic payout, not paid out" or "Deposit after settlement or after the order closed, not paid out" (the last two with "; now conflicted or missing" once it is). Staff not party to the order can open it read-only (see P3).
- **Payment-review dispositions** (A-31; POST `/moderator/payment-review`, `payments.disposition`, `disposition_note`, `disposition_txid`, `disposition_amount`, `disposed_at`, migration 066): each open flag on the desk has *Record the review* for a moderator or administrator who is not party to the order, confirmed with their password (and authenticator code when enrolled; the role and suspension are read again, A-156): *no action* (a 10–1000 character reason), *refunded by hand* (the refund's 64-hex transaction ID and the amount, at most the deposit; refused for a credited deposit, which its payout settles) or *escalate to an administrator* (moderators only; every administrator not party to the order is notified and only an administrator then records one of the other two). Nothing is sent and no payout row is written; a deposit refunded by hand is left out of every later payout (`payoutBasis`). Each review writes one order event (read by both parties; a refund's transaction ID is hidden from the vendor at render, as for payouts, A-214), one audit row and a buyer notification (with a refund's transaction ID, A-231). A reviewed flag leaves the desk; the buyer's deposit label reads "Refunded by hand on DATE: AMOUNT, transaction TXID" (the vendor's without the transaction ID) or, for a late deposit, "…; reviewed by market staff on DATE: no action" / "…; escalated to an administrator on DATE"; a late-deposit notice episode ends once every late flag of the order is reviewed (escalated ones keep it open). A second review of the same flag is refused (409), including one submitted at the same moment (the order and payment rows are locked and the disposition is written by compare-and-set, A-252), as is one by staff party to the order (403); buyers and vendors get 403. A credited deposit that regresses again after confirming is a new, unreviewed flag. There is no action that pays out a flagged deposit: refunds are sent by hand from the wallet ([runbook](testnet-runbook.md#handle-a-payment-review-flag)). Evidence: `TestPaymentReviewDisposition` (fake wallet, PostgreSQL) and `db-payment-review.spec.ts` (Chromium with JavaScript off, flags seeded in SQL; no wallet, so the order page lists no deposits and the browser test reads the outcome in the order history).
- **Minimum payouts** (A-99, A-232; `payments_hooks.go` `minPayoutBTC`, `minPayoutXMR`): a payout whose counted sum is below the minimum is never queued. Bitcoin: 10,000 satoshi (0.0001 BTC) for every release, refund and return, because `sendtoaddress` subtracts the network fee from the amount sent, so an amount at or below the fee can never be sent (on regtest 3,000 satoshi came out 6 satoshi negative after the fee; 5,000 was sent). The minimum removes that never-sendable class, not every failure: fees move, and a payout just above it can still fail and be requeued as before. Monero: 0.001 XMR for every release, refund and return (releases since A-232), an economic floor: every Monero payout has the fee taken from it (very roughly 0.00003–0.0001 XMR per transfer at the default priority, more when spending many small outputs), so below 0.001 XMR the fee would take several percent of it or more (`TestMoneroReleaseBelowFloorFlagged`, `TestDustXMRRefundIsFlaggedNotQueued`). Listings cannot be priced below either minimum (400 naming it: `TestListingRefusesBTCPriceBelowPayoutFloor`, `TestListingRefusesSubFloorXMRPrice`). Instead of a payout row, the order's counted deposits are flagged once (`payments.flagged` and `payments.below_floor`, migration 058): one order-history note naming the amount, the minimum and each deposit, ending "Moderator review required.", one notification to the buyer and the vendor that the payout "was not sent" and staff were notified, and one "Payment review needed" notification to every moderator and administrator not party to the order; later watcher passes add nothing. The order still reaches its final state and its deposits stay as they were (credited or not). The complete, paid-cancel and resolve forms say the payout is "below the minimum automatic payout … not sent automatically". If deposits recorded before the order closed confirm later and lift the sum to the minimum, the single payout pays all of them and the flag closes; a deposit first recorded after the order closed is never counted (see *Late deposits*). Payout rows queued below the minimum before this rule are unchanged. A listing priced below the minimum before its listing rule (0.0001 BTC before A-99, 0.001 XMR before A-232) takes no new draft or payment request in that currency (400 naming the minimum, nothing reserved, no wallet address; the other currency is unaffected: `TestLegacySubFloorListingRefusesBTCOrder`, `TestLegacySubFloorXMRListingRefusesXMROrder`). An existing order at such a price (A-216) cannot split an overpayment into the price and a return, because the vendor's share alone could never be sent: its whole counted sum is one release to the vendor. When the excess is more than the price, that release is held with the large-payout hold (`Larger than the order price:`; administrators are notified, and releasing it on `/admin` needs the "reviewed" confirmation), and both parties are told the release "includes … more than the price; the price is below the minimum automatic payout of 0.0001 BTC (or 0.001 XMR), so the amount paid over it cannot be returned separately"; the complete form and the release outcome of the resolve form state the same. An excess not above such a price goes to the vendor unheld with the release, as before (`TestSubFloorPriceOverpaymentIsHeld`, `TestSubFloorXMRPriceOverpaymentIsHeld`, `TestSubFloorPriceSmallExcessUnchanged`, `TestSplitPayoutSubFloorPrice`; fake wallet only). Tests: `payments_floor_test.go`, `payments_subfloor_test.go`.
- Payouts: completing an order queues a release to the vendor. Cancelling a funded order queues a refund to the buyer. Resolving a dispute queues a release or refund according to its recorded outcome. The transition and the payment watcher's retry both queue it through one dispatcher (`settleTerminal`, the only caller of `enqueuePayout`; `TestTerminalSettlementGoesThroughOneDispatcher`), which refuses an escrow order instead of paying it from the pooled wallet; no escrow orders exist, so every order is paid as described here. Each payout is a single wallet call, run on a context detached from shutdown and bounded to 30 s (ordinary wallet and node reads stay bounded to 10 s; no client or transport timeout cuts a send shorter): failed or stuck payouts are shown to administrators and never retried automatically. A failure is recorded as a definite wallet rejection (the wallet reported a pre-broadcast error: nothing was broadcast) or as ambiguous (timeout, dropped connection, unreadable reply after the request was sent, or a Monero error the wallet can raise after submitting: it may have been broadcast); failures recorded before this classification existed count as ambiguous. For Bitcoin every `sendtoaddress` JSON-RPC error is definite, because Bitcoin Core stores the transaction in its wallet before submitting it and does not return a failed relay as an error. For Monero only the `transfer` error codes that monero-wallet-rpc v0.18.5.1 raises before `commit_tx` submits the transaction are definite (-2 wrong address, -16 transaction not possible, -17 not enough money, -18 transaction too large, -19 not enough outputs to mix, -20 no destination, -37 not enough unlocked money); any other code, including -38 (no daemon connection, raised when `sendrawtransaction` times out after the daemon may have relayed), -4 and -1, is ambiguous; migration 055 reclassifies Monero failures recorded before this rule with any other code as ambiguous. This classification is from the wallet source and simulated wallet RPC tests; it has not been exercised against a daemon killed mid-send. It holds only for the pinned node images (A-100): `compose.nodes.yaml`, `.env.example` and the installer default to `bitcoin/bitcoin:31.1` and Seth for Privacy's `simple-monerod`/`simple-monero-wallet-rpc` `v0.18.5.1`, never `latest`; CI's Compose job fails on a `latest` or untagged default, and `tests/test_installer.py` fails if the tags disagree with each other or with the versions named in `payments_watcher.go`. Before a tag changes, `moneroPreSubmitCodes` must be re-verified against the new wallet source ([bump checklist](operator-guide.md#node-image-versions)). CI cannot see an operator's `.env` (installs from before A-100 wrote `latest` there), so the application checks the running wallet (A-174): every provider check (startup and each watcher pass) reads monero-wallet-rpc `get_version`, which reports the RPC interface version `(major<<16)|minor` and whether it is a release build, not the release. Only the answer v0.18.5.1 gives, 1.31 from a release build (`moneroVerifiedWalletRPC`), is verified; any other answer, a failed call, or a check that failed before reading it makes every Monero `transfer` JSON-RPC error ambiguous (`unverifiedWalletError`; the recorded error names the version), and `/admin` *Payment providers* shows "XMR wallet version not verified" with the version, notes that fee deduction on payouts is unverified too, and names the bump checklist; with the verified wallet nothing changes. A later release that leaves the RPC unchanged also reports 1.31 and is not detected. The same panel shows the Bitcoin Core version from `getnetworkinfo` (display only; the Bitcoin rule does not depend on it). Evidence: `TestMoneroWalletVersionGatesDefiniteSendErrors`, `TestBitcoinNodeVersionIsRecorded`, `TestUnverifiedMoneroWalletRecordsSendFailuresAmbiguous` (simulated wallet RPC, PostgreSQL) and the `wallet-journey.spec.ts` leg that switches the simulated wallet's version. Administrators can release a held payout, requeue a failed or stuck one, or mark one sent with its transaction ID (password-confirmed, audited, compare-and-set on the payout state). Requeueing an ambiguous failure, a failure restored from backup or a stuck send, or releasing a payout held by a restore from backup, is refused by the server unless the administrator also confirms that the wallet shows no broadcast transaction; that confirmation is recorded in the audit trail and the order history. `scripts/restore.sh` sets a persistent gate pausing all outbound payouts until complete wallet reconciliation and explicit SQL unlock; pending, sending, blocked and held rows receive manual recovery holds, and failed rows are marked possibly sent (a definite failure in the backup may have been requeued and sent after it); a hold for an account suspension keeps its text behind the restore marker, so its release needs both confirmations, and the script adds one audit row with the counts. Any other restore (volume snapshot, point-in-time recovery, manual `pg_restore`) skips all of this: UPGRADING.md section 6 gives the SQL to apply before starting the application, which also adds an audit row; the runbook's unlock SQL takes the administrator's handle, refuses an unknown one and audits the clear. Orders paid out after the backup come back with no payout row and also require reconciliation: the testnet runbook gives the ordered procedure and the SQL (exercised by `scripts/test-backup-restore.sh`) that records such a payout as sent and moves the order to its final state. A payout waits ("blocked") until the recipient saves a payout address, which is validated against the provider's network. **Recipients see their unsent payouts** (A-120): the *Payout addresses* panel of `/account` (`#payout`) lists every payout to the viewer that is not sent (blocked, held, queued, sending or failed), oldest first and uncapped, each with its order link, kind and amount, its destination (shown only to its recipient) and a fixed status and next step chosen from its state, never the wallet's error text: blocked, save an address; held by the watcher, a deposit is re-confirming and the watcher releases it itself; held for a suspension, an administrator checks the payout address; held by a restore from backup, an administrator checks the market wallet; a definite failure, "the market wallet refused the send before broadcasting; administrators have been notified" (the watcher notifies every administrator in the transaction that records the failure); an ambiguous failure, a failure restored from backup or a send stuck for more than five minutes, "may have been broadcast; an administrator checks the wallet before any resend". The vendor desk shows how many there are, linking to that list. On a closed order with an unsent payout to the viewer, the order page gives that next step (and the link) instead of "No further changes are possible", and its payout panel shows the recipient the same status and the destination; the other party and staff reviewers see neither the destination nor the reason for a hold, only "Held — waiting for an administrator check" (or, for the watcher's hold, that a deposit is re-confirming). Saving an address writes no order history (`TestRecipientSeesEveryUnsentPayout`, `TestOrderPageShowsPayoutNextStepToRecipientOnly`, `TestSuspensionNoticesCountHeldPayouts`; browser: `wallet-journey.spec.ts`). Saving or removing a payout address needs the current password (plus an authenticator code when TOTP is enrolled) and notifies the account, naming the currency but not the address, so a change made by someone who knows the password is seen; payouts to a suspended account are held until an administrator checks the address (see *Account suspension*). Saving an address gives it only to payouts that have none (blocked, or held without one); an unsent payout that already has an address keeps it (A-121), so a stolen password cannot re-point money already on its way. The save notification names those orders by short ID (no address, no link): "N unsent payout(s) still use your previous address (orders …); an administrator must confirm the change" for held payouts and definite failures, and separately the others (queued, being sent or possibly broadcast), which stay on the previous address. An administrator moves a held payout (not held by a restore from backup) or a definite failure to the recipient's current saved address with POST `/admin/payout` `op=repoint` (*Use the account's current address* under *Resolve payout N*, offered when the addresses differ): the form shows the payout's address, the account's current address and when it last changed; the server requires the password (and authenticator code when enrolled), the `address_checked` confirmation (400 without it), and the two addresses the page showed (409 if either changed since), refuses a payout that is sending or stuck, an ambiguous failure and anything held or marked by a restore (409, nothing changed), and changes only `payouts.address` by compare-and-set on the state, address and error it read, so a concurrent claim, release, requeue or second move leaves one outcome. ### P6 Transparency

- **Operator key.** An administrator saves the operator's armored OpenPGP public key (`/admin/operator-key`); it is parsed (single, unrevoked public key; private keys rejected) and its fingerprint recorded in the audit log.
- **Warrant canary.** The administrator pastes a statement the operator clearsigned offline (`/admin/canary`). It is rejected with the reason unless it is exactly one clearsigned message, with nothing before or after it, that verifies against the operator key. Accepted text is stored as pasted in a single-row `canary` table (migration 060). `/canary` re-verifies it on every view and shows exactly one of: "No signed canary published", "Signature verified" (statement, grouped fingerprint, signature date, posted date, the signed message and public key for independent `gpg --verify`), or "INVALID" with the reason (for example after a key change or database tampering). The application never writes, edits or signs canary text.
- **Signed audit export.** Administrators download `/admin/audit-export?upto=N` as NDJSON (`id`, `user_id`, `handle`, `action`, `created` in RFC 3339 UTC, ordered by id) and `&sig=1` as a text file with the Ed25519 public key, SHA-256 and signature over the exact export bytes. The key is read only from `AUDIT_SIGNING_KEY`; when it is unset or malformed the export returns 409 and the admin and `/canary` pages say it is unavailable. `upto` must not exceed the latest settled event (a brief `SHARE` lock waits for in-flight audit writers), so the same `upto` always yields byte-identical files. Rate limit: 10 downloads per 10 minutes per administrator. The public key is published on `/canary`. The export sets its own time limits (A-139): one minute to read the events instead of the 12 s request bound (it also moves the server's 15 s read deadline, defensively only: net/http already clears the read deadline once a body-less GET has been read, so that timeout never cancels the export), then 20 s plus one second per 32 KiB to send the file instead of the server's 20 s write timeout, so a large export survives onion throughput (0.19–0.45 MB/s measured); every other route keeps the server's timeouts (`TestAuditExportOutlivesServerTimeouts`, `TestAuditExportBuildOutlivesRequestBound`, `TestAuditExportWriteWindowScalesWithSize`). A download cut short fails `verify-audit` with "export sha256 does not match the signature file", and the admin page says so.
- **Verifier.** `go run ./cmd/verify-audit -pub <hex> export.jsonl export.sig` (standard library only) checks the signature with the pinned key, not the key named in the `.sig` file, and that events are well formed with ascending ids; exit status 0 or 1.
- **Limits.** The signature proves origin from the server-held key only. Anyone controlling the server (or `AUDIT_SIGNING_KEY`) can sign an altered history; exports are not a tamper-proof log. Canary verification proves which key signed the text, not that its author acts freely or that the statement is true.

## Not yet implemented

XMPP delivery (the XMPP address is stored as a profile field only), automatic mirror orchestration, multisig escrow, marketplace fee or commission accounting, QR-code TOTP enrollment and an audio CAPTCHA alternative are not implemented. Narrower gaps are listed under each package above (for example, no order auto-completion timers and no automatic payout retries). Payments work on test networks unless the operator configures mainnet, and deposits are held in the operator's pooled wallet, not in escrow ([per-order escrow](escrow.md) is planned). Unavailable interface states say so; no mock balances or deposit addresses are presented as real.

Tor deployment isolates inbound exposure. Local nodes use direct peer-network egress. Selecting external database/RPC services explicitly permits application egress; this is not an all-traffic-through-Tor configuration. Read the [operator guide](operator-guide.md) before deployment.

This is a functional marketplace on test networks by default. Mainnet is an operator opt-in with no mainnet run recorded ([verification](verification.md#not-verified); see [before accepting real funds](operator-guide.md#mainnet)). It is not a production cryptocurrency exchange or escrow service.

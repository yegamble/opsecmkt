# Implementation status

The Figma reference is adapted to Go-rendered HTML and CSS. The browser loads no JavaScript or third-party resources. Product artwork is decorative CSS illustration, not product photography. The original `[OPSECMKT]` wordmark is retained.

## Working application behavior

- Token-protected, transactional first-run administrator setup; repeated setup is rejected.
- Buyer registration, bcrypt password hashing, rotating hashed sessions, session revocation, CSRF validation, bounded forms and authentication concurrency.
- Two HttpOnly, SameSite=Strict cookies: `session` is set only at sign-in (with a fresh token) and cleared at sign-out or revocation; `anon` holds the pre-login token that CSRF forms and the CAPTCHA are bound to while no session is present. A request without cookies (for example, a link followed from another site, which Strict withholds) gets only a new `anon` cookie and never overwrites `session`, so the user stays signed in on their next direct visit. A form rendered on such a landing page carries an `anon`-derived CSRF token; its same-site POST, which then sends both cookies, is served as the anonymous request it was rendered for (it cannot act as the signed-in user, but its sign-in form and CAPTCHA work). Origin and `Sec-Fetch-Site` checks apply to every POST. Session cookies from before this change keep working.
- Server-enforced buyer, vendor, moderator, and administrator roles.
- PostgreSQL-backed listing creation, catalog search/category/region filters, product and vendor pages.
- Atomic-unit BTC/XMR price storage; idempotent **unfunded draft** creation and owner-only order access. Draft creation does not reserve stock or collect payment; requesting payment from the order page does (see P3, P5).
- Orders carry a canonical state (`draft`, `awaiting_payment`, `paid`, `shipped`, `delivered`, `completed`, `disputed`, `resolved`, `cancelled`). A server-side transition table, row locks and compare-and-set updates guard every change and log it in `order_events`. Buyers, vendors, moderators and the payment watcher move orders only through it (see P3 Orders and P5 Payments).
- Versioned, idempotent schema migrations applied at startup under an advisory lock (see [migrations](operator-guide.md#migrations)). Startup refuses, changing nothing, a database that records a migration the server does not include (one migrated by a newer release). Connecting, waiting for the migration lock, migrating and payment provider startup have separate bounds (`DATABASE_CONNECT_TIMEOUT` 15s, `MIGRATION_LOCK_TIMEOUT` 10m, `MIGRATION_TIMEOUT` 10m, payments a fixed 15s); a timeout exits with an error naming the phase, and a timed-out migration is rolled back. A failed connection names its class (authentication failed, database missing, host not found, connection refused, timed out or TLS required) without printing `DATABASE_URL`.
- Storage of messages the sender encrypted with OpenPGP beforehand (packets are inspected and plaintext is rejected; see P2), in-app recipient notifications (linked from the main navigation at every width, with the unread count as text), and account audit history. The server cannot decrypt messages.
- Moderators resolve disputes on paid, shipped or delivered orders with a release or refund outcome; the payment system then queues the matching test-network payout from the operator's wallet (see P3, P5).
- Docker internal/external database selection, separate clearnet/Tor exposure, optional operator-supplied node containers (pruned by default, full node on request), encrypted database backup and transactional restore scripts.

## What the server keeps

`/canary#records` tells users the same thing, and `/register`, `/account` and the `/messages` notice link to it. Everything below is kept in PostgreSQL (and in every backup) until the operator removes it: there is no account, message or order deletion. The operator, anyone else who controls the server or database, and anyone holding a decrypted backup can read all of it; the list says who else can read it through the application. Checked against `internal/market/schema.sql` and `internal/market/migrations/` (001–060).

- **Handle and role** (`users.handle`, `role`, `created`; `suspended_at`, migration 011). The handle cannot be changed (`/register` and `/setup` say so). Shown to trading and messaging partners, moderators and administrators, and publicly with a vendor's listings and vendor page. Administrators see every handle and role and the suspended accounts with their time.
- **Password** (`users.password_hash`, bcrypt).
- **Second factors** (migrations 010, 020): TOTP secret and pending secret sealed with AES-256-GCM under a key derived from `SETUP_TOKEN` (so the database plus `SETUP_TOKEN` opens them); recovery codes as SHA-256 hashes, with newly issued codes sealed in `users.recovery_reveal` for at most about 11 minutes; `pgp_2fa`. The account and administrators (second-factor reset list) see which factors are on.
- **PGP public key** (`users.pgp`, stored canonically; `pgp_fingerprint`, `pgp_verified_at`, migration 020). Shown to any signed-in account that looks up the handle, to trading partners, and publicly on a vendor page (see P2).
- **XMPP address** (`users.xmpp`). Rendered only on the owner's `/account`.
- **Messages** (`messages`: sender, recipient, canonical ciphertext, `created`, `encrypted`, `recipient_match`). The server cannot decrypt them. Sender and recipient see them; moderators and administrators have no message view.
- **Notifications** (`notifications`): plain text such as "New message from <handle>", short order IDs with the new state, payment notes and payout transaction IDs; read state. Only the account sees them.
- **Orders and drafts**, including unpaid drafts and cancelled orders (`orders`; `order_events` with actor, time and notes such as the vendor's note to the buyer and the cancellation reason). The buyer and vendor, and moderators and administrators while the order is disputed or resolved or a payment on it is flagged (see P3).
- **Disputes** (`disputes`: reason, resolution, outcome, plain text). The parties, moderators and administrators.
- **Reviews** (`reviews`, migration 030): rating and text; public on product and vendor pages by month without the reviewer's handle; the vendor sees the review with the buyer's handle on the order page.
- **Digital deliveries and listings** (`deliveries`, migration 030; `products` including `delivery_content`): delivered content is unencrypted and shown to the buyer and vendor, and to moderators and administrators once disputed; listings are public; automatic delivery content is shown only to the vendor.
- **Payments** (`payment_addresses`, `payments`: addresses, amounts, transaction IDs, confirmations). The parties, moderators and administrators on disputed, resolved or flagged orders, administrators on payouts; transactions are also public on the test network.
- **Payout addresses** (`users.payout_btc`/`payout_xmr`, copied onto `payouts.address` with the payout `txid`, migration 050; the time each was last saved or removed, `users.payout_btc_changed`/`payout_xmr_changed`, migration 057, NULL before it). The account; administrators on payouts that need attention; both parties see the payout transaction ID on the order.
- **Activity log** (`audit_events`: action text naming handles, key fingerprints, short order IDs and transaction IDs, with time), including every sign-in and sign-out. The account sees its latest 15 on `/account`; administrators see every account's on `/admin` and in the signed audit export (see P6).
- **Temporary sign-in records**: hashed session tokens (`sessions`, 12 hours), pending sign-ins (10 minutes), CAPTCHA answer hashes (10 minutes) and PGP ownership challenges (30 minutes). Expired sessions, pending sign-ins and CAPTCHAs are deleted opportunistically, not by a timed sweep; an expired PGP challenge stays until the account starts another, proves ownership or changes its key.
- **Not recorded**: no IP address, user agent or other browser details and no access log (no table has such a column and no handler reads them), and no email address. A reverse proxy, the Tor service or the hosting provider in front of the application may log connections. The only application log line that can carry a network address is Go's `http: panic serving <address>` if a handler panics; behind the bundled deployments that address is the proxy's or Tor's, not the visitor's. Server errors (5xx) are logged as one line with the route, status, a reference shown to the user and a cause class, never the request, its sender or the error text ([operator guide](operator-guide.md#troubleshooting)).
- **Signed audit export**: it names every account's activity, so it is private operator evidence, never to be published; `/canary` publishes only its public key so the operator can prove an export they hold came from this server.

## Feature packages

Each package updates only its own subsection when it lands.

### P1 Authentication

- **TOTP second factor** (`/totp`): RFC 6238 (HMAC-SHA-1, 30-second steps, 6 digits, one step of clock skew either way) implemented with the Go standard library. Enrollment generates a random 160-bit secret, stored encrypted (AES-256-GCM, key derived from `SETUP_TOKEN`) and inactive until the user confirms a correct code. When PGP sign-in verification is already on, activating TOTP also needs the current password (starting enrollment does not), so a session alone cannot add a second factor; the audit row notes the confirmation. Every accepted code advances a per-account step counter, so a code cannot be used twice, including by concurrent requests. Turning TOTP off requires the password and a current code or recovery code.
- **Sign-in challenge**: after a correct password, an account with TOTP enabled always receives a 10-minute pending login and must complete `/challenge`; no session is issued before that. Code guesses are limited to 10 per pending login and 10 per account per ten minutes (in-memory limits, per application instance). Limiter entries are created only for pending logins that exist and, for sign-in, registration and setup (each 10 per handle per ten minutes, case-insensitive, with separate budgets), only for a well-formed handle whose request passed the CAPTCHA (when it is on; setup has none), so a wrong or absent CAPTCHA never spends a handle's budget. Only failed passwords spend a handle's sign-in budget: a correct sign-in spends nothing, and registration and setup attempts never touch it. After 10 failed passwords the handle's sign-in is refused (429, even with the right password) for the rest of that ten-minute window, with a message that sign-in for this handle is paused for up to 10 minutes, that someone else may have caused it and that the password may be fine. Because the budget is per handle (there is no per-client signal over Tor), anyone who knows a handle, including the administrator's, can keep it paused with 10 wrong guesses per ten minutes, each needing a solved CAPTCHA when it is on and nothing when it is off. While any handle is paused, sign-in failures and refusals log `sign-in limiter refusing handles=N` at most once a minute (a count, never a handle); restarting the application clears the in-memory limits ([operator guide](operator-guide.md#authentication)). Registering a taken handle is answered "Handle unavailable" before any password hashing and spends no budget. Password checks and hashing run at most four at a time. A sign-in or registration takes one of these slots only after its input, CAPTCHA, free-handle and limit checks pass, so requests refused by those checks never keep real sign-ins or confirmations waiting; a password confirmation takes its slot before its attempt is counted. A sign-in, registration or password confirmation refused because every slot is busy (503) spends none of its budget. When the in-memory table (4096 entries) is full, the non-blocking entry with the lowest count is evicted; an entry that is currently refusing requests is never evicted, so junk keys cannot reset a blocked counter. If every entry is blocking, new keys are refused with 429 until entries expire (at most ten minutes); filling the table that way takes a limit's worth of requests per key, each passing the CAPTCHA for sign-in keys when it is on.
- **Recovery codes**: 10 codes of 80 random bits each, issued on activation and on replacement (which requires a current code and invalidates all earlier codes). Codes are checked against stored SHA-256 hashes; each code is marked used in the same transaction that signs in. The plaintext codes are displayed once, on the first `/totp` view within 10 minutes of issue; until then they are kept encrypted in `users.recovery_reveal` (AES-256-GCM, key derived from `SETUP_TOKEN`, so a copy of the database plus `SETUP_TOKEN` reveals them). That view deletes them. If it never happens, they are deleted by a background sweep that every running app process runs at startup and then once a minute, or earlier when the account opens `/account`, `/pgp`, `/admin` or `/totp` after the window. So the encrypted codes exist for at most about 11 minutes after issue while the app runs; if it is stopped they remain until it next starts, and a backup taken within that time contains them.
- **Image CAPTCHA** on `/login` and `/register` (not on first-run setup): six characters from a 30-character alphabet, drawn server-side as a same-origin PNG from a built-in 5×7 bitmap font with jitter, shear, wave and noise. Each challenge is bound to the browser's session or pre-login (`anon`) token, single-use (a wrong answer consumes it), expires after 10 minutes, and at most 30 are issued per session per ten minutes. Only a hash of the answer is stored. It is on for new and upgraded installations; administrators can turn it off or on from `/admin`, and each change is audited.
- **Password change** (`/account`, POST `/account/password`): needs the current password and, when TOTP is enrolled, a current authenticator code or an unused recovery code (spent). The new password follows the registration rule (12–72 bytes) and must be typed twice and differ from the current one; it is hashed with bcrypt at the application's cost before the transaction. The same transaction ends every other session and pending sign-in of the account and rotates the current session token, and is audited ("Changed password; ended N other session(s) …", with how it was confirmed). Attempts share the per-account limit of 10 password confirmations per ten minutes.
- **Administrator second-factor reset** (`/admin`, POST `/admin/reset-factors`): for a user who lost their authenticator and recovery codes or their PGP private key. The administrator confirms with their own password (and authenticator code when enrolled; recovery codes are not accepted here). It turns TOTP off (clearing the secret, pending secret, step counter, recovery codes and any undisplayed codes) and PGP sign-in off, keeping the saved PGP key and its verification; ends the user's sessions and pending sign-ins; writes an audit row on both accounts naming the other side and what was turned off; and notifies the user, who then signs in with the password only. The form takes the account's handle (exact, case-sensitive), looked up on the server, so any account can be reset however many accounts exist; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle kept, before the password is checked. It is refused for the administrator's own account, for other administrators (403) and for accounts with no second factor (409). Beside the form, a collapsed list shows up to 100 non-administrator accounts that have a factor, by handle, and says it is capped.
- **Account suspension** (`/admin`, POST `/admin/suspend`, *Suspend or restore an account*): contains a compromised or abusive non-administrator account. The administrator enters the handle (exact, case-sensitive, looked up on the server; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle and choice kept, before the password is checked), chooses suspend or restore and confirms with their own password (and authenticator code when enrolled). Suspending sets `users.suspended_at` (migration 011) and, in the same transaction, ends every session and pending sign-in of the account, writes an audit row on both accounts naming the other side ("Suspended account H; ended N session(s) and any pending sign-ins", "Account suspended by administrator A; …") and notifies the account. A suspended account cannot sign in: the password step answers "This account is suspended. Contact the market staff." (403) only after the correct password, so a wrong password gets the usual "Invalid handle or password"; a sign-in challenge (TOTP or PGP) that was already pending is refused the same way when it would create the session; and a session row that still exists never authenticates. Suspending also holds the account's unsent payouts in the same transaction: `pending` and `blocked` payouts to it, and payouts the watcher holds for a re-confirming deposit, become `held` with an error starting "Suspended account:" (the audit rows add "held N unsent payout(s)"), and a payout queued for a suspended recipient (an order completed, cancelled or resolved in its favour, or a late refund queued by the watcher) is created held the same way; queueing takes a share lock on the recipient's account row, so a payout queued while a suspension is in progress is held too. /admin labels them "Held: account suspended — check the payout address before releasing". Neither restoring the account nor the watcher releases them (the watcher lifts only its own hold). An administrator releases one only with their password and an explicit "Payout address checked" confirmation (the release form shows the address); without it, or while the payout has no address (it gains one when the recipient saves it after being restored), the release is refused with 409 and nothing changes; the release is audited with the address and noted in the order history, and a deposit still below the threshold keeps it held as before. Restoring clears the flag, audits both accounts and notifies the account, which can sign in again. Role, listings and orders are not touched: orders waiting on this account stop until it is restored; the other party can still complete, cancel where allowed, or open a dispute. To take away a vendor's listings, change the role instead. Suspended moderators and administrators are not resolvers or contacts: they are left out of the dispute and payment-review notifications, of the independent-resolver check (see *Disputes*) and of the order page's "Contact dispute staff" list, and count again once restored. Refused for the administrator's own account and for other administrators (403); suspending a suspended account or restoring one that is not suspended is answered 409 without change. A list under the form shows up to 100 suspended accounts, most recently suspended first, with the time.
- **Role changes** (`/admin`, *Assign an account role*) take the account's handle (exact, case-sensitive), looked up on the server, so any buyer, vendor or moderator can be changed however many accounts were created after it; an unknown handle, or an administrator's, is answered 404 with the admin page again, the reason in an alert and the handle and role kept. A collapsed list beside the form shows the 100 newest accounts and their roles. Role changes are recorded on both accounts: the administrator's row names the account and the old and new role ("Changed role of H from buyer to vendor"), and the account gets "Role changed from buyer to vendor by an administrator" in the same transaction. The admin audit trail shows the account each row is recorded on. Rows written before this change keep their original text ("Changed user role").
- Not provided: QR codes for enrollment (the secret and `otpauth://` URI are shown as text), an audio or other non-visual CAPTCHA alternative, WebAuthn/security keys, administrator-forced TOTP, and any password reset for a forgotten password (no email; administrators cannot reset passwords). Administrator lockout is recovered only by the operator on the host: a lost administrator password with `docker compose run --rm app -reset-admin-password <handle>`, lost administrator second factors with SQL in the database ([operator guide](operator-guide.md#authentication)). A CAPTCHA only slows automated sign-ups; it does not stop a determined attacker or a solving service.

### P2 PGP identity

- Profile keys are parsed with OpenPGP (`internal/market/pgp.go`); garbage, private keys, revoked keys and multi-key blocks are rejected. The key is stored as a canonical re-armor of its decoded packets: the packets (user IDs, signatures, subkeys) are unchanged, but text before or after the block, armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped. Keys saved before this are shown in the same canonical form wherever they are displayed (no rewrite migration; a stored key that no longer parses is handled as before), and saving the profile again stores the canonical form. Re-saving the same key, as pasted or as the canonical text the form shows, is not a key change: ownership proof and PGP sign-in stay and no confirmation is asked. The account page shows the fingerprint and the key's user IDs and, above the key field, who can see the key. Re-armoring does not remove user IDs, the creation time or third-party signatures from the key; the note tells users to use a key made only for this market.
- Ownership is marked **Verified** (with UTC date) only after the user signs a server nonce (clearsigned or armored detached signature) or decrypts a nonce the server encrypted to the key, on `/pgp`. Decrypt challenges store only the nonce's SHA-256. Changing or removing the key clears verification, PGP sign-in and any open challenge; every change is audited with the fingerprint. While PGP sign-in is on, changing or removing the key and turning PGP sign-in off need the current password (plus a current authenticator code when TOTP is enrolled), as turning TOTP off does. While TOTP is enrolled, changing or removing the key and turning PGP sign-in on also need the password and a current authenticator code (recovery codes are not accepted here), so a stolen session cannot add a factor that outlives "Sign out everywhere"; the audit row notes how the change was confirmed. An account with no second factor changes its key and turns PGP sign-in on with the session alone. Saving the profile with the stored key unchanged does not re-parse it, so an older key the parser now rejects does not block the form.
- Optional PGP sign-in verification (second factor), available only for a verified key that can receive encrypted messages. After the password, the user requests a one-time code (POST `/challenge/pgp`), decrypts it locally and submits it on `/challenge`; only its SHA-256 is stored and it is deleted with the pending sign-in.
- PGP sign-in code hashes are bound to the current key fingerprint and exact ownership proof. Replacing/re-verifying a key invalidates older codes, even if the original key is later restored. Sensitive password-confirmed changes serialize with TOTP enrollment.
- `/messages` rejects anything that is not an OpenPGP-encrypted message (plaintext, signed-only, malformed or fake armor). The pasted text must be exactly one armored PGP MESSAGE block with only whitespace around it; the whole base64 body is decoded and must be session key packets followed by exactly one integrity-protected encrypted-data packet that runs to the end, so text before, inside or after the block is refused. The server stores a canonical re-armor of those packets: armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped, never stored or shown. Each message shows "Encrypted (to recipient’s key)", "Encrypted (NOT to recipient’s key)" or "Encrypted (recipient unknown)", derived from the recipient key IDs in its packets compared with the recipient's saved key at send time. Messages stored before this check are inspected when displayed; their recipient match is reported as unknown. Messages stored as encrypted before the strict armor check are re-inspected when displayed and shown as not encrypted if they fail it; those that pass, and older messages found encrypted, are displayed as the canonical re-armor, so a stored armor header is never shown.
- Limits: the server cannot decrypt messages, so a key-ID match does not prove the contents (the bytes inside a well-formed encrypted-data packet are opaque to it); hidden-recipient and passphrase-only messages are "recipient unknown". Losing or letting the key expire locks PGP sign-in unless another factor is enrolled; an administrator can then turn PGP sign-in off for a non-administrator account (see P1 second-factor reset).
- Vendor pages and order pages show the other party's armored public key, grouped fingerprint and "Ownership verified YYYY-MM-DD" (UTC date only; the owner's `/account` and `/pgp` show the minute) only when a proof matches the saved key (otherwise "Ownership not verified"); a user without a usable key is named with a note that messages cannot be sent until they add one. Vendor pages are public, so a vendor's key is shown to anonymous visitors. Contact and message links open `/messages?to=<handle>` with the recipient filled in (values not matching the handle pattern are ignored); that page shows the key, fingerprint and verification of any existing handle to any signed-in account, whether or not they trade.

### P3 Orders

Implemented on the Foundation state machine; every action goes through the server-side transition table, row lock and compare-and-set, so a forbidden move returns 403, a stale or repeated one 409, and nothing reports success without a recorded state change.

- **Payment request** (`/orders/pay`, buyer, draft → awaiting payment): refused with 409 "Payment unavailable for BTC/XMR" unless a test-network wallet provider is configured for that currency; the order page shows the step as unavailable instead of a button. On success the draft is repriced from the listing's current price, one unit of stock is reserved and the live provider's address is stored. No address is ever invented by the application. A buyer may hold at most 3 orders awaiting payment (409 beyond that); the payment watcher cancels unpaid orders after `PAYMENT_EXPIRY` (see P5).
- **Cancellation** (`/orders/cancel`): buyer cancels a draft; buyer or vendor cancels an order awaiting payment (the system does when the payment window expires); vendor cancels a paid order. Reserved stock is returned. When confirmed deposits exist, the payment package queues a refund to the buyer (see P5). A vendor's cancel of a paid order needs the payout confirmation below.
- **Shipping** (vendor, physical, paid → shipped) with an optional note; **digital delivery** (vendor, digital, paid → delivered) with 1–32000 characters of content; **completion** (buyer, shipped/delivered → completed), which needs the payout confirmation below.
- **Payout confirmation** (A-161, A-122): completing, a vendor's cancel of a paid order and resolving a dispute each queue one payout, so their forms state it: the amount the payout would pay now (every deposit that is not a locked transfer and is credited or at the provider's confirmation threshold; credited only without a provider — the same rule the payout uses), the recipient's handle, the difference from the price and "(test network)"; the resolve form states both outcomes and each recipient's payout state ("no payout address: the payout waits for one", "account suspended: an administrator must check the address"), or "nothing counted yet; deposits confirming later go to the chosen party". Each form has a required confirmation checkbox (missing: 400, nothing changes) and a hidden `amount_seen`, compared with the amount counted under the payout's row locks: a different amount refuses the whole action with 409 "The amount changed to X — review again", so the order does not move and a dispute stays Open. Repeated or concurrent submissions still queue one payout.
- **All or nothing**: a payout is the whole counted amount to one party. There is no split and no automatic refund of an overpayment: completing releases everything received to the vendor, a vendor's cancel refunds every deposit, and a dispute sends the whole received amount to one party. When the counted deposits of a paid, shipped or delivered order exceed the price, both parties' order pages say so; the buyer's copy reads "Ask the vendor to cancel and refund everything, then order again. After shipping, a dispute sends the whole received amount to one party; there is no split.", the vendor's says cancelling a paid order refunds every deposit. The order history note and the release notification to both parties name the excess.
- **Automatic delivery**: when the payment watcher marks a digital order paid and the listing has delivery content, the content is recorded and the order moves to delivered as the system actor in the same transaction.
- Delivery content is stored **unencrypted** in PostgreSQL, is written only in the same transaction as the delivered transition, and is shown only to the order's buyer and vendor, and read-only to moderators and administrators once the order is disputed.
- **Disputes** move a paid, shipped or delivered order to disputed. Opening one notifies every moderator and administrator who is not a party to the order and not suspended (the parties get the usual state-change notice). If every moderator and administrator who is not suspended is a party, the dispute is still accepted: a system note in the order history records that no independent resolver was available, every administrator is notified that it needs a moderator who is not a party, and the moderation desk shows administrators a "No eligible resolver" note on it while that remains true. **Resolution** requires an outcome (release to vendor or refund to buyer) and a written decision, and is refused to a moderator or administrator who is party to the order. The outcome is recorded before the resolved transition so payment hooks can act on it. Resolving queues one payout of the whole counted amount to one party; the payment watcher sends it automatically. There is no split. The decision is stored unencrypted and read by both parties; its field says so and never to quote an address, real name or tracking number.
- **Verified reviews**: one per completed order, by its buyer, rating 1–5 and up to 2000 characters. Product and vendor pages label them "Verified purchase" because each is keyed to a completed order; reviewer handles and order ids are not shown publicly and dates are shown by month.
- Order pages show the full transition history (actor and time), the moves available to the viewer, the dispute reason and decision, the other party's PGP key, and the delivery and review panels. Orders, vendor desk and moderator desk list the relevant orders with their state; the moderator desk links each dispute to its order page. Open work is never hidden by a row cap: the moderation desk and the disputes page list every open dispute (oldest first) before the 100 most recent resolved ones, the vendor desk lists every paid order on the vendor's listings (oldest first, counted in "To fulfil") before the 100 most recent other orders, and each page says when older history is not shown. The disputes page offers every paid, shipped or delivered order for a new dispute. The orders page, admin order list, messages and notifications still show only the 100 most recent rows.
- Moderators and administrators not party to an order can open its page read-only while it is disputed or resolved (summary, history, dispute, delivery record, payment ledger), and while any of its deposits is flagged for payment review (summary, history with the flag notes, payment ledger; digital delivery content stays hidden unless the order is disputed). No buyer or vendor action renders for them and the order actions return 404. Any other order stays 404.
- **No shipping address field.** For a paid physical order the buyer is prompted to send the address as a message encrypted to the vendor's key; the vendor is told to check Messages. The market keeps that encrypted message (and who sent it to whom and when) but cannot read it. It cannot stop an address being typed into a plaintext field: the vendor's note to the buyer, the cancellation reason, the dispute reason and the review text are stored unencrypted. Each of those fields says so, who can read it (the other party; moderators and administrators when the order is disputed or a payment on it is flagged, or every moderator and administrator for a dispute reason; the public, and the vendor with the buyer's handle, for a review; the operator and backups), and never to include an address, real name or tracking number but to send them encrypted from the order page. The help is tied to its field with `aria-describedby`.

Limits: service listings have no ship/deliver step, so a paid service order can only be cancelled by the vendor or disputed. There are no auto-completion timers. Moderators cannot see the parties' messages, which are encrypted to the recipient's key; parties must describe evidence in the dispute reason, which is stored unencrypted and read by the other party, or send it (and anything identifying, such as an address) as an encrypted message to an independent moderator or administrator from the order page's "Contact dispute staff" keys, which both dispute forms point to (suspended staff are not listed).

### P4 Inventory

- Vendors edit their own listings at `/listing-edit?id=` (title, description, category, region, fulfillment type, stock, BTC/XMR reference prices, optional automatic delivery content). Administrators may edit any listing except its automatic delivery content: an administrator editing another vendor's listing sees only whether content is set ("only the vendor can view or change it"), their saves keep the stored content whatever the form sends, and changing such a listing to physical is refused (400) while content is stored. The audit log records "as administrator". Other vendors get 404.
- Create and edit share one validator. Only `physical` and `digital` fulfillment are accepted: the order state machine has no fulfillment step for a `service` kind, so the form no longer offers it. The Bitcoin price must be at least 0.0001 BTC (10,000 satoshi, the minimum Bitcoin payout; see *Minimum payouts* under P5), otherwise 400 with the reason; the forms say so. Monero prices have no minimum. Listings priced lower before this rule keep their price until edited; an edit must raise it.
- Archive/restore (`/listings/archive`, `/listings/restore`): archived listings disappear from the catalog, search, product, checkout and vendor pages, and new order drafts are refused (400). The owner still sees them on the vendor desk with an "Archived" badge. Existing orders are not changed.
- Changing a vendor's role to buyer or moderator archives their active listings in the same transaction (audited for the administrator and the account). Listings whose owner is not a vendor or administrator refuse new drafts (400), payment requests (409) and restores (409); existing orders continue and the former vendor can still fulfil them.
- The fulfillment type cannot change while the listing has open orders (409), because orders read it from the listing. A draft takes the current price when it is resubmitted and again when payment is requested; from then on the order keeps that price.
- Stock edits are refused (409) when stock changed after the form was opened (payment requests reserve stock); saving other fields keeps the current stock.
- Automatic delivery content is digital-only, at most 32000 characters, **stored unencrypted in PostgreSQL**, and never loaded on public pages. It is released only by the order package's confirmed-payment step, so the editor says "Automatic delivery requires a payment provider" whenever no provider is configured.
- Migration `040_inventory.sql` adds `products.updated` and `products.archived_at`.

### P5 Payments

Implemented, **test networks only** (disabled unless configured; see [feature configuration](operator-guide.md#feature-configuration)):

- Bitcoin Core adapter (testnet3, testnet4, signet, regtest) over wallet JSON-RPC with Basic auth, and a monero-wallet-rpc adapter (stagenet, testnet) with HTTP Digest auth. Startup exits with an error when a node or wallet reports mainnet or `BITCOIN_CHAIN`/`MONERO_NETWORK` (blank = any test network) disagree with the node. An unreachable node or a wallet that is not loaded/open leaves that currency unavailable (payment requests refused, error on the admin page) and is checked again at the start of every watcher pass, which also reloads/reopens wallets after a node restart; a node that reports mainnet after startup disables its currency. Passes skip a currency while its node is syncing, or while its tip is below the highest tip the watcher has recorded for that currency (`payment_status.tip_height`, migration 056; Bitcoin `getblockchaininfo` `blocks`, monero-wallet-rpc `get_height`), as after a node restarted or restored from an older state or a wallet rescanning: nothing is read, recorded or announced until it catches up, and the admin page shows the reason. An order never expires unless its address was read from the wallet in the same pass. Wallet-returned addresses with a mainnet prefix are refused.
- Administrators independently pause/resume new BTC and XMR payment addresses with password/TOTP confirmation and audit. Existing monitoring, top-ups and payouts continue. Migration 052 persists this intake policy. The order panel shows the remaining amount after valid confirmed and unconfirmed receipts; enough unconfirmed funds prompts waiting instead of another payment.
- One background watcher per deployment (PostgreSQL advisory lock) polls every `PAYMENT_POLL_INTERVAL`. Deposits are recorded in an idempotent ledger keyed by `(currency, txid, output)`. An order moves from `awaiting_payment` to `paid` only through the state machine, once confirmed deposits reach the order amount at the configured confirmation threshold. Each pass reads the deposit address of every order awaiting payment and of every funded order that is not yet settled (`paid`, `shipped`, `delivered`, `disputed`), however long ago it last changed, plus terminal orders changed in the last 24 hours, every order with a payout waiting to be sent or held (by the watcher, or by a suspension or a restore from backup, so the ledger an administrator's release is checked against stays current) whatever its age, and the late-deposit window below. A payout is sent only in a pass that read its order's deposit address from the wallet and applied it to the ledger without error, and the send claim re-checks that ledger; a payout released while a pass runs (payout address saved, administrator release or requeue) for an order that pass did not read waits for the next pass.
- **Deposits after funding**: a deposit first recorded while its order is paid, shipped, delivered or disputed (not a locked transfer) is announced once: an order-history note (state unchanged, system actor) and a notification to the buyer and the vendor give its TESTNET amount and say that, if it has the confirmation threshold, as last recorded by the market, when the order is completed, cancelled or resolved, it is included in the order's single release or refund, and otherwise is not paid out automatically (a confirmation seen later is flagged to moderators, see Late deposits). Repeated passes add nothing (migration 054 adds `payments.late_notice`). The payout amount rule is unchanged: one payout per order, paying every credited or threshold-confirmed deposit. The payout is exactly the deposits it marks credited: they are row-locked while it is queued, so a deposit that confirms or conflicts at that moment is either paid and credited (and holds the payout if it conflicts) or left out and flagged if it confirms. When the currency's provider is configured but unavailable in that process (for example after a restart while its node is down), the payout still applies the configured threshold to the confirmations last recorded by the watcher, and a credited deposit recorded below it holds the payout. Nothing is sent until the provider is working again, and, as with a working provider, a credited deposit later found conflicted or below the threshold holds the unsent payout. With a disabled or unconfigured provider only deposits already credited count.
- **Credited deposit regressions**: a credited deposit that the watcher reads back below the confirmation threshold (conflicted or missing from the wallet, or at a lower depth after a reorg, including 0 confirmations) while its order is not closed or its payout is not yet sent is announced once per episode: one order-history note (system actor, state unchanged, ending "Moderator review required."), a notification to the buyer and the vendor, and a "Payment review needed" notification to every moderator and administrator not party to the order and not suspended; the deposit is flagged, so staff can read the order and it is listed for payment review. The order is never reverted automatically, and unsent payouts are held (a payout queued later starts held). When the deposit reaches the threshold again the episode ends, the watcher lifts its own hold, whatever the age of the order and its address, and a later regression is announced again (migration 056 adds `payments.regress_notice`). A regression on a closed order whose payout was already sent is not announced (if the deposit was flagged in an earlier episode, the desk shows its current reason among the other flags). An order is read for this only while it is in the watch set above: a regression on a closed order last changed more than 24 hours ago whose payout is blocked (no payout address) is found (and announced) in the first pass after the recipient saves an address, before anything is sent. The vendor is not prevented from shipping; the notification tells both parties the payment is not final until the deposit confirms again, and the order page shows the regression.
- **Payment window**: an order awaiting payment whose address is older than `PAYMENT_EXPIRY` (default 24h) with no deposit seen (conflicted or locked ones do not count) is cancelled by the watcher as the system actor ("payment window expired") and its stock is returned. An order with a deposit still confirming stays open.
- **Late deposits**: cancelled, completed and resolved orders stay watched while their address is less than 30 days old and a deposit is below the threshold or confirmed but neither credited nor flagged. Funds that confirm after a cancellation that refunded nothing are refunded to the buyer (blocked without an address) and the buyer is notified. Extra funds on completed or resolved orders, or after a refund is already queued, are flagged to moderators, never paid automatically. Exception: a refund (or release) whose counted sum is below the minimum automatic payout (see *Minimum payouts*) is not queued at all; its deposits are flagged to moderators once instead, and a later deposit that lifts the sum to the minimum is refunded with them in the order's single payout. Addresses older than 30 days are not polled for late deposits; they are read only while the order has a payout waiting to be sent or held.
- **Locked Monero transfers** (non-zero `unlock_time`) are recorded and shown as "Locked transfer — not counted", never counted toward payment or payouts; the order history and moderators get one "locked transfer ignored" note and the buyer one notification (migration 051 adds `payments.locked`).
- **Payment-review flags**: "flagged to moderators" above means the deposit is marked `payments.flagged`, a system note ending "Moderator review required." is added to the order history, and every moderator and administrator who is not suspended is notified ("Payment review needed for order" plus the first 8 characters of the order ID; for a credited deposit regression or a payout below the minimum, staff who are party to the order get the buyer/vendor notification instead). The moderation desk lists flagged deposits under *Payment review*: every open flag first, oldest first and never cut, then the 100 most recently flagged others, with the count of others and a notice when older ones are cut. A flag is open while it has nothing that settles it: a locked transfer, a deposit received after settlement or a deposit of a payout below the minimum until a payout includes it (no disposition action exists yet), or a credited deposit in an announced regression that has not confirmed again. Each row shows the full order ID linking to the order, amount and currency, full transaction ID and output, flag time (the latest flag note for the deposit; "Not recorded" if none matches) and a reason from the deposit's current confirmations: "Credited deposit conflicted or missing", "Credited deposit below threshold (N of T confirmations)", "Credited deposit confirmed again (N confirmations)", "Locked transfer (unlock time), not counted or paid out", "Below the minimum automatic payout, not paid out" or "Deposit confirmed after settlement, not paid out" (the last two with "; now conflicted or missing" once it is). Staff not party to the order can open it read-only (see P3). There is no web action to dismiss a flag or pay out a flagged deposit; an open flag stays listed, and a manual refund from the wallet is recorded as a written order-history note and audit row, never as a payout row ([runbook](testnet-runbook.md#handle-a-payment-review-flag)).
- **Minimum payouts** (A-99; `payments_hooks.go` `minPayoutBTC`, `minAutoRefundXMR`): a payout whose counted sum is below the minimum is never queued. Bitcoin: 10,000 satoshi (0.0001 BTC) for every release and refund, because `sendtoaddress` subtracts the network fee from the amount sent, so an amount at or below the fee can never be sent (on regtest 3,000 satoshi came out 6 satoshi negative after the fee; 5,000 was sent). The minimum removes that never-sendable class, not every failure: fees move, and a payout just above it can still fail and be requeued as before. Monero: 0.001 XMR for refunds only, an economic floor: the pooled wallet pays the fee on top (very roughly 0.00003–0.0001 XMR per transfer at the default priority, more when spending many small outputs), so refunding a smaller stray deposit would cost several percent of it or more and dust could drain the wallet in fees; Monero releases have no minimum. Instead of a payout row, the order's counted deposits are flagged once (`payments.flagged` and `payments.below_floor`, migration 058): one order-history note naming the amount, the minimum and each deposit, ending "Moderator review required.", one notification to the buyer and the vendor that the payout "was not sent" and staff were notified, and one "Payment review needed" notification to every moderator and administrator not party to the order; later watcher passes add nothing. The order still reaches its final state and its deposits stay as they were (credited or not). The complete, paid-cancel and resolve forms say the payout is "below the minimum automatic payout … not sent automatically". If later deposits lift the sum to the minimum, the single payout pays all of them and the flag closes. Payout rows queued below the minimum before this rule are unchanged. Tests: `payments_floor_test.go`.
- Payouts: completing an order queues a release to the vendor. Cancelling a funded order queues a refund to the buyer. Resolving a dispute queues a release or refund according to its recorded outcome. Each payout is a single wallet call, run on a context detached from shutdown and bounded to 30 s (ordinary wallet and node reads stay bounded to 10 s; no client or transport timeout cuts a send shorter): failed or stuck payouts are shown to administrators and never retried automatically. A failure is recorded as a definite wallet rejection (the wallet reported a pre-broadcast error: nothing was broadcast) or as ambiguous (timeout, dropped connection, unreadable reply after the request was sent, or a Monero error the wallet can raise after submitting: it may have been broadcast); failures recorded before this classification existed count as ambiguous. For Bitcoin every `sendtoaddress` JSON-RPC error is definite, because Bitcoin Core stores the transaction in its wallet before submitting it and does not return a failed relay as an error. For Monero only the `transfer` error codes that monero-wallet-rpc v0.18.5.1 raises before `commit_tx` submits the transaction are definite (-2 wrong address, -16 transaction not possible, -17 not enough money, -18 transaction too large, -19 not enough outputs to mix, -20 no destination, -37 not enough unlocked money); any other code, including -38 (no daemon connection, raised when `sendrawtransaction` times out after the daemon may have relayed), -4 and -1, is ambiguous; migration 055 reclassifies Monero failures recorded before this rule with any other code as ambiguous. This classification is from the wallet source and simulated wallet RPC tests; it has not been exercised against a daemon killed mid-send. Administrators can release a held payout, requeue a failed or stuck one, or mark one sent with its transaction ID (password-confirmed, audited, compare-and-set on the payout state). Requeueing an ambiguous failure, a failure restored from backup or a stuck send, or releasing a payout held by a restore from backup, is refused by the server unless the administrator also confirms that the wallet shows no broadcast transaction; that confirmation is recorded in the audit trail and the order history. `scripts/restore.sh` sets a persistent gate pausing all outbound payouts until complete wallet reconciliation and explicit SQL unlock; pending, sending, blocked and held rows receive manual recovery holds, and failed rows are marked possibly sent (a definite failure in the backup may have been requeued and sent after it); a hold for an account suspension keeps its text behind the restore marker, so its release needs both confirmations, and the script adds one audit row with the counts. Any other restore (volume snapshot, point-in-time recovery, manual `pg_restore`) skips all of this: UPGRADING.md section 6 gives the SQL to apply before starting the application, which also adds an audit row; the runbook's unlock SQL takes the administrator's handle, refuses an unknown one and audits the clear. Orders paid out after the backup come back with no payout row and also require reconciliation: the testnet runbook gives the ordered procedure and the SQL (exercised by `scripts/test-backup-restore.sh`) that records such a payout as sent and moves the order to its final state. A payout waits ("blocked") until the recipient saves a payout address, which is validated against the provider's test network. Saving or removing a payout address needs the current password (plus an authenticator code when TOTP is enrolled) and notifies the account, naming the currency but not the address, so a change made by someone who knows the password is seen; payouts to a suspended account are held until an administrator checks the address (see *Account suspension*). Saving an address gives it only to payouts that have none (blocked, or held without one); an unsent payout that already has an address keeps it (A-121), so a stolen password cannot re-point money already on its way. The save notification names those orders by short ID (no address, no link): "N unsent payout(s) still use your previous address (orders …); an administrator must confirm the change" for held payouts and definite failures, and separately the others (queued, being sent or possibly broadcast), which stay on the previous address. An administrator moves a held payout (not held by a restore from backup) or a definite failure to the recipient's current saved address with POST `/admin/payout` `op=repoint` (*Use the account's current address* under *Resolve payout N*, offered when the addresses differ): the form shows the payout's address, the account's current address and when it last changed; the server requires the password (and authenticator code when enrolled), the `address_checked` confirmation (400 without it), and the two addresses the page showed (409 if either changed since), refuses a payout that is sending or stuck, an ambiguous failure and anything held or marked by a restore (409, nothing changed), and changes only `payouts.address` by compare-and-set on the state, address and error it read, so a concurrent claim, release, requeue or second move leaves one outcome. The payout keeps its state, so nothing is sent until the existing release, requeue or watcher path sends it; the audit row records the old and new address, and the order history and a notification to the recipient say it moved, without the address (`TestAdminMovesHeldPayoutToCurrentAddress`, `TestAddressSaveDoesNotRepointUnsentPayouts`, `TestRepointRefusedUnlessHeldOrDefiniteFailed`, `TestRepointIsCompareAndSet`).
- Order pages show the deposit address, amounts and confirmations only when they come from a live provider and the ledger, each labelled `TESTNET <network>`. Footer, catalog, checkout, product and vendor pages state "Payments disabled" or "TESTNET payments (<networks>) — no real funds". The admin page lists each provider's network, status, last poll and last error, plus every payout that needs attention (blocked, held, failed or stuck sending; counted and listed first, oldest first, with its resolve form, whose summary names the payout, kind, amount, recipient and short order ID; the payout and deposit tables wrap inside their scrollers so every resolve confirmation is readable at desktop width) and the 50 most recent other payouts. A payout the watcher holds while a credited deposit is still below the threshold offers no *Release* form: its row names each such deposit (transaction ID and output, deposit address, confirmations of the threshold) and links to the order, and says the watcher releases the payout itself once the deposit confirms again; *Mark sent* remains. A release submitted anyway is refused (409) with that explanation and nothing changes.
- The payment step and the other order actions (`/orders/pay`, ship, complete, cancel, dispute outcomes) are provided by the Orders package; `lifecycle_integration_test.go` drives listing → payment → delivery → completion → payout and dispute → refund end to end against the fake wallet.

Not implemented: multisig escrow, marketplace commission or fee accounting, automatic payout retries, and mainnet payments (by design). Funds sit in one pooled custodial wallet per currency. Bitcoin payouts deduct the network fee from the amount sent. Monero payout fees are paid from the pooled wallet. The regtest smoke test (`scripts/regtest-smoke.sh`) and the real local-chain browser journey ([local-chain testing](local-chain-testing.md)) are manual and not part of CI. Their recorded runs (2026-09-23), with commits and the limits of each record, are in the [evidence table](verification.md#evidence-table). No public test network run is recorded, and no real-chain run covers the payout changes made after `cdb69f2`.

### P6 Transparency

- **Operator key.** An administrator saves the operator's armored OpenPGP public key (`/admin/operator-key`); it is parsed (single, unrevoked public key; private keys rejected) and its fingerprint recorded in the audit log.
- **Warrant canary.** The administrator pastes a statement the operator clearsigned offline (`/admin/canary`). It is rejected with the reason unless it is exactly one clearsigned message, with nothing before or after it, that verifies against the operator key. Accepted text is stored as pasted in a single-row `canary` table (migration 060). `/canary` re-verifies it on every view and shows exactly one of: "No signed canary published", "Signature verified" (statement, grouped fingerprint, signature date, posted date, the signed message and public key for independent `gpg --verify`), or "INVALID" with the reason (for example after a key change or database tampering). The application never writes, edits or signs canary text.
- **Signed audit export.** Administrators download `/admin/audit-export?upto=N` as NDJSON (`id`, `user_id`, `handle`, `action`, `created` in RFC 3339 UTC, ordered by id) and `&sig=1` as a text file with the Ed25519 public key, SHA-256 and signature over the exact export bytes. The key is read only from `AUDIT_SIGNING_KEY`; when it is unset or malformed the export returns 409 and the admin and `/canary` pages say it is unavailable. `upto` must not exceed the latest settled event (a brief `SHARE` lock waits for in-flight audit writers), so the same `upto` always yields byte-identical files. Rate limit: 10 downloads per 10 minutes per administrator. The public key is published on `/canary`.
- **Verifier.** `go run ./cmd/verify-audit -pub <hex> export.jsonl export.sig` (standard library only) checks the signature with the pinned key, not the key named in the `.sig` file, and that events are well formed with ascending ids; exit status 0 or 1.
- **Limits.** The signature proves origin from the server-held key only. Anyone controlling the server (or `AUDIT_SIGNING_KEY`) can sign an altered history; exports are not a tamper-proof log. Canary verification proves which key signed the text, not that its author acts freely or that the statement is true.

## Not yet implemented

XMPP delivery (the XMPP address is stored as a profile field only), automatic mirror orchestration, multisig escrow, marketplace fee or commission accounting, mainnet payments (refused at startup by design), QR-code TOTP enrollment and an audio CAPTCHA alternative are not implemented. Narrower gaps are listed under each package above (for example, no order auto-completion timers and no automatic payout retries). Payments work only on test networks, and deposits are held in the operator's pooled test-network wallet, not in escrow. Unavailable interface states say so; no mock balances or deposit addresses are presented as real.

Tor deployment isolates inbound exposure. Local nodes use direct peer-network egress. Selecting external database/RPC services explicitly permits application egress; this is not an all-traffic-through-Tor configuration. Read the [operator guide](operator-guide.md) before deployment.

This is a functional test-network marketplace, not a production cryptocurrency exchange or escrow service.

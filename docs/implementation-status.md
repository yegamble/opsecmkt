## Security hardening boundary

The native executable embeds its UI and provides deployment, key generation/import,
application and upload-gateway roles. Interactive terminals open a guided setup
when no arguments are supplied; explicit `setup` provides the same path, while
headless serving and flag-based automation remain compatible. The guide previews
commands, confirms configuration/start separately and identifies generated or
imported key files without printing their values. Native Tor identities can be
imported with their matching full address/keypair or generated with an optional
prefix of up to six characters. Restart and app replacement retain selected keys.
`OPSECMKT_PROFILE=prod` requires an external
database with TLS certificate validation, a separate upload gateway, app/backend TLS and authenticated
HTTPS Monero services when escrow is enabled. The application refuses original
uploads in isolated mode; only its separate mutual-TLS listener accepts bounded
normalized images, with final session, role, ownership and quota checks. The gateway
receives original files and performs scanning and image decoding. Its same-origin
proxy sees browser credentials and sessions, so it remains a trusted service.
Different endpoint names are declarations of separation, not proof of physical
host placement. See [Binary installation](install/binary.md).

The administrator-only service panel reports isolation notices and installed/latest
versions for PostgreSQL, Monero daemon/wallet RPC, Tor, ClamAV and Go. A separate
`versions-worker` polls fixed official release feeds and signs a local report;
the application verifies it without internet release requests. Go and PostgreSQL
versions are observed locally; integrated ClamAV uses its cached engine version and,
with isolated uploads, ClamAV uses the engine version in the upload gateway's latest
scanner report (A-552); other inventory is operator-reported. Missing, invalid, stale and unknown states
remain warnings. The worker never installs updates. The deployment controller
retains existing service references for application-only redeployment; see
[Service topology and sizing](install/service-topology.md).

Optional Tor administrator ingress uses a separate Unix HTTP socket and a
client-authorized admin onion; when enabled, the public listener refuses setup,
administrative endpoints and administrator sessions (an administrator's sign-in
there gets the wrong-password refusal and budget spend whether the password is
right or not, A-611), and the private ingress
keeps its own sign-in, code, PGP and confirmation budgets and admission
classes, so public traffic cannot pause or refuse an administrator's sign-in
there, by password, TOTP or PGP (A-570). Uploads still share their limits. `AUDIT_EXPORT_RECIPIENT`
optionally encrypts audit export and signature bytes to an offline-held OpenPGP
private key before download or host file creation. Deployment packaging can
exclude evidence, CI and cloud documentation tooling without changing public
source history. See [Security and OPSEC operations](security-operations.md).

Native production Tor requires that private ingress. Its networkless preparation
helper validates public client records and preserves the separate onion identity
volume. The CLI also encrypts an offline installation bundle, checks a hardened
Linux tmpfs and unlocks administrator-decrypted input without a plaintext bundle
file. Retention remains on persistent external storage. Manual emergency commands
confirm the saved project/context, stop and inventory its containers, and permit
explicitly targeted LUKS keyslot erasure only after successful stopping. No
automatic event invokes an erase or reboot. See the
[RAM and emergency procedure](install/ram-secrets-and-emergency.md).

These controls do not encrypt the whole database, remove online wallet keys,
guarantee memory destruction or guarantee anonymity. Local Docker deployment,
app-only replacement, RAM unlock and offline Tor startup have
[working-tree evidence](evidence/native-cli-2026-10-15.md). Live public Tor client
authorization, remote hosts and production policy still require operator rehearsal.

## XMPP notifications

Migration 131 adds private recipient opt-in/version state, notification audiences and a transactional delivery
outbox. Administrators configure the outgoing sender account, server, port, TLS mode and encrypted password under
`/admin/site#xmpp-outgoing`; each recipient opts in separately at `/account#xmpp-notifications`. Both changes
require password/TOTP confirmation, CSRF and a submission nonce. The sender credential is excluded from generic
page settings and never populated into an HTML password field. The destination is account-private.

New frontend notification rows supply the XMPP notice and recipient, so order payment/shipping, received-message
metadata and dispute open/update/close notices agree across channels. Migration 132 adds optional forwarding of
already PGP-encrypted message armor: both the administrator's **Allow PGP-encrypted message contents in XMPP**
and the recipient's **Include PGP-encrypted message contents** choices must be enabled. They default off; the
recipient also needs enabled XMPP and a usable PGP encryption public key, without a PGP-sign-in or key-ownership
proof requirement. Only encrypted armor is appended; forwarding never decrypts a message or sends its plaintext.
Both current permissions are rechecked at delivery, and a global forwarding-permission revision suppresses
content from earlier queued alerts while retaining their summaries; a recipient preference change invalidates
earlier queued deliveries. Forwarding needs a visible key ID for the current usable recipient encryption key.
Hidden-recipient messages, key mismatches, replaced keys and unavailable contents remain summary-only.
Existing messages and deliveries are not backfilled. Content forwarding is bounded to a 256 KiB XMPP body; packet/key checks do not prove ciphertext integrity or decryption without the private key.

New drafts and checkout require usable PGP public encryption keys for both buyer and vendor, plus successful
PGP challenge decryption in the buyer's current session. New per-order automatic and manual digital delivery records are
encrypted to the buyer's PGP key before being stored; only encrypted delivery armor is eligible for optional
XMPP content forwarding. The shared automatic-delivery listing template remains server-readable, and historical
plaintext delivery records are preserved and never forwarded as XMPP contents. Delivery encryption failure
refuses manual delivery or leaves automatic delivery pending without storing plaintext.

Order-linked notices include an authorized order reference. Encrypted direct messages retain their message references; encrypted support tickets have their own ticket references and staff workflow (migration 133, below).
Administrators also receive vendor-application and
bond-review states plus sanitized security/unusual-activity alerts. Moderators receive dispute notices and their
own account/order activity. Admin-only notification audiences require a current active administrator, dispute
staff audiences require current active staff, and personal notices remain limited to their named account.
Frontend reads and delivery both recheck the audience after role changes. Dispute notification eligibility does
not change the administrator-only permission to resolve Monero escrow.
Historical ticket closure alerts carry an explicit metadata-only grant; removal of an expired ticket reference
cannot turn an ordinary administrator ticket alert into a historical moderator alert.

Opt-in is off by default and does not replay existing notifications. A changed destination or opt-out invalidates
queued messages tied to the earlier preference. A delivery failure does not roll back the frontend notice.
Verified STARTTLS or direct TLS is mandatory; SASL authentication follows TLS. Outgoing connections are direct,
including in Tor mode: this feature does not add Tor egress. XMPP providers can read and retain notification
text, routing metadata and optional encrypted armor. PGP protects the forwarded message contents; TLS does not
add end-to-end protection to the notification text or metadata. Retries can duplicate an alert
after an ambiguous send, and outgoing-server acceptance is not a receipt from the user. Each notice has at most
12 send attempts, exponential retries from 30 seconds to one hour, and a 24-hour delivery window. Disabling
outgoing delivery cancels pending sends when processed. See the
[operator setup and privacy details](operator-guide.md#xmpp-notifications).

## Encrypted support tickets

Migration 133 adds support tickets, separate from direct messages. `/tickets` lists the signed-in account's tickets
or the authorized staff queue; `/ticket?id=…` opens a permitted ticket thread. Tickets have Open, Closed and
Ignored states, a current staff assignee and an administrator escalation boundary. Users handle routine support
through these pages, without host access or database commands.

Opening or replying to a ticket requires a usable public encryption key and successful PGP challenge decryption
in the sender's current session. Opening one also requires a selected active staff
member whose key is available through the public staff list or configured staff contact. Hidden staff accounts
are not exposed as a selectable roster. Every ticket body is prepared in the user's own PGP client and submitted
as recipient-encrypted armor; there is no plaintext subject. Ticket IDs, participants, assignments, status and
history remain plaintext metadata. The market stores ciphertext and checks recipients, without decrypting it.

The opener remains a participant after reassignment or escalation. Active staff can read and manage normal
tickets; administrators can inspect the full queue. Administrator-only or escalated tickets exclude moderator
staff access, while a moderator who opened one retains their own personal participant view. That exception does
not grant administrator queue access or management. Replies are accepted only while Open, encrypted to both the
opener and current assignee, with hidden recipient IDs refused. A current assignment does not make earlier PGP
bodies decryptable, and copies already obtained by a former recipient cannot be recalled.

The opener can close their own Open ticket. Reopening a Closed or Ignored ticket, ignoring one, assignment and
escalation require the permitted current staff role; assignment and escalation are limited to Open tickets.
After reassignment, active staff who previously handled or messaged in the ticket can receive a generic closure
or ignore notice. A former moderator assignee can receive that minimal metadata after escalation but cannot
open the administrator-only thread or receive its protected contents.

Frontend and XMPP ticket notifications use the same ticket and role checks. Ticket-content forwarding also
requires current global permission, the recipient's separate opt-in, a usable key and a visible recipient key
match. Hidden-recipient armor is not forwarded. Disabling consent, changing assignment or escalating a ticket
cannot send its protected content to an account that no longer qualifies. See the
[support workflow](operator-guide.md#encrypted-support-tickets).

Retention maintenance expires ticket bodies after 90 days or earlier when their opener or sender is closed or
erased, respecting related account holds across current/historical participants and workflow staff. Closed or
Ignored metadata is removed after 90 days without an update only once all bodies are gone and no hold applies;
Open metadata stays for workflow. Deletions are journaled for restore replay.

## Vendor onboarding

A-544, migration 121 (`vendor_applications.go`). `/register` offers **Buyer account** (the default) or **Vendor
account** as plain radios. A vendor account is a buyer account plus a vendor application; a buyer can also apply
later, and withdraw an open application, under *Sell on this market* on `/account` (POST `/account/vendor-application`,
unapproved buyers and moderators, with a submission nonce). A vendor sign-up lands on `/account#vendor-application`.

The administrator's vendor policy (*Admin → Vendors → Vendor applications*, `/admin/vendors`, POST `/admin/vendor-policy`) has a bond in XMR
(`vendor_bond_xmr`, stored in atomic piconero; 0 = none) and an approval mode (`vendor_approval`, `manual` or
`automatic`; defaults 0 and manual), plus free-text bond payment instructions (`vendor_bond_instructions`, at most
2000 characters, shown to applicants waiting for a bond). The four combinations behave as follows:

| Policy | New application | Becomes a vendor when |
| --- | --- | --- |
| Bond + manual approval | waiting for bond | the bond is received (automatic XMR deposit, or recorded by an administrator), then an administrator approves |
| Bond + automatic approval | waiting for bond | the bond is received on the Monero network, or an administrator records (or waives) it |
| No bond + manual approval | waiting for administrator approval | an administrator approves |
| No bond + automatic approval | approved at once | immediately (the sign-up or application itself) |

**The bond is a non-refundable fee.** An administrator may always record the bond as received (*Record bond
received*, `how='manual'`) or waive it (`how='waived'`) on POST `/admin/vendor-applications`. Each application captures the bond and approval mode in force
when it is created, so a policy change applies to new applications only; the payment instructions shown are the
current ones. Administrators approve or reject an application with an optional note of at most 500 characters on one
line, which the applicant sees; an application waiting for its bond can be rejected but not approved (409). The
application's `note` column holds the latest non-empty administrator note: a decision without a note keeps the bond
step's note, and a decision with one replaces it (the bond step's note stays in the applicant's notification of that
step) (A-583). A suspended applicant is held until restored: approval, and a bond step that would approve
automatically, are refused (409 "H is suspended: restore the account before approving it. Nothing was changed."),
while rejection still works (A-583, `TestVendorApplicationAuthz`). Approval grants selling authority: buyers become vendors through an audited role change, while moderators retain their staff role and gain independent selling approval. Rejected and withdrawn applicants stay buyers and
cannot reach the listing actions (403). At most one open application per account (partial unique index; a second →
409). Every admin vendor form needs the administrator's password (and authenticator code when enrolled), records a
submission receipt and is audited on both accounts; every decision notifies the applicant. *Admin → Assign an
account role* and the `-set-role` host command can still set the vendor role directly; a promotion to vendor closes
any open application (withdrawn) and records an approved one without a bond, decided by that administrator (none for
the host command) with the note "Role assigned by an administrator". A demotion keeps the approved application:
`/account` then shows "Vendor role removed by an administrator" and "Your vendor role was removed by an
administrator", and the account may apply again (an approved application never counts as open). A promotion to
moderator or administrator, by the form or `-set-role`, withdraws an open application (audited "Vendor application
withdrawn: role changed to R by …", with the note "Role changed to R" on the application, and the role-change
notification says so), since that role cannot be decided as
an application; a moderator may apply again. A demotion to buyer leaves an open application open (A-583,
`TestVendorRoleFormKeepsApplicationsConsistent`).

*Verified vendor* (POST `/admin/vendor-verify`; `users.vendor_verified`, with `vendor_verified_set_by`/`_set_at` for
the latest change): an administrator marks a vendor account verified, or removes the mark. The badge shows on the
vendor page, the product page and listing cards, only while the vendor is active (`verifiedVendorSQL`: marked or an
administrator, and `activeVendorSQL`); the vendor page says it is the staff's judgment, not an identity
check. A suspension hides the badge and keeps the mark, so a restore shows it again; a role change away from vendor
(to buyer, moderator or administrator, by the form or `-set-role`) removes the mark, audited on the account
("Verified vendor mark removed: role changed to R by …") and in its role-change notification, so a later promotion
back to vendor shows no badge until an administrator marks it again. Any role change away from administrator also
removes a mark kept from before A-583 (an administrator is verified by its role and the form refuses to mark one), even
back to vendor (A-583,
`TestVendorVerifiedBadgeFollowsActiveVendor`). Existing vendors were grandfathered by migration 121 with an approved application (no bond) and are not
verified. `activeVendorSQL(alias)` is the shared SQL condition for an approved, active vendor (vendor role, administrator role or independent selling approval, not
suspended, closed or restricted for closure).

### Vendor bond paid in XMR (A-547)

Owner decision 2026-10-18, migration 124 (`vendor_bond.go`). While bond addresses may be issued — `ESCROW_XMR=on`
and Monero escrow ready, new XMR payments on (*Admin → Payments*, intake *escrow*), and neither the restore gate
(`payments_recovery_required`) nor the restore sweep (`xmr_escrow_sweep_required`) set — the Monero escrow watcher
gives each application waiting for a bond a **one-time deposit address**: an account of the market's **bond wallet**
(`bond-NN`, one long-lived wallet on the escrow wallet-rpc, created when the first address is needed, its password
derived from `MONERO_WALLET_SECRET` and its seed sealed to `ESCROW_XMR_SEED_KEY` like an escrow wallet's), made by
`create_account` and stored only once `get_address` agrees (`vendor_bond_accounts`), used for that application alone
and never reused. No page or form makes an RPC: `/account` says the address is being prepared until the watcher's next
pass. `/account` shows, without JavaScript and **before** the address, that the bond is a non-refundable fee and that
anything paid above it or after the application stops waiting is kept too (the market asks for no refund address and
never sends coins back); then the address, the XMR received with at least the threshold, the XMR still confirming with
its confirmations, and what is still to pay. While issuance is not allowed the address is not shown: an application
with no address yet is told the bond is recorded by hand by an administrator, with the administrator's instructions;
one that already has an address is told that payments sent to it are still counted automatically and that new
addresses are not being issued right now. An application opened before migration 124 (`before_bond_addresses`) is told
beside its new address not to pay again if it already paid as the instructions said, and to ask an administrator to
record it.

Deposits (`vendor_bond_deposits`, one row per transaction and account, unique on `(txid, account_id)`) count from the
Monero escrow threshold (`max(PAYMENT_CONFIRMATIONS_XMR, 10)`) with no unlock time and no `double_spend_seen`. Once the
counted deposits of an application waiting for its bond cover the bond captured on it, the bond is recorded as
received (`how='xmr'`, "detected on the Monero network"), audited and notified, and the application waits for
approval, or under automatic approval is approved (an active buyer account only; a suspended, closed or closing one
waits for an administrator). An under-payment waits with no time limit (an administrator may still record or waive
the bond); an over-payment is kept and the administrators told; a deposit with an unlock time, and a deposit the
application did not count because it had stopped waiting for its bond (withdrawn, rejected, waived, recorded by hand
or approved), is kept and flagged to the administrators once it has confirmed (as an over-payment when the bond was
recorded from earlier deposits), and changes nothing. A counted deposit that later falls
below the threshold or disappears (a reorganisation) is flagged once; nothing is revoked and no role changes. The
administrators' *Vendors* queue and the account page in the user directory show the bond address, the XMR received
and these flags.

**No send path.** The market never transfers, refunds or forwards from the bond wallet; the bond fee address (A-550,
`ESCROW_XMR_FEE_ADDRESS`) is never involved. The operator sweeps the bond wallet offline from its sealed seed
([operator guide](operator-guide.md#vendor-bond-wallet)). An account of the bond wallet with no row (a lost
`create_account` answer, or a database restored to an earlier point) is recorded for no application and the
administrators are told once; coins there, at account 0 or at an account whose application was erased fund nothing and
are reported once. While XMR intake is paused, or under the restore gate or sweep, no bond wallet or account is
created and no address shown; deposits are always read, and only the gate and sweep hold recording: no bond is
recorded and nothing approved until both clear. A restore (`scripts/restore.sh` and UPGRADING.md section 6) moves the
bond wallet in use to `closed`: it is still read and its recorded addresses still credit their applications, but it
never issues again, so an account it gave out after the backup is never given to another applicant; addresses come
from a new `bond-NN` (PE-1). The sweep opens the bond wallet names after the newest row (a bond wallet created after the
backup is recorded as an orphan with its seed sealed and its funded accounts listed, then read like a closed wallet, so
a later deposit to it is reported) and raises each bond wallet's lookahead past its highest recorded account. While the
bond wallet in use does not open, no address is promised. A bond wallet is
Monero escrow state for the network pin (`pinXMRNetwork`), and its addresses are parsed for the verified network.

exact, automatic, under, over, late after withdrawal, rejection, waiver, recording and approval, and locked deposits;
`TestVendorBondReorgAfterApprovalFlagsOnly`; `TestVendorBondWatcherIdempotent`;
`TestVendorBondGateHoldsIssuanceAndApproval`; `TestVendorBondNetworkPin`; `TestVendorBondRowlessAccountRetired`;
`TestVendorBondRestoreSweep`), `vendor_bond_cases_test.go` (`TestVendorBondRestoreClosesWallet` with restore.sh's own

## Fresh-install payment boundary

The current source is Monero only. Listings, drafts, escrow checkout, intake controls and settlement use XMR. Bitcoin key registration, signing pages, checkout actions and node provisioning are removed. Historical evidence and immutable database migrations remain as records of earlier versions.

Monero escrow is off by default and custodial: the market holds its wallet keys. A local node alone enables no payment. Native `opsecmkt deploy init` defaults to stagenet (`--monero-network mainnet` opts into real funds); the legacy `scripts/install.sh` bundled nodes default to mainnet, so pass `--monero-network stagenet` there for test funds. No real-funds mainnet transaction is recorded. Unit, database and simulated-RPC tests are the mainnet evidence boundary.

Monero conceals sender, recipient and amount details on-chain; it does not conceal order/payment metadata from the market, defeat traffic correlation or protect a compromised host. Tor-mode settlement relay waits for explicit node Tor configuration or explicit acceptance of clearnet exposure. Monero delivery through Tor remains unverified.

One public stagenet digital claim is [recorded](evidence/public-testnet/2026-10-10-ac71878dfde4/stagenet-xmr/README.md). Public refunds and physical deadlines remain unverified. See [Monero escrow](escrow.md) and [verification](verification.md).

## Working application behavior

- Token-protected, transactional first-run administrator setup; repeated setup is rejected. The operator can instead create the first administrator on the host with `-bootstrap-admin HANDLE` (password on stdin, no setup token, same transaction and lock; no web path).
- Buyer registration, bcrypt password hashing, rotating hashed sessions, session revocation, CSRF validation, bounded forms and authentication concurrency.
- Two HttpOnly, SameSite=Strict cookies: `session` is set only at sign-in (with a fresh token) and cleared at sign-out or revocation; `anon` holds the pre-login token that CSRF forms and the CAPTCHA are bound to while no session is present. A request without cookies (for example, a link followed from another site, which Strict withholds) gets only a new `anon` cookie and never overwrites `session`, so the user stays signed in on their next direct visit. A form rendered on such a landing page carries an `anon`-derived CSRF token; its same-site POST, which then sends both cookies, is served as the anonymous request it was rendered for (it cannot act as the signed-in user, but its sign-in form and CAPTCHA work). Origin and `Sec-Fetch-Site` checks apply to every POST. Session cookies from before this change keep working.
- **Return to the page after sign-in** (A-126): an anonymous request for a signed-in page (for example "Review order draft" or "Message vendor") is redirected to `/login?next=<page>`, and `/login` says "Sign in to see <page title>." Signing in, registering (`/register` keeps the target, and the links between the two pages carry it) and finishing `/challenge` (TOTP or PGP code; the pending sign-in stores the target, so the PGP code request and a failed attempt keep it) land on that page; a wrong CAPTCHA answer re-renders the form with the target kept (A-269). A recovery-code sign-in still lands on `/totp`, which shows the remaining codes and a "Continue to <page>" link, both with its one-shot notice only (a reload or a crafted `/totp?next=` shows neither, A-287). The target is accepted only as a registered page named exactly (`/checkout`, never `//host`, a scheme, a backslash, an encoded character or an action path) other than the sign-in pages, with at most its `id` query and the `/messages` recipient `to` (other query parameters are dropped; a malformed one refuses the target); it is rebuilt by the server, so it can never lead off the market, and anything refused signs in to `/` as before. The header's "Sign in" link carries no target.
- **Refusal pages** (A-514, A-59 widened): a refused form post (any 4xx from the request checks, the action's checks or a pre-check, and an admission refusal), an unknown or switched-off page, a page whose object does not exist, a page the account may not see, and an invalid query string answer with one server-rendered HTML page (`web/templates/partials/refusal.html`, `refusal.go`) in the usual layout and with the usual headers (`Cache-Control: no-store`, the CSP), keeping the status code: the title "Error: …", one heading, the reason in the error alert, and a link back to the page the form belongs to (the registered page the action path names, else a same-origin `Referer` that is a registered page, rebuilt with at most its `id` or `to`, never copied; else `/`). A 401 to a browser that is not signed in adds a Sign in link that returns there. A refused post that passed the Origin checks shows its long text fields (title, description, delivery content, message or review body, dispute reason, reply and decision, notes, a PGP key, the operator key and canary statement, a claim or refund address) in read-only, unnamed textareas under "Your text, to copy", each cut to its form's limit and escaped; passwords, authenticator, recovery, PGP sign-in and CAPTCHA codes, the setup token, CSRF tokens and form nonces are never shown, and nothing shown is stored or logged. A refused `/login` or `/register` post gets its form again with the typed handle (never the password) and a fresh CAPTCHA. A listing refusal names each field in error ("Monero price: use a positive amount with at most 12 decimal places.", "Stock: …", "Category: …"). 5xx faults (with a reference), the admission-control busy answer, raw downloads (the audit export and CAPTCHA images) and image routes still answer as before (`TestRefusalPageForRefusedPostEchoesText`, `TestRefusalPageBackLinkIsLocal`, `TestRefusalPageExpiredSessionOffersSignIn`, `TestRefusedSignInKeepsHandle`, `TestRefusedListingNamesFieldAndKeepsText`, `TestRefusalPageInPreview`).
- Server-enforced buyer, vendor, moderator, and administrator roles.
- **Staff attention counts** (A-35): moderators and administrators see separate, uncapped counts for disputes, payment reviews and escrow alerts. The counts represent actionable categories and may overlap; role, suspension and non-party visibility are rechecked when loaded.
- PostgreSQL-backed listing creation, catalog search/category/region filters, product and vendor pages.
- **Catalog search and paging** (A-181, with A-16 for the catalog and A-60 PA-8): the search term is cut to 64 characters (so at most 256 bytes; the search boxes carry `maxlength="64"`, which never admits more, so a typed term is searched in full) and matched literally as a substring of title or description, case-insensitively, so `%`, `_` and `\` are ordinary characters. The category and region filters are capped at 80 bytes each. A query string holding a NUL byte or invalid UTF-8, here as on every page, is refused with 400 "Invalid address: a query parameter is not valid UTF-8 or contains a NUL character." before the page is loaded (QA5W4B-5; the bytes used to be dropped from the term and filters here, and made other pages answer 500). The catalog shows 25 listings a page, newest first, with the total count, "showing X–Y" and plain *Previous*/*Next* links ("Page X of Y", marked `aria-current`) that keep the search, filters and display currency; a page number past the end shows the last page and anything else that is not a positive number shows the first. Listing cards on the catalog, vendor page and vendor desk show at most 300 characters of the description (cut on a character boundary, ending "…"); the product and checkout pages show all of it. A catalog page of maximum-size listings (140-character titles, 10 000-character descriptions) is about 44 KB. Search still scans titles and descriptions (`ILIKE`, no trigram index: `pg_trgm` is deferred because creating the extension fails on locked-down external databases); migration 062 indexes `products(archived, created)` for the unfiltered listing order. The vendor page is paged the same way, 25 listings a page with links that keep the display currency (A-189); the orders page, messages and notifications keep their row caps (A-16).
- **Purchasability on listing cards** (A-575): one rule (`purchasable.go`) says whether a listing takes a new order now. The draft action (`/orders`) refuses through its listing side (stock, archived, legacy service) and `lockNewIntake`, shared with Monero escrow checkout, through its seller side (not a vendor, suspended or banned, deactivated, on vacation, no usable encryption key), each with its established message; the product and checkout pages show the seller side's reason; and the catalog, vendor page and vendor desk compose both sides with the shared escrow-only intake check (`listingEscrowBlock`), the distinct-unit check (`availableDigitalBatch`) and the settlement-floor note. A card for a listing it refuses says "Not available for purchase" in place of "N AVAILABLE" ("OUT OF STOCK" is unchanged), and on the vendor desk adds why and what the vendor can do. Unbuyable listings stay listed rather than hidden, so the catalog's count and pages are unchanged and agree with the cards; the encryption-key condition is evaluated in Go (key expiry), which a SQL filter could not share. Not listing conditions, and so not marked: the buyer's own listing, key and session proof, the quantity asked (a multi-unit order can clear the settlement floor; cards check one unit), and intake paused by the administrator (market-wide; escrow checkout refuses it). Deactivated storefronts stay off the catalog as before. Manual digital fulfilment is marked buyable, since escrow takes it under the current rule (A-573 is the owner's decision). Tested with PostgreSQL over `httptest` (`TestCatalogMarksUnbuyableListings`, `TestCatalogMarksEscrowIneligibleListings`, each condition mutation-checked) and in the database browser project (`db-catalog-paging.spec.ts`).
- Atomic-unit XMR price storage; idempotent **unfunded draft** creation and owner-only order access. Draft creation does not reserve stock or collect payment; requesting payment from the order page does (see P3, P5).
- A-58: migration 105 leaves historical order listing snapshots NULL; the central Draft → Awaiting payment stock reservation copies the listing’s title, full description and fulfillment kind under the listing row lock in the same transaction. The buyer/vendor order and dispute views use the saved terms, with an explicit unavailable label for orders without a copy; the current listing remains a separate live link. The full saved description is shown only on an authorized order page and retained with the order and backups after later listing edits or archiving. Automatic delivery content is not part of the copy.
- Orders carry a canonical state (`draft`, `awaiting_payment`, `paid`, `shipped`, `delivered`, `completed`, `disputed`, `resolved`, `cancelled`). A server-side transition table, row locks and compare-and-set updates guard every change and log it in `order_events`. Buyers, vendors, moderators and the payment watcher move orders only through it (see P3 Orders and P5 Payments).
- Versioned, idempotent schema migrations applied at startup under an advisory lock (see [migrations](operator-guide.md#migrations)). Startup refuses, changing nothing, a database that records a migration the server does not include (one migrated by a newer release). Connecting, waiting for the migration lock, migrating and payment provider startup have separate bounds (`DATABASE_CONNECT_TIMEOUT` 15s, `MIGRATION_LOCK_TIMEOUT` 10m, `MIGRATION_TIMEOUT` 10m, payments a fixed 15s); a timeout exits with an error naming the phase, and a timed-out migration is rolled back. A failed connection names its class (authentication failed, database missing, host not found, connection refused, timed out or TLS required) without printing `DATABASE_URL`.
- **Database session timeouts** (A-177): every connection of the application's pool (and the one `/healthz` connection) starts with `statement_timeout` 8 s, `lock_timeout` 3 s and `idle_in_transaction_session_timeout` 15 s; startup checks that the database accepts them before migrating, so a pooler that refuses these startup parameters stops startup with nothing changed ([Connection poolers](operator-guide.md#connection-poolers)). A payment request, and whatever may queue behind one (a checkout, listing edit, archive or takedown, a cancellation returning stock, a payment-intake change, and an administrator's suspension, second-factor reset or role change), waits up to 11 s for a row lock (its statement limit is raised to 11 s with it), because the request holds its rows while the escrow node is asked about the escrow address; one account has at most one payment request in progress at a time (another is refused at once with 429 and `Retry-After: 5`), so a burst from one account cannot hold the pool's connections queued on its own row. A page or form whose statement hits one is answered 503 with `Retry-After`, not 500, and logged with cause `57014` or `55P03`. So is one whose database connection is lost or refused mid-request (a restart or failover: SQLSTATE `57P01`–`57P03`, `53300`, `08000`, `08001`, `08003`, `08004`, `08006`, or cause `db-connection`; QA-178-2), when the failed statement ran before the change was committed. A lost `COMMIT` acknowledgement for password-confirmed actions and TOTP changes answers 500 with an outcome-unknown message and no `Retry-After`; the change may have committed, so staff should reload and check its state before acting again. Ordinary pre-commit database failures remain retryable busy 503 responses. An upload's lost `COMMIT` answers 500 with an outcome-unknown page and no `Retry-After`: the photo or avatar may have been saved, so reload the listing or account to check before uploading again. The shared form path's own commit, and an audit row that fails after its change was already committed, also answer 500. Migrations run on a separate connection without them (bounded by `MIGRATION_TIMEOUT` instead), as do `-status`, `-bootstrap-admin`, `-reset-admin-password` and the backup and restore scripts, which open their own sessions. The signed audit export's single streamed query lifts the statement limit (it runs under the export's own one-minute bound instead of the 12 s request bound, keeping the lock and idle-transaction limits; one million audit rows took about 6 s), and each payment watcher pass is bounded to 5 minutes, so a pass that cannot get a database connection ends, logs and leaves its work to the next pass.
- **Overload admission** (A-178): the server accepts at most 2048 connections at once (later clients wait in the kernel's backlog; while all 2048 are taken, HTTP keep-alive is off, so idle keep-alive connections are closed and cannot hold the slots), serves at most 64 page requests (GET/HEAD), 16 form posts charged to a signed-in account's write budget and 16 public ones (sign-in, registration, the sign-in challenge, whoever sends them) at once, 16 requests to the public image route (A-187; they take no page slot), and at most 8 CAPTCHA image renders and 4 password checks within those; a request that finds its class full is refused at once with 503, `Retry-After: 5` and `Connection: close`, and is not logged: a page before any database work, a form post after its session lookup (the only database read before its slot). A form post takes its slot only after its body is read (64 KiB cap, 15 s read timeout; a body with more than 64 fields is refused with 400 before it is parsed, so a flood of junk bodies costs about 150 KB of allocation each instead of 3.7 MB) and its Origin, `Sec-Fetch-Site` and CSRF checks pass, so slow-body posts hold only a connection; sign-in, registration and setup posts with a malformed handle or password, or a CAPTCHA id that is not a live one issued to that browser session, are refused (400) before taking a slot, as are sign-in challenges without a pending sign-in cookie (401). A post's session lookup, one indexed read, takes a slot of its own class of 16 for that query only, waiting its turn for up to 2 s before a 503; pages never take it, so a flood of pages cannot refuse a signed-in or staff post. A flood of well-formed public posts, anonymous or from a signed-in account, can still refuse real sign-ins on the public listener as busy; signed-in and staff changes are unaffected by it. Requests through the private administrator ingress (A-570) take classes of their own instead of these: 8 pages, 8 public-image requests, 2 CAPTCHA images, 4 public and 4 signed-in form posts, 4 session lookups and 2 password checks (so bcrypt runs at most 6 at a time across both), selected only by the private socket's request context, so a flood that fills every public class refuses none of them, and filling the private classes refuses no public request (`TestAdminIngressAdmissionReserved`). Both ingresses still share the application's 12-connection database pool and the host's CPU, so a public flood can still slow private requests, which wait for a pool connection within their request timeout. Uploads are not separated either: a flood of public uploads can fill `uploadWork` (and, on an isolated upload gateway, the signed-in post class the gateway's uploads take), so an administrator's photo, avatar or logo upload can be refused as busy. `/healthz` and `/static/` take no slot, and `/healthz` pings the database on its own connection, so a flood of pages or an exhausted pool does not starve the health probe. Every 503 carries `Retry-After: 5` and every 429 `Retry-After: 600` (the ten-minute limiter window), except the 429 refusing a second concurrent payment request from one account (one at a time per app process), which carries `Retry-After: 5`. A slot is released as soon as the response starts, so a slow reader holds only its connection. Server-error log lines are limited to 10 a second; the rest are counted in one `http 5xx suppressed=N` line. Measured with `TestLoadSearchFloodKeepsHealthz` (500 concurrent catalog searches from one keep-alive client, a fresh-connection `/healthz` probe every 20 ms; opt-in with `LOAD_TEST=1`, manual only and never run in CI, [command](ci-cd.md)): on Linux (a Docker container with 8 CPUs, backlog 4096) probe p99 103–145 ms and maximum 172 ms over three 10 s runs, with about 16 000–18 000 requests a second answered, 3–4 % of them search results and the rest refusals, with the connection cap then at 256; with the check on the server's own cap of 2048 (`market.MaxConns`), one 10 s run on a shared 4-CPU Linux host gave probe p99 162 ms and maximum 170 ms, with about 9 700 requests a second answered, 10 % of them search results; on macOS (backlog 128) the flood overflows the accept backlog and dropped connection attempts retried after 1–4 s, so the check is meaningful only on Linux. Load was generated on the same host, not over Tor.
- **Image scanner client** (A-185; the upload pipeline it serves is A-186, below): with `CLAMD_ADDRESS` set, the app polls clamd every 30 s (PING and VERSION) and caches its state: *Ready*, *Unavailable* or *Signatures stale* (the daily signature database is older than `SCANNER_MAX_SIGNATURE_AGE_DAYS`, default 30, 7–90, or its date is unreadable); without it, *Disabled*. `/admin/system#image-scanner` shows the state, engine, daily version, build date and age, the last successful scan and about 24 hours of in-memory counts (stored, refused as infected by signature, refused because the scanner failed), never linked to accounts; pages read only the cache, and `/healthz` never contacts clamd. The client sends upload bytes once, unmodified, with zINSTREAM (64 KiB chunks, 3 s to connect, 10 s per exchange) and accepts them only on the exact reply `stream: OK`; any other reply, a timeout or a closed connection refuses the upload, and so does an OK the client can see was sent with part of the stream unread (a write that fails, or a reset instead of an orderly close); the client cannot detect a server that reads everything and answers OK without scanning, so clamd itself is trusted. ClamAV checks uploads for known malware; it does not review picture content. A matched signature name appears only in one log line beside a reference the uploader is shown, and in the admin counts; the uploader's audit row is fixed copy. Tested against a fake clamd (`clamd_test.go`, `db-admin.spec.ts`); the opt-in `TestRealClamd` (`CLAMD_TEST_ADDRESS`) passed locally against ClamAV 1.5.4 (`clamav/clamav-debian:stable`, macOS and a Linux container: VERSION parsed, a stream with no match accepted, EICAR found, a stream over `StreamMaxLength` refused without pausing the scanner). `TestRealClamd` does not run in CI; CI's container job runs the production image against the pinned clamd in both database modes instead (A-192, `scripts/ci-smoke.sh <mode> scanner`), with one test signature as its only database, packed at job time into an unsigned `daily.cud` whose build date clamd reports in `VERSION`, so the 30-day gate passes on any day. - **Photo and avatar upload pipeline** (A-186; the forms that post to it are A-188, below; stored images are served by the image routes (A-187, below) and shown on pages (A-189, below)): `POST /listings/photo` (vendors and administrators, on a listing they may manage that is neither archived nor taken down) and `POST /account/avatar` (vendors, administrators and moderators; always the poster's own avatar, replacing any earlier one) use the listing-photo/avatar upload pipeline. Public listing and avatar variants are served, as the re-encoded JPEG (`-f`, at most 1200 px) or its thumbnail (`-t`), addressed by the row's 128-bit random id (32 lowercase hex). `GET`/`HEAD /img/<id>-t|-f` is public: it runs before any cookie or session code (it reads no session and sets no cookie), takes one of 16 image slots of its own (`imageWork`) instead of a page slot, so a page of thumbnails or a flood of image requests cannot refuse pages (and a full image class answers 503 with `Retry-After: 5`), and serves a photo only while its listing is published (not archived, not taken down) and its vendor (or the administrator whose listing it is) is not suspended and still has that role, a vendor's avatar while the vendor is not suspended, and a moderator's or administrator's avatar only while the "public staff list" setting is on and that account has not hidden itself (both off/hidden by default; owner decision). `GET`/`HEAD /desk/img/<id>-t|-f` reads only the session cookie (under a page slot, like a page) and serves an image to its owner whatever its state (an archived or taken-down listing's photo), any image to an administrator, a staff member's avatar to the buyer, vendor and moderators of an order on which that member recorded the dispute decision, and an archived (or taken-down) listing's photos to whoever may read an order placed on that listing by the order page's rule (A-264: its buyer and vendor, and moderators and administrators while that order is disputed or resolved or has a dispute record from a party concession or has a flagged payment); moderators get nothing else there (they see vendors' images on the public route), and the public route still refuses an archived listing's photos (`TestArchivedListingPhotosThroughOrder`). Every other GET or HEAD (a malformed path, a hidden image, no session) gets the same 404 as an unknown image id (status, headers and body; neither route sets a cookie), so an id cannot be probed; a POST gets 405. The image bytes held by responses still being written are capped at 64 MiB on `/img` and, separately, 32 MiB on `/desk/img`, so a signed-in flood of the desk route cannot refuse public images (`TestDeskImageFloodLeavesPublicImages`) (a GET reserves the largest size of what it asked for before its query, never waiting, and keeps what the image needs until it has been written): a client that never reads cannot pin memory beyond that, and a GET whose largest size no longer fits gets the busy 503 with `Retry-After: 5` while pages are unaffected and a HEAD, which reads only the length, still answers (`TestImageSlowReadersBoundedByByteBudget`: 33 clients that never read fill it, the heap grew 61 MiB with 49 of them connected). A served image carries exactly `Content-Type: image/jpeg`, `Content-Length`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: private, max-age=86400, immutable` (a browser may reuse a viewed image for a day without asking again, and keep it on disk until its cache is cleared: `max-age` sets freshness, not retention), `Cross-Origin-Resource-Policy: same-origin` and `Content-Disposition: inline; filename="image.jpg"`: no `ETag`, `Last-Modified` or `Set-Cookie`. No other query reads image bytes: outside `image_routes.go`, no SQL string or concatenation of strings and constants names the `full` or `thumb` column (in any case) except inside `octet_length(...)` or an `INSERT INTO images(...)` column list, none reads whole `images` rows (`*`, `alias.*`, the row itself, `row_to_json` and the like), and no other file uses the helper that builds the byte-reading query (`TestOnlyImageRoutesSelectImageBytes`; the checker's own evasion cases are `TestImageBytesCheckerCatchesEvasions`). It reads Go source text, so SQL assembled at run time from non-constant parts is outside what it can see. Tested over `httptest` and a loopback server against PostgreSQL (`image_routes_test.go`), not in a real browser or over Tor; `/canary#records` says what a browser keeps (A-191).

## What the server keeps

The [data retention and private information policy](data-retention-privacy-policy.md) defines required deadlines,
preservation exceptions, recipient-encrypted private channels and the operator-access model.
[Retention maintenance](retention.md) is implemented but off by default: it expires database records, preserves scoped duties,
retires financially closed escrow mappings and reapplies deletion after restore. Operators must schedule backup/export expiry
and track external wallet, log, snapshot and media cleanup. Recipient-encryption enforcement for remaining private fields is pending.
The storage behavior below describes the current release. Privileged access reveals retained plaintext, metadata and
ciphertext, but properly recipient-encrypted bodies still require a recipient private key to decrypt.

Content described below as public follows the site-access policy: anyone can
read it in public mode, while members-only mode requires a signed-in account.
Existing listing, account and staff-role restrictions still apply. Members-only
image responses use `Cache-Control: no-store`; previously downloaded or cached
copies cannot be recalled by changing access.

`/canary#records` tells users the same thing, and `/register`, `/account` and the `/messages` notice link to it. Most records below are kept in PostgreSQL and in backups until removed, except photos and avatars (below); form submission receipts expire and are swept as described below; without retention enabled there is no account, message or order deletion lifecycle. With it enabled, individual messages expire after 90 days, audit events after 180 days, accounts after inactivity notice or a verified request, and private order content and records after verified financial closure; see the linked schedule and preservation exceptions. Migration 098 clears the deprecated XMPP profile values from the live database while retaining the column for compatibility. Backups made before that migration can still contain the old values until restored and upgraded or the backup is removed. The operator, anyone else who controls the server or database, and anyone holding a decrypted backup can read retained data; the list says who else can read it through the application. Checked against `internal/market/schema.sql` and `internal/market/migrations/` (001–144). Migration 119 adds the durable application-host reboot request records; migration 120 adds market branding storage and authorized logo-upload tickets; migration 122 adds, to a deposit's payments row, the escrow wallet's block height when a credited Monero escrow deposit was first found missing (A-554; no personal data). Migration 123 adds an account's ban (A-546, below).

- **Retention state and exceptions** (migrations 112–117): accounts record observed authentication, notice, deletion-request, restriction and closure dates; orders record verified financial closure and private-content expiry. Administrators see scoped preservation identifiers, authority/reason, owner, authorized readers and review/release conditions, along with financial/account exceptions and protected physical-wallet cleanup inventory. The external private directory holds the instance ID, monotonically ordered prepared/committed operations, minimal deletion identifiers and current backup-preservation metadata. These are sensitive operator records, not public data. Minimal global key/address hashes and allocation floors prevent reuse after escrow retirement and can still be linked using outside information. The [operations guide](retention.md) defines expiry and remaining manual cleanup.
- **Form submission receipts**: receipt-backed mutations return the recorded result for the same account, session, action and request. Current roles, passwords and route eligibility are rechecked for confirmed actions; receipts do not repeat wallet sends or override newer settlement state. Receipts store keyed request hashes and result metadata, not passwords or submitted content. Image uploads have their separate idempotency rules.
- **Handle and role** (`users.handle`, `role`, `created`; `suspended_at`, migration 011). The handle cannot be changed (`/register` and `/setup` say so). Shown to trading and messaging partners, moderators and administrators, and publicly with a vendor's listings and vendor page. Moderators' and administrators' handles and roles are public on `/canary#staff` only while an administrator has turned the public staff list on and that account has chosen to be listed (A-189). Administrators see every handle and role and the suspended accounts with their time.
- **Account bans** (`users.banned_at`, `banned_by`, `ban_reason`, `ban_prior_suspended_at`, and `banned_handles`, migration 123, A-546): when an administrator banned the account, which administrator (unlinked when that account is erased), their reason (10–500 characters) and the time of any suspension the account already had (restored if the ban is lifted); and the banned handle in lower case, kept with the time it was reserved. Administrators see them on `/admin/users`; the reason is also written to the audit rows of both accounts (the account sees its own audit rows on `/account`, so it reads the reason only if the ban is lifted) and so into the signed audit export. Lifting the ban clears the four columns and the reserved handle; retention closure of the account clears the columns with the profile, and the audit rows follow the audit trail's own retention. The reserved handle is never removed by retention: it outlives the account's erasure, so the handle is never registered again, and it is the only thing kept about the account then.
- **Vendor applications and the verified mark** (`vendor_applications`, `users.vendor_verified*`, migration 121, A-544): each application's state, the bond and approval mode it was created under, when and by which administrator the bond was recorded or waived and the application decided, and the administrator's note. The applicant sees their latest on `/account`; administrators see open applications, and each account's latest on its page in the user directory (A-545). Closing an account withdraws its open application; erasing the account deletes its applications, and erasing an administrator unlinks their id from applications and verified marks (the audit rows on both accounts follow the audit trail's own retention).

The applicant sees their own address and totals on `/account`; administrators see them in the vendor queue and the user directory. Erasing an account deletes its applications and leaves its bond address and deposits with no application (financial records kept with the bond wallet); nothing in them names the account.
- **Password** (`users.password_hash`, bcrypt).
- **Second factors** (migrations 010, 012, 013, 020): TOTP secret and pending secret sealed with AES-256-GCM under a key derived from `APP_SECRET_KEY` (or `SETUP_TOKEN` on a legacy installation, so the database plus that secret opens them); recovery codes as SHA-256 hashes, with newly issued codes sealed in `users.recovery_reveal` for at most about 11 minutes; `pgp_2fa`; `pending_logins.factor_failed` marks a pending sign-in whose second factor already failed once (migration 012); `pending_logins.password_digest` is the SHA-256 of the password hash the sign-in's password was checked against (migration 013, A-157), so a password change also ends a sign-in whose password was checked just before it. - **PGP public key** (`users.pgp`, stored canonically; `pgp_fingerprint`, `pgp_verified_at`, migration 020; `pgp_changed_at`, when the key was last added, replaced, removed or updated without keeping its proof, and `pgp_expiry_notice`, the last expiry notice sent, migration 067). Shown to staff, to trading partners and accounts the owner has messaged, to any signed-in account when the owner is an active vendor, a listed staff member or the staff contact, to both parties of every disputed or resolved order when the owner is a moderator or administrator (A-543), and publicly on a vendor page (see P2).
- **Messages** (`messages`: sender, recipient, canonical ciphertext, `created`, `encrypted`, `recipient_match`, nullable `recipient_extra_keys`). The last field is the send-time count of distinct visible additional recipient key IDs; legacy rows and unknown recipient keys remain unmeasured. No separate recipient IDs are stored outside the ciphertext. The server cannot decrypt them. Sender and recipient see them; moderators and administrators have no message view. While a dispute is open, staff who are not party to it see, on the moderation desk and `/disputes`, how many messages each party sent to each current moderator or administrator since it opened and the time of the latest, from `sender_id`, `recipient_id` and `created` only (A-162).
- **Order correspondence, replacements and image evidence** (`order_messages`, `order_delivery_updates`, and `images` with `kind=evidence`): belong to one order, follow its private-content schedule and applicable order preservation holds, and are removed by order-private deletion replay and final retirement. Correspondence is ciphertext visible only to actual parties. New replacement deliveries contain buyer-recipient PGP armor. - **Payment-provider outage episodes** (`provider_episodes`, `provider_episode_deliveries`, migration 101): a fixed Monero escrow provider key, an episode counter, first failed/skipped time, alert state and per-administrator outage/recovery delivery receipts. Current unsuspended administrators alone see the plain-text notices; paused new-payment intake is not an outage.

The decision is final because the custodial watcher can send immediately. Reasons and decisions are plaintext; private evidence belongs in recipient-encrypted messages.

Administrators can hide a review from the public pages (`reviews.hidden_at`, migration 031); a hidden review is kept, not deleted, and administrators still see it.

The buyer, vendor and eligible dispute staff see that stored armor, which requires the buyer’s private key to decrypt. The automatic-delivery listing template remains server-readable and shown only to the vendor. Historical plaintext deliveries remain in the database and backups; they are not eligible for XMPP content forwarding. Listings are public. Unit inventory (`digital_units`, migration 141) contains server-readable content, a deduplication fingerprint while retained, listing/order allocation and reservation/delivery times. Content and fingerprint share listing/order retention and restore replay; consumed rows never return automatically to available stock. Orders store quantity and aggregate amount (migration 140).

The uploaded file, its name and its metadata are never kept: no column holds them, and the re-encoding keeps only the pixels (see the upload pipeline above). In public mode, listing photos and their descriptions are public to anyone, signed in or not, while the listing is published and its vendor (or the administrator whose listing it is) keeps that role and is not suspended; a vendor's avatar is public while the account is a vendor and not suspended. A staff avatar is public on `/canary#staff` (and on an administrator's vendor page) only while an administrator has turned the public staff list on and that staff member has chosen to be listed (`users.staff_hidden`, hidden by default); otherwise it is shown only beside that staff member's dispute decisions, to the buyer and vendor of those orders and to moderators, and to administrators (the parties' and moderators' access needs that member to have decided a dispute and to be still staff and not suspended; administrators can open any image on `/desk/img`). Demoting a staff member removes their staff avatar: an administrator changing a moderator's role deletes it in that transaction, notifies them and records "Staff avatar removed when the role changed" in their activity log, and resets their public staff list choice to hidden, so a later promotion starts hidden again (PR #28 review). Demoting a vendor to buyer, archiving a listing, an administrator's listing takedown and suspending the account hide its images from the public without deleting them; administrators, and the owner while signed in, still see them on `/desk/img`. In public mode, image routes send `Cache-Control: private, max-age=86400, immutable`; in members-only mode, they require a valid signed-in account and send `Cache-Control: no-store`. In public mode, a normal browser may keep viewed images in its disk cache: it reuses them for a day without asking the server, and the files can stay until its cache is cleared. Tor Browser keeps them in memory only, until it closes (not yet tried in Tor Browser, A-199). Removing or replacing an image, or a staff takedown, deletes it from the database at once; copies remain in backups made before that and, until PostgreSQL reuses the space, in its data files and write-ahead log. If the operator restores a backup made before a removal, the image returns until it is removed again (`scripts/restore.sh` says how many images it restored). The activity log keeps that an image was added, replaced, removed or taken down (with the listing's short id and a takedown's reason, never the image), and a takedown's reason also reaches the owner as a notification. ClamAV checks uploads for known malware; it does not review picture content. An upload it flags stores no image: the uploader's activity log records "Upload refused by the malware scanner", and the server log keeps the signature name and the reference shown to the uploader, for as long as Docker's logs are kept (3 × 10 MB rotation), and its time can be matched to the uploader's activity-log row; the log line itself names no account (see the [operator guide](operator-guide.md#troubleshooting)).
- **Payments** (`payment_addresses`, `payments`: addresses, amounts, transaction IDs, confirmations; for a flagged deposit, the staff review with its reason or note, migration 066; older rows may hold a hand refund's transaction ID and amount). Amounts, confirmations and payment status are shown to both parties. `payment_addresses` holds no rows (migration 108, A-492). Escrow deposit identifiers remain visible to both parties for verification. Deposits are recorded for escrows on a supported test network.
- **External escrow address reservations** (`escrow_external_addresses`, migration 111): the recipient account, currency and every previously accepted external refund or claim address. They remain in PostgreSQL and backups to prevent that account from reusing an address, including across its buyer and vendor roles. Other accounts cannot look up these records through the application, and their checkout or claim is not refused because of another account's external address history. Market-owned addresses and the buyer's refund address on the same order remain forbidden claim destinations.
- **Historical payout addresses** (`users.payout_btc`/`payout_xmr`, migration 050; the time each was last saved or removed, `users.payout_btc_changed`/`payout_xmr_changed`, migration 057, NULL before it), saved before escrow and kept in the database; no page shows or edits them and no code reads them for an escrow (A-508). The `payouts` and `payment_addresses` tables hold no rows: migration 108 refuses a database with any and both refuse new rows (A-492).
- **Monero escrow** (migrations 084 to 086, 090, 128 and 135; WR-escrow Phase 3, development branch): `escrows.coin` records each escrow's coin (`XMR` for current escrows) and `escrows.xmr_slot_id` a Monero escrow's account. The Monero tables: `xmr_escrow_wallets` (each monthly escrow wallet's name, primary address, restore height, seed sealed to the operator's OpenPGP key with that key's fingerprint, state and retention dates), `xmr_escrow_slots` (each wallet account's index and address, and the order that claimed it), `xmr_settlements` and `xmr_settlement_outputs` (each settlement's destinations and amounts, and its stored transaction) and `payments.xmr_settlement_id`. With `ESCROW_XMR=on` (off by default, a local fakechain or, since A-449, stagenet) the Monero escrow watcher writes the wallets and slots, Monero escrow checkout writes `escrows` (the slot's address, the buyer's refund address, the market fee) and claims a slot, the escrow's deposits go to `payments` like the others (with `payments.missing_height`, migration 122, A-554: the escrow wallet's height when a deposit credited toward the funding was first found missing, from which its release or refund waits twice the confirmation threshold in blocks before it is built without it; a credited deposit below the threshold again holds the release or refund; one a release was built without is never left out for a stray refund, one a refund was built without is left out and returned to the buyer once it is listed again), a cancellation holding coins (an underpaid order at the end of its payment window included) or a dispute decided for the buyer writes a requested refund to `xmr_settlements`, and the watcher requests a stray refund for deposits after close or left out of a settlement (one first-generation stray refund in progress per order; an administrator's re-request of a failed one does not hold that slot, migration 135, A-616); the watcher alone builds each settlement and stores it (its outputs in `xmr_settlement_outputs`, its transaction hash, metadata, blob, fee, input total and key images, and the claim of each deposit it spends in `payments.xmr_settlement_id`) before it relays it, then records it relayed, confirmed and 100 confirmations deep, or external or failed; `xmr_settlements.send_error` (migration 085) records why a settlement waits, failed or is held, or that it is set aside because building it twice made the escrow wallet-rpc stop responding; an administrator's request to build a set-aside settlement again clears it and is an order-history note and an audit event. An administrator's re-request of a failed settlement is a `xmr_settlement_rerequests` row (migration 085: the settlement, the administrator, when it was asked and decided, refused with a fixed reason or done with the new settlement) and an audit event; carried out, it supersedes the failed settlement with a new row. An administrator's record closing a failed settlement the market will never send is one `xmr_settlement_hand_settled` row (migration 128, A-613: the settlement, its kind, `nothing-owed` for one never built that was dismissed or `settled-by-hand` for one whose stored transaction's re-request was refused on-chain or key-image-spent, the administrator, the time and their plain-text note) and an audit event; staff who can read the order see it under the settlement, the parties do not, it is never changed, and it is deleted with the order's other escrow records by a certified retention retirement. The watcher keeps each wallet's `last_closed_at` and `destroy_after` (90 days after its last order closed), retains a closing wallet with no open order, and destroys a retained wallet once nothing is left in it (its password replaced by one never kept, `seed_sealed` wiped, `destroyed_at` recorded); the start of each destruction is recorded first (`destroy_started_at`, migration 086); a wallet that no longer opens is `missing` with its seal kept (destroyed again automatically only when its destruction was recorded as started, it then refuses its own password, staff were never told it holds something, and no restore is being reconciled), and an administrator's confirmation of a missing wallet's destruction past `destroy_after` wipes its seal and is an audit event; `escrow_xmr_destroy_held_<wallet id>` records that administrators were told a wallet past its destruction date still holds something. After a restore (`scripts/restore.sh`), Monero settlements with a stored transaction are held in `send_error`, free slots are retired, active and sealed wallets are closing, and `xmr_escrow_sweep_required` stays set until the watcher's sweep has recorded the wallets created after the backup (`orphan`, then sealed and `retained`) and checked every wallet; an administrator's confirmation of a held settlement's relay is its `send_error` and an audit event. A wallet account with no slot row (a lost `create_account` answer, or a database restored to an earlier point without `scripts/restore.sh`) is recorded as a retired slot, never a free one; on the active wallet outside a restore every free slot of that wallet is retired with it, and the administrators get one notification and an audit row with no user (A-556). Checkout claims a slot only of the active wallet the watcher has reconciled since this process started (in memory; PAY66-9), and coins at a retired account are reported to the administrators once per account (`escrow_xmr_funded_<wallet id>_<account>` in `settings`, PAY66-10). `settings` keeps the secret verifier and seed key fingerprint pins, the sweep marker and, while coins sit at a wallet's account 0, a marker so administrators are told once (`escrow_xmr_account0_<wallet id>`). A deposit the database refused as another order's escrow account is one row of `xmr_escrow_collisions` (migration 090, A-480): the order, the wallet name and account, the transaction ID (its first 20 characters only for a row backfilled from an earlier order note), when it was noted and, once recorded, the staff member, the time and their plain-text note of what was done. Moderators and administrators who are not parties read it on the order page; the parties do not. The settings row `escrow_xmr_fee_seen` keeps the market fee rate and full fee address the last start with Monero escrow on saw (A-550): a record only, never read as the fee, which is host configuration (`ESCROW_XMR_FEE_BPS`, `ESCROW_XMR_FEE_ADDRESS`) that no administrator form changes; a start that finds the host values changed writes one audit row naming the old and new rate and address and notifies every administrator once.
- **Activity log** (`audit_events`: action text naming handles, key fingerprints, short order IDs and transaction IDs, with time), including every sign-in and sign-out. The account sees its latest 15 on `/account`; administrators see every account's on `/admin/system` and in the signed audit export (see P6).
- **Temporary sign-in records**: hashed session tokens (`sessions`, 12 hours: the token's SHA-256, the account, and when the session started and ends; no IP address, user agent or other client data; the owner sees the start times on `/account`, A-157), pending sign-ins (10 minutes; with the page the sign-in returns to, A-126), the ids of CAPTCHA challenges that were answered (`captcha_spent`: the id and its expiry, at most 10 minutes after the challenge was shown, deleted by a sweep every minute; a challenge that is only shown stores nothing) and PGP ownership challenges (30 minutes). Expired sessions and pending sign-ins are deleted opportunistically, not by a timed sweep; an expired PGP challenge stays until the account starts another, proves ownership or changes its key.
- **Not recorded**: no IP address, user agent or other browser details and no access log (no table has such a column and no handler reads them), and no email address. A reverse proxy, the Tor service or the hosting provider in front of the application may log connections. The only application log line that can carry a network address is Go's `http: panic serving <address>` if a handler panics; behind the bundled deployments that address is the proxy's or Tor's, not the visitor's. Server errors (5xx) are logged as one line with the route, status, a reference shown to the user and a cause class, never the request, its sender or the error text, at most 10 lines a second with the rest counted in one summary line; overload refusals are not logged ([operator guide](operator-guide.md#troubleshooting)).
- **Signed audit export**: it names every account's activity, so it is private operator evidence, never to be published; `/canary` publishes only its public key so the operator can prove an export they hold came from this server.

## Feature packages

Each package updates only its own subsection when it lands.

### P1 Authentication

- **TOTP second factor** (`/totp`): RFC 6238 (HMAC-SHA-1, 30-second steps, 6 digits, one step of clock skew either way) implemented with the Go standard library. Enrollment generates a random 160-bit secret, stored encrypted (AES-256-GCM, key derived from `SETUP_TOKEN`) and inactive until the user confirms a correct code. Activating TOTP needs the current password on every account, including one with no factor yet (starting enrollment does not), so a session alone cannot add a factor that locks the owner out after "Sign out everywhere" (A-152); the audit row notes the confirmation. Every accepted code advances a per-account step counter, so a code cannot be used twice, including by concurrent requests. Turning TOTP off requires the password and a current code or recovery code. Someone who lost the authenticator can also turn it off while signing in (A-154), so one recovery code is enough to recover without staff: the recovery-code form on `/challenge` has an unchecked "I lost my authenticator — turn two-step sign-in off" checkbox, honoured only with a recovery code (ignored with an authenticator code). In the sign-in's transaction it turns TOTP off (secret, pending secret, step counter, every recovery code and any unrevealed codes), writes one audit row "TOTP turned off at sign-in with a recovery code (N remaining)" in place of the usual recovery-code row and notifies the owner once. Other sessions and pending sign-ins are left as `/totp/disable` leaves them; PGP sign-in, when also on, stays on and is asked for at the next sign-in; a suspended account's sign-in is refused and nothing changes. Every recovery-code sign-in lands on `/totp`, which says once (a one-shot notice set with the new session, A-287) how many recovery codes remain (or that TOTP is now off). Every path that changes an account's pending sign-ins, recovery codes or account row takes the row locks in the order `/challenge` does (pending sign-in, then recovery codes, then the account row): the sign-in, password change, TOTP activation, recovery-code replacement, turning TOTP off, the administrator's factor reset and suspension, and the `-reset-admin-password` tool, so none of them deadlocks with a concurrent sign-in.
- **Sign-in challenge**: after a correct password, an account with TOTP enabled normally receives a 10-minute pending login and must complete `/challenge`; no session is issued before its factor succeeds. A-549: `/login`'s optional "Authenticator code (if you use one)" field completes the second step in the same request for an account whose only enrolled factor is TOTP. After the password, the account's suspension and the A-272 lost-PGP-key notice are checked as before; the code then spends one attempt of the same per-account budget `/challenge` uses and is checked with the same replay guard, committed with the rotated session and the "Signed in with password and TOTP" audit row, and the sign-in lands on its `next` page. A wrong, expired or reused code opens the usual pending sign-in, recorded as its failed second step (audit row and owner notice, A-152), and `/challenge` shows "The authenticator code was not accepted"; a correct password reaches `/challenge` anyway, so this tells a password guesser nothing new. A blank field keeps the two-step flow, an account without TOTP ignores it, and an account with PGP sign-in also on ignores it and completes `/challenge` (`TestLoginWithAuthenticatorCode`). Recovery codes are accepted only on `/challenge`. While a handle's sign-in is paused (below), the same field rescues any account with TOTP enabled (A-571; before, A-159(a) offered this only to a sole administrator): its password with a current authenticator code signs it in, landing on `next`. The code is checked first: a wrong, malformed or already-used code, an unknown handle, an account without TOTP, a suspended account or an ambiguous legacy handle is refused with the same 401 "Invalid handle or password" before any bcrypt and without spending the sign-in code budget (`TestPausedRescueRefusesBeforeBcryptWithoutBudget` counts the password checks and holds every password slot). Each code that is checked spends only the rescue path's own budget of 10 per account per ten minutes (`rescue-code:<account>`, reserved atomically before the check, so concurrent guesses cannot exceed it, given back by a right code, and kept from eviction like the sign-in code budget); once it is spent, every rescue for that account is refused with the same 401 before its code or password is checked, a right code included, while `/challenge` and sign-in after the pause still work (SEC-A571-1: someone who has the password can cause the pause, and without this budget could then guess codes without limit; `TestPausedRescueWrongCodesSpendRescueBudgetOnly`, `TestPausedRescueConcurrentWrongCodesStayWithinBudget`, `TestPausedRescueCodeBudgetSurvivesBogusHandleChurn`, `TestLimiterProtectsRescueCodeEntries`). Only a right code reaches the password check, and that attempt spends one of the account's 10 code attempts per ten minutes (`totp-verify:<account>`, the `/challenge` budget, reserved before bcrypt, so concurrent requests cannot exceed it), whether the password is right or wrong; a right code with a wrong password gets the same 401. Someone who does not know a current code therefore cannot spend that budget or lock the account out of `/challenge` through this path, which owner commit 6fce9ff0 (2026-10-13) had allowed by charging every rescue attempt before bcrypt; whether a code was right is visible only in the response time of a request that then fails on its password. Residual: anyone who knows the handle can spend both the password budget (10 wrong passwords) and the rescue budget (10 wrong codes), and for as long as they keep repeating that every ten minutes the account cannot sign in with its password at all: the rescue is closed, and `/challenge` is reached only from a pending sign-in opened before the pause. In one transaction the rescue ends this browser's live pending sign-in, then checks the code again under the account lock with its replay guard and starts the rotated session with the "Signed in with password and TOTP" audit row, so the used step and the session commit together and a replayed code makes no second session. It takes the pending sign-in before the account row, the order `/challenge` takes them in, so a `/challenge` from the same browser is never deadlocked (a 5xx) and, if that `/challenge` completes this browser's pending sign-in while the rescue runs, the rescue is refused rather than making a second session (`TestPausedRescueWaitsForSameBrowserChallenge`, `TestPausedRescueRacesSameBrowserChallenge`). Recovery codes are not accepted by this path, and an account that also has PGP sign-in is not asked for it, as `/challenge` also accepts the authenticator code alone. Every refusal on this path, wrong codes included, is counted in `paused sign-in rescue refused attempts=N`, logged at most once a minute (a count since the previous line, never a handle); the logging itself touches no limiter (A-534). Code guesses are limited to 10 per pending login and, per account each ten minutes, 10 through the sign-in code budget plus 10 through the paused-sign-in rescue's own budget, so at most 20 (A-571; in-memory limits, per application instance). Limiter entries are created only for pending logins that exist and, for sign-in, registration and setup (each 10 per handle per ten minutes, case-insensitive, with separate budgets), only for a well-formed handle whose request passed the CAPTCHA (when it is on; setup has none), so a wrong or absent CAPTCHA never spends a handle's budget. Only failed passwords spend a handle's sign-in budget: a correct sign-in spends nothing, and registration and setup attempts never touch it. After 10 failed passwords the handle's sign-in is refused (429, even with the right password) for the rest of that ten-minute window, with a message that sign-in for this handle is paused for up to 10 minutes, that someone else may have caused it and that the password may be fine. Because the budget is per handle (there is no per-client signal over Tor), anyone who knows a handle, including the administrator's, can keep it paused with 10 wrong guesses per ten minutes, each needing a solved CAPTCHA when it is on and nothing when it is off. With the private administrator ingress enabled (A-570), a request through it spends budgets of its own of the same sizes (`adm:auth:<handle>`, `adm:totp-verify:<account>`, the pending-login `adm:challenge:` budget, the PGP sign-in code (`adm:pgp-login:`), the PGP key challenge and proof, the password-confirmation, TOTP-management and audit-export budgets and the registration and setup keys, in their own 4096-entry table), so a public table full of blocking entries refuses none of them (`TestFullPublicLimiterTableRefusesNoAdminIngressStep`, `TestFullPublicLimiterTableRefusesNoAdminIngressPGPStep`); a paused sign-in's rescue there charges only the private code and rescue-code budgets (`adm:rescue-code:<account>`), so a rescue-code budget spent on the public listener does not close it (`TestPausedRescueThroughAdminIngress`), and failed passwords and rescue codes on the public listener never pause sign-in or code checks on the private onion, and failures there never spend the public budgets; someone who holds the onion's client-authorization key is limited by the private budgets, which gives that client at most another 10 password guesses per handle and 20 code guesses per account each ten minutes (10 through its sign-in code budget, 10 through its rescue budget) (`TestPublicListenerCannotPauseAdminIngressSignIn`, `TestAdminIngressLimiterTableIsSeparate`, `TestSpoofedHeadersCannotSelectAdminIngressBudgets`). Only the private socket's request context selects that namespace; no Host, forwarding header, cookie or form field can. The administrator's sign-in protection panel lists private-ingress pauses separately. While any handle is paused, sign-in failures and refusals log `sign-in limiter refusing handles=N` at most once a minute (a count, never a handle); restarting the application clears the in-memory limits ([operator guide](operator-guide.md#authentication)). Registering a taken handle is answered "Handle unavailable" before any password hashing and spends no budget. Password checks and hashing run at most four at a time (two more through the private administrator ingress, which has its own slots, A-570). A sign-in or registration takes one of these slots only after its input, CAPTCHA, free-handle and limit checks pass, so requests refused by those checks never keep real sign-ins or confirmations waiting; a password confirmation is refused before taking a slot once its account's budget is spent, and otherwise takes its slot before its attempt is counted. Every password-confirmed change (the administrator and moderator actions, resolving a dispute, payment reviews, settings, key, TOTP and password changes) shares one per-account budget of 10 **failed** confirmations per ten minutes (A-274, as A-153 for sign-in): a wrong password, or, when TOTP is enrolled, a wrong authenticator or recovery code after the right password. Each password reserves one attempt before bcrypt runs and each code another under the account row lock, and a right one gives it back, so a correct confirmation spends nothing (a moderator can resolve any number of disputes) and concurrent guesses still cannot exceed it. After 10 failures the account's confirmations are refused (429 "Too many failed password confirmations. Try again in ten minutes.") for the rest of that window, even with the right password; only someone signed in to the account can spend it, and restarting the application clears it. A sign-in, registration or password confirmation refused because every slot is busy (503) spends none of its budget. When the in-memory table (4096 entries) is full, the non-blocking entry with the lowest count is evicted; an entry that is currently refusing requests is never evicted, so junk keys cannot reset a blocked counter. If every entry is blocking, new keys are refused with 429 until entries expire (at most ten minutes); filling the table that way takes a limit's worth of requests per key, each passing the CAPTCHA for sign-in keys when it is on. The private administrator ingress's keys live in a separate table of the same size (A-570), so filling the public one does not refuse them.
- **Recovery codes**: 10 codes of 80 random bits each, issued on activation and on replacement (which requires the current password and a current authenticator code and invalidates all earlier codes). Codes are checked against stored SHA-256 hashes; each code is marked used in the same transaction that signs in. The plaintext codes are displayed once, on the first `/totp` view within 10 minutes of issue; until then they are kept encrypted in `users.recovery_reveal` (AES-256-GCM, key derived from `SETUP_TOKEN`, so a copy of the database plus `SETUP_TOKEN` reveals them). That view deletes them. If it never happens, they are deleted by a background sweep that every running app process runs at startup and then once a minute, or earlier when the account opens `/account`, `/pgp`, an administration page (`/admin` or a section) or `/totp` after the window. So the encrypted codes exist for at most about 11 minutes after issue while the app runs; if it is stopped they remain until it next starts, and a backup taken within that time contains them.
- **Image CAPTCHA** on `/login` and `/register` (not on first-run setup): six characters from a 30-character alphabet, drawn server-side as a same-origin PNG from a built-in 5×7 bitmap font with jitter, shear, wave and noise. Each challenge is bound to the browser's session or pre-login (`anon`) token, single-use (a wrong answer consumes it; the 400 answer to one is the same form again with the error and a fresh challenge, so no reload is needed without JavaScript) and expires after 10 minutes. Challenges are stateless (A-176): the id carries its expiry and a MAC over it and the session, and the answer derives from the id under the server key, so showing `/login`, `/register` or the image writes nothing to the database; posting an answer records the id in `captcha_spent`, and a second use of it is refused. There is no per-session issuance cap: a page view costs no database write, and at most 8 images render at once (more are refused with 503 and `Retry-After`). The image of a used, unexpired id can still be fetched (it is the same image); only its answer is refused. A challenge shown before the upgrade that introduced this is refused after it: reload for a new one. It is on for new and upgraded installations; administrators can turn it off or on from `/admin/security`, and each change is audited. The image has no audio or text alternative (it fails WCAG 2.2 criterion 3.3.8 for a person who cannot read it), and there is no second way in (A-517): while it is required and the staff contact is unset or a bare handle (which only an account can message), `/admin/security` shows a warning, and `/login` and `/register` say there is no way in without the image; with a contact that is not a bare handle they say to write to it and ask for the CAPTCHA to be turned off. `install.sh check` cannot warn, because both settings are only in the database. Tests: `captcha_contact_test.go`.
- **Sessions on `/account`** (A-157): the Sessions panel lists the account's live sessions (count, each one's start time to the minute in UTC; this browser's first, marked "This session", then the newest others, at most 20 listed and all counted, since a correct password spends no sign-in budget). A session row holds nothing about the client, so no IP address, device or browser is shown or kept. "Sign out everywhere" (POST `/revoke-sessions`) ends every session of the account, this one included, and every pending sign-in (so someone parked at `/challenge` after the password step cannot finish), deleting the pending sign-ins first (the `/challenge` lock order), and is audited ("Revoked all sessions: ended N session(s) and M pending sign-in(s)"). The panel says that this does not stop someone who knows the password, who can sign in again (with the second factor too, if one is on); only a password change stops them. There is no per-session sign-out: "Sign out" ends this browser's session only; its POST form is the first control in the /account content and keeps its CSRF token (A-129, `TestAccountSignOutIsNearTopAndKeepsItsCSRF`). A password-checked sign-in racing an administrator's suspension cannot leave a usable session (`TestSuspendDuringSignInLeavesNoSession`, A-108).
- **Sign out in the site header** (A-548): every signed-in page shows a "Sign out" button after the handle at the top right, a plain CSRF-protected POST to `/logout` (no JavaScript) that lands on `/login` with "Signed out."; the `/account` sign-out stays. It is styled quieter than the handle, follows it in keyboard order (search, handle, Sign out, main navigation), is a 44 px target with the standard focus ring, and on phones moves with the handle to its own row under the brand; at any width a long handle at enlarged text puts Sign out on the next line instead of widening the page. Refusal pages that show the signed-in header carry that session's token in it, so Sign out works there too. Anonymous pages have none; the private administrator listener renders the same header; the read-only preview shows it and refuses the post like its other forms.
- **Password change** (`/account`, POST `/account/password`): needs the current password and, when TOTP is enrolled, a current authenticator code or an unused recovery code (spent). The new password follows the registration rule (12–72 bytes) and must be typed twice and differ from the current one; it is hashed with bcrypt at the application's cost before the transaction. The same transaction ends every other session and pending sign-in of the account and rotates the current session token, and is audited ("Changed password; ended N other session(s) …", with how it was confirmed). A sign-in whose password was checked before the change committed but that starts its session or reaches `/challenge` only afterwards is refused too ("Sign-in verification expired. Sign in again."): its pending sign-in, or the password-only sign-in itself, carries the password hash it was checked against, and the session starts only while the account still has that hash (A-157; the operator's `-reset-admin-password` gets the same effect). Wrong passwords and codes spend the per-account budget of 10 failed confirmations per ten minutes; a correct confirmation spends nothing (A-274).
- **Security notifications and sign-in records** (A-152): in the same transaction as the change, the owner gets one plain-text notification and one audit row for TOTP turned on or off, recovery codes replaced, a sign-in with a recovery code ("N remaining"; "TOTP turned off at sign-in with a recovery code (N remaining)" when it also turned TOTP off, A-154), the PGP key added, changed, renewed (A-155) or removed, key ownership proved and PGP sign-in turned on or off. After a correct password, the first failed second-factor check of a pending sign-in (a wrong, used or missing code, or a PGP code not yet requested) writes "Correct password but failed second sign-in step (TOTP | recovery code | PGP code)" and notifies the owner; later failures of the same pending sign-in add nothing, and the pending sign-in stays usable. The texts carry no code, secret, fingerprint, address or link and end "If this was not you, someone else may know your password: change it and contact the market staff." New "Signed in" rows name the method ("Signed in with password", "Signed in with password and TOTP", "… and recovery code", "… and PGP code"); rows written before this keep the plain "Signed in" and are not rewritten, so earlier signed exports stay byte-identical. The owner reading a notification does not stop someone who has the password: only changing it does.
- **Administrator second-factor reset** (`/admin/users`, POST `/admin/reset-factors`): for a user who lost their authenticator and recovery codes or their PGP private key. - **Account suspension** (`/admin/users`, POST `/admin/suspend`, *Suspend or restore an account*): contains a compromised or abusive non-administrator account. The administrator enters the handle (exact, case-sensitive, looked up on the server; an unknown handle is answered 404 with the admin page again, the reason in an alert and the handle and choice kept, before the password is checked), chooses suspend or restore and confirms with their own password (and authenticator code when enrolled). Retention still closes and erases a banned account on its schedule (inactivity or an earlier deletion request); only the reserved handle stays.

### P2 PGP identity

- **Required decryption for purchases and messages:** a usable saved public key and a current-session decryption proof are required at the server mutation. A signature ownership proof or TOTP alone does not grant that access. Session proofs are bound to the canonical saved public key, so a key change or another session requires a fresh decrypt challenge. Private keys are rejected and never stored. The administrator's `allow_login_without_pgp` setting defaults to true for upgrade compatibility, permitting browse-only login; false requires PGP decryption during sign-in. Vendors must retain a usable public key and cannot trade without one. MFA remains encouraged.
- **Established-key protection and recovery:** replacing/removing any saved nonempty PGP binding, including an expired or unreadable key, requires current-session old-key decryption or fresh confirmation with preexisting TOTP. Unsafe same-fingerprint rollback is guarded too. A first authenticator and its pending/recovery material cannot bootstrap replacement from a password-only browse session; inactive enrollment material is cleared at first binding and for legacy keyed inactive accounts in migration 129. Explicit privileged reset can bind a validated replacement public key after identity verification; the host reset supports strict-policy last-administrator recovery without changing that setting. Sessions, pending logins, challenges and old-generation codes are invalidated; the replacement remains unverified until actual proof.
- **Vendor availability:** vacation keeps profiles/listings public and blocks new purchases; deactivation hides public profiles, listings and photos while preserving authorized existing-order access. Message opt-out while away is enforced server-side and removes buyer message links. Last seen is opt-in, recorded at hour precision only while enabled, cleared on opt-out and omitted from public data while private. See [the operator guide](operator-guide.md#vendor-availability-and-activity-privacy).

- Profile keys are parsed with OpenPGP (`internal/market/pgp.go`); garbage, private keys, revoked keys and multi-key blocks are rejected, and so is a key in which a revoked user ID carrying only its revocation sits next to a revoked user ID that keeps its self-signature, a structure on which the OpenPGP library (go-crypto v1.4.1) dereferences nil (A-266; a minimal export with revoked user IDs, which carry only their revocations, is accepted). Such a key already stored is treated as unreadable everywhere ("No usable key" to others); the expiry sweep skips an unreadable key, or one on which the library panics, with the fixed log line "pgp expiry sweep: skipped one key that could not be read" and carries on, and a proof signature that makes the library panic is answered as not verifying (`TestKeyWithUnreadableUserIDsRefused`, `TestKeyExpirySweepSkipsUnreadableStoredKey`, `TestUnreadableStoredKeyPagesRender`, `TestProofSignedBySubkeyOfKeyWithoutUserIDSelfSignatureRefused`). A saved key that cannot be read never lets PGP sign-in fall back to the password alone (A-272): while PGP sign-in is on and the key cannot be read (or no longer matches its ownership proof), a correct password on `/login` either leads to `/challenge` asking for the authenticator code or a recovery code (TOTP enrolled; the PGP method is not offered) or is refused with 409 and no session or pending sign-in: "PGP sign-in is on for this account, but your saved PGP key can no longer be read …", that PGP sign-in is the account's only method, that an administrator can turn it off with *Reset a user's second factors* (for an administrator, whom that web reset refuses, only the operator's `-reset-admin-factors` is named), what to do after that, and the staff contact (A-119). A wrong password still gets "Invalid handle or password". After a correct password the owner is notified once per saved key (plain text: no key, fingerprint or code; not again until the key is changed; concurrent sign-ins send one, as the account row is locked first) that PGP sign-in could not be used (`TestUnreadableKeyRefusesPasswordOnlySignIn`, `TestUnreadableKeyWithTOTPSignsInWithAuthenticator`, `TestUnreadableKeyNoticeOncePerSavedKey`, `TestUnreadableKeyNoticeConcurrentCallsSendOne`). The key is stored as a canonical re-armor of its decoded packets: the packets (user IDs, signatures, subkeys) are unchanged, but text before or after the block, armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped. Keys saved before this are shown in the same canonical form wherever they are displayed (no rewrite migration; a stored key that no longer parses is handled as before), and saving the profile again stores the canonical form. Re-saving the same key, as pasted or as the canonical text the form shows, is not a key change: ownership proof and PGP sign-in stay and no confirmation is asked. The account page shows the fingerprint and the key's user IDs and, above the key field, who can see the key. Re-armoring does not remove user IDs, the creation time or third-party signatures from the key; the note tells users to use a key made only for this market. Only public key, public subkey, user ID and signature packets are accepted and published (A-110). A key carrying a photo ID (an OpenPGP user attribute packet, usually an image of the owner's face) is refused on `/account` before any password check, with the `gpg --edit-key <fingerprint>`, `uid <n>`, `deluid`, `save` steps to remove it; a key with any other packet type (a compressed packet or a private/experimental one can carry a photo ID that GnuPG still imports; keyring trust packets) is refused with a `gpg --armor --export <fingerprint>` hint. Nothing is saved. A key stored with such packets before this refusal is never shown with them: its canonical form keeps only the allowed packets, dropping the signatures that follow a removed packet except direct-key signatures and key revocations (every other packet unchanged, same fingerprint), and the owner saving the account form stores that form. If that form is not exactly one key with the same fingerprint (a skipped packet sat between a user ID or subkey and its signature), the stored key is treated as unreadable: others see "No usable key", never the broken key or its ownership proof. There is no rewrite migration.
- Ownership is marked **Verified** (with UTC date) only after the user signs a server nonce (clearsigned or armored detached signature) or decrypts a nonce the server encrypted to the key, on `/pgp`. Decrypt challenges store only the nonce's SHA-256. Changing or removing the key clears verification, PGP sign-in and any open challenge (renewing the same key may keep them, see *Renewing the same key*); every change is audited with the fingerprint. Adding, changing or removing the key and turning PGP sign-in on or off need the current password on every account (A-152), plus a current authenticator code when TOTP is enrolled (recovery codes are not accepted here), as turning TOTP off does: a stolen session can neither add a factor that outlives "Sign out everywhere" nor swap in the key buyers encrypt shipping addresses to. The audit row notes how the change was confirmed. Saving the profile with the stored key unchanged does not re-parse it, so an older key the parser now rejects does not block the form, unless it holds a photo ID or a packet outside the A-110 allowlist: that key is refused until the owner pastes an export without them or removes it with their password.
- Optional PGP sign-in verification (second factor), available only for a verified key that can receive encrypted messages. After the password, the user requests a one-time code (POST `/challenge/pgp`), decrypts it locally and submits it on `/challenge`; only its SHA-256 is stored and it is deleted with the pending sign-in.
- **Sign-in code names the market** (A-572): the encrypted message names the handle, the market name, the UTC request time, until when it is valid (the pending sign-in's expiry, at most 10 minutes) and the official addresses, then the code on its last line; only the code is accepted, as before. The addresses come only from the operator's `OFFICIAL_ADDRESSES` (at most 8 HTTPS or HTTP v3 onion origins, validated at startup), never from `Host` or any request header; unset, the message says "no official address configured". The market name is flattened to one line so it cannot forge another line. A code requested on the private administrator listener (the socket handler's context capability, not a header) says it was requested on that private connection instead of pointing at the listed addresses, still without naming that onion. A native configuration that records the private administrator onion's address refuses it in that list; a Compose install, a native install whose administrator onion came from an older identity volume, an edited env file and `serve --official-addresses` are not checked, so there the operator must keep it out. This lets a user notice a relayed sign-in by comparing the address bar, but does not stop a user who ignores the instruction, and nothing proves the operator configured the right addresses. The key-ownership decrypt challenge on `/pgp` (a signed-in proof, separate code path) is unchanged; no other PGP challenge issues a sign-in code.
- PGP sign-in code hashes are bound to the current key fingerprint and exact ownership proof. Replacing/re-verifying a key invalidates older codes, even if the original key is later restored. Sensitive password-confirmed changes serialize with TOTP enrollment.
- `/messages` rejects anything that is not an OpenPGP-encrypted message (plaintext, signed-only, malformed or fake armor). The pasted text must be exactly one armored PGP MESSAGE block with only whitespace around it; the whole base64 body is decoded and must be session key packets followed by exactly one integrity-protected encrypted-data packet that runs to the end, so text before, inside or after the block is refused. The server stores a canonical re-armor of those packets: armor headers such as `Version:` and `Comment:` and CRLF line endings are dropped, never stored or shown. Each message shows "Encrypted (to recipient’s key)", "Encrypted (NOT to recipient’s key)" or "Encrypted (recipient unknown)", derived from the recipient key IDs in its packets compared with the recipient's saved key at send time. Since A-569 (policy: `docs/data-retention-privacy-policy.md`, private channels; `inspectMessage` in `messages_status.go`, no migration) a send stores only ciphertext its recipient can be expected to read, so new messages are "to recipient’s key" or "recipient unknown", never "NOT": after the plaintext check, a recipient whose saved key cannot receive encrypted messages now (none, unreadable, expired, revoked or signing-only; `canReceiveEncrypted`) is refused with 409, and a passphrase-only message (no public-key session packet) or one whose visible recipient key IDs are all other keys, even beside a hidden one, with 400; each refusal names what to do ("Encrypt it to <handle>’s key <fingerprint>", or ask the recipient to add a usable key) and stores, notifies and audits nothing. A message whose recipient key IDs are all hidden (`gpg --throw-keyids`) cannot be checked: without the `hidden_recipients` confirmation the compose form comes back (400) with the explanation, the recipient and its key, the ciphertext kept (canonical) and an unticked, required confirmation box, so a browser without JavaScript sends it with one more submission; confirmed, it is stored as "recipient unknown". `/messages?to=` also says, beside a recipient's missing or unusable key, that messages to them cannot be sent until they save a usable key (`TestMessageRecipientEnforcement`; browser, no JavaScript: `db-pgp-messages.spec.ts`). Migration 103 preserves a nullable send-time count of distinct visible additional key IDs; a badge warns about other visible keys even alongside hidden-recipient packets. Hidden recipients may also exist, and packet IDs do not prove decryptability. Labeled readonly textareas support keyboard copying of messages, deliveries and PGP challenges while preserving leading newlines and escaping markup. Messages stored before this check are inspected when displayed; their recipient match is reported as unknown. Messages stored as encrypted before the strict armor check are re-inspected when displayed and shown as not encrypted if they fail it; those that pass, and older messages found encrypted, are displayed as the canonical re-armor, so a stored armor header is never shown.
- **Message and recipient-lookup budgets** (A-516, in memory per app process, cleared by a restart): an account sends at most 20 messages in 10 minutes, apart from its budget of 100 changes; an attempt counts once its armor passes the format check, before the recipient lookup and packet inspection, so an unknown recipient or a refused packet counts too, and the 21st is refused with 429 "Message not sent: an account can send at most 20 messages in 10 minutes" and writes nothing (no message, notification or audit row; `TestMessageBudgetSeparateFromWrites`). `/messages?to=<handle>` looks up at most 60 different handles per account in 10 minutes (A-92); looking up a handle again in that window costs nothing. Past it the page shows neither the key nor whether the handle may be messaged, only that lookups are paused, so it no longer tells whether a handle exists (`TestMessageRecipientLookupBudget`).
- **Who can be messaged:** ordinary accounts may contact public vendors, listed or configured staff, and staff reachable through their own dispute. Vendors may reply to legitimate customers through visible orders or prior buyer/vendor exchanges; a saved buyer draft alone does not expose the buyer to its vendor. Historical buyer-to-buyer messages remain readable but never authorize replies. Vendor opt-out while away applies to both new and existing buyer conversations. A deactivated vendor is hidden from strangers; an existing customer may contact it only while it accepts messages. Unknown and forbidden recipients return the same response and no public key. Ordinary users have no arbitrary handle field; staff retain support compose access. The shared recipient rule governs sends, recipient-key lookup and reply links.
- Limits: the server cannot decrypt messages, so a key-ID match does not prove the contents (the bytes inside a well-formed encrypted-data packet are opaque to it); a hidden-recipient message the sender confirmed is "recipient unknown" and cannot prove the recipient can read it (a passphrase-only message, and one to a recipient without a usable key, were "recipient unknown" before A-569 and are now refused). Losing or letting the key expire locks PGP sign-in unless another factor is enrolled; an administrator can then turn PGP sign-in off for a non-administrator account (see P1 second-factor reset). When no code can be encrypted to the key, `/challenge/pgp` answers 409 saying so and naming what is left: the authenticator or a recovery code when TOTP is on, otherwise that PGP sign-in is the account's only method and an administrator can turn it off with *Reset a user's second factors* (for an administrator, only the operator's `-reset-admin-factors`), after which the owner renews the key (A-155).
- **Key expiry** (A-155): `/account` and `/pgp` show when the primary key and the encryption subkey expire (UTC date, "Never", or "Expired …"; for a key nothing can be encrypted to any more, the subkey that expired last). When encryption to the key stops within 30 days they say so with the renewal commands (`gpg --quick-set-expire <fingerprint> 2y`, and `… 2y '*'` for the subkeys); when nothing can be encrypted to the key now (`canReceiveEncrypted`) they say "Buyers cannot encrypt to this key" (A-225). Every running process checks all saved keys at startup and then once a day and notifies the owner once when encryption to the key stops within 30 days and once when it has stopped (the key or its encryption subkey expired), with the renewal commands and no fingerprint; `users.pgp_expiry_notice` records the notice per key and expiry, so each is sent once, also when sweeps overlap (a compare-and-set on that column), and a renewed or replaced key is warned about again (`TestKeyExpiryNotifiedOnce`, `TestConcurrentKeyExpirySweepsNotifyOnce`). A key that is signing only, revoked or unreadable gets no expiry notice. PGP sign-in can still be turned on for a key close to expiry; the dates and the notices are the warning.
- **Renewing the same key** (A-155): a pasted key with the saved key's fingerprint but different packets (a new expiry from `gpg --quick-set-expire`, a new user ID or subkey, a third-party certification) needs the password like any key change. It keeps the ownership proof and PGP sign-in, with the notice "Key updated: the same key (same fingerprint) with new signatures…", one owner notification and an audit row "Updated PGP key (same fingerprint …; ownership proof and PGP sign-in kept)", when every revocation signature (key, subkey or user ID) in the saved key is still in it and still revokes the same key, subkey or user ID as OpenPGP software reads the pasted key (A-261: a subkey or user ID revocation moved before the first user ID, where readers ignore it, or a revoked subkey or user ID left out, or an unrevoked copy of a revoked subkey added beside it, counts as a dropped revocation) and the encryption subkey it selects is the saved key's or one created no earlier (not a rollback to an older subkey). Otherwise it is saved as a changed key: proof, PGP sign-in and any open challenge are cleared, the change time is recorded, the owner is notified and `/account` shows an alert naming the missing revocation or the older subkey, never the plain "Profile saved." notice (`TestKeyExpiryShownAndRenewalKeepsSignIn`, `TestKeyUpdateThatDropsRevocationOrRollsBackSubkeyClearsProof`).
- Vendor pages and order pages show the other party's armored public key, grouped fingerprint and "Ownership verified YYYY-MM-DD" (UTC date only; the owner's `/account` and `/pgp` show the minute) only when a proof matches the saved key (otherwise "Ownership not verified"); a user without a usable key is named with a note that messages cannot be sent until they add one. A key is usable only if something can be encrypted to it now (A-68, one check, `canReceiveEncrypted` in `pgp.go`): not expired or revoked, with an encryption-capable subkey (or primary key) that is neither expired nor revoked. A saved key that has expired, is signing-only, or whose encryption subkey expired or was revoked is shown wherever a contact key is offered (vendor page, `/messages?to=`, order page, dispute staff contacts) as "No usable key", without its fingerprint or armored text; this is checked each time the page is shown, so a key that expires later stops being offered (`TestHuntUnusableEncryptionKeyShownAsUsableContact`). The owner's `/account` and `/pgp` pages say "Buyers cannot encrypt to this key"; on a paid physical order the vendor also sees a warning to update the key on `/account` (A-225, `TestPaidOrderVendorKeyStopsBeingUsable`). On a paid physical order, the buyer's view of the vendor's key says "This key was changed or re-verified on YYYY-MM-DD UTC, after this order was placed — confirm with the vendor before sending your address" when the key was added, replaced or updated without keeping its proof (`users.pgp_changed_at`, migration 067) or its ownership was proved again (`pgp_verified_at`) after the order was created; a key last changed and proved before the order shows nothing, nor does the vendor's view (A-158, `TestVendorKeyChangedAfterOrderWarnsBuyer`). Keys changed before migration 067 have no recorded change time, so only a later proof or change is warned about; a renewal that keeps the proof (A-155) is not a change. Vendor pages are public, so a vendor's key is shown to anonymous visitors. Contact and message links open `/messages?to=<handle>` with the recipient filled in (values not matching the handle pattern are ignored); that page shows the key, fingerprint and verification only of a handle the viewer may write to (see *Who can be messaged*, A-543); staff see any account's.

### P3 Orders

Implemented on the Foundation state machine; every action goes through the server-side transition table, row lock and compare-and-set, so a forbidden move returns 403, a stale or repeated one 409, and nothing reports success without a recorded state change.

- **Confirmation wait**: a deposit that is still confirming keeps its escrow order open while the watcher checks its required confirmations. The daemon sync guard delays payment-window expiry during an outage.
- **Encryption-key requirement**: both buyer and vendor need usable PGP public encryption keys for every new draft and payment checkout, for physical and digital listings; the buyer must also prove challenge decryption in the current session, while optional PGP sign-in enrollment remains separate. Existing order access, cancellation and dispute rights remain available.
- **Payment request**: buyer drafts request Monero escrow through `/orders/escrow-xmr`. Checkout reserves stock, records the current listing snapshot and pins a fresh refund address. `/orders/pay` and Bitcoin checkout are unavailable.
- **Cancellation** (`/orders/cancel`): buyer cancels a draft; buyer or vendor cancels an order awaiting payment (the system does when the payment window expires); vendor cancels a paid order. Reserved stock is returned. When confirmed deposits exist, the escrow refund is requested for the buyer (see P5). A vendor's cancel of a paid order needs the settlement confirmation below.
- **Shipping and completion**: the vendor marks a paid physical order shipped with a fresh claim address and password confirmation (`TestXMREscrowShipStepUp`). The buyer confirms receipt with password step-up (`TestXMREscrowConfirmReceiptStepUp`); the shared release deadline can also complete an undisputed order. The buyer may cancel a paid physical order that was not shipped within the recorded window (`TestXMREscrowNoShipCancel`). Digital funding follows the server-side transitions and automatic delivery (`TestXMREscrowFundingThreshold`; real fakechain: `TestXMREscrowRegtestFunding`).
- **Settlement confirmation**: a vendor cancellation, administrator dispute decision or party concession chooses the recorded Monero escrow outcome with password confirmation. The watcher builds and sends that release or refund from the order account.
- **Overpayments**: the settlement plan records each destination and amount before relay. Extra eligible deposits can require a separate stray refund to the buyer’s pinned address, less fees; amounts below the Monero output floor follow the documented settlement rules.
- **Automatic delivery**: when the escrow watcher marks a digital order paid, distinct-inventory mode combines its reserved entries into one delivery and reusable mode supplies the listing content. The combined content is encrypted to the buyer’s usable PGP key, recorded, and the order moves to delivered as the system actor in the same transaction. An unusable buyer key or encryption failure leaves delivery pending, without storing plaintext. Manual mode waits for one vendor submission covering the whole quantity.
- New manual delivery follows the same buyer encryption rule before storage; its plaintext input exists on the running server while it is encrypted. Delivery records are written only in the delivered transition’s transaction and shown as armor to the buyer and vendor, and read-only to eligible dispute staff. The shared listing template and older plaintext delivery records remain server-readable.
- **Party concessions** (A-166): the buyer may release a disputed order to the vendor; the vendor may refund it to the buyer. The amount statement, required acknowledgment and current password/authenticator confirmation apply. The dispute closes atomically before the order transition; a simultaneous staff resolution has one winner and one conflict. Concession does not return stock. Parties see withdrawn concessions in the closed list and counts, and independent staff retain order access through the dispute record. Closure notices go to currently eligible unsuspended independent staff, with administrator fallback; no durable opening-recipient list exists.

- **Disputes**: an eligible party opens a dispute with a reason. Only an independent administrator decides a Monero escrow release or refund, with password confirmation and an unchanged recorded amount. The decision is final because the custodial watcher can send immediately. Reasons and decisions are plaintext; private evidence belongs in recipient-encrypted messages.
- **Dispute reply** (A-124; POST `/disputes/reply`): while a dispute is open, the party who did not open it (the actor of the move to disputed) may put one reply of 20–5000 characters on record from the order page. It is stored once as a disputed → disputed `order_events` row (note "Dispute reply: …"; no state change, the transition table is not involved) and shown under Dispute on the order page to both parties and staff reviewers, and on `/disputes` and the moderation desk, labelled with its author's role; the history entry says only that a reply was made. The reason, reply and decision keep their line breaks (`white-space: pre-wrap`). The opener is refused (403), a second reply, a reply after resolution, on an order with no dispute or on a dispute with no recorded opener are refused (409), and nothing is written; the dispute row is locked first, so concurrent replies store one. The dispute-opened notice to the other party says it may reply. The form carries the same stored-unencrypted warning as the other plaintext fields, and first points to encrypted messages to dispute staff when one of them has a usable key (or says none has). The resolve form says whether the other party replied, and carries what it showed (`reply_seen`): once a reply is on record, `/resolve` refuses a form that did not show it (or does not say) with 409 and the moderation desk again, showing the reply, the reason in its alert ("The vendor replied to this dispute after the form was loaded. …") and the typed decision kept, and nothing changes; the check runs under the dispute row lock the reply takes, so a reply racing the decision is either seen or refused (A-280; `TestDisputeCounterpartyResponse`, `TestResolveRefusesFormLoadedBeforeReply`; browser: `db-disputes.spec.ts`).
- **Who decides, as the parties see it** (A-584; templates only): on an escrow order (one with an `escrows` row; eligibleResolverSQL) the order page tells the buyer and vendor that an administrator who is not a party decides the dispute: in the open-dispute help (`/disputes` says it for escrow orders), the reply help ("The administrator who decides this dispute reads your reply…"), the decision heading ("Administrator decision") and *Contact dispute staff*, which advises messaging an independent administrator first and labels administrators "decides escrow disputes" and moderators "can pass evidence on to an administrator". The panel lists the same independent, unsuspended moderators and administrators as before. A historical order without escrow, which a moderator may still decide, keeps the moderator wording (`TestXMREscrowDisputePartyCopy`; browser: `db-disputes.spec.ts`).
- **Private staff correspondence** (A-162): the resolve form and desk entry of each open dispute list, for staff who are not party to it, the moderators and administrators each party messaged since the dispute opened, with the count and the latest time ("Buyer → mod_a (2, latest …)", "Vendor → none"; a holder suspended since is labelled "mod_a (suspended) (2, latest …)", A-280; one removed from staff after the message, as its role-change audit row records, stays listed as "mod_a (no longer staff) (2, latest …)" counting only the messages sent before the latest such change, A-294, A-304), read from message metadata only; a party's own staff account is never listed as a holder (A-285) (never a body or ciphertext); the resolve help points first to image evidence on the order, and says to ask private correspondents about any earlier evidence, or that neither party messaged a current moderator or administrator, nor one recorded as removed from staff after being messaged. The parties' "Contact dispute staff" panel says other staff can see which staff member they messaged and when, never what (`TestDeskShowsWhoHoldsDisputeEvidence`). The role-change rows are read through the partial index `audit_events_role_change` (migration 072, A-301), not by scanning the audit log (`TestDisputeEvidenceReadsRoleChangesByIndex`).
- **Verified reviews**: one per completed order, by its buyer, rating 1–5 and up to 2000 characters. Product, vendor and order pages label them "Completed order (test network)" on a test market because each is keyed to a completed order; reviewer handles and order ids are not shown publicly and dates are shown by month.
- **Hiding reviews** (A-125; POST `/admin/review`): administrators can hide a review, for example one that exposes a vendor's identity, and restore it. An administrator viewing a product or vendor page gets *Hide this review* under each review (a `<details>` form; no ID is typed), confirmed with their own password (and authenticator code when enrolled). A hidden review is kept (`reviews.hidden_at`, migration 031): it is left out of the public list and of the rating average and count on both pages; the buyer and vendor still see it on the order, labelled "Hidden from the listing and vendor pages by an administrator". Administrators see hidden reviews on the product and vendor pages labelled "Hidden by an administrator", with a count of hidden reviews and a *Restore this review* form, which works the same way. Both actions are audited on the administrator ("Hid review of order <8-character order ID> (confirmed with password)", "Restored review of order …") and on the reviewer ("Review of order … hidden by administrator <handle>"), and the reviewer gets a link-free notification; none of them copies the review text. Hiding a hidden review or restoring a public one is answered 409 without change; an unknown review 404; moderators, vendors and buyers 403 (reviews are content moderation, an administrator power like suspension and listing edits; moderators handle disputes and payment reviews). There is no report-a-review button: someone who wants a review hidden contacts the market staff. Tests: `review_hide_test.go`, `tests/e2e/db-review-hide.spec.ts`.
- Order pages show the full transition history (actor and time), the moves available to the viewer, the dispute reason, the other party's reply and the decision, the other party's PGP key, and the delivery and review panels. Orders, vendor desk and moderator desk list the relevant orders with their state; the moderator desk links each dispute to its order page. Open work is never hidden by a row cap: the moderation desk and the disputes page list every open dispute (oldest first) before the 100 most recent resolved ones, the vendor desk lists every paid order on the vendor's listings (oldest first, counted in "To fulfil") before the 100 most recent other orders, and each page says when older history is not shown. The disputes page offers every paid, shipped or delivered order for a new dispute. The orders page, messages and notifications still show only the 100 most recent rows. There is no admin order list (A-127): staff see an order only while it is disputed or resolved or a payment on it is flagged for review ([What the server keeps](#what-the-server-keeps)).
- **Staff access to orders**: independent staff may read authorized dispute and payment-review cases. A Monero account-collision record also opens a staff alert until its password-confirmed disposition (`TestXMREscrowCollisionStaffAlert`, `TestXMREscrowCollisionConcurrentDisposition`, `TestXMREscrowCollisionRecordedOnce`). A settlement requested for more than 24 hours can appear as an alert (`TestXMREscrowRequestedSettlementStaffAlertAfter24Hours`); that threshold remains experimental. A failed Monero settlement that was not superseded, and one set aside because building it stopped the escrow wallet-rpc, are alerts too (A-560): the desk entry and the order page's staff help say whether it can be re-requested (its transaction is stored) or built again, and otherwise to settle what it owed by hand with the operator; a payment-review row of a deposit that a failed settlement spends says it failed, and the parties see none of this (`TestXMREscrowFailedSettlementStaffAlert`, simulated wallet RPC). A failed settlement without a stored transaction is never re-requested (A-613): a refund too few raises no alert, because its deposits are flagged for payment review and returned by a stray refund (`TestXMREscrowRefundTooFewNoStaffAlert`); any other (nothing-to-settle: nothing was sent because no deposit counted at that time) stays an alert until an administrator who is not a party dismisses it as nothing owed on the order page, with a note, the password and an audit row, which clears the desk entry, the badge, the staff help and retention's `escrow_alert` reason; the alert and the form say not to pay it by hand, and a deposit listed again afterwards is still handled automatically (a stray refund returns it) and flagged for review (PAY613-1, `TestXMREscrowDismissedDepositReturnsAutomatically`); one that still claims a deposit (a re-request that failed so, PAY613-4) is never dismissed: its alert and payment-review reason say its coins are in the escrow wallet and to settle with the operator, and nothing in the market clears that alert (`TestXMREscrowClaimingUnbuiltNotDismissed`); since A-614 the market leaves no such row, because a re-request whose claimed deposit is no longer listed stays requested (*deposit-missing*, staff told once, no bounded wait since it can spend no other coins) and is built from exactly the stored key images once the deposit is listed again, while the payment-review reason of each deposit it claims and the desk's 24-hour line name it and say not to pay it by hand (A-617) (`TestXMREscrowReRequestWaitsForMissingDeposit`, simulated wallet RPC; `TestXMREscrowRegtestReRequest`, local fakechain run only, not yet CI), so only a database that ran an earlier build can hold one; the record is staff-only and written once (`TestXMREscrowSettledByHand`, `TestXMREscrowSettledByHandConcurrent`, `TestXMREscrowSettledByHandReplay`, simulated wallet RPC; no browser journey reaches an unbuilt failure). A failed settlement with a stored transaction whose re-request was refused on-chain or key-image-spent can never be superseded: its alert tells staff to check the wallet and the chain, then marking it settled by hand clears it (refused before any re-request, while one waits and after an in-pool refusal, which is re-requested again later), after which it is never re-requested again (`TestXMREscrowSettledByHandRefusedReRequest`, `TestXMREscrowSettledByHandFinalRefusalsOnly`, simulated wallet RPC; no browser journey). A retention retirement deletes the record with the order (`TestRetentionEscrowRetirementMoneroDeletesDismissedSettlement`). Unrelated orders remain private.
- **Restore pause shown to staff** (A-559): while Monero escrow is on and the restore gate (`payments_recovery_required`) or the restore sweep (`xmr_escrow_sweep_required`) is set, the staff summary on `/admin` and `/moderator` carries an alert naming what is paused and what still runs, *Admin → Payments* flags the gate and sweep on the Monero escrow recovery view with the number of checkouts refused while paused since the server started (in memory only), and *Escrow readiness* reads `intake: paused (restore)`. A checkout refused by the pause is a 503 refusal page logged as `http paused …`, not a referenced server error, so it is not listed under *Recent server errors*. The sweep completing under the gate notifies each administrator once (in the transaction that clears its marker). Nothing here clears the gate: that stays the operator's reconciliation step (`TestXMREscrowRestoreGateVisible`, `TestXMREscrowRestoreGateQuietWhenOff`).
- **No shipping address field.** For a paid physical order the buyer is prompted to send the address as a message encrypted to the vendor's key; the vendor is told to check Order correspondence. If the vendor's key stopped being usable after payment (expired or removed), the buyer sees "No usable key" in place of that prompt, with a warning never to send the address unencrypted: message the vendor or open a dispute (`TestPaidOrderVendorKeyStopsBeingUsable`). The market keeps that encrypted message (and who sent it to whom and when) but cannot read it. It cannot stop an address being typed into a plaintext field: the vendor's note to the buyer, the cancellation reason, the dispute reason, the dispute reply and the review text are stored unencrypted. Each of those fields says so, who can read it (the other party; moderators and administrators when the order is disputed or a payment on it is flagged, or every moderator and administrator for a dispute reason or reply; the public, and the vendor with the buyer's handle, for a review; the operator and backups), and never to include an address, real name or tracking number but to send them encrypted from the order page. The help is tied to its field with `aria-describedby`.

Limits: service listings have no ship/deliver step, so a paid service order can only be cancelled by the vendor or disputed. One timer completes orders: a shipped Monero escrow order with no dispute is completed automatically at its release deadline (`release_at`) and its release becomes buildable; it does not run while the restore gate is set (`TestXMREscrowDeadlineWithBTCOff`, `TestXMREscrowDeadlineDisputeRace`, `TestXMREscrowRestoreExtendsDeadline`). Moderators cannot see encrypted buyer/vendor order correspondence. Actual parties upload JPEG/PNG evidence on the disputed order; parties and independent dispute staff may view those normalized images. Private staff support remains a separate direct channel, and its metadata can still help locate earlier evidence sent privately.

### P4 Inventory

- Vendors edit their own listings at `/listing-edit?id=` (title, description, category, subcategory, primary and additional shipping regions, fulfillment type, stock, XMR price, optional automatic delivery content). Administrators may edit any listing except its automatic delivery content: an administrator editing another vendor's listing sees only whether content is set ("only the vendor can view or change it"), their saves keep the stored content whatever the form sends, and changing such a listing to physical is refused (400) while content is stored. The audit log records "as administrator". When an administrator's save changes another vendor's listing, the same transaction notifies the vendor (link-free, naming the listing and the changed fields: title, description, category, subcategory, region, additional shipping regions, fulfillment type, Monero price, stock, dispatch window) and records "Listing <8-char id> edited by administrator <handle>: changed …" in the vendor's audit trail; a save that changes nothing, and a vendor's edit of their own listing, write neither (A-516, `TestAdminListingEditNotifiesVendor`). Other vendors get 404.
- Create and edit share one validator. Only physical and digital fulfillment are supported. The XMR price must be at least 0.001 XMR; a lower price is refused with a field-specific reason. A pre-existing below-floor listing cannot create a new Monero draft and must be raised before ordering (`TestLegacySubFloorMoneroListing`).
- **Legacy service listings (A-20):** product, checkout and listing-edit pages identify the actual product kind; a legacy `service` listing cannot be ordered or funded, and editing requires an explicit supported fulfillment kind instead of silently converting it. Backend refusals remain in force (`TestLegacyServiceListingRequiresExplicitSupportedKind`, `TestLegacyServiceCannotBeOrdered`).
- Archive/restore (`/listings/archive`, `/listings/restore`): archived listings disappear from the catalog, search, checkout and vendor pages, and new order drafts are refused (400). The owner still sees them on the vendor desk with an "Archived" badge. Existing orders are not changed. The product page of an archived (or taken-down) listing answers 404 except to whoever may read an order placed on it, by the order page's rule: its buyer and vendor, and moderators and administrators while that order is disputed or resolved or has a dispute record from a party concession or has a flagged payment (A-164). They see the listing as it is now with an "Archived" badge, no order-draft link and no delivery content (never the takedown reason); its photos are shown there on the signed-in `/desk/img` route under the same rule, while the public image route still refuses them (A-264). The order page links to the listing ("Listing as it is now; it may have changed since purchase"), as do the moderation desk's dispute entries and payment-review rows, the `/disputes` entries and the vendor desk's incoming-order rows, for whoever may open the order (A-265, `TestDeskOrderRowsLinkTheirListing`); no snapshot of the listing at payment is kept yet (A-58).
- **Listing takedown** (A-163; POST `/admin/listing`): an administrator archives another vendor's listing only by taking it down from its edit page (*Take down listing*, a `<details>` form), with a reason of 10–500 characters (after trimming, with no NUL byte; otherwise 400) and their own password (and authenticator code when enrolled). The plain archive answers an administrator 400 on another vendor's listing; an administrator's own listing is archived from the vendor desk as usual. The reason is stored unencrypted in `products.admin_archive_reason` (migration 041; non-NULL only while archived) and shown to the vendor on `/listing-edit` and on the vendor desk card ("Taken down"), never on public pages. Both accounts are audited with the reason ("Took down listing <8-character ID> of <vendor>: …", "Listing … taken down by administrator <handle>: …") and the vendor gets one link-free notification with the listing's title, the reason and what it means. The vendor can still edit the listing, but their restore is answered 409 quoting the reason and telling them to ask an administrator to review it, with the staff contact (A-119, A-279), as the vendor desk card and the edit page do; the takedown notification shows it under it on `/notifications`; an administrator's plain restore is 409 as well. Only the administrator's *Restore listing* form, confirmed the same way, clears the reason; like every restore it is refused (409) when the owner is no longer a vendor, and it share-locks the owner's account row so a concurrent role change is not missed (A-70). Archiving by a role change never sets a reason. While a listing is taken down, a payment confirmed on one of its digital orders leaves the order paid instead of releasing the automatic delivery content, with the history note "Not delivered automatically: an administrator took this listing down…"; the vendor delivers by hand or cancels and refunds. Other roles get 403. Tests: `listing_takedown_test.go`, `tests/e2e/db-listing-takedown.spec.ts`.
- Assigning Buyer or explicitly revoking selling approval archives active listings in the same transaction. Promotion of an approved vendor to moderator or administrator preserves selling access and listings. Administrators derive selling authority only while holding that role. Approved moderators use the same listing, checkout, photo and vendor-desk workflows. Former sellers retain historical order access. Private staff uploads recheck selling approval at authorization, gateway admission and final storage.
- The fulfillment type cannot change while the listing has open orders (409), because orders read it from the listing. A draft takes the current price when it is resubmitted and again when payment is requested; from then on the order keeps that price.
- Stock edits are refused (409) when stock changed after the form was opened (payment requests reserve stock); saving other fields keeps the current stock.
- The reusable automatic-delivery listing template is digital-only, at most 32000 characters, **stored unencrypted in PostgreSQL**, and never loaded on public pages. It is released only by the order package's confirmed-payment step, so the editor says "Automatic delivery requires a payment provider" whenever no provider is configured.

- **Interrupted listing uploads (A-207):** after a valid listing ID is parsed, an upload refusal while the multipart body is still being read links back to that listing; invalid IDs and photo-first forms retain the vendor-desk fallback. The no-JavaScript oversized-photo regression covers the listing backlink.

### P5 Payments

Monero per-order custodial escrow is the only payment path. Checkout claims an account in a monthly wallet, pins the buyer's refund address and waits for the configured confirmations. The market builds and checks each settlement, stores it before relay and never automatically rebuilds an ambiguous send. Network pins, a wallet-secret pin, the offline seed recipient and a dedicated wallet-rpc protect configuration consistency.

Digital orders can be claimed by the vendor. Physical orders release after buyer confirmation or the recorded release deadline; administrator dispute decisions determine release or refund. Wallet retention, late-deposit handling, guarded retries and restore reconciliation are described in [Monero escrow](escrow.md) and the [operator guide](operator-guide.md#monero-escrow).

Fakechain tests exercise real daemon and wallet behavior. Browser journeys use a simulated wallet with JavaScript disabled; they are not chain evidence. The recorded public stagenet digital claim does not establish public refund, physical-deadline, Tor-delivery or mainnet readiness.

### P6 Transparency

- **Operator key.** An administrator saves the operator's armored OpenPGP public key (`/admin/operator-key`); it is parsed (single, unrevoked public key; private keys, photo IDs and other non-public-key packets rejected), stored without armor metadata, and its fingerprint recorded in the audit log. Previously stored operator keys are shown with only public keys, subkeys, user IDs and signatures; an unusable stripped key is not shown.
- **Warrant canary.** The administrator pastes a statement the operator clearsigned offline (`/admin/canary`). It is rejected with the reason unless it is exactly one clearsigned message, with nothing before or after it, that verifies against the operator key. Accepted text is stored as pasted in a single-row `canary` table (migration 060). `/canary` re-verifies it on every view and shows exactly one of: "No signed canary published", "Signature verified" (statement, grouped fingerprint, signature date, posted date, the signed message and public key for independent `gpg --verify`), or "INVALID" with the reason (for example after a key change or database tampering). The application never writes, edits or signs canary text.
- **Signed audit export.** Administrators download `/admin/audit-export?upto=N` as NDJSON (`id`, `user_id`, `handle`, `action`, `created` in RFC 3339 UTC, ordered by id) and `&sig=1` as a text file with the Ed25519 public key, SHA-256 and signature over the exact export bytes. The key is read only from `AUDIT_SIGNING_KEY`; when it is unset or malformed the export returns 409 and the admin and `/canary` pages say it is unavailable. `upto` must not exceed the latest settled event (a brief `SHARE` lock waits for in-flight audit writers), so the same `upto` always yields byte-identical files. Rate limit: 10 downloads per 10 minutes per administrator. One export per server process is admitted through its final response write, bounding concurrent export buffers; another receives 503 with `Retry-After: 5` (`TestAuditExportOneBufferThroughFailedDownload`). The public key is published on `/canary`. The export sets its own time limits (A-139): one minute to read the events instead of the 12 s request bound (it also moves the server's 15 s read deadline, defensively only: net/http already clears the read deadline once a body-less GET has been read, so that timeout never cancels the export), then 20 s plus one second per 32 KiB to send the file instead of the server's 20 s write timeout, so a large export survives onion throughput (0.19–0.45 MB/s measured); every other route keeps the server's timeouts (`TestAuditExportOutlivesServerTimeouts`, `TestAuditExportBuildOutlivesRequestBound`, `TestAuditExportWriteWindowScalesWithSize`). A download cut short fails `verify-audit` with "export sha256 does not match the signature file", and the admin page says so.
- **Verifier.** `go run ./cmd/verify-audit -pub <hex> export.jsonl export.sig` (standard library only) checks the signature with the pinned key, not the key named in the `.sig` file, and that events are well formed with ascending ids; exit status 0 or 1.
- **Limits.** The signature proves origin from the server-held key only. Anyone controlling the server (or `AUDIT_SIGNING_KEY`) can sign an altered history; exports are not a tamper-proof log. Canary verification proves which key signed the text, not that its author acts freely or that the statement is true.

## Native application-host bootstrap and configuration recovery

`host plan/packages/apply/confirm/rollback` provide a versioned Ubuntu 24.04
static-network application-host ingress recipe, optional distribution dependency
installation, owned nftables table, pending-change rollback and boot dependencies
for Docker/containerd. SSH is verified against preconfigured key-only access; it
is not rewritten. Persistent sysctl/coredump/update defaults apply subsequently.
See [supported profile and verification boundaries](install/server-bootstrap.md).

`deploy recovery export/restore` preserves encrypted operator configuration,
application secrets, TLS materials and managed Tor identities. Restore starts no
services and requires explicit production storage rebinding. It excludes database,
wallets, volumes and current external retention state; see [recovery](install/recovery.md).
No production host, locked reboot or live Tor recovery is established by unit tests.

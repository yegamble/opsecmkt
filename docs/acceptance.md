# Acceptance checklist and capability boundaries

## Marketplace design and private order communication

- [x] Real subcategories and additional shipping regions persist through listing creation/editing; category/type/destination/search filters combine and survive sorting and pagination. Ratings count only eligible public reviews. Vendor links remain separate from listing links (`TestCatalogDesign*`, `preview-catalog-design.spec.ts`).
- [x] Administrators have derived verified selling access, moderators need independent approval, revocation preserves historical orders, and private ingress remains protected. Hidden staff with no published listing are not exposed by generic vendor-contact lookup (`TestVendorCapability*`, `TestSellingCapabilityDoesNotExposeHiddenStaffContacts`, `db-vendor-capabilities.spec.ts`).
- [x] Order correspondence and append-only digital replacements remain order-bound, exclude the direct inbox, enforce actual-party permissions and use the order-private retention clock without extending it (`TestOrderMessages*`, `TestOrderChannel*`, `db-order-channels.spec.ts`). Existing direct messages are not assigned to inferred orders.
- [x] Valid pasted PGP ciphertext retains identical decoded packets and decrypts once to the original text; replay sends once. Plaintext and invalid/wrong-recipient ciphertext remain rejected. Automatic server-side plaintext encryption is not implemented (`TestPastedCiphertextIsNeverEncryptedAgain`, `TestMessageRecipientEnforcement`).
- [x] Dispute JPEG/PNG evidence uses ClamAV on every accepted upload, strips metadata through normalization, refuses documents/SVG, enforces private case access and quotas, and participates in preservation, purge and restore replay (`TestDisputeEvidence*`). Private approved-moderator photo handoff and retention-restricted staff evidence complete without enabling their listing/avatar uploads (`TestApprovedModeratorPrivatePhotoCapability`, `TestRestrictedPrivatePartyCanUploadOnlyDisputeEvidence`).
- [x] A published listing no buyer can order now is marked "Not available for purchase" instead of "N AVAILABLE" on the catalog (with search, category, region and paging; the count and pages are unchanged and agree with the cards), on its vendor's public page and, with the reason and what the vendor can do, on the vendor desk: a suspended or banned seller, a seller no longer a vendor (no storefront, 404), a vendor on vacation or without a usable encryption key, a legacy service listing, a distinct-inventory digital listing with no free unit, a price below the settlement minimum, and while intake is escrow only a listing escrow does not take (no dispatch window, no deliverable reusable content) or every listing when Monero escrow is not enabled. The draft action refuses each one and accepts the control; the draft action, escrow checkout's seller check and the product page read the same rule (`purchasable.go`). Paused intake is market-wide and does not mark listings (`TestCatalogMarksUnbuyableListings`, `TestCatalogMarksEscrowIneligibleListings`, `db-catalog-paging.spec.ts`).
- [x] Published sold-out listings remain visible by default and an optional stock filter hides them. Multi-unit drafts use checked totals; checkout atomically reserves the saved quantity and cancellation returns it once, with no payment mutation on stale-stock or overflow refusal (`order_quantity_test.go`, `catalog_stock_test.go`).
- [x] A-520 (PRIV60-6): a listing's exact stock is shown only to its vendor, moderators and administrators; buyers and signed-out visitors see its band (1–5, 6–20, 21+) on catalog and vendor-page cards, the listing page and the checkout page, whose quantity field carries no exact maximum; a quantity above the stock is refused with the same count-free message; sold-out and unbuyable cards and the in-stock filter are unchanged (`TestStockBandEdges`, `TestPublicStockShownInBands`, fails against the previous templates; browser: `db-batched-orders.spec.ts`, `db-catalog-paging.spec.ts`).

- [x] Manual digital fulfillment submits one batch for the whole order; distinct automatic inventory allocates separate entries into one bounded, scrolling delivery. Private inventory, consumed-state protection and listing/order purge replay pass the final local PostgreSQL race and browser checks. Cancellation cannot return entries to an expired listing; they remain subject to their order's private lifecycle (`digital_inventory_test.go`, `db-batched-orders.spec.ts`).

These are implementation and local test claims. Browser preview, browser database, simulated wallet RPC and deployment evidence remain separate; the war-room ledger records the integrated run and its limits.


## Optional security hardening

Use the [focused security checks](operations-tests.md#optional-security-controls)
for private administrator ingress, encrypted audit exports and deployment
packages. Their test coverage must include header spoofing, public administrator
session denial on shared staff routes, ordinary moderator access, absent or
malformed client authorization, socket lifecycle, ciphertext round-trip and
signature verification, and package runtime sources and exclusions.

Code and Compose tests do not establish deployed Tor client authorization.
Require the [operator access rehearsal](install/tor.md#verify-access-and-maintain-credentials)
and offline export verification before activating these optional controls in
production. Keep live Tor reachability, image builds and container mount behavior
marked unverified until a run records them.

Native production Tor requires private administrator ingress. The current
[native CLI evidence](evidence/native-cli-2026-10-15.md) records local Docker
startup, application-only replacement, Linux RAM unlock and offline Tor startup.
It does not establish remote host isolation or a live authorized Tor circuit.
Production acceptance must also check the separate upload host's failure/scan
states, administrator-only topology/version notices, independent report signing
pin, persistent retention outside RAM and recovery with the same keys/identities.
Emergency device/reboot tests use fakes; validate destructive behavior only on
an explicitly approved disposable target through the
[manual incident procedure](install/ram-secrets-and-emergency.md).

This is a verification plan, not a declaration that every check has passed. Record actual results separately. ## Moderation agent

Use the [moderation design](moderation-agent-design.md) and
[operator guide](moderation-agent.md) when reviewing this service. These are
acceptance requirements, not a declaration of deployed verification:

- Deterministic normalization and replay remain stable for the same input and
  policy. Injection fixtures include instruction overrides, delimiter imitation,
  Unicode controls and mixed scripts, oversized inputs, nested JSON and an
  instruction to mark an order delivered.
- Missing, timed-out, stopped and invalid local model responses leave the market
  usable and preserve a human-review path. No vendor request waits for inference.
- Grammar constraints are followed by Go schema, allowlist, bounds, canary and
  evidence-reference validation. Stage B receives validated findings rather than
  raw submitted text. No model response gains a tool, signer or database authority.
- The model does not judge listings by text (A-651, `moderation-v5`, v4 pins
  refused). With the model enabled, listing and upload jobs make no model call
  and the adapter refuses them; with no deterministic finding they record the
  Go-only `MODEL_NOT_USED` and route exactly as an absent model does
  (`QUEUE_HUMAN`, never `AUTO_APPLY`), while reviews still reach the model.
  Stage B has no `actor_reputation`, no market code sets a model's reputation figure
  (A-653's Go rule is for administrators only and never reaches the worker), and
  neither prompt carries a handle, PGP fingerprint, image hash, payment address,
  ban/takedown/listing-rejection reason or reputation figure; a stored v4
  decision keeps its bytes and still renders
  (`TestListingAndUploadNeverReachModel`, `TestStageBViewHasNoReputation`,
  `TestPromptsCarryNoIdentityOrBehaviourData`,
  `TestOldPromptPinAndDraftReplyAreRefused`,
  `TestModerationListingSkipsModelWhenEnabled`,
  `TestNoMarketCodeSetsActorReputation`,
  `TestModerationStoredV4DecisionStaysReadable`; unit and database integration
  with a capturing fake runtime, which proves what is sent, not model quality).
- Durable claims recover after interruption. Reprocessing one input/revision and
  policy reuses its decision identity. Stale entity revisions do not change
  marketplace state. Deadline expiry preserves state (`HOLD`).
- A capture refused by capacity is not lost: the marketplace write commits, one
  content-free marker per target remains, and the worker later captures that
  target's current revision once capacity frees, in first-refusal order and
  without a refused backlog spending the budget; deleted sources are dropped
  without an allocation at the next worker pass, and archiving a listing or
  hiding a review never withdraws it from capture. One account holds a
  bounded number of markers, past which (or past a full table, with a counted
  `backfill_capacity` warning) a lossless rescan of its live records takes over;
  a job made stale only by changed context is not captured again. An account
  with a backlog cannot jump it with fresh writes or change-time bumps, a vanished source never stops
  the worker, and disabling capture, the sweep, job completion (capacity row
  first, A-667) and account erasure do not deadlock. A revision that completed
  stale does not suppress a later capture of the same content, while an evaluated
  revision is still not queued twice. One actor cannot take more than its 24-hour
  share of lifetime allocations. New proposals hold no per-field digests
  (`TestModerationActorCapOverflowBackfilledAfterDrain`,
  `TestModerationPendingSaturationBackfill`,
  `TestModerationRetainedExhaustionBackfillAfterRaise`,
  `TestModerationBackfillCoalescesAndDropsDeletedSource`,
  `TestModerationBackfillTableBounded`, `TestModerationConcurrentBackfillSweep`,
  `TestModerationStaleRevisionRecapturedOnRevert`,
  `TestModerationActorShareOfLifetimeBudget`,
  `TestModerationArchivedRestoreRecaptured`,
  `TestModerationHiddenReviewUnhideRecaptured`,
  `TestModerationEditDoesNotDeferOwnMarker`,
  `TestModerationActorMarkerQuotaRescan`,
  `TestModerationActorRescanRepeatsAfterRefusalDuringScan`,
  `TestModerationRefusedBacklogDoesNotStarveSweep`,
  `TestModerationContextStaleDoesNotRecapture`,
  `TestModerationBacklogActorCannotJumpOwnQueue`,
  `TestModerationAdmissionSkipsUnknownActor`,
  `TestModerationSweepSurvivesConcurrentSourceRemoval`,
  `TestModerationDisableSweepNoDeadlock`,
  `TestModerationRescanOrderNotSteerableByChangeTime`,
  `TestModerationDeletedSourceReleasesMarkerCount`,
  `TestModerationDisableClearsRescanPosition`,
  `TestModerationArchiveDuringWindowStillCaptured`,
  `TestModerationDeleteTriggerNoDeadlock`,
  `TestModerationPrivacyV2NoFieldDigestsOrUnusedTextHash`; database integration,
  fake model).
- A marketplace write never waits on the capacity ledger (SEC72AA-1, migration
  148): while another session holds it, an edit or a new listing commits within
  2 seconds and leaves only a reference (kind, target id, time noted; no
  account, and no counter, overflow note, marker or account row touched). A
  transaction that admits one change and then locks a second listing (a
  moderated edit or a stock-only update) does not deadlock with a concurrent
  edit of that listing, nor with a worker result or a private-panel review that
  locks it, nor does a dispute resolution with a watcher flagging a locked
  deposit on the same order. The next pass (before its half-full queue check)
  admits each reference's current revision through normal admission and drops
  a deleted or unflagged source; deleting a record removes its reference without
  the ledger lock; capture disabled keeps the references. Concurrent admissions
  never exceed a cap, and after the drain the counters equal their rows and
  every listing is covered by a job, marker or rescan. The worker result, both
  reviews and the capture switch take the ledger row first
  (`TestModerationAdmissionNeverWaitsOnCapacity`,
  `TestModerationDeferredDrainIsLossless`, `TestModerationPersistLockOrder`,
  `TestModerationReviewActionLockOrder`,
  `TestModerationAdmissionResolveVsWatcherFlagNoDeadlock`,
  `TestModerationCapacityLockIsFirstStatement`,
  `TestModerationConcurrentAdmissionHasAtomicCaps`, and the admit-then-lock leg
  of `TestModerationDeleteTriggerNoDeadlock`, five runs, no deadlock; each
  deadlock test failed with SQLSTATE 40P01, or the held-ledger edit timed out,
  before migration 148; database integration, fake model).
- An administrator raises the lifetime moderation budget under Moderation
  budget on the private panel (A-654): password and enrolled TOTP, CSRF and a
  single-use form receipt; one audit row "Moderation budget raised from R1
  allocations / B1 MiB to R2 / B2 MiB by administrator X" with no target data; a
  replayed form raises nothing twice and concurrent raises serialise on the
  capacity row. A wrong password, a lower or unchanged value, a value out of
  bounds or below the allocations already made is refused with "Nothing was
  changed". Public ingress answers 404 before reading the body or a cookie. A
  target waiting under `retained_capacity` is captured on the next pass of the
  same worker and the Admin overview alert clears. A worker restarted with a
  lower `--max-records` or `--max-reserved-bytes` keeps the stored value and logs
  "stored moderation budget is higher; flag ignored"; a higher flag still raises
  it (`TestModerationBudgetRaiseConfirmedAudited`,
  `TestModerationBudgetRefusesLower`, `TestModerationBudgetPublicIngress404`,
  `TestModerationBudgetRaiseCapturesWaiting`,
  `TestWorkerFlagNeverLowersStoredBudget`; database integration, fake model).
- Proposal queues/status require an authenticated current administrator on the
  existing private ingress. The separate offline page accepts only a valid,
  revision-bound signed review token with CSRF/origin checks; it exposes no queue
  data without an application login. Public ingress, spoofed
  `Host`/forwarding headers and ordinary marketplace accounts cannot reach
  protected moderation data.
- Optional offline packets are encrypted before export and their signatures
  verify against an independently pinned worker key. Action-token signatures
  use a separate offline key and installation audience; replay, expiry, changed
  content and already-reviewed items are refused transactionally. Token review
  still changes no marketplace entity or payment.
- Moderation cannot move money, change an order, ban an account or hide a listing.
  Any later binding action uses the existing independently authorized workflow.
  The guard scans `internal/moderation`, `internal/market/moderation*`,
  `cmd/server/moderation*`, `internal/market/reputation*`, every other file that
  imports `internal/moderation`, the panel's templates and the reputation partial.
  In that code, not its comments, none names:
  - a ban, escrow, dispute-decision or order-change route;
  - a settlement or a refund address;
  - the state machine, the ban refund or a wallet send;
  - anything the money files declare, apart from three read-only dispute status
    texts that the reputation rule counts by.

  `internal/moderation` imports no database package. The rest may write only
  `moderation_*` tables, append to `audit_events`, and write `settings` with the
  one reviewed statement `UPDATE settings SET value=$1 WHERE key='moderation_enabled'`.
  That statement must match exactly (white space aside), appear once, in
  `moderation_worker.go`, as the literal query of an `Exec`/`ExecContext` call.
  Any other string literal that writes `settings` fails the scan. The key it
  names must be the only `moderation_` key in the migrated `settings` table. The
  moderation pages' forms post only under
  `/admin/moderation`, and no `moderation*` database function writes money,
  order, account, settings or audit tables. Reads are allowed: the worker's
  snapshot of the scored target, the reputation counts and the panel's link to
  its page.

  Evidence: `TestModerationNeverMovesMoney`, an AST and text scan. It was shown
  to fail on each of these plants:
  - a `transition`/`withBanRefund` call and a `payments` write;
  - a form posting to `/admin/ban-orders`;
  - the worker setting `payments_recovery_required` (as a literal key and as a
    parameter);
  - an `audit_events` update;
  - a `transition(` call in `reputation.go`.

  `TestModerationSettingsWritesExact` (unit) feeds the settings check these
  variants, and each is refused:
  - `OR true`, `OR key='payments_recovery_required'` and `key LIKE`;
  - a parameter key, another literal key, an `INSERT` or a `DELETE`;
  - a second statement in the same literal;
  - the reviewed statement extended by concatenation, by a format string, or
    through a constant;
  - the reviewed statement in another file.

  Not checked: SQL built from fragments at run time with no write verb in any
  literal.
- `/canary#records` and the retention summary say, in the same words whether
  collection is on or off, that legacy copies and new abuse-review references,
  digests and image fingerprints have no automatic expiry and remain after the
  source is removed; the photos item names the perceptual fingerprint
  (`TestNewAbuseReviewRecordNoticeIdenticalWithCaptureOnAndOff`,
  `TestRecordsListPhotosAndAvatars`, `preview-records.spec.ts`).
- A database at 001–124 plus 128 takes 125–127 and 134 on upgrade; a recorded
  migration whose name differs from this build's migration of that number is
  refused before any change (`TestModerationMigrationsAfterMain128`,
  `TestMigrationNameMismatchRefused`).
- The adapter accepts only its configured local Unix socket, with bounded calls
  and no external inference, redirects, model downloads or ambient proxy egress.
  Deployed runtime secret/mount/network isolation needs an actual host rehearsal;
  package tests alone cannot establish it.
- Administrator diagnostics expose only bounded review metadata and health
  classes, not runtime endpoints, credentials or raw transport errors. Verify
  no-JavaScript rendering and sensitive-data access on the deployed private path.
- Build documentation in strict mode and record actual test results. A skipped
  database, browser, runtime/container or live Tor check remains unverified.

Model selection, resource budget, SLA, evidence retention and deployed isolation
remain [operator decisions](moderation-agent-design.md#decide-operator-gates).

The strengthened v2 contract additionally requires:

- Model summaries/free evidence are refused; trusted Go presentation remains
  marker-free for custom model implementations and historical queue rows.
  Deterministic field-code evidence keeps its provenance without claiming model
  involvement. Actual native GBNF checks cover both finite-reference grammars.
- New pending/completed captures and archived inputs contain no copied prose.
  All five kinds bind hydration to the captured digest, changed/deleted sources
  skip inference, and completed raw actor links are removed. Historical copies
  survive an authentic pre-134 upgrade without rewritten bytes or timestamps.
- Barrier-concurrent actor/global/slot/byte admissions remain within their
  bounds. Duplicates, rollback, leases, retries and legacy policy replay charge
  and release exactly once. Saturation keeps actual listing/dispute workflows
  functional and shows bounded private warnings without a fabricated verdict.
- Every review signal is visible for human review, even with high confidence or
  a model's contradictory `NO_ACTION`. Stale financial evidence still escalates.
- Aging priority lets old ordinary work overtake new urgent work. Live ownership
  rate checks still work after completed actor-link removal. Restarted controllers
  preserve configured policy; explicit partial limit updates preserve other limits.
- Uniform, monotone and low-contrast new image hashes do not create perceptual
  matches. Exact SHA256 and useful informative/legacy hashes remain supported;
  no orientation/crop/semantic-image guarantee is implied.
- New gateway hashes use an anti-aliased downscale, so a recompressed or resized
  copy of a textured fixture, a 1% crop and a horizontal mirror (compared at match
  time; stored hashes are not rewritten) match within the perceptual threshold,
  and unrelated fixtures do not (synthetic fixtures only).
- A recognised external destination or a weak instruction phrase blocks automatic
  history (human review) without an injection accusation; strong injection markers,
  including reason-code suppression, still escalate. The labelled injection corpus
  records expected misses explicitly.

## Installation and deployment

  and imports. Regression tests cover private file permissions, overwrite refusal,
  secret redaction, mutual TLS and production topology validation.

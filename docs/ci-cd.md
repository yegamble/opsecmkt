# CI and release delivery

Every pull request and every push to `main` runs `.github/workflows/ci.yaml`; other branches are tested through their pull request, or on demand with **Run workflow** (`workflow_dispatch`). The stable **CI passed** check succeeds only when every mandatory job succeeds, including all matrix entries. Branch protection on `main` requires that check; do not accept a skipped or cancelled suite as a pass.

The suite covers:

- Workflow linting, Go formatting, module integrity, vet, race detection and coverage, with the Go tests split over two parallel jobs (see the next item). PostgreSQL integration tests cover schema migrations, the order state machine, every feature package (TOTP/CAPTCHA, PGP, orders, inventory, payments, canary/audit export) and per-order escrow integrations against simulated node RPCs. Fresh escrow-only migration and legacy refusal/record preservation are covered against PostgreSQL; retired pooled adapter and lifecycle tests are removed. No real node or wallet is contacted by these Go jobs (the `escrow-regtest` job below is the one that uses a real regtest node).
- The Go tests as two parallel jobs, **Go and PostgreSQL** (`go`) and **Go escrow and Monero tests** (`go-escrow`), each with its own runner and `postgres:17-alpine` service (A-465). Both run `go test -race -count=1 -timeout 17m ... ./...`, with the same pattern `'^(TestEscrow|TestXMR|FuzzEscrow)'`: `go` passes it as `-skip`, `go-escrow` as `-run`, so every top-level test (each name the packages' `go test -list .` output prints) runs in exactly one job, none is skipped from both and none is weakened; the count changes with every new test, so recheck it rather than trusting a number: `go test -list . ./... | grep -cE '^(Test|Fuzz|Example)'` is the total, `go test -list '^(TestEscrow|TestXMR|FuzzEscrow)' ./... | grep -cE '^(Test|Fuzz|Example)'` the `go-escrow` share, and the `go` job runs the rest. `go` keeps formatting, `go mod verify`, `go vet`, workflow linting, govulncheck, the `cjpeg` install (only `TestDecodeAllocationWithinEstimate` uses it) and the `go-coverage` artifact (`coverage.out`); `go-escrow` uploads `go-escrow-coverage` (`coverage-escrow.out`). Both are listed in **CI passed**. `tests/test_ci_go_split.py` fails unless the two patterns are the same string, anchored and without `/`, neither job narrows with a second selector, both keep `-race -count=1` and the 17-minute timeout, and `go-escrow` is in the aggregator; when you rename or add a test, check that its name lands in the job you expect (`go test -list '^(TestEscrow|TestXMR|FuzzEscrow)' ./...` lists the `go-escrow` set). **Why:** the single job's test step took 12 minutes on the head of PR #40 (cc4b565) and 14 min 42 s on 1438f96 (formatting, `go mod verify` and vet are inside that step), `internal/market` runs its tests serially (no `t.Parallel`) under a 17-minute per-package timeout, and Phase 4 adds tests there; raising a timeout would only hide the problem. **Balance**, measured on the shared 4-CPU development host under load (load average 7 to 8, other test suites running, so absolute times are about twice a quiet host's): with `go test -race -count=1 -skip|-run` against a dedicated PostgreSQL 17, the `-skip` half (740 tests) took 955 s wall (per-test sum 1074 s, of which `cmd/server` 129 s) and the `-run` half (353 tests, 27 of them real-regtest tests that skip without a node) 851 s wall (sum 842 s), together 1806 s: 53% and 47%, so neither is above 60% of the total. On a CI runner each half is expected to take roughly half of the former 14 min 42 s step; the CI durations are to be recorded here after the first run on a pull request. If a half grows toward the 17-minute limit again, split further by name prefix (for example `TestXMR` from `TestEscrow`; per-test sums in the `-run` half were 369 s for the 209 `TestEscrow` tests and 473 s for the 144 `TestXMR` tests) by adding a third job with the same `-run`/`-skip` rule, not by raising the timeout. `-timeout` is per package, so a package that exceeds it fails the job rather than being skipped.
- Bitcoin escrow against a real Bitcoin Core node on regtest (`escrow-regtest`, A-438; runs in parallel with the Go job, adds nothing to its time, and is listed in **CI passed**). The job starts `bitcoin/bitcoin:31.1` (the tag the installer and `compose.nodes.yaml` pin; `tests/test_ci_escrow_regtest.py` asserts the job's tag is the installer's) with `docker run`, because a service container cannot pass bitcoind arguments, next to a `postgres:17-alpine` service, then runs `scripts/test-escrow-regtest.sh`: every leg named in its header, with the app running inside `go test` against the node as the `rpcwhitelist` user and every party's signature made by that party's own Core wallet. A leg that fails, is skipped or does not run fails the job. The node has an operator user with full rights (standing in for the buyers' and vendors' own nodes), the app's whitelisted user, since A-454 the escrow signer's user (whitelisted to `decodepsbt`, `descriptorprocesspsbt` and, since QA4W2-1, `getdescriptorinfo`) with the retired pooled RPC user removed; the three RPC passwords are generated for each run (`openssl rand`), masked before any output, passed to bitcoind as salted HMACs (`-rpcauth`) and to the script inside the URLs through `GITHUB_ENV`, so none is committed, on a command line or in a log. Since A-441 a second node with the same users runs `-privatebroadcast -proxy=127.0.0.1:9 -listen=0` (a proxy nobody answers, inside its own container; not connected to the first node or any other) for the private-broadcast leg, with two more URLs, and its log is kept and it is removed with the first. The script fails a transcript that holds a serialized `tprv`. When the script's documented whitelists change, the job's copies must change with them (`tests/test_ci_escrow_regtest.py` fails until they agree). The transcript of the legs and the node's log are kept as the `escrow-regtest-results` artifact for 14 days (they hold txids, no passwords). The node is removed with its volume even when a step fails. **What it proves:** the escrow code does what the legs say against a real local chain, regtest, that nobody else can reach: real Core wallets, PSBT signing, finalizing, mempool policy, fee replacement, reorgs and confirmations. **What it does not prove:** anything on a public test network (signet, testnet4) or mainnet, with another wallet than Bitcoin Core, with Monero (the `escrow-xmr-regtest` job below covers only a local fakechain) or about the Tor deployment; the script refuses any node that does not report `regtest`, and no public network is contacted. Measured locally on 4 cores with the image already pulled (steps only, so without runner provisioning, the image and service pulls, checkout and Go setup): 89 s with a warm Go build cache and 129 s with a cold one, `go test` itself about 60 s; the job's 20-minute limit leaves the script's own 15-minute `go test` timeout to fire first. The CI duration is to be recorded here after the first run on a pull request. The script's `--private-signet` mode (A-443: two signet nodes with `-signetchallenge=51` on an internal Docker network) is not in CI: on a loaded 4-core host a first run took about 25 minutes (9 of them maturing its first coins) and a run from the cached datadir about 20, so it stays a manual check ([runbook](testnet-runbook.md#11-bitcoin-escrow-on-signet-or-testnet4)).
- Monero escrow against a real `monerod` and three `monero-wallet-rpc` on a local fakechain (`escrow-xmr-regtest`, A-498; parallel to the other jobs and listed in **CI passed**). The job starts `ghcr.io/sethforprivacy/simple-monerod:v0.18.5.1` and `simple-monero-wallet-rpc:v0.18.5.1` (the tags the installer and `compose.nodes.yaml` pin; `tests/test_ci_escrow_xmr_regtest.py` asserts them) with the `docker run` commands in the header of `scripts/test-escrow-xmr-regtest.sh`, next to a `postgres:17-alpine` service, then runs that script: its fifteen legs, with the app inside `go test`. The script refuses a daemon that is not a fakechain and fails a leg that fails, is skipped or does not run, so no leg can skip and pass. The transcript and the nodes' logs are kept as the `escrow-xmr-regtest-results` artifact for 14 days. The nodes and their network are removed even when a step fails. **What it proves:** the Monero escrow code against a real local fakechain nobody else can reach; nothing about stagenet, testnet, mainnet or Monero multisig. Measured locally at 569 s (`go test` 525 s) on the frozen A-498 run; the job's limit is 25 minutes. The CI duration is to be recorded here after the first run on a pull request.
- Reachable Go vulnerabilities with a pinned govulncheck version, plus high/critical npm dependency vulnerabilities. Node and Playwright are development tools only; the delivered application remains Go with server-rendered HTML/CSS.
- Shell syntax, installer selection/secret-file regressions (including the malware scanner's installer and Compose tests) and Python PostgreSQL helper regressions, failing if any Python test is skipped; encrypted backup and restore against disposable PostgreSQL 17 databases, both for synthetic tables and for the real application schema (migrated by the server, restored into an empty database with its queued payout held, then served again by the server), and backup and restore through the internal-db Compose service, which publishes no database port (`scripts/test-internal-db-restore.sh`: side-by-side and fresh-volume restores with the payout gate), and the move of a `SQL_ASCII` and a `LATIN1` database to UTF8 that UPGRADING.md section 42 describes, in its own PostgreSQL 17 container (`scripts/test-utf8-migration.sh`). See [operations-tests.md](operations-tests.md).
- Upgrade from `v0.1.0-alpha.1` (`scripts/test-upgrade.sh`): the alpha.1 server, built from its tag, populates a PostgreSQL 17 database through its own forms; the current server then migrates it. Health, every migration recorded once, orders moved to `draft` with the old status column gone, the one-draft-per-buyer/product/currency rule (database and order form), preserved messages/users/settings and alpha.1 sign-in are checked, and a second start applies nothing.
- Six supported Compose configurations spanning clearnet/Tor, internal/external PostgreSQL and Tor mirror enabled/disabled are parsed without starting a stack or connecting to a cryptocurrency network. The checks also resolve the optional Bitcoin and Monero daemon profiles, the Monero escrow wallet-rpc profile, and the escrow signer profile. In every row the resolved configuration (`config --format json`) must give the app the healthcheck `/app/server -healthcheck`, and in the Tor rows `tor` (and `tor-mirror` when the mirror is on) the healthcheck `test -s /var/lib/tor/marketplace/hostname`, which `up --wait` relies on. In the Tor rows it must also give `tor`, and `tor-mirror` when the mirror is on, a `service_started` dependency on the app with `restart: true`, so Tor restarts whenever Compose recreates the app. In every row the resolved `bitcoin` command must contain `-datadir=/data` and `-prune=<n>` with `n` at least 550, and the `monero` command `--prune-blockchain --sync-pruned-blocks` (the pruned defaults); with `BITCOIN_PRUNE_MB=0` and a blank `MONERO_PRUNE_FLAGS` the same check requires `-prune=0` and no Monero prune flag (full nodes). The resolved `bitcoin`, `monero` and escrow wallet-rpc images must carry release tags other than `latest` or a digest; the step names the service that does not (A-100, [Node image versions](operator-guide.md#node-image-versions)). Every resolved service must carry the resource limits and log rotation in [Resource limits and log rotation](operator-guide.md#resource-limits-and-log-rotation) (`mem_limit`, CPUs as `cpu_quota`/`cpu_period` and never `cpus`, `pids_limit`, json-file logs of at most three 10 MB files; A-180, A-144) and the app `GOMEMLIMIT=400MiB`; a service the check does not list fails it. Those rows pass `--profile` flags explicitly, so the Tor rows with the mirror on also run `scripts/test-mirror-commands.sh` for their database: it writes `COMPOSE_FILE` and `COMPOSE_PROFILES` into `.env` as the installer does and checks every documented onion-mirror command against it (see [operations-tests.md](operations-tests.md#documented-onion-mirror-commands)). This checks the configuration only; no Compose stack is started.
- Tor image build and offline configuration validation with networking disabled. The build installs the pinned tor from the Tor Project's repository and fails unless `tor --list-modules` reports `pow: yes`; the job then requires tor 0.4.8 or later, `pow: yes`, `tor --verify-config` to accept `deploy/torrc`, and `tor --dump-config short` to show every onion-service defence at its intended value ([Onion-service defences](operator-guide.md#onion-service-defences); A-179). The same job runs `scripts/test-tor-identity-restore.sh`: the operator guide's `.env` and onion-identity backup and restore commands, verbatim, against that image with networking disabled (backup, volume removed, restore, Tor starts with the same address; a root-owned archive; see [operations-tests.md](operations-tests.md#documented-env-and-onion-identity-backup-and-restore)).
- Production Docker image startup with internal and external PostgreSQL (`scripts/ci-smoke.sh`); `up --wait` must see the app healthy by its own Compose healthcheck (`/app/server -healthcheck`), and it must still be healthy at the end; after bootstrap `/app/server -status` inside the container must print `installed=true schema=NNN keyroot=setup_token` (the smoke environment sets only the legacy `SETUP_TOKEN`) and nothing else; health, first-admin bootstrap, authenticated admin access and setup lockdown. External mode verifies the application Compose project did not start a database service. The image runs with `AUDIT_SIGNING_KEY` set and escrow off: the site must stay healthy without restarting, the admin page must offer escrow or paused intake with no pooled payout mutation forms and show the signed audit export as available with the pinned key, and a downloaded export must pass `cmd/verify-audit` (a tampered copy must fail). Every stylesheet the layout links must be served as `text/css` with this checkout's bytes. The same job then runs the malware scanner leg for each database mode (`scripts/ci-smoke.sh <mode> scanner`, A-192): the image with the pinned clamd of `compose.scanner.yaml`, whose only signature is a test signature (`deploy/testdata/clamav-test.ndb`) packed at job time into an unsigned `daily.cud`; curl, as a browser without JavaScript, checks that a marker PNG is refused and stores nothing, a PNG without the marker is stored and served re-encoded, uploads are refused while clamd is stopped (health and catalog still answer) and resume after it starts, `SHUTDOWN` is refused, and clamd reaches neither the database nor anything outside ([operations tests](operations-tests.md#malware-scanner-leg-in-ci)). The internal row also runs `scripts/test-scanner.sh` (the scanner container read-only and offline with the image's own signatures). This is not a production signature feed.
- Playwright browser regressions against both the preview and a separate disposable PostgreSQL application. Every `preview*.spec.ts` (layout, auth, PGP, orders, inventory, payments, transparency) runs in six Chromium/Firefox/WebKit viewport projects; a `db-setup` project initializes the database once, then `database-chromium` runs every other `db-*.spec.ts` (account, TOTP sign-in and recovery, orders, inventory, fresh escrow-only payment controls, removed pooled route refusal and immutable historical records, listing photos against a loopback fake clamd) and `database-firefox` the `@firefox` tests of `db-listing-photos.spec.ts` (photo upload, scanner refusal and an over-4-MB upload answered with its page, in Firefox with JavaScript off). `npm run test:e2e` runs all projects, so new specs matching those names are picked up without workflow changes. A separate job, **Escrow browser journeys (simulated nodes, real application)** (`browser-escrow`, A-474; listed in **CI passed**), runs `npm run test:e2e:escrow` (the Bitcoin escrow paste journeys against the simulated escrow node) and then `npm run test:e2e:escrow-xmr` (the Monero escrow journey against the simulated escrow wallet-rpc and fakechain daemon) in Chromium only, each against its own fresh database (`e2e_escrow` and `e2e_escrow_xmr`) on a `postgres:17-alpine` service. ## Release a tested version

Push a version tag, for example `v0.1.0`, on the intended reviewed commit. The release workflow reruns the entire CI workflow against that tag before building any release output. It requires the tag to use `vMAJOR.MINOR.PATCH` (an optional prerelease suffix is supported). The image is built without any Actions cache.

The pipeline creates a **draft GitHub release** with:

- `opsecmkt.oci.tar.gz`: Linux amd64 OCI image archive, with embedded BuildKit provenance and SBOM.
- `build.json`: exact source commit, tag, platform and Actions run URL.
- `verify-audit-linux-amd64`, `verify-audit-linux-arm64`, `verify-audit-darwin-amd64`, `verify-audit-darwin-arm64`, `verify-audit-windows-amd64.exe`: static builds of `cmd/verify-audit`, the offline checker for signed audit exports (standard library only, no network access).
- `SHA256SUMS`: checksums for the archive, build record and every verifier binary.

It does not publish a registry package, contact a production host, or deploy. There are no deployment credentials to configure. A draft is visible only to people with write access to the repository. The repository is public, so publishing a release makes its assets available to anyone: review the draft and its green checks first. A pre-existing release makes a rerun fail instead of silently replacing release assets; delete an unwanted draft explicitly before retrying packaging.

To retrieve and inspect a release on an authorized workstation:

```sh
gh release download v0.1.0 --repo OWNER/opsecmkt --dir release-v0.1.0
cd release-v0.1.0
sha256sum -c SHA256SUMS
gunzip -k opsecmkt.oci.tar.gz
skopeo copy oci-archive:opsecmkt.oci.tar docker-daemon:opsecmkt:v0.1.0
```

To check a signed audit export downloaded from **Admin → Signed audit export**, verify the release checksums as above, then run the verifier for your platform with the Ed25519 public key you pinned from the market's `/canary` page (not the key named inside the `.sig` file):

```sh
chmod +x verify-audit-linux-amd64
./verify-audit-linux-amd64 -pub <pinned-hex-key> audit-events-upto-N.jsonl audit-events-upto-N.sig
```

It exits 0 only when the signature over the exact export bytes verifies with that key and every line is a well-formed event in ascending id order; otherwise it prints the reason and exits 1. From a source checkout, `go run ./cmd/verify-audit` is equivalent. A valid signature proves the export came from the holder of the signing key; it does not prove the history was never altered on the server before export.

The OCI archive is intended for an OCI-aware importer; do not assume every Docker version can load it directly. Review embedded metadata in the archive before import; copying to a Docker daemon can discard attestations. The checksums detect corruption and BuildKit metadata records the build; neither is an independent cryptographic signature. The workflow does not create GitHub artifact attestations (available to public repositories via `actions/attest-build-provenance`).

A future deployment workflow needs an explicitly selected target, environment protection, deployment credentials, backup policy, and rollback decision. Database migrations are one-way (there are no down-migrations, and migration 001 drops `orders.status`), so an older image cannot simply be redeployed against a migrated database: rolling back means restoring the encrypted backup taken before the upgrade into a fresh database and rebuilding the previous tagged revision against it (Compose builds the app from the checkout), losing everything written since. Keep the previous release tag, its `.env` and that verified pre-upgrade backup until the new release is trusted. See [UPGRADING.md](../UPGRADING.md).

## Workflow maintenance

Actions are pinned to verified full commit SHAs, permissions default to read-only, and checkout does not persist credentials. Only the release packaging job receives `contents: write`. Pull requests never receive release permissions or production secrets. Dependabot proposes dependency/action updates for review.

CI uses disposable PostgreSQL credentials that are intentionally committed test fixtures. Never substitute production URLs or credentials in these jobs. Do not commit local environment files, backups, browser authentication state, or private test traces. Browser artifacts can contain the generated fixture records used in CI.

Sources: [GitHub secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use), [artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), and [Docker build attestations](https://docs.docker.com/build/metadata/attestations/).
